# Step 003 — step-specific context

Feature-wide facts are in `context.md`; the decisions this step implements are D2 (400 and
why not 401), D6 (the cookie flags, applied through step `002`'s writer), D9 (idempotent
logout, 204), D10 (the paths, and the one model serving two routes) and D13 (no
normalization). None of that is repeated here.

## The two paths this plan chose, and the one the doc fixed

`backend-structure.md` fixes **`GET /api/me`** — its path, its body, its 401 behaviour and
that `auth.py` owns it — and fixes **no path at all** for login and logout. The plan
chooses `POST /api/auth/login` and `POST /api/auth/logout`, and `outcome.md` asks the
architect to record the surface exactly as `003/outcome.md` entry 3 did for
`POST /api/bootstrap/create`.

`/api/me` stays at the prefix root rather than moving under `/api/auth/`: three other docs
(`frontend-structure.md`'s admin boot sequence, `admin-surfaces.md`, `deployment.md`'s
not-ready passage) cite it by that exact path, and a route rename to satisfy symmetry
would silently invalidate all three.

The API client requires every path to begin `/api/` (`002/004`), which all three satisfy
without special-casing.

## Getting the generator out of application state

`001.backend-foundation`'s app factory holds the process's single snowflake generator on
**`app.state.id_generator`**. `001` freezes no named dependency for retrieving it, so:

- if the delivered `001` code exposes a dependency or accessor for it, use that;
- otherwise the route reads it from the application state reachable on the request, which
  is HTTP plumbing and therefore the router's business, and passes it into the service.

Either way the **service takes it as an argument** (step `001`, DoD-7). This is the same
resolution `003/003.context.md` recorded for the bootstrap router, and the skeleton agent
resolves which form the delivered code supports.

## Setting a cookie while still returning a pydantic model

`backend-structure.md` requires routes to return pydantic models rather than bare dicts or
a hand-built `JSONResponse` — that is what keeps the JSON id boundary mechanical. A route
that must also set a header therefore takes FastAPI's **response object as a parameter**
and mutates it, and still returns its model. Constructing a `JSONResponse` by hand to
attach the cookie would bypass `models/` and is the defect to avoid. The exact form is the
skeleton's to freeze; the requirement is that the identity body goes through the model.

## The error needs no translation here

`001` registers **one** handler for the domain-error base class, so `invalid_credentials`
reaches the client as a `400` in the one wire shape with the router catching nothing. A
`try`/`except` here, or an `HTTPException` raised by hand, would be a second error path and
is the defect to avoid — the same rule `003/003.context.md` recorded for
`already_configured`.

## Why logout carries no guard, restated where it will be doubted

A reviewer will read "logout with no session answers 204" as a missing check. It is not
one: `context.md` D9 records both halves of the reason — the 401 trap, and the fact that
signing out of an expired session is the *normal* case, not an error. The route reveals
nothing by answering 204: it says only that the caller now has no cookie, which was already
true.

Revocation is **scoped to the calling session** (DoD-12). Revoking every session for the
user would be a "sign out everywhere" capability, which no product id asks for and which
would surprise someone logging out on one machine.

## The 422 backstop, and what it is not

The request model's non-empty constraints produce FastAPI's own validation response, whose
body is **not** the `{"error": {...}}` envelope. That is accepted (`003/context.md` D16 and
its reasoning apply unchanged): the form cannot submit an empty field, so this path is
defensive. Consequence for the frontend, held by step `005`: such a response decodes to
`002`'s synthetic `client_malformed_error` at status 422 and renders in the form's general
inline alert.

**Do not invent a domain error code for empty credentials.** This feature adds exactly
three codes to the architect's table, all of them in steps `001` and `002`.

## Gotcha — the login route must never answer 401

DoD-5 is a whole criterion for one status code because the failure it prevents is invisible
in the backend and catastrophic in the UI: the shared API client navigates the document to
`/login` on **any** 401 and then still throws (`002/004` DoD-10), so a 401 from this route
reloads the login page and destroys the message US-005.AC-2 requires. Nothing in this route
— not an empty body, not a malformed one, not an unknown user — may produce 401.

## Gotcha — the login response is not the client's source of truth

The body exists for contract quality and manual verification (`context.md` D10). Step
`005`'s form **reads no field of it** and performs no role branch (`context.md` D12). Do
not add a field here on the grounds that the entry might want it, and do not remove the
body on the grounds that no client reads it — `003/003.context.md` recorded the same
tension for the bootstrap create response and resolved it the same way.

## Gotcha — two logins, two sessions

Nothing here caps the number of live sessions per user or reuses an existing one. A second
login mints a second row, which is what lets one person use two browsers, and it is what
makes FEAT-003's disable path "revoke **every** live row for that user" rather than "revoke
the row".
