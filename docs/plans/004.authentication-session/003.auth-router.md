# Step 003 — The auth router: login, logout, and `GET /api/me`

## Goal

Expose authentication as three routes that own HTTP and nothing else — a login that sets
the session cookie, an idempotent logout that clears it, and the identity route three
later features already depend on.

## Source files

```
backend/app/models/auth.py
backend/app/routers/auth.py
backend/app/main.py
```

## Test files

```
backend/tests/test_auth_router.py
```

## Interface intent

**`backend/app/models/auth.py`** — two pydantic models and nothing else.

- **A login-request model** carrying a username and a plaintext password, both constrained
  to be **non-empty** by a field constraint — the same defensive backstop `003` chose
  (`003/context.md` D16), answered by FastAPI's own `422` rather than the domain-error
  envelope, and adding **no new domain error code**. The values are used **exactly as
  received**: no trimming, no case folding, no normalization (`context.md` D13).
- **An identity model** carrying the caller's **id**, username and role, used as the
  response model of **both** `GET /api/me` and the login route. The id field uses `001`'s
  **outbound** snowflake alias from `app/models/ids.py`, so it serialises as a **decimal
  string** — a bare `int` id field is the defect. It carries **no token, no expiry and no
  session field**: the token lives in the cookie and nowhere else.

**`backend/app/routers/auth.py`** — the router, owning HTTP and nothing else: no business
rule, no SQL, no password handling.

- It carries the `/api` prefix and declares three routes: **`POST /api/auth/login`**,
  **`POST /api/auth/logout`** and **`GET /api/me`** (`context.md` D10 — the last is fixed
  by `backend-structure.md` and is deliberately not moved under `/api/auth/`).
- **The login route** takes the request model, the connection dependency, the settings
  dependency, FastAPI's response object, and the process's snowflake generator resolved
  from **application state**. It calls step `001`'s authentication operation, then its
  open-session operation with the TTL from `Settings.session_ttl_hours`, sets the session
  cookie through step `002`'s cookie writer, and answers **200** with the identity model.
  It carries **no authorization dependency** — it is the route that creates the session —
  and it translates no error by hand: the base-class handler `001` registered renders
  `invalid_credentials` as a **400** on its own (`context.md` D2).
- **The logout route** takes the connection dependency, the settings dependency and
  FastAPI's response object, reads the session cookie by the configured name, calls step
  `001`'s revoke operation when there is a token at all, clears the cookie through step
  `002`'s clearer, and answers **204** — **the same answer whether or not a live session
  resolved** (`context.md` D9). It carries **no `require_user`**: a 401 here would trip the
  client's return-to-login navigation in the one place the person is already leaving.
- **`GET /api/me`** carries `require_user` and returns the identity model built from the
  `CurrentUser` that dependency yielded. It reads nothing else, queries nothing itself, and
  carries no counts, no other accounts and no content (`backend-structure.md`).

**`backend/app/main.py`** — include the auth router in the app factory, beside the health
router and (from `003`) the bootstrap router. Nothing else changes: the factory's frozen
ordering stands and the **lifespan still runs no DDL**.

## Definition of done

1. `[test]` `POST /api/auth/login` with a correct username and password for an enabled
   account answers **200**, sets a `Set-Cookie` for the configured session cookie name,
   and afterwards exactly one live `auth_sessions` row exists for that user.
   (US-004.AC-1)
2. `[test]` That response body carries the caller's id, username and role — the id as a
   **decimal string**, never a JSON number — and carries **no token, expiry or session
   field**.
3. `[test]` The cookie it sets is `HttpOnly`, `SameSite=Lax`, `Path=/`, carries **no
   `Secure` flag**, and has a `Max-Age` matching `Settings.session_ttl_hours`; overriding
   `session_cookie_name` changes the cookie's name. (`context.md` D6)
4. `[test]` `POST /api/auth/login` answers **400** with the wire shape
   `{"error": {"code": "invalid_credentials", ...}}` and sets **no cookie** for an unknown
   username, for a wrong password, and for a **correct password on a disabled account** —
   with the same code, status and message in all three, and no `auth_sessions` row created
   in any of them. (US-005.AC-1, US-006.AC-1)
5. `[test]` The login route **never answers 401**, for any input — which is what keeps the
   API client's 401 navigation away from the login screen (`context.md` D2).
   (US-005.AC-2, US-006.AC-2)
6. `[test]` An empty username or an empty password is refused before anything is written,
   with no `auth_sessions` row created afterwards.
7. `[test]` The credential is used exactly as sent: a username or password differing only
   by leading/trailing whitespace or letter case from the stored one is **refused**, and
   the account's own exact credential still succeeds. (`context.md` D13)
8. `[test]` `GET /api/me` with the cookie from a successful login answers **200** with that
   user's id (decimal string), username and role. (US-004.AC-1)
9. `[test]` `GET /api/me` answers **401** with no cookie, with a cookie holding an
   unissued token, after that session has been revoked, after it has expired, and when the
   account has since been disabled. (US-007.AC-2, US-006.AC-1)
10. `[test]` `POST /api/auth/logout` on a live session answers **204**, clears the cookie,
    marks that session revoked, and makes the **same cookie** answer 401 on `GET /api/me`
    immediately afterwards. (US-007.AC-1)
11. `[test]` `POST /api/auth/logout` answers the **same 204 and clears the cookie** with no
    cookie at all, with an unissued token, and with an already-revoked or expired session —
    it never answers 401 and never raises. (`context.md` D9)
12. `[test]` Two logins for the same user produce two live sessions, and logging one out
    leaves the other working — logout revokes the calling session only.
13. `[test]` The router issues no SQL and holds no rule: its only database contact is
    through `001`'s connection dependency, every stored value comes from the service, and
    the generator it passes down comes from application state rather than a module global.
14. `[manual/live]` `routers/auth.py` declares exactly these three routes, the login and
    logout routes carry no authorization dependency, and `GET /api/me` carries
    `require_user`. Verifier confirms by reading the module.
15. `[manual/live]` `main.py`'s lifespan still runs no DDL, and the router registration is
    the only change to the factory. Verifier confirms by reading it.
16. `[manual/live]` `uvicorn app.main:app` on port 8184 starts; against a bootstrapped
    database, logging in through `curl` yields a cookie that `GET /api/me` accepts and that
    `POST /api/auth/logout` invalidates.
17. `[manual/live]` `mypy app`, `ruff check .` and `pytest` all pass from `backend/`.

## Dependencies

Steps `001` (authentication, the session lifecycle and the refusal error) and `002`
(`require_user`, `CurrentUser` and the two cookie writers).
