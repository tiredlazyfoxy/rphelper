# Step 001 — The `auth_sessions` table, the uniform refusal, and the session service

## Goal

Declare `auth_sessions` in the registry and give the backend one module that
authenticates a credential pair — refusing wrong username, wrong password and disabled
account identically — and that opens, resolves and revokes a session, with no HTTP
anywhere in it.

## Interface intent

**`backend/app/db/schema.py`** — add the **`auth_sessions` `Table(...)` literal** to the
single `MetaData` already in that file, per the file's own documented rule (every table is
a literal in this one file; no per-feature table module, no builder callable). Columns are
`data-model.md`'s authoritative list and **all of them are declared**:

- the snowflake primary key, stored as SQLite's integer rowid alias and declared as
  SQLAlchemy Core's big-integer type, **not** auto-incrementing;
- `user_id`, not nullable, a declared **foreign key to `users.id`**;
- `token_hash`, not nullable, text, holding the digest and never the token;
- `created_at` and `expires_at`, not nullable, UTC ISO-8601 text per `data-model.md`'s
  convention;
- `revoked_at`, **nullable**, NULL until the row is revoked — a revocation is observable
  because the row is never deleted (`data-model.md`).

Two indexes beyond the primary key, both load-bearing rather than decorative: `token_hash`
is **unique** (it is the lookup key on every authenticated request, and uniqueness states
the intent), and `user_id` is indexed (FEAT-003's disable path revokes every row for one
user in one transaction). **No other table, no view, and no column beyond the six.**

**`backend/app/errors.py`** — add **one subclass** of the existing domain-error base,
following that base's established pattern exactly: `code` and `http_status` as **class
attributes the subclass sets**, per-instance message/detail, and the inherited render
method producing the one wire shape. Its `code` is **`invalid_credentials`**, its
`http_status` is **400** (`context.md` D2), its `detail` carries **nothing**, and its
message is **one fixed sentence that names no cause** — it is raised identically for an
unknown username, a wrong password and a disabled account (`context.md` D1). It needs no
new handler: `001` registers one handler for the base class. No existing error, handler or
registration entry point is modified.

**`backend/app/services/auth.py`** — a new service module. Takes plain arguments, returns
plain results or raises the typed error, and **never imports `fastapi`, never sees a
`Request` and never knows a status code**. Four operations plus the plain results they
carry:

- **A credential-authentication operation.** Takes a Core `Connection`, a username and a
  plaintext password, and returns a plain result carrying the authenticated user's id,
  username and role. It selects the `users` row by **exact** username match
  (`context.md` D13), verifies the password through `003`'s hashing seam in
  `app/services/passwords.py`, and requires the account to be enabled. On **any** of the
  three failures it raises the `invalid_credentials` error above, with no branch that
  distinguishes them to the caller. When **no row matched**, it still performs a
  verification — against a fixed decoy encoded hash — before raising, so the refusal path
  does not return measurably faster for an unknown username (`context.md` D1). It opens
  no transaction: it only reads.
- **An open-session operation.** Takes a Core `Connection`, the process's snowflake id
  generator, the authenticated user's id and the TTL in hours, and returns a plain result
  carrying the **plaintext token** and the **expiry instant**. Inside one `with
  conn.begin():` block it generates a high-entropy random token, mints the row id from the
  **generator passed in** — never a module global — computes `created_at` as now (UTC) and
  `expires_at` as now plus the TTL, and inserts the row with the token's **digest**, never
  the token. The plaintext token is returned to the caller and stored nowhere.
- **A resolve-session operation.** Takes a Core `Connection` and a plaintext token, and
  returns the same plain identity result as authentication, or **nothing** when the token
  does not resolve. It looks the row up **by digest**, and yields an identity only when the
  row is **not revoked**, **not past its expiry**, and its joined `users` row is
  **enabled** — with `role` read **live from `users`** on every call (`context.md` D7). It
  raises nothing and opens no transaction: "no live session" is an ordinary answer, and the
  HTTP meaning of it is the dependency's business in step `002`.
- **A revoke-session operation.** Takes a Core `Connection` and a plaintext token, sets
  `revoked_at` on the matching row inside its own `with conn.begin():` block, and is
  **idempotent**: an unknown token, an already-revoked row and an expired row are all
  ordinary no-op successes, not errors (`context.md` D9). It deletes nothing.

The module reads **no settings** — the TTL and the cookie name arrive as arguments or are
the router's business — imports no `fastapi` symbol, and logs at most a user id as a
decimal string plus an outcome code. It **never logs a token, a digest, a password or a
username on a failed login** (`context.md`'s redaction constraint).

## Definition of done

1. `[test]` The registry exposes an `auth_sessions` table carrying exactly the columns
   `data-model.md` names — `id`, `user_id`, `token_hash`, `created_at`, `expires_at`,
   `revoked_at` — and no others; `revoked_at` is nullable and the other five are not.
2. `[test]` `id` is the primary key and does **not** autoincrement; `token_hash` is
   uniquely indexed; `user_id` carries a declared foreign key to `users.id` and is
   indexed.
3. `[test]` The `invalid_credentials` error carries code `invalid_credentials`, HTTP
   status **400**, an empty `detail`, and renders in the one wire shape
   `{"error": {"code", "message", "detail"}}` through the handler `001` already
   registered — no second handler is added.
4. `[test]` Authentication with a correct username and password for an **enabled** account
   returns that user's id, username and role. (US-004.AC-1)
5. `[test]` Authentication raises `invalid_credentials` for an unknown username, for a
   wrong password on an existing account, and for a **correct** password on a **disabled**
   account — and the error raised in all three cases carries the **same code, the same
   status and the same message**, with nothing in it that distinguishes which happened.
   (US-005.AC-1, US-006.AC-1)
6. `[test]` Opening a session inserts exactly one `auth_sessions` row for that user, with
   `revoked_at` NULL, an `expires_at` that is the creation instant plus the TTL it was
   given, and a **`token_hash` that is not the returned token**; the returned token is a
   high-entropy value and two successive calls return **different** tokens.
7. `[test]` The open-session operation mints the row id from the generator it is
   **given**: two calls with two different generators produce ids from those generators,
   and nothing in the module reaches a process-wide generator.
8. `[test]` Resolving the token returned by a freshly opened session yields that user's
   id, username and role. (US-004.AC-1)
9. `[test]` Resolution yields **nothing** for: a token that was never issued, a token
   whose row is **revoked**, a token whose row is **past `expires_at`**, and a token whose
   user has since been **disabled** — and it raises in none of those cases.
   (US-006.AC-1, US-007.AC-2)
10. `[test]` Resolution reads the role **live**: changing a user's role in `users` changes
    what the *same* token resolves to on the next call, with no new session.
    (`context.md` D7)
11. `[test]` Revocation sets `revoked_at` on the matching row, **deletes nothing**, and
    leaves that user's other sessions untouched; revoking an unknown token, an
    already-revoked token and an expired token all succeed without raising.
    (US-007.AC-1)
12. `[test]` `services/auth.py` imports no `fastapi` symbol, references no HTTP status
    code, takes no `Request` and reads no settings — it is callable with a plain
    connection, a generator and plain strings.
13. `[manual/live]` The authentication path performs a password verification **even when
    no user row matched**, so the refusal does not return measurably faster for an unknown
    username. Verifier confirms by reading the module; no timing assertion is written
    (`context.md` D1).
14. `[manual/live]` No log line in this module can carry a token, a digest, a password, or
    a username on a failed login. Verifier confirms by reading every logging call in the
    module.
15. `[manual/live]` `mypy app`, `ruff check .` and `pytest` all pass from `backend/`.

## Dependencies

None within this feature. It builds on `001.backend-foundation` (the registry, the engine,
the error base, the id generator) and on `003.first-run-bootstrap` step `001` (the `users`
table, the `Role` enum and the password-hashing seam).
