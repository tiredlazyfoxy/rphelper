# Step 006 — step-specific context

Feature-wide facts are in `context.md`; the decisions this step implements are D1 (one
`shared/`, four entries), D2 (pure data contracts — asserted here by absence), D5 (the
ids rule as a test) and D13 (the emitted layout), and the seams it touches are S1, S2
and S3. None of that is repeated here.

## The forbidden patterns the ids scan enforces

`frontend-structure.md`: *"`id: number` on a type, a prop, a store field or a route
param is a defect — the reviewable form of this rule is one grep over `frontend/src`"*
and *"No `parseInt`, no numeric sort, no arithmetic."*

The scan covers every `.ts` and `.tsx` file under `frontend/src`, recursively, and
fails on any of:

1. **A binding whose name ends in `id` or `Id` annotated as a number.** The shapes to
   catch are a property or parameter named `id`, `Id`, or anything ending in those (for
   example `sessionId`, `message_id`, `characterId`), followed by a type annotation of
   `number` or `number[]` — with any amount of whitespace and an optional `?` between
   the name and the colon.
2. **Any occurrence of `parseInt`.**
3. **Any occurrence of `Number.parseInt`.**

There is **no exception list and no suppression comment.** If a later feature has a
genuine need for one of these, the architecture changes first and this test changes with
it — which is exactly the review the rule wants and would not get from a lint
suppression.

The failure message must name the **file path and the line number** of the first
offence. A scan that only says "a violation exists" costs more to act on than the grep
it replaced.

## What the scan deliberately does not try to catch

Numeric sorting and arithmetic on ids are forbidden by the doc but are not
textually detectable — `a.id - b.id` is indistinguishable from any other subtraction
without type information, and a regex that tried would produce false positives that
teach people to work around the scan. The three patterns above are the mechanically
checkable subset; the rest stays a review matter. Recorded so the gap is deliberate
rather than assumed complete.

## Why the pure-data-contract check is an absence check

`context.md` D2 fixes the convention; this feature ships no store and no draft class,
because `brief.md` puts all page content out of scope and a store invented against no
page would freeze a shape against no requirement. DoD-10 asserts that absence, so that
the first store in the project is written by the feature that has a page for it and is
written against the recorded convention rather than against an example this feature
left lying around.

## The router basename, restated because it is the easiest thing here to get wrong

`frontend-structure.md` states **`BrowserRouter basename="/admin"`**. `deployment.md`'s
nginx block serves the document from **`location /admin/`** with a trailing slash. These
are two different strings for two different mechanisms:

```
nginx      location /admin/  { try_files $uri $uri/ /admin/index.html; }
react      <BrowserRouter basename="/admin">
```

React Router strips the basename from the pathname before matching, so `/admin/users`
matches the route `/users`. A trailing slash in the basename would break that match.
Copying either string from the other is the defect.

## The placeholder marker

A stable attribute on the rendered element — the entry's own name — is enough for
DoD-1 and is not page content. It gives a later feature nothing to carefully preserve:
`003` and `005` replace their entry's route table wholesale.

## Gotcha — testing the four entries without loading four documents

Each `main.tsx` mounts on evaluation, which is what makes it an entry and also what
makes it awkward to import from a test. The behaviour the DoD items describe — which
marker renders, which basename is in effect, which stylesheet is imported — is
observable either by evaluating the module against a prepared DOM containing the mount
element, or by reading the module source for the import-level items (DoD-5, DoD-6).
Which route each item takes is the test-coder's call; the skeleton's shape decides how
much of it is possible.

## Gotcha — `MemoryRouter` is not a substitute for DoD-3

The `basename` behaviour under test is `BrowserRouter`'s handling of a real pathname.
Setting the jsdom location to `/admin/users` and evaluating the entry is what exercises
it; substituting a memory router with an `initialEntries` array tests React Router
rather than this step.

## Gotcha — DoD-14 and tree separation

The check is that the bundles are genuinely separate documents, which is the first of
`frontend-structure.md`'s two reasons for the four-entry split: *"the roleplayer's
document contains no administrative surface at all, not even dead-code-eliminated
remnants, not even a route table naming `/admin`"*. With four placeholder route tables
the check is trivially satisfiable today — it is written down now so that the feature
that adds the first admin page inherits a criterion rather than discovering the rule.

## Seam S1, restated so the coder does not try to solve it here

`deployment.md`'s nginx fallback ends with `location / { try_files $uri $uri/
/index.html; }`, and the `app` entry's routes are mounted at the origin root. The build
emits the app document at `dist/app/index.html`. Making it also answer at `/` is
`fast/001`'s nginx and image configuration, not this step's. **Do not create a root
`frontend/index.html`** — that would be a fifth entry the architecture's input list does
not have, and DoD-13's "exactly four" would then be wrong. The consequence in dev, that
`http://localhost:8193/` does not resolve, is on the same seam and is out of scope here.
