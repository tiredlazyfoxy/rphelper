# Step 005 — Providers, the colour scheme and the failure-notification channel

## Goal

Create the single provider component all four entries mount — carrying the theme, the
persisted dark-by-default colour scheme and the notifications outlet — together with
the scheme toggle and the one function that puts a failure's reason on screen.

## Interface intent

**`frontend/src/shared/colorScheme.ts`** exports:

- **the storage key**, as a named constant whose value is `rphelper.color-scheme`;
- **the colour-scheme manager**, built with Mantine's own
  `localStorageColorSchemeManager` on that key. No second persistence mechanism is
  written and no hand-rolled `localStorage` access appears anywhere;
- **the default scheme**, as a named constant whose value is `"dark"`.

The module is deliberately separate from `theme.ts`: a theme is design tokens, a
manager is persistence, and the two have different reasons to change.

**`frontend/src/shared/AppProviders.tsx`** exports **one component** taking children.
It renders Mantine's provider configured with the theme from `shared/theme.ts`, the
manager and default scheme from `shared/colorScheme.ts`, and inside it Mantine's
notifications outlet configured with a 5000 ms auto-close, above the children.

It also owns the stylesheet imports and their **order**: Mantine's core stylesheet,
then the notifications stylesheet, then `src/global.css` **last**, so the resets land
after Mantine's base sheet. Deciding the cascade order in one file rather than by
import-statement order in four entries is the reason this component owns them.

It does **not** import `shell.css` — that is the `app` entry's alone, in step `006`.
It creates no React context of its own, provides no store, and takes no props but
children: stores are passed explicitly as props everywhere in this project.

**`frontend/src/shared/ColorSchemeToggle.tsx`** exports **one component** taking no
props. It reads the **computed** colour scheme — so that a future `"auto"` setting can
never leave the control ambiguous about what it is about to do — and renders an
`IconButton` that sets the opposite scheme. The icon is a sun when the current scheme
is dark and a moon when it is light, and the `label` states the action it will perform
rather than the state it is in, so the tooltip and the accessible name are both a
command. It uses `sizeVariant` `"main"`.

It is exported and mounted by no entry in this feature; `005` and `008` place it
(`context.md`, seam S4).

**`frontend/src/shared/notifyFailure.ts`** exports **one function** taking a thrown
value and showing a transient failure notification carrying that failure's reason. It
resolves the message from an `ApiError` when the value is one, and falls back to a
generic reason otherwise; the notification is red and inherits the 5000 ms auto-close
from the outlet.

It has **no success path and no success parameter**, by construction — the mechanism by
which *"a notification whose message is a success is a defect"* is satisfied rather than
merely stated. It is the only sanctioned way anything in this project raises a
notification; nothing else calls Mantine's notification API directly.

It is called by the feature that has decided a failure has **no place to render**. A
failure that already renders in place — a field error, an inline `Alert`, a banner —
does not also call it.

## Definition of done

1. `[test]` The exported storage key is exactly `rphelper.color-scheme`, and it is not
   the workspace-layout key.
2. `[test]` The exported default scheme is `"dark"`.
3. `[test]` No file in this step performs a direct `localStorage` read or write —
   persistence goes through Mantine's manager and nowhere else.
4. `[test]` Rendered inside `AppProviders` with nothing persisted, the document
   resolves to the **dark** scheme.
5. `[test]` With a scheme already persisted under the storage key, `AppProviders`
   resolves to that persisted scheme rather than to the default.
6. `[test]` `AppProviders` renders its children, and a Mantine component among those
   children is themed — the theme from `shared/theme.ts` is in effect.
7. `[test]` `AppProviders` mounts the notifications outlet, configured with a 5000 ms
   auto-close, and a notification raised while it is mounted becomes visible.
8. `[test]` `AppProviders` takes no props but `children` and provides no React context
   of its own beyond Mantine's.
9. `[test]` Activating `ColorSchemeToggle` under `AppProviders` flips the resolved
   scheme from dark to light, and activating it again flips it back.
10. `[test]` `ColorSchemeToggle`'s accessible name names the action it will perform and
    changes with the current scheme.
11. `[test]` `ColorSchemeToggle` renders through `IconButton` — it exposes an
    accessible name and a tooltip carrying the same string, which a bare `ActionIcon`
    would not.
12. `[test]` `notifyFailure` given an `ApiError` shows a red notification carrying that
    error's message.
13. `[test]` `notifyFailure` given a non-`ApiError` thrown value still shows a red
    notification with a generic reason rather than throwing or rendering nothing.
14. `[test]` `notifyFailure` is the module's only export, takes only the thrown value,
    and exposes no success or colour parameter through which a success notification
    could be raised.
15. `[test]` No file anywhere under `frontend/src` calls Mantine's notification API
    except `shared/notifyFailure.ts`.
16. `[manual/live]` `AppProviders` imports Mantine's core stylesheet, then the
    notifications stylesheet, then `src/global.css`, in that order, and imports
    `shell.css` not at all.
17. `[manual/live]` `npm run typecheck` passes, and both schemes render correctly.
