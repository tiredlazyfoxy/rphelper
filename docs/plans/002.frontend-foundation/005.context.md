# Step 005 — step-specific context

Feature-wide facts are in `context.md`; the decisions this step implements are D3 (both
schemes, dark default, the distinct storage key) and D9 (provider placement and the
stylesheet import order), and the constraint it holds is the no-success-notifications
rule. None of that is repeated here.

## The two halves of the notification rule

`ui-conventions.md` is explicit about both:

- **What it carries** — a failure's *reason*, for any typed failure not already
  rendered in place: `llm_unreachable`, `model_not_enabled`, `translation_failed`,
  `tool_failed`, and the rest of the backend's error table on the same condition.
- **What it must not** — a failure that already has somewhere to render (a field error
  in a modal, the inline `Alert` above an admin table, the no-embedding-model banner
  above the stream) keeps rendering there and does **not** also raise a notification.
  And: *"A notification whose message is a success is a defect. That is the whole
  test."*

`notifyFailure`'s signature is what makes the second half structural: with no success
parameter and no colour parameter, a success notification is not something a call site
can express. DoD-15 is the other half of the same enforcement — a single call site for
Mantine's own API.

## The split this step must not collapse

US-044.AC-3 wants a retry to remain **possible**; US-044.AC-4 wants the reason **not to
persist**. `ui-conventions.md` resolves that by splitting them: the **reason** goes on
the transient notification (~5s, then gone) and the **retry** affordance lives in the
stream at the failed exchange, persisting until the exchange succeeds or is abandoned.

So `notifyFailure` carries a reason and **never** an action, a button or a retry. That
is a design constraint on this function's shape, and it is why it takes a thrown value
and nothing else. (This feature cites no product id; the two ids are named here only
because they are the reason the split exists in the doc this function implements.)

## Why the toggle reads the *computed* scheme

Mantine's colour scheme can be `"light"`, `"dark"` or `"auto"`. Reading the raw setting
would let the control render a sun while the document is actually light, because the
raw value is `"auto"`. Reading the computed value gives what the user is actually
looking at, which is what the label must describe. This feature sets no `"auto"`
default, but the hook choice is what keeps the control correct if a later feature adds
one.

## Why the toggle is mounted nowhere

`brief.md` puts page content in every entry **Out** of scope, and a scheme toggle
floating in an otherwise empty document is page content. It is exported for `005`'s
admin shell and `008`'s workspace user menu to place — the same situation as
`IconButton`, which is also exported and mounted nowhere here. See `context.md` seam
S4.

## Gotcha — the storage key must not be the layout key

`008` owns a `rphelper.workspace-layout` record, app-entry-only. The colour scheme
applies to all four entries and therefore cannot live in it. DoD-1 asserts the two are
distinct so that a later feature does not consolidate them and silently make the login
page's scheme depend on a workspace record.

## Gotcha — `localStorage` in jsdom

jsdom provides `localStorage`, and it persists across tests in the same file unless
cleared. DoD-4 (nothing persisted → dark) and DoD-5 (something persisted → that value)
are order-sensitive: a test that does not clear the key first will observe whatever the
previous test wrote. Clearing storage between tests is the test-coder's business, noted
here only because these two items are the pair that fails silently otherwise.

## Gotcha — the notifications outlet and auto-close

Mantine's notifications outlet has a global auto-close setting and per-notification
overrides. The 5000 ms figure is set **on the outlet** so that no call site can pick a
different one. `notifyFailure` therefore does not pass an auto-close of its own, and a
test for DoD-7 reads the outlet's configuration rather than a notification's.

## Gotcha — timers

A five-second auto-close is longer than a test should wait. Vitest's fake timers are
the way to observe the dismissal without a real wait; whether DoD-7 is satisfied by
reading the configured value or by advancing timers is the test-coder's call.
