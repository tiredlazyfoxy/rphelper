# Step 001 — step-specific context

Feature-wide facts are in `context.md`; the decisions this step implements are D4
(no linter, the compiler flags), D10 (the test stack), D11 (tests outside `src/`),
D12 (`tests/setup.ts` is source), D13 (the Vite specifics) and D14 (the dependency
list). None of that is repeated here.

## The verbatim block this step reproduces

`docs/architecture/frontend-structure.md` § "The multi-entry build" gives the
`vite.config.ts` shape verbatim, including the four input keys and their paths and the
`server` block. The skeleton agent reproduces it from the doc; this plan does not
restate it.

## Why `vitest/config` rather than `vite/config`

The `test` key is not part of Vite's own configuration type. Importing `defineConfig`
from `vitest/config` types it without a triple-slash reference and without a second
config file — which is the point of reusing one config (D10).

## Why `globals: false`

With globals off, the setup file must import `afterEach` from `vitest` itself rather
than relying on an ambient binding, and every test imports `describe` / `it` / `expect`.
`@testing-library/jest-dom`'s Vitest entry point extends Vitest's `expect` directly, so
matcher registration works without globals.

## The two commands that must not be conflated

The root `CLAUDE.md` lists `build` and `typecheck` as **separate** commands. `build`
therefore runs the bundler alone; it does not chain a `tsc` pass. A chained build would
make one failing command report two different kinds of fault and would make the
verifier's `build` and `typecheck` results non-independent.

## What a test can and cannot assert about the configuration

`vite.config.ts` is an ordinary ES module exporting an object, so a test may import it
and read its fields directly — that is how DoD-1 through DoD-5 and DoD-10 are covered
without running a build. `package.json` and `tsconfig.json` are read as JSON from disk.
`tsconfig.json` permits comments in practice; if the file is written without them a
plain JSON parse suffices, and the coder should keep it comment-free for that reason.

## Gotcha — the include pattern

The include pattern must not match `src/`. If it did, step `006`'s ids scan would
eventually read files that a test had generated, and more immediately a stray
`*.test.ts` under `src/` would ship inside a bundle. One pattern, rooted at `tests/`.

## Gotcha — `strictPort`

Vite's default behaviour on a busy port is to increment silently. With `strictPort`
enabled it exits instead. That is the desired behaviour here because the `/api` proxy
is the only thing making the frontend reach the backend in dev, and a dev server that
moved to 8194 would appear to work until the first API call.
