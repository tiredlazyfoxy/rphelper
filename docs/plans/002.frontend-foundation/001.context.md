## Building the absolute paths — use `__dirname`, not `import.meta.url`

The config file resolves its paths from its own directory. Use Node's `__dirname`
(typed via `@types/node` in `tsconfig.node.json`; Vite supplies it when it loads the
config), **not** a `fileURLToPath(new URL(..., import.meta.url))` construction. The
config module is also imported by `build-config.test.ts`, and under Vitest's jsdom
environment `import.meta.url` is an `http://localhost/@fs/...` URL, on which
`fileURLToPath` throws — the red-gate run on this feature already hit exactly that in
the tests.

## Why the Vitest block needs its own root

Vitest takes its root from the Vite config's `root` unless the `test` block sets one.
With the build rooted at `src`, the unchanged `tests/**` include and `./tests/setup.ts`
would be resolved under `frontend/src/`, and Vitest would find no tests at all — a
silent, green-looking failure. Setting the test block's root to `frontend/` restores the
original resolution without rewriting the include or setup strings. DoD-6 is the live
proof: if the harness runs at all, the root is right.

## Why `vitest/config` rather than `vite/config`

The `test` key is not part of Vite's own configuration type. Importing `defineConfig`
from `vitest/config` types it without a triple-slash reference and without a second
config file — which is the point of reusing one config (D10).

## Why `globals: false`

With globals off, the setup file must import `afterEach` from `vitest` itself rather
than relying on an ambient binding, and every test imports `describe` / `it` / `expect`.
`@testing-library/jest-dom`'s Vitest entry point extends Vitest's `expect` directly, so
matcher registration works without globals.

## The two commands that must not be conflated

The root `CLAUDE.md` lists `build` and `typecheck` as **separate** commands. `build`
therefore runs the bundler alone; it does not chain a `tsc` pass. A chained build would
make one failing command report two different kinds of fault and would make the
verifier's `build` and `typecheck` results non-independent.

## What a test can and cannot assert about the configuration

`vite.config.ts` is an ordinary ES module exporting an object, so a test may import it
and read its fields directly — that is how DoD-1 through DoD-5 and DoD-10 are covered
without running a build. Because the path-valued fields (`root`, `build.outDir`, the
four inputs, the test block's root) are absolute and machine-specific, DoD-1, DoD-4 and
DoD-5 are statements about **what each value resolves to** relative to the `frontend/`
directory, not about a literal string. `package.json` and `tsconfig.json` are read as
JSON from disk. `tsconfig.json` permits comments in practice; if the file is written
without them a plain JSON parse suffices, and the coder should keep it comment-free for
that reason.

## Gotcha — the include pattern

The include pattern must not match `src/`. If it did, step `006`'s ids scan would
eventually read files that a test had generated, and more immediately a stray
`*.test.ts` under `src/` would ship inside a bundle. One pattern, rooted at `tests/`
under the Vitest root (`frontend/`).

## Gotcha — `emptyOutDir`

With `outDir` outside `root`, Vite neither empties it nor fails — it warns and writes
alongside whatever is already there. `emptyOutDir: true` is what keeps `dist/` holding
exactly one build's output, which step `006` DoD-13's "exactly" depends on.

## Gotcha — `strictPort`

Vite's default behaviour on a busy port is to increment silently. With `strictPort`
enabled it exits instead. That is the desired behaviour here because the `/api` proxy
is the only thing making the frontend reach the backend in dev, and a dev server that
moved to 8194 would appear to work until the first API call.
