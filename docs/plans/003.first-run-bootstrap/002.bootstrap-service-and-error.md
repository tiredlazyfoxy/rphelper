# Step 002 — The configured fact, `already_configured`, and the one-transaction creation

## Goal

Give "is this instance configured" exactly one definition, declare the
`already_configured` domain error with a human-readable default message, and create the
schema and the first administrator in a single transaction that really covers the DDL,
so a half-bootstrapped instance is never reachable. That last part needs the engine to
run SQLite with transactional DDL, so `app/db/engine.py` is in this step's scope.

## Interface intent

**`backend/app/db/engine.py`** — the engine now runs with **transactional DDL**. On every
connection the engine hands out, the pysqlite driver's own implicit transaction handling
is off, and SQLAlchemy's `begin` is what sends the real `BEGIN`. The result: every
statement inside a `with conn.begin():` block commits or rolls back with the block,
including `CREATE TABLE` and other DDL. The reference is SQLAlchemy's documented
"pysqlite transactional DDL" configuration (SQLite dialect docs, "Serializable isolation /
Savepoints / Transactional DDL"). The coder picks the exact mechanism: the documented
event-hook recipe, or Python 3.12's sqlite3 `autocommit` connect argument. It must hold
all of these constraints:

- the existing `connect` listener keeps its order and its contents: load `sqlite-vec`,
  then `PRAGMA foreign_keys = ON`, then `PRAGMA journal_mode = WAL`;
- neither PRAGMA ever runs inside a transaction. Any mode where the driver keeps a
  transaction open permanently is therefore excluded, because WAL cannot be entered
  inside one;
- `sqlite-vec` is still loaded on every connection, and a failed load still raises the
  dedicated extension-load exception;
- `get_connection` still opens no transaction of its own;
- no public name is added to or removed from the module. The factory, the cache,
  disposal, the path helper, the loader seam and the exception stay what `001/005`
  delivered.

The change applies to the whole engine, not only to bootstrap (`002.context.md`
explains why).

**`backend/app/errors.py`** — add **one subclass** of the existing domain-error base.
It follows the base's pattern: `code` and `http_status` are **class attributes the
subclass sets**, `detail` is per-instance, and the inherited render method produces the
one wire shape. Its `code` is **`already_configured`**, its `http_status` is **`409`**
(`context.md` D2), and its `detail` is **empty** (`backend-structure.md:585`). When
raised with **no arguments**, it carries a **non-empty, human-readable message** saying
that the instance is already configured, so the wire body's `message` is a string and
not null. The subclass supplies that default itself. The base class, its handler, its
registration entry point and `SecretRefError` are **not modified**. No new handler is
needed, because `001` registers one handler for the base class and it covers every
subclass.

**`backend/app/services/bootstrap.py`** — a new service module. It takes plain
arguments, returns plain results or raises the typed error, and **never imports
`fastapi`, never sees a `Request` and never knows a status code**. Two entry points:

- **A configured-instance predicate.** Takes a Core `Connection` and answers whether the
  instance is configured. Per `context.md` D3, that means a `users` table is **present**
  *and* holds **at least one row whose role is the administrator value**. It checks for
  the table in SQLite's own catalogue before querying it, so a database with no schema
  answers false instead of raising. It only checks existence, and one row is enough.
  This is the **only** definition of the fact in the backend (`context.md` D4).
- **A create-first-administrator operation.** Takes a Core `Connection`, the process's
  snowflake id generator, and the credentials (a username and a plaintext password). It
  returns a plain result with the new administrator's id, username and role. It does the
  following in order, **all inside one `with conn.begin():` block**:
  1. re-check the predicate on the same connection and **raise the
     `already_configured` error** if the instance is configured. Step `003`'s guard is
     the route-level enforcement. This re-check is the service's own invariant, so a
     caller that does not go through HTTP cannot bypass it;
  2. apply the registry: SQLAlchemy's create-if-missing creation of every table in
     `db/schema.py`'s single `MetaData`, bound to that connection (`context.md` D8);
  3. mint the id from the **generator passed in**, never from a module global;
  4. hash the password through step `001`'s hashing seam;
  5. insert the one `users` row: minted id, username, hash, role `admin` (UC-001),
     `is_enabled` true, `created_at` and `updated_at` as UTC ISO-8601, and
     `rp_language`/`preferred_language` left NULL (`context.md` D15).

  It sets **no cookie, mints no token and writes no `auth_sessions` row**. That table
  does not exist, and US-001.AC-2 belongs to `004` (`context.md` D9). It logs at most the
  new id as a decimal string and the outcome. It never logs the password or the hash.

**`backend/app/services/health.py`** — the widening that `001/006:52` anticipated, done
as a **delegation**: the probe's `configured` branch now calls the predicate above
instead of running its own copy of the query. Its signature, its `schema` branch, its
`status` precedence and its "never imports `fastapi`" property do not change. The status
roll-up is **not** re-decided (`context.md` D5).

## Definition of done

1. `[test]` The `already_configured` error carries code `already_configured`, HTTP status
   `409`, an empty `detail`, and renders in the one wire shape
   `{"error": {"code", "message", "detail"}}` through the handler `001` already
   registered. No second handler is added. When raised with **no arguments**, its
   `message`, both on the instance and in the rendered body, is a **non-empty
   human-readable string** and not null.
2. `[test]` The predicate answers **false** on a database with no schema, and **false**
   on a database whose `users` table exists but is empty. A present but empty table
   still means no administrator exists. (US-003.AC-1)
3. `[test]` The predicate answers **false** when `users` holds only non-administrator
   rows, and **true** as soon as one administrator row exists. (US-003.AC-1)
4. `[test]` Run on a database with no schema, the creation operation leaves every
   registry table present and exactly one `users` row. That row's role is the
   administrator value, its `is_enabled` is true, its `password_hash` is not the
   plaintext, and its `rp_language` and `preferred_language` are NULL. (US-001.AC-1)
5. `[test]` The stored `password_hash` verifies against the supplied password through
   step `001`'s verification operation, and fails against a different password.
   (US-001.AC-1)
6. `[test]` The creation operation raises `already_configured` when the instance is
   already configured, and the existing database is **left untouched**: the row count
   and the existing administrator's stored hash do not change. (US-003.AC-1)
7. `[test]` The creation is **atomic, schema included**. When the insert cannot
   complete, the connection is left with no administrator row, so no partial bootstrap
   is observable. In particular, on a database with **no schema**, a creation that fails
   **after** the registry would have been applied leaves **no registry table** and no
   administrator row. This is checked on the same connection and on a freshly acquired
   one. The failure is provoked through the operation's own inputs, not by patching its
   internals. On a no-schema database the lever is the generator parameter: a supplied
   generator that fails when asked to mint. Afterwards the same connection is still
   usable: a creation with a working generator then succeeds.
8. `[test]` The creation operation mints the id from the generator it is **given**: two
   calls with two different generators produce ids from those generators, and nothing
   in the module reaches a process-wide generator.
9. `[test]` `/api/health` still reports correctly after the delegation. On a database
   with no `users` table it answers `configured: false`, `schema: "missing"` and
   `status: "degraded"` (`context.md` D5). This corrects the `001`-era expectation for a
   fresh database and is the only change to that file's existing assertions. On a
   database holding one administrator and every registry table it answers
   `configured: true`, `schema: "ok"` and `status: "ok"`.
10. `[test]` The health probe and the guard cannot disagree: the probe's `configured`
    value equals the predicate's answer on the same connection in all four combinations
    of (table present / absent) × (administrator present / absent).
11. `[test]` `services/bootstrap.py` imports no `fastapi` symbol, references no HTTP
    status code and takes no `Request`. It can be called with a plain connection, a
    generator and two strings.
12. `[manual/live]` The creation is one `with conn.begin():` block covering the registry
    application, the id mint and the insert. The verifier confirms this by reading the
    module. DoD-7 tests atomicity by behaviour, but the single-block shape is what later
    features must not split.
13. `[manual/live]` Nothing in this step declares `auth_sessions`, mints a token, sets a
    cookie or adds a setting. The verifier confirms this by reading the four source
    files.
14. `[manual/live]` `mypy app`, `ruff check .` and `pytest` all pass from `backend/`.
15. `[test]` The engine runs DDL inside transactions. On a connection from the
    production engine factory, a `CREATE TABLE` run inside a `with conn.begin():` block
    that is then rolled back (the block exits by exception) leaves **no such table**, on
    that connection and on a freshly acquired one. The same `CREATE TABLE` in a block
    that exits normally is present afterwards.
16. `[test]` The `001/005` engine guarantees still hold with transactional DDL on:
    `PRAGMA foreign_keys` is enabled and `PRAGMA journal_mode` reports `wal` on each
    freshly acquired connection, and `sqlite-vec` is loaded on every connection. The
    existing tests in `backend/tests/test_db_engine.py` pass **unmodified**.
17. `[manual/live]` The `engine.py` edit adds or removes no public name, leaves the
    `connect` listener's order and PRAGMAs as they were, sets no PRAGMA inside a
    transaction, and leaves `get_connection` opening no transaction. The verifier
    confirms this by reading the module.
