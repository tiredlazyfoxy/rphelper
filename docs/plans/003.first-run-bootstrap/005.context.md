# Step 005 — step-specific context

Feature-wide facts are in `context.md`; the decisions this step implements are D9 (the
hand-off, and why there is no cookie), D12 (no `notifyFailure` in this entry), D13 (draft
placement and the MobX contract) and D16 (validation kept to what is required). None of
that is repeated here.

## The route this form posts to

`POST /api/bootstrap/create`, from step `003`. Its request body is a username and a
plaintext password and nothing else; its success is **201** with a body the form does not
read; its refusal is **409** with code `already_configured`; an empty field is refused with
FastAPI's own **422**, whose body is not the error envelope and therefore decodes to `002`'s
`client_malformed_error` at status 422 — **not** the not-ready condition, which requires
status ≥ 500 (`context.md` D10). So a 422 lands in the general inline alert, which is
correct: the form prevents it client-side and its arrival means a client bug, not a
deployment state.

## The draft-form convention this follows, and the one half that is this step's

`002`'s D6 splits error handling in two: **one decode, in the client** — `shared/api.ts`
throws a typed `ApiError` — and **one field mapping, per draft**, performed in the `submitX`
free function *"by status or code, not by parsing prose"*, with anything unmappable landing
on a general key. This step writes the second half for the first time in the project. It
does not re-decode and it does not introduce a second error shape.

`ui-conventions.md`'s draft convention, as `002` records it: modal open/target flags are
component-local `useState`, not store state, and a **fresh draft instance per open**. There
is no modal here — the form is in the page — but the fresh-instance rule still applies and
is why the draft is created with `useState(() => new …Draft())` at the mount that renders
it.

## Why the refusal is a page state and not a form error

UC-003's postcondition is that bootstrap *stays unavailable*, and US-003.AC-2 requires the
person be **directed to sign in**. A red message beside a still-enabled submit control
satisfies neither: it invites a second attempt and offers no way forward. Flipping the whole
page to the refusal state is the rendering of the product's own words, and it is why the
submit function resolves to an outcome the caller acts on rather than writing every failure
onto the draft.

This is also the reason the refusal path is recognised by **code** — `already_configured` —
and not by status `409`: `002`'s D7 is explicit that call sites branch on `.code`, never on
a status number and never on a message string.

## Why the hand-off is a document navigation, and why it is injectable

`frontend-structure.md`, "Navigation between entries": within an entry `react-router-dom`;
**between** entries a plain document navigation (`window.location.assign`), because the
entries are separate documents with no shared router. `bootstrap` → `login` is a
cross-entry move, so it is a document navigation — never a router navigation and never a
`<Link>`.

The default is the real navigation; the prop exists so a component test can observe the
hand-off without fighting jsdom's location object. DoD-5 asserts the call, and DoD-11
asserts the real navigation in a browser.

## What the hand-off does not do — US-001.AC-2, restated where it will be looked for

`003` returns **no cookie**, so after the hand-off the operator arrives at `/login` **not
signed in** and signs in there. That is `context.md` D9's deferral, taken by user decision,
and it is why no DoD item in this step claims US-001.AC-2. **FEAT-001 is not fully
delivered until `004.authentication-session` ships.** Do not add an item claiming otherwise
to make coverage look complete, and do not mint a token or set a cookie here to close it.

## Gotcha — the confirmation field is a UI decision, not a requirement

`docs/product/` states no password policy and no confirmation requirement. The field exists
because this is a one-shot, irreversible operation on an instance with **no password-reset
path anywhere in the product**, so a typo would strand the operator (`context.md` D16). Its
DoD items therefore cite no acceptance criterion. It is **not** sent to the backend — DoD-4
asserts the request body carries the username and password only.

## Gotcha — no icon-only action, deliberately

`ui-conventions.md` makes a bare `ActionIcon` wrapping a Tabler icon a defect: every
icon-only action goes through `shared/IconButton` (`icon`, required `label`, required
`onClick`, optional `disabled`, optional `color`, optional size variant, stroke 1.5). This
form has no such action — a password-visibility toggle was considered and left out, because
the confirmation field already covers the typo risk it would address and two mechanisms for
one risk is one too many. If a later change adds one, it goes through `IconButton`.

## Gotcha — do not touch the rest of the page

`BootstrapPage.tsx` is in this step's Source files for one reason: mounting the form inside
the **offer** state. The probing, refusal, not-ready and failed states, the probe lifecycle,
the retry stopper, the entry marker and the absence of any stylesheet import are step
`004`'s and are covered by its tests. Editing them here would put two steps' criteria in one
file with no way to tell which broke.
