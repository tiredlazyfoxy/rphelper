# Step 002 — step-specific context

Feature-wide facts are in `context.md`. The decisions this step implements are D2 (409),
D3 (what `configured` reads), D4 (one definition, health delegates), D5 (the roll-up is
not re-decided), D8 (`create_all` inside the transaction, and its dependence on
transactional DDL), D9 (no cookie) and D15 (what the insert writes). None of them is
repeated here.

## The error-hierarchy pattern this subclass follows

`app/errors.py` comes from `001.backend-foundation/003`. It has a base domain-error
exception whose `code` and `http_status` are **class attributes each subclass sets**,
per-instance `detail`, a render-style method producing exactly
`{"error": {"code", "message", "detail"}}`, and **one handler registered for the base
class** so every subclass is covered. `001` defines only `secret_ref_missing`.
**`already_configured` is not declared anywhere in `001`**, so this step declares it as a
subclass that follows that pattern.

The handler logs the code and the status and nothing else. This step does not change it.

## Gotcha — the base class has no default message

The base constructor takes an optional message and an optional detail, and stores the
message exactly as given. The render method outputs it unchanged. There is no
class-level fallback. So a subclass raised with no arguments, which is how step `003`'s
guard raises `already_configured`, renders `"message": null`. That contradicts the
architecture's wire example (`backend-structure.md:568`), where `message` is a string.
The first build of this feature produced exactly that null.

The fix belongs to **the subclass alone**: it supplies its own default human-readable
message when none is given. It is **not** a class-level default added to the base,
because that would change what `SecretRefError` and every future error renders by
default. It is **not** a change to the handler either. The wording is the coder's call.
It should say that the instance is already configured, which is UC-003's condition.
Adding the default changes the subclass's construction surface, so the skeleton
re-freezes it. Step `003`'s call site keeps raising it with no arguments.

## What the connection dependency does and does not give you

`get_connection` from `app/db/engine.py` (`001/005`) yields a Core `Connection` and
**opens no transaction**. Transaction boundaries are `with conn.begin():` blocks at the
service's own level (`001/005.db-engine-and-registry.md:66-68`). That is why the
creation operation opens its own block, and why the predicate, which only reads, does
not.

**This step edits that module**, and only to make the engine's transactions include DDL
(the gotcha below). The dependency's contract does not change: it still opens no
transaction, and a service still owns its `begin()` blocks. What changes is that a
`begin()` block now covers everything inside it, `CREATE TABLE` included.

The database **file** is created as a side effect of connecting to the resolved path,
and a missing `data_dir` is created instead of raising (`001/005` DoD-5). There is no
"create the file" call to make, and the file's existence says nothing about whether the
instance is configured (`context.md` D3).

## Gotcha — pysqlite's legacy transactions leave DDL outside the block

This caused the SPEC fault in the first build. Under the stdlib `sqlite3` driver's
default (legacy) transaction control, SQLAlchemy's `begin()` **does not send `BEGIN`**.
The driver opens a transaction lazily, and only right before a DML statement (`INSERT`,
`UPDATE`, `DELETE`). A `CREATE TABLE` issued before the first DML statement runs in
autocommit and is permanent immediately. So `create_all` followed by the insert, inside
one `begin()` block, behaved like this: the tables committed on their own, the insert
opened the driver's implicit transaction, and when the insert failed the rollback
removed only the row. The instance was left with tables and no administrator, which is
exactly the state D8 rules out.

SQLAlchemy documents the fix in its SQLite dialect docs as the "pysqlite transactional
DDL" configuration. It turns off the driver's implicit transaction handling, so the
driver never opens or commits anything on its own, and has SQLAlchemy's `begin` send the
real `BEGIN`. After that, SQLite's own transactional DDL applies, and SQLite fully
supports rolling back `CREATE TABLE`. Savepoints (`begin_nested`) also become reliable
under the same setting.

**Why this is engine-wide and not a bootstrap special case.** The `connect` listener
runs on every connection. Configuring only the bootstrap path would need a second engine
or a per-call switch, which would give two transaction semantics in one process. Later
features rely on the same guarantee. Settle's two UPDATEs plus the `session_vec`
refresh, a memo write plus its embedding write, and disabling an account plus revoking
its sessions are all "commit together or not at all" (`backend-structure.md`,
Persistence access, reason 1). `007`'s admin-triggered DDL benefits too. The honest
semantics belong to every connection.

**What must not move:**

- **PRAGMAs stay outside any transaction.** `journal_mode = WAL` cannot be entered
  inside a transaction, and `foreign_keys` is silently a no-op inside one. With implicit
  transactions off, the `connect` listener's statements run in autocommit, which is what
  they need. This rules out Python 3.12's PEP 249 mode (`autocommit=False`), where the
  driver keeps a transaction open at all times, including right after connect. The
  `connect` listener's order (load `sqlite-vec`, then `foreign_keys`, then
  `journal_mode`) stays unchanged. If the mechanism needs a statement in that listener,
  it goes in without reordering the three existing steps.
- **`sqlite-vec` loading is unaffected.** It is a driver call, not a statement, and it
  still runs on every connection.
- **`get_connection` still opens no transaction.** SQLAlchemy's autobegin (the implicit
  transaction a `Connection` starts on its first `execute`) now sends a real `BEGIN` as
  well. That is expected, and it is still not the dependency opening one.

**`is_configured`'s rollback of its own autobegun read stays valid.** The predicate
checks whether the caller already had a transaction open. If not, it rolls back the one
its read autobegan, so that a later `with connection.begin():` on the same connection is
not refused. Under the new setting, that autobegun transaction is a real deferred
`BEGIN` holding a read snapshot, and the rollback ends it. When the predicate runs
inside the creation block, which already has a transaction open, it does not roll back,
so the re-check and the DDL stay in the same transaction. None of this logic changes.

The probe's own `sqlite_master` read (`services/health.py`, from `001`) autobegins and
does not end its transaction. That is pre-existing behaviour, and the pool's
reset-on-return rolls it back. Under WAL, an open read snapshot does not block the
writer. This step does not change it.

## Applying the registry, concretely

`db/drift.py`, `db/sync.py`, `alembic.ini` and `versions/` **do not exist** and nothing
here may depend on them. They belong to `007`, and Alembic is not a dependency. Applying
the registry here means calling SQLAlchemy's own create-all on the single `MetaData` in
`db/schema.py`, bound to the request's `Connection` so it runs inside the surrounding
transaction. With the engine change above, that transaction really does include it.
Create-all's default create-if-missing behaviour makes it idempotent. Because the
registry is the single source of truth, this stays correct with no edit here when later
features add their own `Table(...)` literals.

## The health probe's existing shape, which this step must not disturb

From `001/006.app-factory-and-health.md:41-62`: the probe takes a Core `Connection`
**and a metadata registry as a parameter**. The registry is a parameter on purpose, so a
test can supply one containing a table and observe the `"missing"` branch. The probe
returns a plain result. This step does not change its `schema` branch, its precedence
roll-up or its parameter list. The only edit is that the `configured` branch calls step
`002`'s predicate.

A consequence readers will trip over: now that `users` is in the production registry, a
pre-bootstrap instance reports `schema: "missing"` and therefore `status: "degraded"`.
That is `context.md` D5. It is an honest report, and it is why the frontend (step `004`)
branches on `configured` alone.

## The generator is passed in, not reached for

The app factory builds the process's snowflake generator and keeps that single instance
on **application state** (`001/006:33-35`, and `backend-structure.md`'s `app/ids.py`
section: one generator instance per process, kept on application state). A service must
not reach for a module global to get it, so the creation operation **takes it as an
argument**. Step `003`'s router reads it from application state and passes it down.
DoD-8 tests this rule. The generator parameter is also the lever for DoD-7's no-schema
case (below).

## Gotcha — re-checking the predicate inside the transaction is not redundant

Step `003`'s `require_unconfigured` refuses before the handler runs, so the service's
re-check looks like a duplicate. It is not. The service can be called without HTTP at
all, which is the point of the routers/services split. The check inside the transaction
makes the refusal a property of the operation instead of one transport. Two callers
racing on a fresh instance also resolve correctly: the second caller's check runs inside
its own transaction, against the schema the first caller committed.

## Gotcha — testing atomicity without reading the implementation

DoD-7 requires atomicity to be tested through the operation's **own inputs**, because
the test-coder never reads source and must not patch internals. The two claims need
different levers:

- **"No administrator row is left behind."** A username that the table's own
  constraints reject works: the write fails inside the block. This lever needs the
  `users` table to exist **before** the call, so it cannot show that DDL rolls back.
- **"No registry table is left behind."** The database has to start with **no schema**
  and the failure has to come **after** the registry step. Of the operation's inputs,
  only the generator fails at that point: the id is minted after the registry is
  applied and before the insert. A supplied generator that fails when asked to mint is
  the lever. Under the old legacy-transaction behaviour this case left the tables behind
  and was the first build's fault. A pre-existing-row id collision is not available on a
  no-schema database, because there is no row to collide with.

The test-coder chooses the exact provocation. The DoD fixes the observable outcome:
no table and no row, on the same connection and on a fresh one, and the connection is
still usable afterwards. DoD-15 makes the same claim one level down, against the engine
directly, so a regression shows up there even if the service changes.

## Gotcha — do not log the credential

`deployment.md`'s redaction rule has no exception for any log level. This module may log
the new id as a decimal string and the outcome code. It must never log the password, the
encoded hash, or a request body.
