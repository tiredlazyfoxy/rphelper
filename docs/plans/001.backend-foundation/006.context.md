# Step 006 — step-specific context

Feature-wide facts — decisions D3 and D10, the routers/services split, the JSON id
boundary, "no DDL at startup" — are in `context.md`.

## The response shape, verbatim

From `docs/architecture/backend-structure.md` § `/api/health`:

```json
{ "status": "ok" | "unconfigured" | "degraded",
  "configured": true|false,
  "schema": "ok" | "drift" | "missing" }
```

Three consumers make it load-bearing: it is the container healthcheck target
(`supervisord` has no wait-for ordering, so nginx can accept connections before uvicorn
is listening and the probe has to come from the app); it is the basis for the
`bootstrap` and `admin` entries' not-ready-yet handling; and `configured` is the signal
the bootstrap entry uses to decide whether to offer bootstrap at all.

So it must be **cheap and always answer**.

## What the architecture does not state, and this step decides

**No HTTP status codes are given for the three `status` values.** Ruling: all three
answer **200**. Reasoning — the body *is* the answer, and all three consumers need to
read it. `"degraded"` returned as a 503 would make the SPA's fetch path treat a
reportable condition as a transport failure and discard the very body that explains it.
A probe that cannot read the database at all is a different thing: that is an
operational fault and surfaces as a 500, which is what makes the endpoint capable of
failing at all.

**The probe's home.** `backend-structure.md`'s services list does not name
`services/health.py`. It is created here because the split this feature establishes
forbids a router from issuing SQL, and the probe issues SQL. Decision D10 records the
reasoning and `outcome.md` asks the architect to record the module.

Both rulings are planner inferences and are flagged as such in `outcome.md`.

## Why `schema == "ok"` against an empty registry is right

Decision D3. The probe answers what it was asked: "is every declared table present?"
With nothing declared, the answer is yes. The alternative — special-casing an empty
registry into `"missing"` or `"unconfigured"` — would encode "this feature has not
shipped its tables yet" into a runtime signal, and would have to be removed the moment
the first table lands. Designing it as a widening is the point: `003` sharpens
`configured`, `007` adds the `"drift"` branch, and neither rewrites the function.

The registry arrives as a **parameter** rather than an import for the same reason — it
makes the `"missing"` branch reachable in a test today, before any table exists.

## The pydantic field-name gotcha

`schema` collides with a member name on pydantic's model base. The field is therefore
declared under a safe Python name with a serialisation alias of `"schema"`, and the
model is configured so that the JSON key is literally `schema` on the way out. The
skeleton freezes the exact declaration; DoD-1 pins the observable outcome, which is the
part that matters — the wire key is `schema` and nothing else.

## Routes return pydantic models

The health route returns the response model, never a plain `dict` and never a
`JSONResponse`. That is not tidiness: a route returning a `dict` bypasses `models/` and
therefore bypasses the JSON id boundary. No id appears in this response, so the rule
costs nothing to hold here — and holding it at the first router is what makes it the
convention rather than an aspiration.

## Ordering inside the factory

`configure_logging` runs **before** any router is registered, so a failure during
registration is already captured by both sinks. This is unobservable from outside the
factory, which is why DoD-12 is `[manual/live]` rather than `[test]` — the honest
classification, not a gap.

The generator is constructed **once** by the factory and held on application state. That
is the code-level half of `data-model.md`'s "exactly one generator process per node id"
guarantee; DoD-9 pins the single instance.

## What must NOT appear in this step

- `GET /api/me` — feature `004`.
- Any authentication dependency. `require_unconfigured`, `require_user` and
  `require_role` are `004`'s; `/api/health` is unauthenticated by design and is safe so
  because it names no table contents and no user.
- Any DDL, including a create-if-missing convenience in the lifespan.
- Any drift detail. The `schema` field is a **coarse roll-up**; the detailed per-table
  report is admin-only and belongs to `007`'s `admin_db.py`.
- Any second router. `routers/health.py` is the only one in scope.
