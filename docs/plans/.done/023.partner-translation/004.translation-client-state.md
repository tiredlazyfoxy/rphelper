# Step 004 — `translationApi.ts` and the per-row flicker state

## Goal

Add the translate call and a MobX `TranslationState` holding per-row flicker state. Add the
free-function effects flick, cancel, invalidate and dispose, and the derivation the UI
reads (D13, D4 client half, D14's effect).

## Interface intent

**`src/app/translationApi.ts`** (new)

- **`Translation`**: the wire type. It has `message_id` (string), `target_language`
  (string), `text` (string) and `cached` (boolean).
- **`translateMessage`**: takes a message id (string) and an optional `AbortSignal`. It
  POSTs `/api/messages/<id>/translation` with no body through `shared/api.ts`'s `apiPost`,
  passing the signal. It resolves to a `Translation`. Like every API function, it rejects
  with `ApiError` on non-2xx and rethrows an abort raw.

**`src/app/translationState.ts`** (new)

- **`TranslationState`**: a class with **observable fields only**, made with
  `makeAutoObservable(this, { <controllers field>: false }, { autoBind: true })`. No
  methods, no getters. It holds, keyed by message id (string):
  - which rows are shown;
  - each row's cached translated text;
  - which rows have a request pending;
  - a non-observable map of each pending row's `AbortController`.
- **A view derivation**: a free function taking the state and a message id. It returns the
  row's display status — `"original"`, `"pending"` or `"translated"` — and, for
  `"translated"`, the translated text.
- **`flickTranslation`**: an async effect taking the state and a message id. It never
  rejects. Depending on the row:
  - pending → behaves as `cancelTranslation`;
  - shown → un-shows the row and makes no request (UC-040);
  - has cached text → shows it and makes **no request** (US-046.AC-1);
  - otherwise:
    1. marks the row pending with a fresh controller, then calls `translateMessage` with
       its signal;
    2. on success, caches the text and shows it;
    3. on an abort, writes nothing beyond clearing pending and does not notify;
    4. on any other failure, stays on the original, calls `notifyFailure(error)` once and
       caches nothing (US-048.AC-1, AC-2).

    Pending and the controller are cleared at the end, but only if the row's controller is
    still the one this call created. Writes happen inside `runInAction`.
- **`cancelTranslation`**: takes the state and an id. It aborts that row's pending request,
  if any. The row stays on the original.
- **`invalidateTranslation`**: takes the state and an id. It aborts a pending request for
  the row, drops its cached text and un-shows it. A late answer to the aborted request
  writes nothing.
- **`disposeTranslations`**: takes the state. It aborts every pending request, for use on
  unmount. Nothing is notified.

## Definition of done

1. `[test]` `translateMessage("7250000000000000101", signal)` calls `fetch` once: POST
   `/api/messages/7250000000000000101/translation` with that signal. It resolves to the
   stubbed `Translation`, with `message_id` a string. A 502 `translation_failed` stub
   rejects with an `ApiError` whose `code` is `translation_failed`. (wire contract)
2. `[test]` On a fresh row, `flickTranslation` makes exactly one POST to that row's path.
   While it is unresolved the view is `"pending"`. After it resolves with text "Привет" the
   view is `"translated"` with text "Привет". (US-045.AC-1)
3. `[test]` Flicking the translated row again makes the view `"original"` and makes **no**
   request. (UC-040)
4. `[test]` Flicking it a third time makes the view `"translated"` with "Привет"
   immediately after the call returns, without awaiting, and `fetch` was still called only
   once in total. (US-046.AC-1)
5. `[test]` A 502 `translation_failed` answer leaves the view `"original"`. `notifyFailure`
   is called exactly once, with an `ApiError` whose code is `translation_failed`. The
   effect's promise resolves. The next flick makes a **new** POST. (US-048.AC-1,
   US-048.AC-2)
6. `[test]` A `fetch` that rejects with a `TypeError` (network) behaves as DoD-5:
   original, one `notifyFailure`, resolved promise, no cached text. (US-048.AC-1)
7. `[test]` Flicking a pending row, and calling `cancelTranslation` on a pending row (two
   cases), each abort the request's signal. The view returns to `"original"`, and
   `notifyFailure` is **not** called. The next flick makes a new POST. A second flick while
   pending never issues a second request. (US-133.AC-2 user-visible half, D4)
8. `[test]` `invalidateTranslation` on a translated row makes the view `"original"`, and
   the next flick makes a new POST, whose answer is then shown. On a pending row it aborts
   the request. A response arriving after that writes nothing: the view stays
   `"original"` and no text is cached. (US-111.AC-2 client half, D14)
9. `[test]` Rows are independent. With row A pending and row B translated, flicking B
   shows its original and cancelling A leaves B's cached text intact. Each row's request
   goes to its own path. (D13)
10. `[test]` `disposeTranslations` with two pending rows aborts both signals, and neither
    calls `notifyFailure`. (D13)
11. `[test]` `TranslationState.prototype` has no own property besides `constructor` (no
    methods, no getters). (pure data contracts)
