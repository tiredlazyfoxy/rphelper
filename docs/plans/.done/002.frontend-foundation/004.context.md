# Step 004 — step-specific context

Feature-wide facts are in `context.md`; the decisions this step implements are D6
(decode once, in the client), D7 (`ApiError`'s shape) and D8 (the synthetic codes and
the unwrapped abort). The reasoning is there and is not repeated.

## The wire shape this step decodes

`docs/architecture/backend-structure.md` gives it:

```json
{ "error": { "code": "...", "message": "...", "detail": { } } }
```

Any id appearing inside `detail` is a **decimal string** and stays one. The client
never applies a `JSON.parse` reviver and never coerces — that is the whole of the
client's obligation under "Ids are strings".

## The two synthetic code strings — fixed here

| Constant meaning | Value |
|---|---|
| non-2xx whose body is absent, not JSON, or not the envelope | `client_malformed_error` |
| `fetch` itself rejected (network down, DNS, connection refused) | `client_transport_failed` |

Both are exported as named constants. Neither collides with any code in
`backend-structure.md`'s error table, and the `client_` prefix makes it unmistakable at
a call site that no backend produced it.

`client_transport_failed` carries status `0`, because there was no HTTP response to
take a status from. A call site that wants to distinguish "no response" from "a
response I could not read" has exactly these two codes to do it with.

## The codes call sites will eventually branch on

`frontend-structure.md` lists the ones the UI must branch on specifically:
`model_not_enabled`, `no_embedding_model`, `translation_failed`, `zone_empty`,
`zone_not_empty`, `nothing_to_reopen`, `message_not_editable`, `already_configured`,
`account_disabled`. **`discussion_not_resumable` is gone** — `zone_not_empty` replaced
it and the rename is not cosmetic.

**This step hardcodes none of them.** `code` is an ordinary string on `ApiError` and
the client has no knowledge of any particular value; the features that own those
behaviours branch on them. An enum here would have to be edited by every later feature
and would turn an unknown future code into a type error rather than a rendered failure.

## The 401 navigation

`frontend-structure.md`: *"A `401` triggers a document navigation to `/login`. A `403`
does not — it is a genuine authorization failure and is rendered, not redirected."*

Two details the doc does not state and this step fixes:

- the navigation is a **document** navigation (an assignment to the browser's location),
  not a router navigation. The entries are separate documents and `login` is one of
  them; there is no shared router that could route to it.
- the client **still throws** after navigating. A navigation is not synchronous
  termination — the remaining statements in the calling async function would otherwise
  run against a response that was never valid.

This makes the 401 path testable without a real navigation: the location assignment is
observable, and the rejection is observable, independently.

## The abort rule, and why it is not an `ApiError`

`ui-conventions.md`'s page-state convention drives every load from a `useEffect` with
an `AbortController` cleanup, and every free function early-returns on an aborted
signal before writing. If the client wrapped an abort into an `ApiError`, an unmount
during a load would be indistinguishable from a network failure and would render an
error for something the user did deliberately. The same reasoning appears in
`frontend-structure.md`'s SSE section, where a stop is explicitly not a failure — the
consumer checks `signal.aborted` rather than inspecting the stream. This client follows
the same rule for the same reason.

The observable form: what the caller catches after aborting is the same rejection the
platform produced, and the exported type guard answers false for it.

## What this step does not build

The SSE consumer. `frontend-structure.md` lists it among `shared/`'s contents, but
`brief.md` puts it explicitly **Out** — it is `019`'s. It speaks to one route, streams
a body reader, and shares nothing with this module by design ("the whole point of the
two routes being two routes").

Also not built: the admin gate's `/api/me` boot round-trip and its "502 is not a deny"
rule. Both are `005`'s, and inventing a 502 policy here would pre-empt it.

## Gotcha — stubbing `fetch`

No network-mocking library is a dependency and none is added (`context.md`, test
conventions). Tests replace the global `fetch` per test and restore it afterwards.
Constructing responses with the platform `Response` type gives real status codes, real
header behaviour and a real body read, which is what DoD-5, DoD-7 and DoD-14 need.

## Gotcha — observing the navigation in jsdom

jsdom does not perform navigations and logs a "not implemented" error if one is
attempted directly. The 401 test needs the location assignment to be observable without
jsdom attempting it. The coder should route the navigation through a form the test can
observe — that is a skeleton-level concern; what this plan fixes is the **behaviour**:
a 401 navigates to `/login` and a 403 does not.

## Gotcha — the empty-body case

A `204` has no body, and a `200` may have a zero-length one. Calling the JSON parser on
either throws a syntax error that has nothing to do with the request failing. DoD-5
exists because that is the easiest way for this module to turn a successful mutation
into a spurious failure.
