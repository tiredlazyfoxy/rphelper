# Step 004 — The API client and its typed errors

## Goal

Create the one module every entry calls the backend through: a same-origin `/api`
fetch wrapper that sends cookies, sets no `Authorization` header, decodes the backend's
error envelope into a thrown typed `ApiError`, and turns a 401, a 5xx and a transport
failure into the same uniform branch-on-`.code` contract.

## Interface intent

**`frontend/src/shared/apiError.ts`** exports:

- **`ApiError`** — a class extending the built-in `Error`, carrying the backend's
  error `code` as its branch key, the `message` it inherits from `Error`, a `detail`
  object of unknown-typed values, and the HTTP `status` it arrived with. Constructed
  from those four values. Its `name` identifies it as an `ApiError`, and instances are
  recognisable with `instanceof`. `detail` defaults to an empty object when the wire
  carried none, so a call site reading it never has to null-check.
- **two synthetic code constants**, named and exported so no call site re-types the
  string: one for *a non-2xx whose body is absent, not JSON, or not the error envelope*
  and one for *`fetch` itself rejecting*. Their values are in `004.context.md`.
- **a type guard** answering whether an unknown thrown value is an `ApiError`, so a
  `catch` block has one sanctioned way to narrow.

**`frontend/src/shared/api.ts`** exports:

- **one request function** — the single entry point. It takes the path, the HTTP
  method, an optional JSON-serialisable body and an optional `AbortSignal`, and
  resolves to the parsed response body. Its behaviour:
  - it **requires the path to begin `/api/`** and throws immediately if it does not.
    There is no base URL, no host and no `import.meta.env` read; the guard is what
    makes "always same-origin `/api/...`" mechanically true rather than a habit;
  - it sends credentials, so the HttpOnly session cookie rides along, and sets **no**
    `Authorization` header;
  - it sets a JSON content type **only when there is a body**, and serialises that body
    with the platform's JSON serialiser — no reviver, no replacer, no id coercion in
    either direction;
  - on a 2xx it parses and returns the JSON body; a `204` or an otherwise empty body
    resolves to nothing rather than throwing on an empty parse;
  - on a non-2xx it reads the body and decodes the `{ error: { code, message, detail } }`
    envelope into an `ApiError` and **throws it**. A body that is absent, not JSON or
    not that shape yields an `ApiError` carrying the malformed-body synthetic code, the
    real status, and a message that does not pretend to be the server's;
  - **additionally**, when the status is 401, it performs a **document navigation** to
    `/login` and then still throws, so the awaiting caller's continuation never runs.
    A 403 does **not** navigate — it is a genuine authorization failure and is rendered;
  - when `fetch` rejects because the network failed, it throws an `ApiError` carrying
    the transport synthetic code and status `0`;
  - when `fetch` or the body read rejects **because the caller's signal aborted**, the
    original abort rejection propagates **unchanged and unwrapped**.
- **four thin named helpers** for GET, POST, PATCH and DELETE, each delegating to the
  request function with its method fixed. They exist so a call site never types a
  method string and so a reviewer can see at a glance which calls mutate.

Neither module knows anything about fields, forms or stores: mapping an `ApiError` onto
a draft's `serverErrors` keys is the draft's `submitX` function's job, per `context.md`
D6. Neither module raises a notification — that is step `005`'s `notifyFailure`, called
by the feature that decides a failure has no place to render.

## Definition of done

1. `[test]` An `ApiError` is an `Error`, is recognised by `instanceof`, and exposes the
   `code`, `message`, `detail` and `status` it was constructed with.
2. `[test]` An `ApiError` constructed with no `detail` exposes an empty object, never
   `undefined` or `null`.
3. `[test]` The exported type guard answers true for an `ApiError` and false for an
   ordinary `Error`, for a plain object of the same shape, and for a non-object.
4. `[test]` A 2xx JSON response resolves to the parsed body, and every id-valued field
   in that body is still the **string** the server sent — nothing is coerced to a
   number at any depth.
5. `[test]` A 204 or an empty 2xx body resolves rather than throwing.
6. `[test]` A non-2xx carrying a well-formed `{ error: { code, message, detail } }`
   envelope throws an `ApiError` whose `code`, `message` and `detail` are the
   envelope's and whose `status` is the response's — including for a 5xx.
7. `[test]` A non-2xx whose body is empty, is not JSON, or is JSON of some other shape
   throws an `ApiError` carrying the malformed-body synthetic code and the real status.
8. `[test]` A rejected `fetch` with no signal abort throws an `ApiError` carrying the
   transport synthetic code and status `0`.
9. `[test]` A rejection caused by the caller's `AbortSignal` propagates **unchanged** —
   it is not an `ApiError` and carries neither synthetic code.
10. `[test]` A 401 triggers a document navigation to `/login` **and** still rejects.
11. `[test]` A 403 triggers **no** navigation and rejects with an `ApiError` carrying
    the envelope's code.
12. `[test]` The request is issued to the path as given, on the current origin, with no
    host or scheme prepended.
13. `[test]` The request sends credentials and sets **no** `Authorization` header.
14. `[test]` A request with no body sets no content-type header; a request with a body
    sets a JSON content type and a JSON-serialised body.
15. `[test]` A path not beginning `/api/` is rejected before any network call is made —
    `fetch` is not invoked.
16. `[test]` The GET, POST, PATCH and DELETE helpers issue their respective methods.
17. `[manual/live]` `npm run typecheck` passes; neither module reads `import.meta.env`
    or any environment value, and neither contains a host, a scheme or a port literal.
