# Step 007 — step-specific context

## Why this depends on 001

Step 001 removed `diagnose` from the console sink and hid engine parameters;
without it, DoD-3..6 would fail on traceback locals rather than on a logging
call. With 001 done, any failure here is a log call or exception-formatting
site that writes content — a finding.

## Declared log lines in planned features (what is expected to be clean)

- 019/002 — stream failure logs session id + exception class only.
- 021/004 — tool failure logs tool name, call id, exception class.
- 023/002 — translation; DoD-17 there is a log-capture precedent.
- 028 — web search no-log DoD-11/12.
- 031 — "no log line carries payload content".

Only 023 and 028 had log-capture tests; this step covers the rest
across the whole world in one sweep.

## Mechanics

- Use the support module's world builder with **real logging** (not the no-op
  option) and its level-0 capture context manager. Capture message,
  `repr(extra)` and exception text (type + value + formatted traceback) of each
  record — DoD-3..6 specifically target the case where an exception's own
  message contains content and a handler logs it.
- The sentinel set checked is "every sentinel of every user" from the registry,
  plus the per-test failure sentinels.
- Drive failures through the fake model seam (raise with a caller-chosen
  message). Web search failure is induced at 028's HTTP seam.
- Errors raised by the app may legitimately carry a sentinel in the **HTTP
  response** to the caller who sent it (e.g. a 422 echoing their own input) —
  only log records are asserted here.
- DoD-9 complements 001's DoD-7 (engine hides parameters): together they keep
  SQL parameters out of logs even if someone lowers a level.
- No AST scan of `logger.*` call sites (user decision); the proof is dynamic.
