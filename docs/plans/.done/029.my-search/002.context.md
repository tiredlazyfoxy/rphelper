# Step 002 — step-specific context

Feature-wide facts are in `context.md`: the 025 / 024 names in "Build prerequisites", U1
(fail-whole), U2 (no memo predicate), D4 (hydration table), D5 (order), D6 (read posture),
the wire contract (field meanings), the Test conventions. Only what is narrow to this step
is below.

## Tables read by the hydration (built source, `app/db/schema.py`)

- **`sessions`** (~L273-313): `id`, `user_id`, `character_id`, `setup_id` nullable,
  `last_used_at`, `archived_at` nullable, `created_at`, `updated_at`. **No title, name or
  partner column** — a session is labelled by its character, its setup and its start time.
- **`messages`** (~L328-361) — never read directly. Entry hydration reads the
  **`settled_entries`** selectable (~L419), which is a Core `select` over `messages` with
  `settled_at IS NOT NULL`, not a SQL view: use it as a subquery and select `id`,
  `session_id`, `user_id` from it.
- **`memos`** (~L381-416): `id`, `user_id`, `scope` (`user` / `character` / `setup` /
  `session`), `scope_id` NOT NULL (for `user` it holds the user's own id), `body`,
  `is_enabled`, `is_forced`, `sort_key`. No `archived_at`.
- `characters` / `setups` columns: `001.context.md`.

## The existing session-label precedent

`services/sessions.py` (~L218-237) reads a session's setup name through an owner-scoped
LEFT OUTER JOIN to `setups`. Session hydration follows the same shape and adds an inner
join to `characters` (owner-scoped) for the character name. Not imported — `sessions.py` is
not touched.

## Hydration statements (one per kind)

- Session: `sessions ⨝ characters (characters.user_id = :u) ⟕ setups (setups.user_id =
  :u) WHERE sessions.user_id = :u AND sessions.id IN (:hit_ids)`.
- Entry: `settled_entries ⨝ sessions (sessions.user_id = :u) ⨝ characters
  (characters.user_id = :u) WHERE settled_entries.user_id = :u AND settled_entries.id IN
  (:hit_ids)`. `session_id` may be taken from the port hit or the row; they agree.
- Memo: `memos ⟕ setups ON memos.scope = 'setup' AND setups.id = memos.scope_id AND
  setups.user_id = :u WHERE memos.user_id = :u AND memos.id IN (:hit_ids)`.
- Empty hit list → no statement.

## Port calls

- Scopes are built with `user_id` only. Passing an extra predicate is a defect here
  (US-137.AC-1).
- The port's own reads roll back after themselves; 029's reads use 029's local helper.
  The whole call is several read windows, not one snapshot; that is accepted (the result
  is a list of pointers, not a consistent report).
