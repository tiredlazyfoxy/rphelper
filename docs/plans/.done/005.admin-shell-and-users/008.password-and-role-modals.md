# Step 008 — The Set Password and Change Role modals

## Goal

Complete the row menu: an administrator-initiated password reset that needs no current
password, and a role change the server refuses when the administrator targets
themselves.

## Interface intent

**`frontend/src/admin/setPasswordDraft.ts`** — the same draft shape step `007` uses
(`context.md` D16): a data class with observable fields only — the new password, its
confirmation, a `serverErrors` map keyed by field name plus a general key, and a submit
status — with pure free functions for the client errors, the merged errors and whether
it may be submitted, and an effectful `submitSetPassword(draft, targetId, onSaved,
signal?)`-shaped free function.

Client validation is exactly: the new password is required and the confirmation must
match. **There is no current-password field** (`context.md` D6: no current password is
required and none is taken) and **no password policy**. The target id is a **`string`**
and is passed in, never held as a number. Server failures map by status with **no
prose parsing**: everything lands on the **general key** except nothing — this route
produces no field-attributable refusal, so the general key is the whole mapping.

**`frontend/src/admin/SetPasswordModal.tsx`** — a Mantine `Modal` with two
`PasswordInput`s and a submit, naming the account it is acting on. No current-password
field, no generated-password display, no "email the user" affordance and no
force-change-at-next-login switch — **none of them exists in this product**
(`admin-surfaces.md`: no email flow, no reset link; `data-model.md`: no must-change
flag). `@mantine/form` is not used, and no success notification is raised.

**`frontend/src/admin/changeRoleDraft.ts`** — the same shape again, holding the selected
role (initialised from the target's current role), a `serverErrors` map and a submit
status, with the same pure functions and an effectful
`submitChangeRole(draft, targetId, onSaved, signal?)`-shaped free function. The only
client rule is that a role is selected; **the self-target refusal is the server's** and
is never re-implemented here. A **409** maps to a clear "an administrator cannot change
their own role" message on the **general key**; everything else lands there too.

**`frontend/src/admin/ChangeRoleModal.tsx`** — a Mantine `Modal` with a `Select` over the
ladder's two values, pre-selected to the account's current role, naming the account it is
acting on. The general key renders above the form.

**`frontend/src/admin/UsersPage.tsx`** — two additions to the existing row menu — **Set
Password** and **Change Role** — each with its own component-local `useState` target
row, and the two modals **conditionally mounted** so a fresh draft is constructed per
open. Both are offered on **every** row, including the administrator's own: the refusal
is the server's and the UI does not hide the action (`context.md` D1). `onSaved` closes
the modal and re-loads the list.

## Definition of done

1. `[test]` The set-password draft reports a missing new password and a confirmation that
   does not match, reports nothing for a filled matching draft, and applies **no policy**
   beyond non-empty. (`context.md` D6 — **no product id**)
2. `[test]` The set-password modal renders **no current-password field**, no generated
   password, no email affordance and no force-change switch.
   (`admin-surfaces.md`'s Set Password paragraph — **no product id**)
3. `[test]` A successful set-password submit posts the new password to that account's
   password route with the target id as a **string**, invokes the saved callback once,
   closes the modal and re-loads the list — and raises **no** success notification.
   (US-010.AC-2)
4. `[test]` A failed set-password submit renders its message on the **general key** above
   the form, keeps the modal open, and does not clear the list.
5. `[test]` The change-role draft initialises to the target's current role, permits a
   submit only when a role is selected, and implements **no self-target rule of its
   own**. (`context.md` D1 — **no product id**)
6. `[test]` A successful change-role submit posts the selected role to that account's role
   route, closes the modal and re-loads the list, after which the row's role badge shows
   the new role. (`admin-surfaces.md`'s "Change Role"; `data-model.md`'s `users.role` —
   **no product id**)
7. `[test]` A **409** from the role route renders a message on the **general key** saying
   an administrator cannot change their own role, keeps the modal open, and changes
   nothing in the list. (`admin-surfaces.md`'s "the backend refuses a self-targeted role
   change" — **no product id**)
8. `[test]` Both actions are offered on **every** row, including one that could be the
   caller's own — the UI hides neither, because the boundary is the server's.
   (`context.md` D1 — **no product id**)
9. `[test]` Both modals are **conditionally mounted**: closing and reopening either one
   yields a fresh draft, with the set-password fields empty and the role re-initialised
   from the row. (`ui-conventions.md`'s draft-lifetime rule — **no product id**)
10. `[test]` Both drafts are data classes with observable fields only — **no methods and
    no computed getters** — with every derivation a free function taking the draft and
    every effect a free function that `runInAction`s its writes and early-returns on an
    aborted signal. (`002`'s D2, `context.md` D16 — **no product id**)
11. `[test]` Neither modal's open flag or target row is a field of the page store.
    (`ui-conventions.md` — **no product id**)
12. `[test]` The row menu now holds Set Password, Change Role and exactly one of
    Disable / Re-enable, all as labelled text entries behind the single `IconDots`
    trigger — the row still contains exactly one icon-only control.
    (`ui-conventions.md` — **no product id**)
13. `[test]` No modal in this step maps an error by reading a message string, and neither
    raises a notification of any kind.
14. `[manual/live]` Against a running backend: an administrator resets another account's
    password, the old password stops working (US-010.AC-1) and the new one works
    (US-010.AC-2); changing another account's role succeeds and takes effect on that
    account's **next request** with no new login; changing one's own role is refused with
    the message rendered in the modal.
15. `[manual/live]` Both colour schemes are correct for both modals and their error
    states.
16. `[manual/live]` `npm run typecheck`, `npm test` and `npm run build` all pass from
    `frontend/`.
