# Step 008 — step-specific context

Feature-wide facts are in `context.md` (D1 on Change Role having no product id and on not
hiding it, D6 on the password-reset posture, D16 on the MobX/draft rules). Only what is
narrow to this step is below.

## Borrowed interfaces, by module path and role

- **`frontend/src/admin/usersPageState.ts`** (step `006`) — the row type (id as a
  **string**, username, role, enabled flag, `last_login_at`), the role union, and the
  load free function `onSaved` calls.
- **`frontend/src/admin/createUserDraft.ts`** (step `007`) — the **pattern** these two
  drafts follow. Do not import from it and do not generalise the three into one shared
  draft base: three drafts with three field sets sharing a shape is the convention
  working, and a base class would put effectful behaviour back into a class hierarchy the
  convention deliberately flattened.
- **`frontend/src/shared/api.ts`** / **`apiError.ts`** (`002/004`) — see
  `007.context.md`. A 409 does not navigate; only a 401 does.

## The two routes this step posts

`POST /api/admin/users/{id}/password` with one plaintext password, and
`POST /api/admin/users/{id}/role` with one role (`context.md` D5). Both answer **200**
with the affected account; the role route additionally answers **409**
`self_role_change_refused` when the target is the caller, and both answer **404**
`user_not_found` for a stale row.

## Why the role change needs no session handling

`004`'s D7 fixes that every authenticated request reads `role` **live** from `users`, so
a role change takes effect on the target's next request with no session rewrite and
nothing to invalidate. The modal therefore has no "the user must sign in again" copy,
because they must not.

## Why the password reset needs none either

`context.md` D6: setting a password does not revoke the target's sessions, by decision.
The modal must not claim that it does.

## Gotchas

- **Do not re-implement the self-target refusal client-side.** The UI may hide the action
  on one's own row per `admin-surfaces.md`, but this plan chose not to (D1), and a
  client-side *check* is worse than either: it would duplicate the rule in a place that
  cannot be trusted and would make the server's 409 unreachable in testing.
- **A 409 here is not "username taken".** The by-status mapping is per modal; step
  `007`'s draft keys 409 to the username field for its own route, and this one keys it to
  the general key with its own message. Neither is a shared table.
- **The target id comes from the row the menu was opened on**, held in component-local
  `useState`, and is a `string` throughout.
- **Three modals, one row menu.** After this step the menu is Set Password, Change Role
  and one of Disable / Re-enable. The row still has exactly one icon-only control, which
  DoD-12 re-asserts because this is the step that could break it.
