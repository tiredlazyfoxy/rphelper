# Step 001 — `users.last_login_at`, the login stamp, and revoking every session for one user

## Goal

Add the nullable `last_login_at` column the admin Users table needs, stamp it where a
login actually succeeds, and give the backend the bulk "revoke every live session for
this user" operation that `004` anticipated but did not build.

## Source files

```
backend/app/db/schema.py
backend/app/services/auth.py
```

## Test files

```
backend/tests/test_db_schema.py
backend/tests/test_auth_service.py
```

Both files exist from earlier features and are **edited**, not replaced.
`test_db_schema.py` carries `003/001` DoD-1's now-false "exactly these nine columns"
assertion (DoD-2 below); `test_auth_service.py` is **extended** with this step's two
behaviours and nothing already asserted in it becomes false.

## Interface intent

**`backend/app/db/schema.py`** — add **one column** to the existing `users` `Table(...)`
literal in the single `MetaData`: `last_login_at`, **nullable** text holding a UTC
ISO-8601 instant, matching the file's `*_at` convention (`data-model.md`). No other
column, no index, no table, no view and no other table literal is touched.

**`backend/app/services/auth.py`** — two additions to the module `004/001` builds, and
nothing else in it changes:

- **The open-session operation stamps the account's last login.** Inside the `with
  conn.begin():` block it already opens, and using **the same "now" it already computes**
  for `created_at`, it writes that instant to the target user's `last_login_at`. It does
  **not** touch `updated_at` (`context.md` D2). The operation's arguments, its return
  value and everything else about it are unchanged, so every `004/001` and `004/003`
  assertion about it still holds.
- **A bulk revoke-for-one-user helper.** Takes a Core `Connection` and a user id, sets
  `revoked_at` — to the current UTC ISO-8601 instant — on **every** `auth_sessions` row
  for that user whose `revoked_at` is NULL, and returns **how many rows it revoked**. It
  **opens no transaction of its own**: the caller's transaction is the boundary, because
  `services/users.py`'s disable must commit the flag flip and these revocations together
  (`context.md` D4, `data-model.md`). It **deletes nothing**, is **idempotent** (a user
  with no live sessions is an ordinary zero), and raises nothing — an unknown user id is
  zero rows, not an error. The returned count exists so a caller can log it; it is not a
  domain answer and reaches no response body.

The module keeps every property `004/001` gave it: it imports no `fastapi` symbol, sees
no `Request`, knows no status code, reads no settings, and logs at most an id as a decimal
string plus an outcome code and a count — never a token, a digest, a password or a
username.

## Definition of done

1. `[test]` The registry's `users` table carries a `last_login_at` column that is
   **nullable**, and the other nine columns keep the nullability `003/001` asserted.
   (`data-model.md`'s `users`; no product id — `admin-surfaces.md`'s "last login" column
   is an architecture requirement, not an acceptance criterion)
2. `[test]` `003/001` DoD-1's assertion that `users` carries **exactly nine** named
   columns "and no others" is **updated to ten**, deliberately and not incidentally, by
   adding `last_login_at` to the expected set. **Every other assertion in that file is
   left alone** — in particular the `auth_sessions` column assertions from `004/001`, the
   `role` value-domain test, the primary-key/autoincrement assertions and the registry
   enumerability assertion.
3. `[test]` A freshly created account has `last_login_at` NULL: nothing but a successful
   session opening writes it.
4. `[test]` Opening a session writes the account's `last_login_at`, and the value written
   is the same instant the new `auth_sessions` row's `created_at` carries.
   (`admin-surfaces.md`'s Users page; no product id)
5. `[test]` Opening a session leaves the account's `updated_at` unchanged.
   (`context.md` D2)
6. `[test]` A second session for the same account **advances** `last_login_at` and leaves
   the first session's row untouched.
7. `[test]` The bulk revoke sets `revoked_at` on **every** live `auth_sessions` row for
   the given user, and none of them can be resolved afterwards. (US-009.AC-1 — the
   mechanism; the route that makes it observable is step `003`'s)
8. `[test]` The bulk revoke **deletes no row** — the same row count exists before and
   after — and leaves an **already-revoked** row's `revoked_at` value unchanged rather
   than restamping it.
9. `[test]` The bulk revoke touches **no other user's** sessions.
10. `[test]` The bulk revoke is idempotent and total: called twice, called for a user with
    no sessions, and called for an id no account has, it raises nothing and reports zero
    newly revoked rows on the second and later calls.
11. `[test]` The bulk revoke **opens no transaction of its own**: called inside a caller's
    transaction that is then rolled back, none of its writes survive — which is what
    makes step `002`'s one-transaction disable possible. (`data-model.md`'s `users`
    disable paragraph; `context.md` D4)
12. `[test]` `services/auth.py` still imports no `fastapi` symbol, references no HTTP
    status code, takes no `Request` and reads no settings — `004/001` DoD-12 holds
    unchanged after this step's additions.
13. `[manual/live]` The diff to `services/auth.py` is confined to the two additions above:
    one write inside the existing open-session transaction and one new helper. No existing
    operation's arguments, return value or transaction shape changes. Verifier confirms by
    reading the module against `004/001`'s Interface intent.
14. `[manual/live]` No log line added in this step can carry a token, a digest, a password
    or a username; the revoked-row count and the user id (as a decimal string) are the
    only new things logged. Verifier confirms by reading every logging call in the module.
15. `[manual/live]` `mypy app`, `ruff check .` and `pytest` all pass from `backend/`.

## Dependencies

None within this feature. It builds on `003/001` (the `users` table), `004/001` (the
`auth_sessions` table and the session service) and `001.backend-foundation` (the registry
and the engine).
