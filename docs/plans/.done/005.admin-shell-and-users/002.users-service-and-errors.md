# Step 002 — The account-management service and its three domain errors

## Goal

Give the backend one module that lists accounts and performs every account lifecycle
operation FEAT-003 requires — create, disable, re-enable, set password, set role — with
their transactions, their refusals, and no HTTP anywhere in it.

## Source files

```
backend/app/errors.py
backend/app/services/users.py
```

## Test files

```
backend/tests/test_users_service.py
backend/tests/test_errors.py
```

`backend/tests/test_errors.py` exists from `001`/`003`/`004` and is **extended**; nothing
already asserted in it becomes false.

## Interface intent

**`backend/app/errors.py`** — add **three subclasses** of the existing domain-error base,
following that base's established pattern exactly (`code` and `http_status` as **class
attributes each subclass sets**, per-instance message and detail, the inherited render
method producing the one wire shape). **No new handler is added** — `001` registers one
handler for the base class. No existing error, handler or registration is modified.

- **`username_taken`**, HTTP **409 Conflict** — the requested username already belongs to
  an account. `detail` carries **nothing**: the username is the caller's own input and
  echoing it buys nothing, and a `detail` that grew to carry the owning account would be
  a disclosure. 409 rather than 400 because the request is well formed and is refused by
  the instance's current state, which is the reading `003`'s `already_configured` already
  set.
- **`user_not_found`**, HTTP **404 Not Found** — the addressed account does not exist.
  `detail` carries nothing. It is reachable in normal use: the administrator's list is a
  snapshot and a row can be addressed after it is gone.
- **`self_role_change_refused`**, HTTP **409 Conflict** — a role change whose target is
  the acting administrator. `detail` carries nothing. 409 for the same reason as
  `username_taken`: the caller is authenticated and authorized (403 is already spoken for
  by `insufficient_role`, and using it here would make "you may not do this at all" and
  "you may not do this to yourself" indistinguishable to the client).

**`backend/app/services/users.py`** — a new service module owning account management
(`backend-structure.md`'s Layout). It takes plain arguments, returns plain results or
raises a typed error, and **never imports `fastapi`, never sees a `Request` and never
knows a status code**. Every operation takes a Core `Connection` as its first argument.
Six of them:

- **List accounts.** Takes the connection and returns every account as a plain result
  carrying **id, username, role, whether it is enabled, and `last_login_at`** — and
  nothing else. No password hash, no language defaults, no session count, no count of
  anything a user owns, and **no parameters**: no filter, no page, no sort key
  (`ui-conventions.md`: every admin list loads and renders the full set). Order is
  **`ORDER BY id` ascending**, which is creation order because the key is a k-sortable
  snowflake (`data-model.md`); it is deliberately not username order, which no
  requirement asks for and which would need a collation decision.
- **Create an account.** Takes the connection, the process's snowflake id generator, a
  username, a plaintext password and a role, and returns the created account in the same
  plain shape the list uses. Inside one `with conn.begin():` it mints the id from the
  **generator passed in** — never a module global — hashes the password through `003`'s
  seam in `app/services/passwords.py`, and inserts the row with **`is_enabled` true**
  (US-008.AC-1), the given role, `created_at` and `updated_at` as the same UTC ISO-8601
  instant, and `rp_language`, `preferred_language` and `last_login_at` **NULL**. The
  username is stored **exactly as received** — no trimming, no case folding, no
  normalization (`004`'s D13: normalization on one side only makes an account permanently
  unreachable).
  **A duplicate username raises `username_taken`, and the refusal comes from the unique
  index**, not from a check-then-insert: the service performs the insert and translates
  the integrity violation. `users` has exactly one unique constraint, so a violation on
  this insert can only be that one.
- **Disable an account.** Takes the connection and a user id. Inside **one**
  `with conn.begin():` it sets `is_enabled` false and `updated_at`, and calls step
  `001`'s bulk revoke helper for that user **in the same block** — the flag flip and the
  revocations commit together or not at all (`data-model.md`, US-009.AC-1). It returns the
  updated account in the list's shape. An account that is already disabled is not an
  error: the flag is written again and the revoke runs again, both idempotently. An id no
  account has raises `user_not_found`, **before** anything is written.
- **Re-enable an account.** Takes the connection and a user id, sets `is_enabled` true and
  `updated_at` inside its own transaction, and returns the updated account. It revokes
  nothing, creates no session and touches no other column — re-enabling restores the
  ability to log in (UC-007's alternate flow) and nothing more. An unknown id raises
  `user_not_found`.
- **Set an account's password.** Takes the connection, a user id and a new plaintext
  password, hashes it through the same seam, and inside its own transaction writes
  `password_hash` and `updated_at`. **No current password is required** and none is taken
  (`context.md` D6). It **does not revoke the target's sessions** (D6's recorded
  decision). An unknown id raises `user_not_found`. It returns the updated account, and
  the result carries **no password and no hash**.
- **Set an account's role.** Takes the connection, the **target** user id, the new role
  and the **acting administrator's id** as a plain argument. When the target is the acting
  administrator it raises `self_role_change_refused` **before any write** — that is what
  keeps an instance from losing its last administrator through one mis-click
  (`admin-surfaces.md`, `data-model.md`'s `users.role` paragraph). Otherwise it writes
  `role` and `updated_at` inside its own transaction and returns the updated account. An
  unknown id raises `user_not_found`. It revokes nothing: `004`'s D7 makes every request
  read the role **live** from `users`, so a role change takes effect on the target's next
  request with no session rewrite.

The module logs at most ids as decimal strings, an outcome code and the revoked-row count
— **never a password, never a hash, never a token, never a username**.

## Definition of done

1. `[test]` `username_taken` carries code `username_taken`, HTTP **409** and an empty
   `detail`; `user_not_found` carries code `user_not_found`, HTTP **404** and an empty
   `detail`; `self_role_change_refused` carries code `self_role_change_refused`, HTTP
   **409** and an empty `detail`. All three render in the one wire shape
   `{"error": {"code", "message", "detail"}}` through the handler `001` already
   registered, and **no second handler is added**.
2. `[test]` Listing returns every account with id, username, role, enabled flag and
   `last_login_at` — and carries **no password hash, no language default, and no count of
   anything** (US-011.AC-1, US-011.AC-2, R5).
3. `[test]` Listing takes no filter, page or sort argument and returns the **full set**,
   ordered by id ascending; adding an account and listing again returns it in last
   position. (`ui-conventions.md`, "No sorting, filtering or pagination")
4. `[test]` Creating an account inserts exactly one `users` row that is **enabled**, with
   the given role, a `password_hash` that is **not** the plaintext, and `rp_language`,
   `preferred_language` and `last_login_at` all NULL. (US-008.AC-1)
5. `[test]` The created account appears in a subsequent listing. (US-008.AC-2)
6. `[test]` The created account's stored password verifies against the plaintext that
   created it through `003`'s verification operation, and against nothing else.
7. `[test]` Creating an account mints the id from the generator it is **given**, and
   nothing in the module reaches a process-wide generator.
8. `[test]` Creating an account whose username already exists raises `username_taken` and
   writes **nothing** — the account count is unchanged and the existing account's row is
   untouched.
9. `[test]` The username is stored exactly as received: two accounts differing only by
   letter case or by surrounding whitespace are both creatable, and neither collides.
   (`004`'s D13)
10. `[test]` Disabling an account sets `is_enabled` false **and** revokes every live
    `auth_sessions` row for that account; afterwards none of that account's tokens
    resolves. (US-009.AC-1)
11. `[test]` The disable is **one transaction**: when the enclosing operation fails after
    the flag flip, neither the flag nor the revocations survive — there is no state in
    which the account is disabled and its sessions are still live, and none in which the
    sessions are revoked and the account is still enabled. (US-009.AC-1,
    `data-model.md`'s `users` disable paragraph)
12. `[test]` Disabling touches **no other account** — another account's flag and sessions
    are unchanged — and disabling an already-disabled account raises nothing.
13. `[test]` Re-enabling sets `is_enabled` true, creates no `auth_sessions` row, and
    leaves the account's revoked sessions revoked. (UC-007's alternate flow)
14. `[test]` Setting a password replaces the stored hash: the old plaintext no longer
    verifies and the new one does (US-010.AC-1, US-010.AC-2), the returned result carries
    no password and no hash, and the account's live sessions are **still live**
    afterwards (`context.md` D6).
15. `[test]` Setting a role writes the new role and leaves every other column but
    `updated_at` unchanged. (`admin-surfaces.md`'s "Change Role"; `data-model.md`'s
    `users.role` — **no product id**)
16. `[test]` Setting a role whose target **is** the acting administrator raises
    `self_role_change_refused` and writes **nothing** — the account's role is unchanged
    afterwards; setting the same target's role as a **different** administrator succeeds.
    (`admin-surfaces.md`'s "Change Role" — **no product id**)
17. `[test]` Every id-addressed operation — disable, re-enable, set password, set role —
    raises `user_not_found` for an id no account has, and writes nothing.
18. `[test]` Each of create, disable, re-enable, set password and set role updates
    `updated_at`, and none of them writes `last_login_at`.
19. `[test]` `services/users.py` imports no `fastapi` symbol, references no HTTP status
    code, takes no `Request` and reads no settings — it is callable with a plain
    connection, a generator and plain values.
20. `[manual/live]` The module contains **no query keyed on anything but an account** —
    no join to `characters`, `sessions`, `messages` or `memos`, and no `COUNT` over any of
    them (R5, UC-066). Verifier confirms by reading every statement in the module.
21. `[manual/live]` No log line in the module can carry a password, a hash, a token or a
    username. Verifier confirms by reading every logging call.
22. `[manual/live]` `mypy app`, `ruff check .` and `pytest` all pass from `backend/`.
