# Step 001 — step-specific context

Feature-wide facts are in `context.md` (D2 for the column and the stamp site, D4 for the
helper's shape and why it opens no transaction, plus the redaction rule and the
no-DDL-at-startup rule). Only what is narrow to this step is below.

## The two touch sites, by module path and role

- **`backend/app/db/schema.py`** — one `MetaData` named `metadata`; every table is a
  `Table(...)` **literal in this one file**, with no per-feature table module and no
  builder callable (`001/005`, `003/001`, `004/001`). The `users` literal is `003/001`'s;
  the edit is one added `Column`. `db/drift.py` (feature `007`) later walks
  `metadata.tables`, which is why the registry — not a migration — is where a column is
  added.
- **`backend/app/services/auth.py`** — `004/001`'s module. Its four operations all take a
  Core `Connection` as their first argument. The one this step edits is the
  **open-session** operation: it runs inside its own `with conn.begin():`, mints the row
  id from the generator it is **given**, computes `created_at` as now (UTC) and
  `expires_at` as now plus the TTL argument, and returns the plaintext token and the
  expiry. Its full contract is
  `docs/plans/004.authentication-session/001.auth-sessions-and-service.md`, "Interface
  intent"; do not restate it and do not change it.

## The `users` column list this step extends

`003/001` declares exactly nine columns, in `data-model.md`'s order: `id`, `username`,
`password_hash`, `role`, `is_enabled`, `rp_language`, `preferred_language`, `created_at`,
`updated_at`. `rp_language` and `preferred_language` are nullable; the rest are not.
`last_login_at` is the **tenth** and is nullable. `data-model.md`'s own preamble
authorises it: *"a plan may add bookkeeping columns, but not remove or re-scope one named
here"*.

## The `auth_sessions` columns the helper writes

`004/001` declares exactly six: `id`, `user_id` (FK to `users.id`, **indexed** — the index
exists for precisely this operation), `token_hash` (uniquely indexed), `created_at`,
`expires_at`, `revoked_at` (**nullable**, NULL until revoked). The helper's predicate is
`user_id = ? AND revoked_at IS NULL`; nothing else.

## Two callers of the open-session operation exist already

Both inherit the stamp for free and neither is edited here:

- `004/003`'s `POST /api/auth/login`;
- `004/004`'s widened bootstrap create transaction, which signs the first administrator
  in — so that account is stamped at creation, which is correct.

## Assertions in other features' tests that must survive

- `004/001` DoD-6 (one `auth_sessions` row per open, `revoked_at` NULL, `expires_at` =
  creation + TTL, `token_hash` ≠ token) and DoD-7 (the id comes from the generator passed
  in) — an added `users` UPDATE in the same transaction breaks neither.
- `004/001` DoD-11 — single-token revocation still sets `revoked_at`, deletes nothing and
  leaves that user's **other** sessions untouched. The new bulk helper is a *separate*
  operation; it does not replace or re-implement the single-token one.
- `004/003` DoD-1..3 and DoD-10..12 — the login and logout routes are untouched.

## Gotchas

- **The stamp must use the transaction's own "now"**, not a second call to the clock:
  DoD-4 asserts the two values are equal, and two clock reads a microsecond apart are
  not.
- **`updated_at` stays put.** It is tempting to bump it in the same UPDATE; DoD-5 forbids
  it (`context.md` D2).
- **Do not filter the bulk revoke by `expires_at`.** An expired row is already unusable,
  but stamping it costs nothing and skipping it would make "every live row" a
  three-part predicate that has to agree with the resolve path's definition forever. The
  predicate is `revoked_at IS NULL` alone, and DoD-8 pins the one case that matters: an
  already-revoked row keeps its original timestamp.
- The helper returns a **count**, not the rows and not the ids. A list of session ids
  would be the beginning of a session-listing surface, which is out of scope
  (`context.md`).
