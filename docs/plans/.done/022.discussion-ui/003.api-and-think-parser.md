## Interface intent

**`app/streamApi.ts`** (changed)

- **`Message`** gains three **optional**, nullable fields (D15). Absent means the same as
  null:
  - `tool_name`: a string or null;
  - `tool_status`: `"ok"`, `"failed"` or null;
  - `tool_args`: a plain object of unknown JSON values, or null.

  The eight existing fields are unchanged, and ids stay strings.
- **`ToolStatus`** (new exported type alias, optional; name final at skeleton): `"ok"` |
  `"failed"`.
- **`fetchDiscussion`** (new).
  - Inputs: the entry id (a string) and an optional signal.
  - It issues `GET /api/messages/<encodeURIComponent(id)>/discussion` through the shared
    `apiGet` and resolves to the **unwrapped** `messages` array, in served order and never
    re-sorted.
  - It rethrows the shared client's `ApiError` unchanged.
- No other call changes. `composeZone`'s optional text is 021 `007`'s and is used as is.

**`app/thinking.ts`** (new)

- **The tag literals** `<think>` and `</think>`, exported as constants.
- **Segment type**: a discriminated union with two cases:
  - an **answer** segment carrying its text;
  - a **think** segment carrying its text and a `closed` boolean.
- **`splitThinking`** (name final at skeleton). Pure. Input: a string. Output: the ordered
  list of segments per `context.md` D4. It never throws. It does not touch markdown or
  `(( ))`.

## Definition of done

1. `[test]` `splitThinking` maps every row of `context.md` D4's worked-examples table (rows
   1–10) to exactly the listed segments, in order, with the listed `closed` flags. (D4,
   021 D4)
2. `[test]` `splitThinking` is consistent with 021 D4 on the strip examples. For rows 3, 4, 6
   and 8, the answer segments joined with a single space equal 021 D4's stripped output:
   `Hello`, `One two`, `` (no answer segment), `((ooc))`. For row 5, the answer segments
   alone equal `Start`. (D4)
3. `[test]` `splitThinking("<THINK>loud</THINK>")` (uppercase) returns one answer segment
   with the text unchanged: the tags are case-sensitive. (D4)
4. `[test]` `fetchDiscussion("7250000000000000042")` issues exactly one `GET` to
   `/api/messages/7250000000000000042/discussion` and resolves to the served `messages`
   array, in the served order. A tool message's `tool_name`, `tool_status` and `tool_args`
   come through unchanged, for example `{"query":"lighthouse"}`. An id containing `/` is
   percent-encoded in the path. (D1, D3)
5. `[test]` `fetchDiscussion` answered 404 `message_not_found` rejects with an `ApiError`
   whose code is `message_not_found`. An aborted signal rejects with the abort and is not
   wrapped. (D1, `frontend-structure.md` "The API client")
6. `[test]` A `Message` literal with only the eight original keys still type-checks, and so
   does one with the three tool keys. This is pinned by a type-level test that compiles
   under `npm run typecheck`. (D15)
