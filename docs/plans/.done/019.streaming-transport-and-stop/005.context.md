# Step 005 — step-specific context

Feature-wide facts are in `context.md`: **D11–D17** (the streaming text, the handle,
`busy` versus streaming, the outcome table, `accepted` handling and re-read ordering,
Settle mid-stream, the accepted races), **D18** (tool frames ignored), and "Test

## Touch site, as harvested: existing `streamState.ts` helpers to reuse

- The private helpers `isAbortRejection`, `setBusy`, `clearDraftIfUnchanged`, and
  `rereadZone` / `rereadEntries` / `rereadBoth(state, signal?) => Promise<boolean>`. Reuse
  `clearDraftIfUnchanged` for D15 and `rereadZone` for every compose re-read.
- **Pass the mount signal to the compose re-reads, not the compose controller's
  signal.** The compose signal is already aborted after a stop, and the post-stop re-read
  must still run.
- `settleComposer` today does: set `busy`; append a non-blank draft (on failure, notify,
  re-read the zone, keep the draft, clear `busy`, stop); settle; re-read both; clear
  `busy`. The prefix goes **before** all of that and leaves the rest byte-for-byte as
  is.
- `notifyFailure(error)` comes from `src/shared/notifyFailure.ts`.
- `ApiError` comes from `src/shared/apiError.ts`, constructed as `(code, message, status,
  detail?)`.

## The linking, precisely

- Register `abort` on the mount signal with a handler that aborts the compose controller.
- Remove it when the compose ends, so a long-lived mount signal does not accumulate one
  listener per compose.
- "Mount aborted" is always checked on the **mount** signal. "Stopped" in the outcome
  only says the compose signal was aborted. The effect distinguishes a user stop from an
  unmount by looking at the mount signal.

## Ordering of re-reads (D15, D16), in one place

```
compose:  [accepted → GET zone (A)] ... outcome → await A → GET zone (final) → clear
settle mid-stream:  busy → stopCompose → await handle.woundDown (includes compose's final
                    GET zone) → existing flow: [POST zone/messages] → POST settle →
                    GET entries + GET zone → busy false
```

The wound-down promise **must resolve, never reject**, including when the re-read fails,
so `settleComposer` cannot hang or throw.

## Test notes

- **The streamed compose body.** A `Response` over a `ReadableStream` the test controls:
  it enqueues frames, holds the stream open, then closes or errors it.
- **The abort.** jsdom's `fetch` is stubbed, so the stub must honour the request's
  `signal`. When it aborts, the stub errors the body stream and/or rejects with a
  `DOMException` named `"AbortError"`, as a browser does. A stub that ignores the signal
  will hang DoD-7, DoD-8 and DoD-10.
- **The persisted partial row.** It is simulated by the zone GET stub serving it after
  the stop. The server side is `002`'s.
- **Keying.** Stubs key on exact pathname + method: `/api/sessions/s1/zone/compose`
  POST, `/api/sessions/s1/zone` GET, `/api/sessions/s1/settle` POST,
  `/api/sessions/s1/entries` GET.
