# Step 005 — The compose effect and Settle-mid-stream

## Goal

Add the compose effect to `app/streamState.ts`. It starts a streamed compose with its own
controller linked to the mount signal, appends `token` text to the streaming text, and
handles each of the four outcomes per D14 and D15: never optimistic, re-reading the zone,
and showing no failure for a user stop. Also give `settleComposer` its user-confirmed
prefix: when a compose is in flight, stop it, wait for it to wind down, then settle as
before (D16).

frontend/src/app/streamState.ts

## Interface intent

**`app/streamState.ts`** (changed)

- **`composeMessage`** (new effect; name final at skeleton). Inputs: the state and the
  optional mount signal. It never rejects. It does nothing when `isStreaming` is already
  true or the draft is blank. Otherwise:
  1. **Starts the compose.** Captures the draft as the sent text. Creates a fresh
     `AbortController`. Links the mount signal so that a mount abort aborts it (if the
     mount signal is already aborted, it returns with no request). Sets the streaming
     text to `""` and the compose handle to `{controller, wound-down promise}`, the
     promise being this run's own completion.
  2. **Calls `004`'s compose call** with the sent text, the frame callback and the
     compose controller's signal.
  3. **Handles each frame** in a `runInAction`, writing nothing once the mount signal is
     aborted:
     - **`accepted`**: clears the draft if it still equals the sent text, and starts a
       zone re-read (D15).
     - **`token`**: appends its text to the streaming text.
     - **Tool frames**: ignored (D18).
  4. **On the outcome.** If the mount signal is aborted, it returns, writing,
     re-reading and notifying nothing. Otherwise it waits for any accepted-triggered
     re-read to settle, then acts per D14:
     - **done**: no notification;
     - **error**: `notifyFailure` with the outcome's `ApiError`;
     - **stopped**: no notification;
     - **unexpected end**: `notifyFailure` with
       `ApiError("llm_unreachable", "The reply ended unexpectedly.", 0, {})`.

     Then it re-reads the zone. In the **same** action as writing the re-read result it
     sets the streaming text and the compose handle back to `null`. If the re-read fails,
     it calls `notifyFailure` with that error and still clears both.
  5. **Removes the mount-signal listener** and resolves the wound-down promise.
  - It never sets or clears `busy`, and never touches `entries` or `kindOverride` (D13).
- **`settleComposer`** (changed: a prefix only). If a compose handle exists, it:
  1. sets `busy`;
  2. calls `stopCompose(state)`;
  3. awaits the handle's wound-down promise;
  4. continues into the existing flow unchanged: append a non-blank draft, settle,
     re-read both, clear `busy` (013 `003`).

  If the mount signal is aborted after the wait, it returns, as every effect does. With
  no handle, the behaviour is exactly as before.

## Definition of done

1. `[test]` With draft `"Write me a reply"` on session `s1`, `composeMessage`:
   - POSTs `/api/sessions/s1/zone/compose` with exactly `{"text":"Write me a reply"}`;
   - sets `isStreaming` true before the body completes;
   - leaves `busy` false throughout.

   (D12, D13)
2. `[test]` A body of `accepted` then tokens `"Once "`, `"upon"` (held open):
   - after `accepted`, the draft is `""` and a `GET /api/sessions/s1/zone` was issued;
   - after the tokens, the streaming text is exactly `"Once upon"`;
   - `zone` contains no row the server did not serve (no placeholder);
   - no request to `/api/messages/...` is ever made.

   (D11, D15, never-optimistic)
3. `[test]` A draft changed by the roleplayer before `accepted` arrives (`"Write me a
   reply"` sent, then `"Write me a reply!"` typed) is **kept** after `accepted`. (D15,
   R10)
4. `[test]` **done.** After `accepted`, a token and `done` with messageId
   `"7250000000000000099"`:
   - `notifyFailure` is not called;
   - the last request is a zone GET, issued **after** the accepted-triggered zone GET has
     resolved;
   - `zone` equals the final served list (which includes an assistant row);
   - the streaming text is `null`;
   - `isStreaming` is false.

   (D14, D15)
5. `[test]` **error.** After one token, an `error` frame `llm_unreachable`:
   - `notifyFailure` is called once with an `ApiError` of that code;
   - the zone is re-read;
   - `entries` is untouched;
   - the streaming text is `null`.

   A **non-2xx** compose response (409 `model_not_enabled`) behaves the same:
   `notifyFailure` gets that code, and the draft is **kept**, because no `accepted`
   arrived. (D14, R10, US-044.AC-1)
6. `[test]` **unexpected end.** A body ending after one token with no terminal frame
   calls `notifyFailure` once with an `ApiError` whose code is `"llm_unreachable"`, then
   re-reads the zone and clears the streaming text. (D14, `llm-and-streaming.md`
   termination table)
7. `[test]` **User stop.** Mid-body, after one token, `stopCompose(state)` is called.
   Then:
   - `notifyFailure` is **never** called;
   - the zone is re-read, and `zone` becomes the served list, which includes the
     persisted partial assistant row;
   - the streaming text and handle are `null`;
   - `isStreaming` is false;
   - `busy` is unchanged, `canSend` is true again for a non-blank draft, and a second
     `composeMessage` can start.

   (US-132.AC-1, US-132.AC-2, D13, D14)
8. `[test]` **Unmount.** Mid-body, the **mount** signal is aborted. The compose request's
   own signal becomes aborted (the link works). Afterwards no further request is made,
   `notifyFailure` is not called, and `zone` and the streaming text are not written
   after the abort. (D12, US-132.AC-2)
9. `[test]` `composeMessage` with a blank draft, or while already streaming, makes no
   request. (D13)
10. `[test]` **Settle mid-stream.** While a compose is streaming (one token received, zone
    holding one row, *my turn*), "Settle" is enabled (`canSettle` true). Calling
    `settleComposer` then:
    - aborts the compose's controller;
    - calls `notifyFailure` **never**;
    - shows request order, from the stub's log: the compose's post-stop zone GET, **then**
      `POST /api/sessions/s1/settle`, **then** the entries and zone GETs;
    - ends with the streaming text `null` and `busy` false;
    - leaves `entries` and `zone` equal to the settle's re-read lists.

    (D16, user-confirmed; `workspace-shell.md` "The stop control")
11. `[test]` `settleComposer` with no compose in flight issues exactly the same requests
    as before: no extra GET, no abort. 013's settle tests still pass unchanged. (D16)
12. `[manual/live]` With 021's route mounted and Send switched to compose:
    - Stop mid-reply leaves the partial text as an editable zone candidate after the
      reload, with no failure notice.
    - **Accepted:** if it appears only on the next re-read, that is the D17 race.
    - Settle mid-reply settles, and the partial appears either as the settled row or as
      a candidate in the fresh zone (D17, accepted).

    (US-132.AC-1, US-132.AC-2)
