# Step 002 — step-specific context

Feature-wide facts are in `context.md`; the decisions this step implements are D3 (the
typed 401 and 403), D6 (the cookie's flags), D7 (what resolution requires), D8 (where the
ladder and the dependencies live) and D15 (the deleted purity clause). None of that is
repeated here.

## Where the deleted clause lives, and what to do if it is somewhere else

`003/001`'s Test files are `backend/tests/test_passwords.py` and
`backend/tests/test_db_schema.py`, and its DoD-4 — the role enum's two members, and the
claim that it exposes **no ladder mapping and no role-comparison or dependency helper** —
had to land in one of the two. `test_db_schema.py` is the likely home, because the enum is
asserted beside the `role` column whose value domain it is, and it is the file this step
lists.

If the delivered `003` tests placed that assertion in `test_passwords.py` instead, this
step's Test files are wrong by one path. That is a **test-coder hand-back to the
orchestrator**, not a licence to edit a file outside the listed scope. Delete only the
"no ladder mapping / no comparison helper" clause; the two-members clause and their values
stay, and nothing in `test_passwords.py` is touched either way.

## The dependency snippet the architecture already fixes

`backend-structure.md`'s "Authorization as router dependencies" carries the factory's
shape verbatim — `ROLE_LADDER` as a mapping from role to rung, and `require_role(min_role)`
returning the dependency callable — plus the reason it is a factory rather than a
`require_admin`: the check every route wants is a **threshold**, so a third rung becomes one
ladder entry instead of a new dependency plus an audit of which routes should have gained
it. Read the snippet there; the skeleton agent freezes the real signatures against it.

The same section states what `require_user` yields and why it matters: *"`require_user`
yields the `user_id` that every service call is scoped by. A service that touches
user-owned data takes `user_id` as a **required positional argument**"* (R5). This step
ships no such service — no route behind these guards touches user-owned data yet — but
`CurrentUser` is shaped so that scope is the obvious thing to pass.

## Reading the cookie: why not `Cookie(...)`

FastAPI's `Cookie(...)` parameter declaration fixes the cookie's **name at import time**,
and the name here comes from `Settings.session_cookie_name`, which tests override through
`app.dependency_overrides[get_settings]` **after** import. A declared alias would therefore
ignore the override and DoD-8 would be unsatisfiable. So the dependency takes the request
and reads the cookie by the name the settings dependency gave it — which is ordinary HTTP
plumbing and squarely the dependency module's business.

## `require_role` resolves through the same path as `require_user`

Not two resolutions, and not a copy: the factory's callable obtains the caller the same
way `require_user` does and then compares. The reason is the one `003` gave for the
configured predicate (`003/context.md` D4): two definitions of the same fact drift, and
here the fact is "who is calling and are they still allowed in at all". A future change to
what a live session requires — another column on `users`, a second revocation condition —
must not have to be made twice.

DoD-9's third clause is the observable form of the ordering that follows: **no session
gives 401, not 403.** Authentication precedes authorization, and a 403 for an absent
session would send the client down the render-it branch (`002/004` DoD-11) instead of the
return-to-login branch that US-007.AC-2 wants.

## The cookie writers, and the one flag that is deliberately absent

`context.md` D6 is the full table. The one worth restating at the call site is **`Secure`
off**: `deployment.md` records HTTP only, with no `listen 443`, no certificate handling and
no certificate mount anywhere, and its TLS `_TBD:` names this cookie's `Secure` flag as
part of the work TLS would require. A `Secure` cookie on an HTTP origin is simply never
sent — the symptom would be a login that appears to succeed and an instance that is never
authenticated.

The clearer must use the **same name and the same path** as the writer. A cookie cleared at
a different path leaves the original in place, and the visible symptom is a logout that
does not log out.

## What this step deliberately does not build

No route uses these guards yet — step `003`'s `GET /api/me` is the first consumer of
`require_user`, and **`require_role` has no consumer at all until feature `005`'s admin
routers**. That is intended by `brief.md`, which claims the ladder and the factory as this
feature's Scope In, and it mirrors `003`'s hashing seam shipping with its verification
operation unused. It is not dead code to prune.

No `require_unconfigured` is touched: it stays in `routers/bootstrap.py` where
`003/context.md` D6 put it, because that router is still its only consumer.
