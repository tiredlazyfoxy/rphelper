# Step 001 — step-specific context

Feature-wide facts are in `context.md`; the decisions this step implements are D1 (the
uniform refusal and its timing), D2 (400), D4 (absolute expiry), D5 (the token and its
digest), D7 (what resolution requires), D9 (revocation is idempotent) and D13 (no
normalization). None of that is repeated here.

## The two registry facts this step binds to

`db/schema.py` ships from `001.backend-foundation/005` with **one `MetaData`** and the
module rule that *every table in RPHelper is declared as a `Table(...)` literal in this
same file* — no per-feature table module, no import-side-effect registration, no builder
callable. `003.first-run-bootstrap/001` adds the first literal, `users`; this step adds the
second. The exact name of the metadata object is `001`'s to freeze and the skeleton agent
reads it from the delivered file.

The column list is **`data-model.md`'s `auth_sessions` section**, read there rather than
from a paraphrase. Its Identifiers section carries the storage rule for the key: `id
INTEGER PRIMARY KEY` in SQLite — the rowid alias, which holds a signed int64 natively —
and the big-integer type in SQLAlchemy Core, with **no `AUTOINCREMENT` anywhere**.

## Nothing already asserted about the schema becomes false here

`003/001` DoD-1 constrains the **columns of `users`** ("exactly the columns … and no
others"), not the set of tables in the registry, and its DoD-7 asserts only that the table
collection is enumerable and **contains** `users`. Adding a second table falsifies neither.
This step therefore only **adds** assertions to `backend/tests/test_db_schema.py` and
`backend/tests/test_errors.py`; it deletes nothing from either. (The one `003` assertion
this feature does invalidate about `roles.py` is step `002`'s — `context.md` D15.)

## What the connection dependency gives you, and what it does not

`get_connection` in `app/db/engine.py` yields a Core `Connection` and **opens no
transaction** — boundaries are `with conn.begin():` blocks at the service's own level.
That is why the two writing operations here open their own block and the two reading ones
open none. The engine also sets `PRAGMA foreign_keys = ON` on every connection, which is
what makes the declared foreign key on `user_id` actually enforced.

## The generator is passed in, not reached for

The app factory constructs the process's snowflake generator and holds that single
instance on **`app.state.id_generator`**; `backend-structure.md`'s `app/ids.py` section
makes one instance per process a guarantee rather than a convenience. A service must not
reach for a module global, so the open-session operation **takes it as an argument** —
step `003`'s router resolves it out of application state and passes it down, exactly as
`003/003` does for bootstrap. DoD-7 is the observable form of the rule.

## The decoy verification, and why the seam's error-swallowing matters to it

`003/001` gives `services/passwords.py` a verification operation that answers **false
rather than raising** for a value that is not a valid encoded hash. That has a
consequence for D1's timing rule that is easy to get wrong: verifying against an
*arbitrary string* would return false immediately and do **no work**, which is precisely
the timing signal the rule exists to remove. The decoy must therefore be a **real encoded
hash** — the conventional shape is one computed once at module import over a constant
value and held as a module-level constant.

The decoy is a fixed value, not a per-request computation, because re-hashing on every
failed login would make the refusal path *slower* than the success path, which leaks the
same fact in the other direction.

## Timestamps, and the comparison pitfall

`data-model.md`'s convention is `created_at` / `expires_at` as **UTC ISO-8601 text**, and
`003`'s first-run insert already writes `users.created_at` / `updated_at` that way. The
pitfall: string comparison of ISO-8601 is only valid when every value is written in **one
fixed-width, single-zone format**. Two formats in one column — one with a `Z`, one with an
offset, one with microseconds and one without — make `expires_at > now` silently wrong,
and the symptom is a session that never expires or one that expires immediately.

Whether the expiry check is done in SQL on the text or in Python on parsed values is the
skeleton's call; what DoD-9 fixes is that an expired row does not resolve. Whatever is
chosen, every timestamp this module writes uses **one** format.

## Gotcha — the plaintext token is returned, never stored

The open-session operation is the only place the plaintext token exists on the server, and
it exists there for the length of one call. It is returned to the caller (the router, in
step `003`, which puts it in a cookie) and is **not** written to the row, not kept in a
field, and not logged. DoD-6 is the observable half of that: the stored `token_hash` is not
the returned token.

## Gotcha — the expiry is computed here and never moved afterwards

`expires_at` is written once, from the TTL argument, and no operation in this module ever
updates it (`context.md` D4). There is no "touch" or "extend" operation and none may be
added; a resolve is a **read**, and making it a write would put the busiest path in the
product behind SQLite's single writer.

## Gotcha — the refusal has no second shape

Do not add a second error code, a `detail` field naming the cause, or a boolean on the
result saying whether the account was disabled. `context.md` D1 is the whole contract, and
a caller that can tell the three cases apart is a caller that will eventually render the
difference. The same rule reaches the logs (DoD-14): a line that records the attempted
username on failure re-creates the distinction in the one place nobody audits.
