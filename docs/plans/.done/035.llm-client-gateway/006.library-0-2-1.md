# Step 006 — Library 0.2.1: tolerant tool loop

## Goal

This step moves the gateway to `llm-client` 0.2.1. As a result:

- a model-side tool mistake becomes a `tool_start` + `tool_fail` pair and a
  failed tool row, and the exchange continues, where 0.2.0 ended it with a
  stream error;
- `auth_failed` is read from the library error's status.

The step changes the existing compose-stream symbols (DEC-035-17). Approved by
the user on 2026-11-09 as part of 035. It changes no architecture doc.

## Interface intent

- **The dependency pin** moves from the `v0.2.0` tag to `v0.2.1`, and the lock
  is refreshed (`DEC-arch-llm-client-library-13`). The Dockerfile and `httpx`
  are unchanged.
- **The gateway's auth test** (the private helper that every operation uses)
  decides `auth_failed` from the library error's HTTP status, 401 or 403. It no
  longer reads the message (DEC-035-20, `DEC-arch-llm-client-library-16`). The
  `Invalid response` prefix test behind `embed`'s `no_usable_vector` stays as it
  is.
- **`ComposeRejected`** (new, in `gateway.py`) is an immutable value: one
  model-side rejection. It carries the call, as a `ToolCall` (minted `call_id`,
  the model's tool name verbatim, the model's argument text verbatim), and the
  rejection kind, one of three gateway-owned values: `not_offered`,
  `bad_arguments`, `unknown_argument` (DEC-035-17).
- **`LlmGateway.compose(model, messages, tools)`** keeps its parameters and its
  queue mechanics (DEC-035-7). It now yields, in order, `ComposeText`,
  `ComposeRejected` or the runner's events. Its `chat_with_tools` call adds two
  things:
  - the explicit tolerant tool-error mode (`DEC-arch-llm-client-library-14`);
  - a tool-event observer.

  Nothing else is passed: no silence limit and no trace switch
  (`DEC-arch-llm-client-library-17`).
- **The tool-event observer** is private to `compose`, and synchronous. It
  turns only the three rejection kinds into a `ComposeRejected`, minting the id
  from the same per-`compose` counter the wrappers use, and ignores every other
  event (DEC-035-17, `DEC-arch-llm-client-library-15`).
- **`ChatClientLike.compose`** (in `llm_registry.py`) widens its yield type to
  include `ComposeRejected`. Its parameters are unchanged.
- **`compose_stream`** keeps its signature. Its drain gains one branch: for a
  `ComposeRejected` it does the following, in this order, without calling
  `dispatch`:
  1. yields the call's `tool_start` frame;
  2. writes the failed tool row through the seam's tool-row write;
  3. logs the rejection (DEC-035-18);
  4. yields the call's `tool_fail` frame (`tool_failed`).

  The runner and the text branch are unchanged.
- **The seam's failed-tool-row write** is the write `dispatch` already performs
  for a failed call. If `compose.py` cannot already call it, it is made public
  here, with no behaviour change. `dispatch` keeps using it. This is the only
  change `seam.py` may receive (006.context.md).
- **The tool callables keep their explicit signatures** (DEC-035-19).

## Definition of done

1. DoD-1 `[test]` — `backend/pyproject.toml` has exactly one `llm-client`
   runtime requirement, `llm-client @ git+https://github.com/Iezious/PythonLLMClient.git@v0.2.1`.
   The installed library reports version `0.2.1`. `httpx` is still a runtime
   dependency. (`DEC-arch-llm-client-library-13`)
2. DoD-2 `[test]` — For all four operations, a library error whose status is 401
   or 403 is `auth_failed`, whatever its message says:
   - `probe` gives the outcome `auth_failed`;
   - `embed`, `complete` and `compose` raise `llm_unreachable` with
     `{"reason": "auth_failed"}`.

   A library error whose message contains `status 401` or `status 403` but which
   carries no status is `unreachable`, and so is any other status. No provider
   text reaches a message, a `detail` or a log, and there is no chained cause.
   (DEC-035-20, US-048, UC-011)
3. DoD-3 `[test]` — For `embed`, a library error whose message starts with
   `Invalid response` is still `no_usable_vector`. An error that the library
   classes as an invalid reply, but whose message does not start that way, is
   `unreachable`. (`DEC-arch-llm-client-library-16`)
4. DoD-4 `[test]` — `compose` calls `chat_with_tools` with `tool_errors="result"`
   and a callable `on_tool_event`, beyond everything step 003 DoD-3 requires.
   Each library client is built with exactly the keywords `model`, `base_url`,
   `timeout` and `bearer_token`, so there is no silence limit and no trace
   switch. (`DEC-arch-llm-client-library-14`, `-17`)
5. DoD-5 `[test]` — For each of the three kinds, a library `error` event yields
   exactly one `ComposeRejected` at its place in the stream: after the text
   streamed before the call, and before the text and events that follow it. The
   value carries:
   - a `call_id` from the same counter as the wrappers, so a wrapper call, a
     rejection and a wrapper call in that order are `call_1`, `call_2` and
     `call_3`;
   - the event's name verbatim, with `""` kept;
   - the event's argument text verbatim;
   - the kind.

   The `call_id` the event itself carries is never used.
   (`DEC-arch-llm-client-library-15`, `-17`; DEC-035-17)
6. DoD-6 `[test]` — `start` events, `result` events, and `error` events of kind
   `tool_raised` or `unserialisable_result` yield nothing and consume no
   `call_id`. A call that reaches a wrapper appears in the stream exactly once,
   through the runner's events. (`DEC-arch-llm-client-library-15`)
7. DoD-7 `[test]` — Nothing from a tool event other than its name and argument
   text reaches a yielded value or a log record: not its `output`, not its
   `call_id`, and not the library's model-facing text. (llm-and-streaming.md
   § Errors, and what never leaves a failure)
8. DoD-8 `[test]` — After a rejection, the stream goes on. Later text pieces
   and runner events are still yielded, and the stream ends normally when the
   library call returns. (UC-051, UC-053; DEC-035-17)
9. DoD-9 `[test]` — When the compose source drains a rejection, it emits that
   call's `tool_start` and then its `tool_fail`, with code `tool_failed`, both
   carrying the minted `call_id` and the model's tool name verbatim (an empty
   name stays empty). It never calls `dispatch`. These frames sit in stream
   order among the token frames, and the exchange reaches `done`, with the
   assistant row holding the joined token text. (US-066.AC-1, UC-051, UC-053;
   `DEC-arch-llm-client-library-15`)
10. DoD-10 `[test]` — Each drained rejection writes one `role='tool'`
    current-zone row, before the exchange's assistant row. The row has:
    - `text` `The tool failed.`;
    - `tool_name` equal to the model's name verbatim, with `""` kept;
    - a payload whose `call_id` is the minted id, whose `arguments` is the
      model's argument text verbatim (not a re-serialisation), whose status is
      `failed`, and whose code is `tool_failed`.

    The zone read shows it with `tool_status` `failed`. (data-model.md
    `messages` tool columns; `DEC-arch-llm-client-library-15`)
11. DoD-11 `[test]` — If the compose source is closed after a rejection's
    `tool_start` frame and before its `tool_fail` frame, no tool row is written
    for that call. Text streamed before the stop is persisted by the harness as
    usual. (US-133.AC-1, US-132.AC-1)
12. DoD-12 `[test]` — Each drained rejection produces one log record that
    carries the tool name and the rejection kind. The record does not contain
    the argument text, nor any library or provider text. (DEC-035-18)
13. DoD-13 `[test]` — Context assembly is unchanged and adds no special case
    for these rows. A rejected row written by this step is read back into the
    next exchange in one of two ways, under the existing replay rule:
    - as its recorded call followed by a `tool` message carrying the failed
      literal;
    - skipped, when its payload cannot be read back into a call/result pair.

    It never produces a `tool` message without its matching call. A
    `not_offered` rejection with object-shaped argument text is replayed as the
    pair. (llm-and-streaming.md § Tool rows are replayed, not skipped)
14. DoD-14 `[test]` — The wrapper path is unchanged when run against the fake
    library in tolerant mode:
    - step 003 DoD-3..DoD-9 and DoD-11..DoD-14 still hold;
    - step 003 DoD-10 still holds for any `LLMError`, `RuntimeError` or
      `ValueError` the library raises, with the auth split as DoD-2 here;
    - step 004 DoD-3..DoD-5 and DoD-8 still hold.

    Step 003's three strict-mode cases are retired, citing
    `DEC-arch-llm-client-library-15`. Those are the unoffered name, unparseable
    arguments and an unknown argument name, each of which ended in
    `unreachable`. (DEC-035-19)
15. DoD-15 `[manual/live]` — With `LLAMA_SWITCH_URL` set, the step 005 live
    checks pass on 0.2.1. A model-side rejection seen against a real server
    yields `tool_start` and `tool_fail` and the exchange continues. This cannot
    be triggered deterministically, so the verifier records it as
    requires-live-run. (`DEC-arch-llm-client-library-15`)
