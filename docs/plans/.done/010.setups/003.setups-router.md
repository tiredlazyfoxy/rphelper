# Step 003 — The setups router

## Goal

Add `routers/setups.py`, the six routes of the wire contract on one router with
router-level `require_user` (D5). Each route converts the service's `Setup` into the
response models, and no delete route exists. Register the router in `main.py` after the
characters router.

## Source files

backend/app/routers/setups.py
backend/app/main.py

## Test files

backend/tests/test_setups_router.py

## Interface intent

**`routers/setups.py`** (new)

- **`router`**: an `APIRouter` with `require_user` as a router-level dependency, declaring
  full paths for both families (`/api/characters/{character_id}/setups` and
  `/api/setups/{setup_id}…`).
- **List handler**: `GET /api/characters/{character_id}/setups`. Takes the path id
  (inbound snowflake alias), the boolean query parameter `include_archived` (default
  false), the current user and the connection. Calls `list_setups` and answers a
  `SetupListResponse`.
- **Create handler**: `POST /api/characters/{character_id}/setups`, status 201. Takes the
  path id, a `CreateSetupRequest`, the current user, the connection and the id generator.
  Calls `create_setup` and answers a `SetupResponse`.
- **Get handler**: `GET /api/setups/{setup_id}`. Calls `get_setup`, answers a
  `SetupResponse`.
- **Update handler**: `PATCH /api/setups/{setup_id}`. Takes an `UpdateSetupRequest`.
  Calls `update_setup` with the supplied fields (`None` for unsupplied), answers a
  `SetupResponse`.
- **Archive handler**: `POST /api/setups/{setup_id}/archive`. **Restore handler**:
  `POST /api/setups/{setup_id}/restore`. Each calls its service operation and answers a
  `SetupResponse` with status 200.
- A private conversion from the service's `Setup` to `SetupResponse`.
- `SetupNotFoundError` and `CharacterNotFoundError` propagate to the already-registered
  domain handler (404). The router catches nothing.
- **No `DELETE` handler.**

**`main.py`** (extended)

- Includes the setups router after the characters router.

## Definition of done

1. `[test]` With no session cookie, each of the six routes answers 401 with code
   `not_authenticated`.
2. `[test]` A signed-in roleplayer who created character C through `POST /api/characters`
   posts `{ "name": "Tavern", "description": "# Night" }` to
   `/api/characters/<C>/setups`. It answers 201 with `name` "Tavern", `description`
   "# Night", `archived_at` null, both timestamps present, and `id` and `character_id`
   JSON **strings** of decimal digits, `character_id` equal to C's id string. A following
   `GET /api/characters/<C>/setups` contains a row with that id, and
   `GET /api/setups/<id>` answers it. (US-023.AC-1)
3. `[test]` The create with `name` `""`, `"   "` or no `name` answers 422, and the
   character's listing is unchanged afterwards. A `name` of `"  Tavern "` is stored and
   answered as `"Tavern"`. A missing `description` is answered as `""`. (D8)
4. `[test]` Right after `POST /api/characters` creates a character, its
   `GET …/setups?include_archived=true` answers `{ "setups": [] }`. (R2)
5. `[test]` As user B, `GET` and `POST` on `/api/characters/<A's character>/setups` each
   answer 404 with code `character_not_found` and an empty `detail`. A's listing (read as
   A) holds no setup created by B. The body equals the body for a character id that exists
   for nobody. (R5, D8)
6. `[test]` As user B, `GET`, `PATCH`, `POST …/archive` and `POST …/restore` on A's setup
   id each answer 404 with code `setup_not_found` and an empty `detail`. A's setup is
   unchanged when read back as A. The body equals the body for a setup id that exists for
   nobody. (R5, D8)
7. `[test]` With A owning two characters each with setups, and B owning one with setups,
   A's listing for each of its characters (with and without `include_archived=true`)
   contains only that character's setups. (R5)
8. `[test]` `PATCH /api/setups/<id>` with `{ "name": "Inn" }`, then with
   `{ "description": "new body" }`, each answers the updated setup. A following
   `GET /api/setups/<id>` returns name "Inn" and description "new body". A PATCH carrying
   `character_id` (the id of another of A's characters) is accepted with that key ignored:
   the setup's `character_id` is unchanged, and it is still listed under its original
   character and not under the other. A body carrying `user_id` or `archived_at` is
   likewise ignored on create and patch. (D5, D8)
9. `[test]` `POST /api/setups/<id>/archive` answers 200 with `archived_at` a string. The
   default listing then omits the setup, the `include_archived=true` listing includes it,
   and `GET /api/setups/<id>` still answers 200 with it. Archiving again answers the same
   `archived_at`. (US-087.AC-1, R6, D9)
10. `[test]` `POST /api/setups/<id>/restore` on that archived setup answers 200 with
    `archived_at` null, and the default listing contains it again. (US-087.AC-2)
11. `[test]` `DELETE /api/setups/<id>` and `DELETE /api/characters/<C>/setups` answer 405,
    and the setup is still returned by `GET /api/setups/<id>` afterwards. (R6)
12. `[test]` After `POST /api/characters/<C>/archive`, listing C's setups and creating a
    setup under C both succeed (200 / 201). (D5)
13. `[test]` A non-numeric path id (`/api/setups/abc`, `/api/characters/abc/setups`)
    answers 422.
14. `[test]` 009's characters routes still behave as before with this router registered:
    `GET /api/characters/<C>` answers the character, and
    `POST /api/characters/<C>/archive` answers 200. (Registration order, D5)
15. `[manual/live]` Against a running dev backend whose database pre-dates 010: after the
    administrator presses Create for `setups` on the Database page, `curl`-ing a
    character's setups listing with a roleplayer's cookie answers `{ "setups": [] }`.
