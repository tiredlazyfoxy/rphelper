# Step 004 — The setups API client and the section state

## Goal

Add `app/setupsApi.ts`, the `Setup` type and the five calls the frontend makes over the
shared client. Add `app/setupsSectionState.ts`, the section's data class (rows, load
status, row-action error, in-flight row, switch) with its load and row-action effects and
the pure apply-a-row upsert rule (D4, D11, D12).

## Interface intent

**`app/setupsApi.ts`** (new)

- **`Setup`**: type mirroring the wire object field for field (`id` string,
  `character_id` string, `name`, `description`, `archived_at` string or null,
  `created_at`, `updated_at`). No renaming layer.
- **`isSetupArchived`**: pure. Takes a `Setup` and returns whether `archived_at` is
  non-null.
- **`fetchSetups`**: takes a character id (string), `includeArchived` (boolean) and an
  optional signal. GETs the character's listing (with `?include_archived=true` only when
  true) and resolves to the unwrapped array.
- **`createSetup`**: takes a character id, `{ name, description }` and an optional
  signal. POSTs to the character's collection and resolves to the created setup.
- **`updateSetup`**: takes a setup id, a patch with optional `name` / `description`, and
  an optional signal. PATCHes with exactly the supplied keys and resolves to the updated
  setup.
- **`archiveSetup`** / **`restoreSetup`**: take a setup id and an optional signal. POST to
  the action route and resolve to the setup.
- No single-setup GET call: no 010 screen reads one setup by id.
- All failures are the shared client's `ApiError`s, rethrown unchanged. Ids are never
  coerced.

**`app/setupsSectionState.ts`** (new)

- **`SetupsSectionState`**: data class, observable fields only, constructed from a
  `characterId` (string):
  - `characterId`: as constructed;
  - `setups`: array of `Setup`, starts empty;
  - `status`: `"idle"`, `"loading"`, `"ready"` or `"failed"`, starts `"idle"`;
  - `showArchived`: boolean, starts false, never persisted;
  - `error`: the row-action failure text, or `null`;
  - `pendingId`: the id of the row whose archive/restore is in flight, or `null`.
- **`loadSetups`**: effect. Takes the state and an optional signal. Sets `"loading"`,
  requests the listing for `characterId` with `includeArchived` equal to `showArchived`,
  and on success writes the rows **in the order received** with `"ready"`. On failure it
  writes `"failed"` and leaves `setups` as they were. Writes nothing once aborted, never
  rejects.
- **`setShowArchived`**: effect. Takes the state and a boolean and sets the flag. It does
  not load (the section reloads in response, `006`).
- **`applySetup`**: takes the state and one server-returned `Setup` and upserts it by 009
  D11's rule (`004.context.md`): present and visible → replaced in place; archived while
  `showArchived` is false → removed if present, not inserted if absent; absent and visible
  → inserted at its `created_at`-descending position.
- **`archiveRow`** / **`restoreRow`**: effects. Take the state, a setup id and an optional
  signal. Clear `error`, set `pendingId` to the id, POST the action, and on success apply
  the returned row. On failure set `error` to **"Could not archive the setup."** /
  **"Could not restore the setup."** and leave `setups` unchanged. Either way `pendingId`
  returns to `null`. Write nothing once aborted, never reject.

## Definition of done

1. `[test]` `fetchSetups("7250000000000000001", false)` requests exactly
   `GET /api/characters/7250000000000000001/setups` (no query string).
   `fetchSetups(id, true)` requests exactly `GET …/setups?include_archived=true`. Each
   resolves to the payload's `setups` array with every `id` and `character_id` the
   identical string the payload carried.
2. `[test]` `createSetup` POSTs `/api/characters/<id>/setups` with the JSON body
   `{ name, description }`. `updateSetup` PATCHes `/api/setups/<id>` with a body holding
   only the keys given. `archiveSetup` / `restoreSetup` POST `/api/setups/<id>/archive` /
   `/restore`. Each resolves to the response's setup. (US-023.AC-1)
3. `[test]` A 404 envelope with code `setup_not_found` makes `archiveSetup` reject with an
   `ApiError` whose `code` is `setup_not_found`. `isSetupArchived` is true for a setup
   whose `archived_at` is a string and false when it is null.
4. `[test]` A fresh `SetupsSectionState("c1")` has `characterId` "c1", no rows, `status`
   `"idle"`, `showArchived` false, `error` and `pendingId` null.
5. `[test]` `loadSetups` sets `"loading"` while pending, then `"ready"` with exactly the
   server's rows in the server's order. It requests `include_archived=true` when
   `showArchived` is true and no flag when false. On a failed request it sets `"failed"`,
   keeps the previous rows and resolves without throwing. With its signal aborted before
   the response settles it writes nothing.
6. `[test]` `applySetup` with a present id replaces that row in place (same index, new
   values). With an absent working row it inserts by `created_at` descending: a row newer
   than all existing ones lands first, and one whose `created_at` falls between two
   existing rows lands between them. (US-023.AC-1)
7. `[test]` `applySetup` with an archived row while `showArchived` is false removes that id
   (and leaves the rows unchanged when the id is absent). While `showArchived` is true it
   replaces the row in place and keeps it. (US-087.AC-1)
8. `[test]` `archiveRow` POSTs `/api/setups/<id>/archive`. While pending, `pendingId` is
   that id and the row is still listed (never optimistic). After the response, with
   `showArchived` false, the row is gone and `pendingId` is null; with `showArchived` true,
   the row is still listed with the response's `archived_at`. (US-087.AC-1)
9. `[test]` `restoreRow` POSTs `/api/setups/<id>/restore`. After the response the row is
   listed with `archived_at` null, and with `showArchived` then set false it remains in
   `setups` (it is working). (US-087.AC-2)
10. `[test]` `archiveRow` / `restoreRow` failures set "Could not archive the setup." /
    "Could not restore the setup.", leave `setups` unchanged, reset `pendingId` to null,
    and resolve without throwing. A row action that starts after a failure clears the
    previous `error` before its request. (D12)
11. `[test]` `setShowArchived` sets the flag and issues no request. An `autorun` reading
    `setups` re-runs after `applySetup`, and one reading `showArchived` re-runs after
    `setShowArchived` (the writes are MobX actions on observable fields).
