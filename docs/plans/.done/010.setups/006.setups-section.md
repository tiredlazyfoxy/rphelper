# Step 006 — The Setups section and its place on the character screen

## Goal

Add `app/SetupsSection.tsx`: the "Setups" region with its header ("New setup", "Show
archived setups"), the table of setups with a per-row overflow menu (Edit, Archive /

character screen in existing mode, between the persona block and the "Sessions" heading,

## Interface intent

**`app/SetupsSection.tsx`** (new)

- **`SetupsSection`**: `observer` component. Props: `characterId` (string). Creates its
  `SetupsSectionState` once with `useState`. It:
  - loads (`loadSetups`) on mount and again whenever `showArchived` changes, each run with
    an `AbortController` aborted when the next run starts or on unmount;
  - holds the modal flags as component-local `useState`: `createOpen` (boolean) and
    `editTarget` (a `Setup` or null) (`ui-conventions.md`);
  - renders a **region** whose accessible name is **"Setups"**, headed by a heading
    **"Setups"** at the same level as the screen's "Sessions" heading;
  - in its header: a labelled button **"New setup"** (`IconPlus` left section) that opens
    the modal in create mode, and a Mantine `Switch` labelled **"Show archived setups"**
    reflecting `showArchived` and calling `setShowArchived` on change;
  - renders the list below the header, by `status`:
    - `"idle"` / `"loading"`: a small Mantine `Loader`;
    - `"failed"`: the text **"Could not load setups"** and a button **"Retry"** that
      re-runs `loadSetups`;
    - `"ready"` with no rows: the text **"No setups yet."** and nothing else;
    - `"ready"` with rows: a Mantine `Table`, one row per setup in state order. Each row
      shows the name, dimmed with an **"Archived"** badge when archived, and a trailing
      `IconButton` (`IconDots`) labelled **"Actions for <name>"**, disabled while that
      row's id is `pendingId`. It opens a Mantine `Menu` with the items **"Edit"**
      (`IconEdit`, sets `editTarget` to the row) and **"Archive"** (`IconArchive`,
      `archiveRow`) for a working row, or **"Restore"** (`IconArchiveOff`, `restoreRow`)
      for an archived one. No confirm;
  - renders the state's `error`, when non-null, in an inline `Alert` inside the region;
  - mounts `SetupModal` only while `createOpen` is true (with `setup` null) or `editTarget`
    is non-null (with that setup). Its `onSaved` applies the row with `applySetup` and then
    closes the modal. Its `onClose` closes it;
  - `void`s every effect from its handlers (the effects never reject). No notification is
    raised anywhere.

**`app/CharacterScreen.tsx`** (edited; 009-owned file)

- In existing mode with status `"ready"`, renders `SetupsSection` for the loaded
  character, **keyed by the character id**, after the screen's Save / Archive / Restore
  actions and before the "Sessions" heading. Nothing else on the screen changes: new mode,
  loading, not-found and failed render no section.

## Definition of done

1. `[test]` `SetupsSection` mounted with `fetch` answering two setups requests exactly
   `GET /api/characters/<id>/setups`, then shows a "Setups" region with a "Setups"
   heading, a "New setup" button, an off "Show archived setups" switch, and a table with
   one row per setup in the payload's order, each showing its name. (US-023.AC-1)
2. `[test]` With an empty listing the region shows "No setups yet." and no table. The
   region holds no other text inviting the user to create a setup. (R2, D13)
3. `[test]` A failed load shows "Could not load setups" and "Retry" in the region, with no
   notification. "Retry" requests the listing again, and on success the rows render.
   (D12)
4. `[test]` Pressing "New setup" opens a dialog "New setup". Entering a name and pressing
   "Create" POSTs to `/api/characters/<id>/setups`. After the 201 the dialog is gone, the
   new setup's row appears first in the table, and no second listing request is issued
   after the POST. (US-023.AC-1, D11)
5. `[test]` Opening a row's "Actions for <name>" menu and choosing "Edit" opens a dialog
   "Edit setup" prefilled with that setup's name and description. Changing the name and
   pressing "Save" PATCHes `/api/setups/<id>`. After the response the dialog is gone and
   the row shows the server's name in the same position. (D2)
6. `[test]` A failed create keeps the dialog open with "Could not create the setup." inside
   it, and the table is unchanged. Cancelling then closes the dialog. Reopening "New setup"
   shows an empty Name (a fresh draft). (D2, D12)
7. `[test]` Choosing "Archive" from a working row's menu POSTs `/api/setups/<id>/archive`,
   and after the response the row is gone from the table. Turning "Show archived setups"
   on requests `…/setups?include_archived=true` and shows the row with an "Archived"
   badge, and its menu offers "Restore" and not "Archive". No confirm dialog appears at
   any point. (US-087.AC-1, D4)
8. `[test]` Choosing "Restore" on that archived row POSTs `…/restore`. After the response
   the row has no "Archived" badge, and after turning the switch off (which requests
   `…/setups` again) the row is still listed. (US-087.AC-2)
9. `[test]` A failed archive shows "Could not archive the setup." in an alert inside the
   region, the row is still listed, and no notification is shown. (D12)
10. `[test]` `CharacterScreen` at `/characters/<id>` (amending 009's tests): once the
    character has loaded, the "Setups" region is present, and in document order it follows
    the "Persona" editor and precedes the "Sessions" heading. At `/characters/new` there is
    no "Setups" region, and the "Character not found" and "Could not load the character"
    states render none either. (D1)
11. `[test]` `CharacterScreen` for an archived character (with "Archived" and "Restore" on
    the screen) still renders the "Setups" region, and creating a setup there POSTs to
    that character's collection. (D5)
12. `[test]` Navigating in-entry from `/characters/<a>` to `/characters/<b>` requests
    `b`'s setups listing and shows `b`'s setups, with none of `a`'s rows and the switch
    back off. (D11)
13. `[test]` 009's existing assertions in `tests/app/CharacterScreen.test.tsx` and
    `tests/app/App.test.tsx` keep passing, with their `fetch` stubs extended to answer
    `GET /api/characters/<id>/setups` (for example with `{ "setups": [] }`). Where a 009
    assertion counts requests or reads "the" Archived text or switch on the screen, it is
    scoped so that the section's requests and controls do not change its meaning. No 009
    assertion is dropped.
14. `[manual/live]` Against a running backend: on a character's page, create a setup with
    a formatted description, edit it, reload the page and see it listed; archive it, turn
    "Show archived setups" on, restore it. The dimmed archived row reads as dimmed in both
    colour schemes.
