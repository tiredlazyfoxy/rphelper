# Step 001 — The `setups` table, its not-found error and its pydantic models

## Goal

Declare the `setups` table in the registry (D7), add the `setup_not_found` domain error
(404, D8), and add the four request/response models for the setup routes. Fix the two
backend test landmines that registering `setups` sets off.

## Source files

backend/app/db/schema.py
backend/app/errors.py
backend/app/models/setups.py

## Test files

backend/tests/test_db_schema.py
backend/tests/test_setups_models.py
backend/tests/test_admin_db_router.py

## Interface intent

**`db/schema.py`** (extended)

- **`setups`**: a module-level `Table` literal bound to the one `metadata`, with exactly
  the eight columns of D7: the snowflake `id` primary key (the registry's id column form),
  `user_id` (NOT NULL, FK to `users.id`), `character_id` (NOT NULL, FK to
  `characters.id`), `name` and `description` (Text, NOT NULL, no server default),
  `archived_at` (Text, nullable), `created_at` and `updated_at` (Text, NOT NULL). Neither
  FK has an `ON DELETE` clause. Plus one non-unique index on `(user_id, character_id)`,
  in that column order.

**`errors.py`** (extended)

- **`SetupNotFoundError`**: a `DomainError` subclass, code `setup_not_found`, HTTP
  status 404, empty `detail`. Same shape as 009's `CharacterNotFoundError` in every other
  respect.

**`models/setups.py`** (new)

- **`SetupResponse`**: response model with `id` and `character_id` (both outbound
  snowflakes → decimal strings), `name`, `description`, `archived_at` (string or null),
  `created_at`, `updated_at`. No `user_id`.
- **`SetupListResponse`**: response model wrapping a list of `SetupResponse` under the
  key `setups`.
- **`CreateSetupRequest`**: request model, unknown keys ignored. `name` is required,
  whitespace-stripped, then at least one character. `description` is optional, defaults to
  the empty string, and is kept verbatim (not stripped). No `character_id` field: the
  parent comes from the path.
- **`UpdateSetupRequest`**: request model, unknown keys ignored. `name` and
  `description` are both optional; absent or `null` means "not supplied". A supplied
  `name` follows the strip-then-non-empty rule. A supplied `description` is kept
  verbatim. No `character_id` field (D5: a setup cannot move).

## Definition of done

1. `[test]` 010 adds `setups` to the registry, and the 010 delta in
   `tests/test_db_schema.py` uses the later-table-proof form that 009's delta uses (009
   `001` DoD-1 / DoD-11; `001.context.md`). `setups` is in `schema.metadata.tables`, and
   the registry minus the tables declared up to and including 010 contains no table this
   feature declared. The assertion must still hold when a later feature adds a table.
2. `[test]` `setups` has exactly the columns `id`, `user_id`, `character_id`, `name`,
   `description`, `archived_at`, `created_at`, `updated_at`. `id` is the primary key.
   Every column except `archived_at` is NOT NULL; `archived_at` is nullable. The table
   has **no** `model_ref`, `system_prompt`, `tools`, `rp_language`,
   `preferred_language`, or `is_default` column. (D7, `data-model.md` `setups`, R2)
3. `[test]` `setups.user_id` is a foreign key to `users.id`, `setups.character_id` is a
   foreign key to `characters.id`, and the table declares a non-unique index whose columns
   are exactly `user_id`, `character_id` in that order. (D7)
4. `[test]` `metadata.create_all` on a fresh test engine creates `setups`. Inserting a
   `setups` row whose `character_id` names no `characters` row fails, and so does one whose
   `user_id` names no `users` row (both FKs are enforced).
5. `[test]` `SetupNotFoundError` is a `DomainError` with code `setup_not_found` and HTTP
   status 404. Raised from a route on an application with the exception handlers
   registered, it answers 404 with the envelope `{ "error": { "code": "setup_not_found",
   … , "detail": {} } }`. (D8, R5)
6. `[test]` `SetupResponse` built from int `id` and `character_id` serialises both as the
   decimal strings of those ints. `archived_at` `None` serialises as JSON `null`. The
   serialised object has exactly the seven keys of the wire contract (`context.md`).
   `SetupListResponse` serialises as an object whose only key is `setups`, holding the
   rows in the order given.
7. `[test]` `CreateSetupRequest`: `"  Tavern  "` parses to `"Tavern"`. `""`, `"   "` and a
   missing `name` each fail validation. A missing `description` gives `""`. A
   `description` of `"  # Scene\n"` is kept exactly. Unknown keys (`user_id`,
   `character_id`, `archived_at`) are ignored, not rejected, and none of them appears on
   the parsed model. `UpdateSetupRequest`: `{}` parses with both fields unset;
   `{"name": null}` is the same as absent; `" Inn "` parses to `"Inn"`; a whitespace-only
   `name` fails; `description` is kept verbatim; unknown keys including `character_id` are
   ignored. (D5, D8)
8. `[test]` 006's and 009's existing registry-delta assertions in `tests/test_db_schema.py`
   still pass with `setups` registered. If they subtract a "declared by later features"
   set, `setups` is added to that set, and no other assertion changes. If they are
   membership/absence checks that already tolerate later tables, they are left as they are.
9. `[test]` **Rescope `tests/test_admin_db_router.py`'s undeclared-name list**: replace
   its `"setups"` entry in `UNDECLARED_NAMES` with a name that is undeclared **and that no
   planned feature will declare** (`001.context.md`), so the 404 `unknown_table`
   expectation holds again and later features do not have to swap it. No other entry or
   assertion in that file changes.
10. `[manual/live]` Against an existing database that pre-dates 010 (with `characters`
    already created), the admin Database page lists `setups` as missing, and its
    **Create** brings it to in-sync. (D7, FEAT-005)
