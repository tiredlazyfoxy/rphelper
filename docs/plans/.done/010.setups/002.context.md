# Step 002 — step-specific context

Feature-wide facts are in `context.md`: **D3** (archive touches nothing else), **D5**
(archived parent allowed; `character_id` immutable), **D6** (own parent check, no
service-to-service call), **D8**, **D9**, **D10**, the **owner-scope**, **no-delete** and
**no-default-setup** constraints, and backend **Test conventions** (the FK chain). 009's
`002.context.md` holds the service conventions this step follows: connection first, reads
roll back the transaction they autobegun, writes inside `with connection.begin():` with
the locating read inside the same block, frozen dataclass values, a per-module private
`_now_text()`, and `next_id()` once per create before the insert. They are cited, not
restated. Only what is narrow to this step is below.

## Scope predicates — what each statement carries

| Operation | Statements |
|---|---|
| parent check (list, create) | `SELECT characters.id FROM characters WHERE id = :character_id AND user_id = :user_id`. No `archived_at` predicate (D5) |
| list | after the parent check, in the same transaction: `setups.user_id = :user_id AND setups.character_id = :character_id` and, unless `include_archived`, `archived_at IS NULL`; `ORDER BY created_at DESC, id DESC` |
| create | parent check, then `INSERT … VALUES (… user_id = :user_id, character_id = :character_id …)`, both inside one `begin()` |
| get / locate-for-write | `setups.id = :id AND setups.user_id = :user_id` |
| update / archive / restore | the UPDATE's own `WHERE` is `id = :id AND user_id = :user_id` too, not only the locating read |

A row that exists for another user and a row that exists for nobody follow the same code
path and raise the same error. There is no "exists but not yours" branch (R5).

## The list read and its rollback

`list_setups` issues two selects (parent check, then rows) on the connection's autobegun
transaction. It must roll back that transaction on **both** exits, the normal return
**and** the `CharacterNotFoundError` raise (DoD-11). A `try` / `finally` around the two
reads does both.

## Why the parent check is a separate select, not a join

A join (`setups JOIN characters`) returns no rows both for "character has no setups" and
for "character is not yours". The route must tell those apart (`[]` versus 404), so the
existence check is its own statement.

## Imports

`setups` and `characters` Tables from `app.db.schema`; `SetupNotFoundError` and
`CharacterNotFoundError` from `app.errors`; `SnowflakeGenerator` from `app.ids`. Nothing
from `app.services.characters` (DoD-12).

## Test seeding

Users first, then characters (a raw insert into the `characters` Table with `id`,
`user_id`, `name`, `sheet`, `archived_at`, `created_at`, `updated_at`), then setups
through `create_setup`. An archived character for DoD-3 is a raw insert with
`archived_at` set. DoD-10 counts rows in the `setups` table directly.
