# Step 003 — step-specific context

Feature-wide facts are in `context.md`: the **Wire contract** (routes, shapes, failure
codes), **D5** (one router, two path families, registration order), **D8**, and backend
**Test conventions** (the FK chain: router tests create characters through
`POST /api/characters`). 009's `003.context.md` holds the handler dependencies this step
uses unchanged: `get_connection`, `require_user` → `CurrentUser` (pass
`current_user.id`), `get_id_generator` from `app.routers.bootstrap`, `SnowflakeIn` for
path ids, a plain `bool` `include_archived` query parameter, and the router test pattern
(file-local `application` / `client` fixtures, `_insert_user`, `_login`, separate clients
per user). They are cited, not restated. Only what is narrow to this step is below.

## One router, full paths

The router is declared with **no prefix** (or the common `/api` prefix) and each handler
carries its full path, because the two families share no longer prefix. Router-level
`dependencies=[Depends(require_user)]` still covers all six routes (009 D6's reason: a
route added later cannot forget it). Each handler also receives `CurrentUser` to scope the
service call.

## Coexistence with the characters router

- `/api/characters/{character_id}/setups` has three segments under `/api/characters`.
  009's `/api/characters/{character_id}` has two, and its `…/archive` and `…/restore`
  have a different literal third segment, so no path overlaps. Starlette matches routes in
  registration order, and registering setups **after** characters keeps 009's routes
  matched first (DoD-14 guards that nothing of 009's changed).
- `main.py`: add one `include_router` for the setups router immediately after the
  characters router's. Nothing else in `main.py` changes, and the lifespan still runs no
  DDL.

## 405 on DELETE

No handler is declared for `DELETE`. Starlette answers 405 when a path matches a route
under another method: `/api/characters/{character_id}/setups` (GET/POST) and
`/api/setups/{setup_id}` (GET/PATCH) both match. DoD-11 asserts the status only.

## Test seeding

Users A and B (role `roleplayer`) through the file-local `_insert_user`, each logged in
on its own client. Characters through `POST /api/characters` as their owner. Setups
through the create route. DoD-12 archives the character through 009's
`POST /api/characters/{id}/archive`. DoD-5's "nobody's id" and DoD-6's are ids that no row
holds, for example a large decimal string.
