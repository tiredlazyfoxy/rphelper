# Step 004 — step-specific context

- **Current client.** `frontend/src/shared/api.ts` exposes `apiRequest`, `apiGet`
  and `apiPost`, and all three always `JSON.parse` the body, so there is no blob
  support today. `ApiError(code, message, status, detail?)` lives in
  `shared/apiError.ts`, together with its type guard. A 401 calls
  `documentNavigation.assign("/login")`, and that object is the test seam for the
  navigation. Nothing in `src` uses `Blob`, `URL.createObjectURL` or the `download`
  attribute yet.
- **Why the helper lives in `api.ts` and not in a separate `download.ts`.**
  `frontend-structure.md` §"One decode in the client" rules that exactly one place
  parses an error body. Placing the blob call beside the JSON calls lets it share
  that decode, the 401 navigation, and the `client_*` synthetic codes. A separate
  module would have to re-decode or reach into `api.ts`'s private decode. Refactor
  the existing decode into a private helper shared by both paths if needed. Its
  behaviour must not change (DoD-9).
- **jsdom gaps.** jsdom implements neither `URL.createObjectURL` nor
  `URL.revokeObjectURL`, and anchor `click()` performs no navigation. Tests stub
  the two URL functions (e.g. with `vi.stubGlobal` or by assigning onto `URL`) and
  observe the click, either through a spy on `HTMLAnchorElement.prototype.click`
  or through a document-level click listener. Fetch is stubbed per test with
  `vi.stubGlobal("fetch", ...)`, as the existing client tests do.
- **Size** is the `Blob`'s `size`, the byte count the user's disk receives. It is
  not a character count.
