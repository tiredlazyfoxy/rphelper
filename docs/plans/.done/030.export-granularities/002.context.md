# Step 002 — step-specific context

- **Root-row lookup is the exporter's own select, not the existing getters.** The
  exporter fetches the character (or session) row with its own full-row select
  filtered on **both** `id` and `user_id`. When no row comes back, it raises the
  existing `CharacterNotFoundError` (`character_not_found`, 404) or
  `SessionNotFoundError` (`session_not_found`, 404) from `app/errors.py`. Reasons:
  - the full row is needed for the payload anyway;
  - it keeps the lookup inside this export's single read snapshot;
  - the exporter cannot depend on whether `services/characters.get_character` and
    `services/sessions.get_session` filter archived rows, and R6 requires archived
    objects to export.

  The errors are the same types those getters raise, so the wire contract is
  unchanged: foreign and missing both mean 404, and there is no 403.
- **Why `role` and `is_enabled` leave the user export.** They are
  administrator-controlled account state, not material the roleplayer owns. Carrying
  `role` into a file the roleplayer holds would put a privilege grant in their
  hands, ready for an import path to apply. `password_hash` leaves for the obvious
  reason. `id` stays because it is the `user_id` of every other row and the
  `scope_id` of `scope='user'` memos, so 031 needs it to remap. Every other `users`
  column, including any added later, flows through.
- **Memo selection predicates** (`schema.memos`, all also filtered on `user_id`):
  - user granularity: `user_id = caller`, with no scope filter;
  - character granularity: (`scope='character'` and `scope_id = character id`) or
    (`scope='setup'` and `scope_id` in the character's setup ids) or
    (`scope='session'` and `scope_id` in the character's session ids). An empty id
    list contributes no term;
  - session granularity: `scope='session'` and `scope_id = session id`.
- **Messages are selected from the raw `messages` Table**, by `session_id`, not
  through `settled_entries` or `current_zone`. Those views drop buried rows, and
  `related_to` would then dangle (`data-model.md` ~L882-884). This is a **read**
  of raw `messages`. R11's "two writers" rule concerns writes, so the read does not
  contradict it.
- **Seeding buried messages.** Append several zone messages, then settle through
  `services/settle.py`. The non-head rows become buried (their `related_to` is the
  head). Archive through the existing characters, setups and sessions services, or
  by setting `archived_at` directly.
