## Why two statuses

The configuration and the models list fail independently: one is the session's, the
other the instance's registry. Holding one status would turn a failed models read into a
failed configuration, and the bar (`011`) would hide tool indicators it could show. The
bar renders one load-failure line when **either** failed, and one Retry that re-runs
`loadSessionConfig` for both (re-requesting a list that already loaded is harmless).

## Branch on `.code` only

`chooseModel` tells `model_not_enabled` apart by `isApiError(e) && e.code ===
"model_not_enabled"`. It never inspects the status or the message (`frontend-structure.md`
"The API client").

## Mutation posture

`chooseModel` takes no signal, as 015 D5's mutations: a choice that started reaches the
server even if the screen is left. Its writes after `await` are still in `runInAction`.
A write into a state whose screen unmounted is harmless.
