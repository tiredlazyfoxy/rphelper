# Step 004 — step-specific context

Feature-wide facts are in `context.md`: **D9** (sub-resources; the character's other
columns are not touched), **D10** (set-time check, no session clear), **D11**
(`updated_at` / `last_used_at`, empty updates), **D12** (imports), **D14** (no user
not-found path). Only what is narrow to this step is below.

## Order inside each update transaction

1. owner-scoped existence check (session or character), which raises not-found before
   any registry read;
2. the set-time model check when a model is being set, **inside the same transaction**
   (`002` DoD-3 makes `validate_chat_model` safe there), so "nothing is written" holds
   atomically;
3. one `UPDATE … WHERE id = :id AND user_id = :caller` with only the supplied columns
   plus `updated_at`.

When nothing is supplied, skip steps 2–3 entirely and still run step 1, so a missing
target is still a 404.

`update_session_configuration` returns `get_session_configuration(...)` **after** the
transaction commits. That read uses its own read context, and "a read then `begin()` on
one connection" is the order to avoid, not this one (`backend-structure.md`
"Transactional DDL").

## `UNSET`

`llm_registry.UNSET` / `Unset` is the sentinel 006 uses for "not supplied" on its own
updates. Reuse it here (D12) rather than defining a second sentinel. A parameter typed
`str | None | Unset` distinguishes "clear" (`None`) from "absent" (`UNSET`). For the
session `model` the type is `ModelRef | Unset`. Clearing is not offered, and the router
never passes `None` (the request model rejects it, `001` DoD-8).

## Timestamps

Use the module's private fixed-width `_now_text()` form (as 011 / 012 / 015 services do:
`YYYY-MM-DDTHH:MM:SS.ffffff+00:00`). DoD-4 / DoD-11 assert the shape and the ordering,
never an exact value.

## Test shape

`test_configuration_writes.py` builds a `create_all` database with raw-inserted users,
characters, sessions (with chosen `last_used_at` / `updated_at`), `llm_servers` and
`models`. It calls the service functions directly. DoD-6's "new session" is created with
`services.sessions.start_session` (built by `002`) or by a raw insert that mirrors D1.
The resolved prompt and tool are read through `get_session_configuration`.
