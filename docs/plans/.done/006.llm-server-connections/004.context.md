# Step 004 — step-specific context

Feature-wide facts are in `context.md` (D2 for measuring the dimension, D4 for use-time
validation with no cascade, D10 for rows persisting, D12 for the validator's argument shape
and the `model_ref` `_TBD`, R4 and R5 in the cross-cutting section). Only what is narrow to
this step is below.

## The two validators ship with no call site, and that is correct

`model_not_enabled` is consumed by the request path in `019`/`021`, whose model reference
is written by `017`; `no_embedding_model` is consumed by `024`'s embedding lifecycle and by
`014`/`015`'s semantic tools. None of those exists yet. So DoD-15 through DoD-20 are tested
**directly against the service**, with rows written by the test's own setup — not through a
session and not through an HTTP route. `context.md` D12 says this plainly so a verifier
does not read the absence of an end-to-end path as a gap.

The consequence for the *next* feature that needs them: the call site is `resolve → validate
→ call`, in that order, with no step that substitutes a model
(`llm-and-streaming.md`, "The model registry and use-time validation"). This step builds
the middle one and nothing else.

## Why the chat-model validator takes a pair and not a reference string

`data-model.md` calls `sessions.model_ref` an "unvalidated reference" and fixes no
encoding. A bare model name is genuinely ambiguous — two registered servers can both offer
the same name, which is why `models` is unique on the *pair*. Rather than invent the packed
form on `017`'s behalf, this validator takes the pair as two plain arguments and the
`_TBD:` in `context.md` D12 carries the question forward. Whatever `017` chooses costs one
unpack at its own call site.

The **level** argument exists because `backend-structure.md`'s error table requires
`model_not_enabled` to carry "the model reference, and **which level set it** — `character`
or `session`, **never `user`**". UC-050 and R1's correction are explicit that there is no
user-level model default; UC-012's phrasing that mentions one is stale wording of the same
prohibition (`domain-rules.md` R4 flags it for `/product-spec`). DoD-17 pins the two-value
constraint so a third level cannot be added by accident.

## R4, in the exact shape it forbids things

`domain-rules.md` R4 (~line 218) states the prohibition three ways, and all three bind
here:

- resolution yields a **reference**, not a validated model — this module does not resolve;
- validation is at **use** time, never at resolution time;
- **"sanitizing" during resolution is forbidden** — a function that quietly drops a
  disabled model and returns the next one passes every happy-path test and violates the
  rule invisibly.

DoD-16 and DoD-19 are written as "returns no substitute" for exactly that reason: the
failure mode is a *success* that should have been an error.

## The union rule this step's persistence exists to serve

`admin-surfaces.md`'s Models modal renders `available ∪ already-enabled`, and the reason is
that a model which was enabled but is no longer offered by the server must still be
visible and still be un-checkable. That only works if a disable is a **flag flip and not a
delete** — DoD-2 is the load-bearing item, and steps `008` and `009` consume it.

## The designation's transaction, and the one thing outside it

The embeddings call is **outside** the transaction and must be: a network call inside a
`with conn.begin():` holds SQLite's single writer open for as long as the provider takes.
The order is therefore: read, resolve, call, measure — then open one transaction that
clears every other row's flag and upserts this one. DoD-9 and DoD-10 together pin both
halves: everything or nothing, and nothing at all when the call failed.

## Gotchas

- **The designation is table-wide, not server-wide.** "At most one row true across the
  whole table" (`data-model.md`) means designating on server B must clear the flag on
  server A. DoD-9 says "including rows on other servers" because a `WHERE server_id = ?`
  clause is the natural and wrong thing to write.
- **Clearing is server-scoped**, because the route is (`context.md` D17) and because the
  row menu offers it only on the server that holds the designation. The asymmetry with
  designating is deliberate.
- **`embedding_dim` is left on the row when a designation is cleared** (DoD-14). It is a
  measured property of that model, not of the designation, and re-designating the same
  model re-measures it anyway.
- **A changed dimension neither forces nor prompts a rebuild** — UC-013's postcondition is
  explicit, and `data-model.md` sends the remedy to UC-016 / FEAT-005. This step therefore
  emits **no warning, no flag and no comparison** against a previously recorded dimension.
- **Set-enabled-models is not `async`.** Only the designation reaches the network. Making
  it `async` for symmetry would make step `005`'s route `async` for no reason.
