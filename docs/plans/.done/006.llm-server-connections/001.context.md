# Step 001 — step-specific context

Feature-wide facts are in `context.md` (D1 for the dropped `active` column, D5 for `kind`
as a label, D7 for the four codes and their statuses, D8 for where the write-time
validation lives, D10 for `models` rows persisting, D13 for the timeout). Only what is
narrow to this step is below.

## The two column lists

`docs/architecture/data-model.md`, sections **`llm_servers`** (~lines 203–222) and
**`models`** (~lines 224–244), give both tables verbatim as tables of columns and notes.
The skeleton agent reproduces them from there; they are not restated here, and this step
adds **no column that section does not name** — `data-model.md`'s own preamble allows a
plan to add bookkeeping columns but the two tables are already complete for this feature's
purposes.

Two notes from that section that are easy to skim past:

- `api_key_ref` holds a **pointer**, and the consequence the doc draws is that the
  whole-database export (FEAT-018 / UC-061) cannot exfiltrate credentials and a drift
  report (FEAT-005) needs no redaction. Nothing in this step may weaken that.
- `embedding_dim` exists **because `vec0` tables are declared with a fixed dimension**
  (`data-model.md`'s Vector-tables section, ~line 563). This step creates **no `vec0`
  table** — that is feature `024`/`007`. It only makes the column exist.

## The registry conventions `001.backend-foundation` froze

`backend/app/db/schema.py`'s docstring binds every feature: **every table is a
`Table(...)` literal bound to the one `metadata`, in this one file**. No per-feature table
module, no builder callable, no import-side-effect registration. Snowflake primary keys
are **big-integer and not autoincrementing** (`data-model.md`'s Identifiers section: ids
are minted in application code before the INSERT, and there is no `AUTOINCREMENT`
anywhere).

The file holds **two** tables when this step starts — `users` (`003/001`, plus
`last_login_at` from `005/001`) and `auth_sessions` (`004/001`). This step appends two
more. Nothing existing is edited.

## The error-class shape this step extends

`backend/app/errors.py` already defines `DomainError` with class attributes `code: str`
and `http_status: int`, per-instance `message: str | None` and `detail: dict[str, Any]`, a
`__init__(self, message=None, detail=None)`, a `to_wire()` producing
`{"error": {"code", "message", "detail"}}`, `domain_error_handler`, and
`register_exception_handlers(app)`. `SecretRefError` (`secret_ref_missing`, 500) is
already there and is the worked example.

**A new code is a new subclass and nothing else.** The handler logs `code` and
`http_status` only and never `detail` — which is why `detail` is free to carry the model
name and the level (step `004`) without touching the redaction rule.

## Why the write-time validator is not in `secrets.py`

`app/secrets.py`'s docstring says explicitly that rejecting a non-`$` value **on write** is
a different mechanism and belongs to this feature. It is a *wire-boundary* concern — it
decides what a request body may contain — so it lives in `app/models/`, beside
`models/ids.py`, which is the established home for an annotated boundary type. That also
keeps `resolve_secret` a pure read-time function with one responsibility.

## The empty-string case, which is the one that gets forgotten

The predicate must **accept** the empty string. It is not a permissive fallback: it is the
payload state that means "clear the stored pointer" on an update and "no pointer" on a
create (`context.md` D9). A validator written as "must start with `$`" makes clearing a
credential impossible and turns D9's three states into two.

## Gotchas

- **`float`, not `int`, for the timeout.** `httpx` takes seconds as a float and a
  sub-second value is a legitimate test configuration.
- **No `CHECK` on `kind`.** The two-member constraint is a pydantic literal at the router
  boundary answered by FastAPI's 422; a database `CHECK` would make a third kind a schema
  migration, which is not what "a label, not a dispatch key" means.
- **The `models` foreign key needs the cascade declared even though step `003` deletes
  explicitly.** The two are not redundant: the declaration is what `db/drift.py` will read,
  the explicit delete is what makes the behaviour hold regardless of the pragma.
- **`test_db_schema.py`, `test_errors.py` and `test_config.py` already exist** and are
  extended, not replaced. `003`/`004`/`005` edit the same files for their own tables,
  codes and fields; clauses belonging to those features are left exactly as found.
