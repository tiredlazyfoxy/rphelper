# Step 005 — step-specific context

Feature-wide facts — decisions D2, D4, D5, D6, D8, D9 and their reasoning — are in
`context.md`. This file carries only what is narrow to the engine and the registry.

## What the architecture states, and what it leaves open

**Stated** (`docs/architecture/backend-structure.md` § Database access): one SQLite
connection factory in `db/engine.py` which **on every connection** sets
`PRAGMA foreign_keys = ON`, sets `PRAGMA journal_mode = WAL`, and loads the `sqlite-vec`
extension "so `vec0` tables and the KNN operators are available on every connection
rather than only where someone remembered".

WAL matters here for a specific reason worth holding: readers do not block the single
writer, and an SSE compose exchange holds a request open while other reads happen.

**Left open**, and therefore decided by this plan: the PRAGMA/WAL lifecycle (D5), the
pooling and threading configuration (D9), and the posture on a failed extension load
(D8). All three are in `outcome.md` for the architect to record.

## Why the connect listener is one listener and not two mechanisms

`foreign_keys` genuinely is per-connection and must be re-set every time. `journal_mode`
is a persistent file-level property, so a first-open special case would be *possible* —
and would be a second mechanism, with its own ordering question, for a statement that
costs nothing when it is a no-op. One listener, every connection, exactly as the
architecture words it.

Neither PRAGMA is per-transaction. Nothing in this backend sets a PRAGMA inside a
`begin()` block.

## Order inside the listener

Load the extension **first**, then the PRAGMAs. If the load is going to fail, it should
fail before anything else has been asserted on a connection that is about to be
discarded.

## Why the loader is a named module-level function

DoD-4 needs a seam. The test-coder never reads source, so the seam has to be named in
the plan: the loader is a module-level function in `db/engine.py`, and a test makes it
fail by patching that name. Without it, "a failed extension load is loud" is untestable
and would have had to be a `[manual/live]` item.

## The test database fixture (decision D4, restated only as mechanics)

A real `.sqlite` file under pytest's `tmp_path`, **one per test**, built by pointing a
settings instance at that directory and calling the same engine factory production
calls. Teardown disposes the engines. `:memory:` is wrong here because WAL is a no-op
there and the extension load takes a different path — the two properties this step
exists to guarantee would go untested.

## Pooling, concretely

The pysqlite dialect's default pool for a **file** database, with the DBAPI's
same-thread assertion disabled via connect arguments. uvicorn hands a pooled connection
to whichever worker thread runs the request; the pool guarantees one connection is never
used by two threads at once, so the assertion is protecting against something the pool
already prevents while forbidding the normal case. DoD-9 pins it.

The engine cache is keyed on the **resolved database path**, not on the settings object
— settings instances are not hashable, and two tests with different `tmp_path`
directories must get different engines in one process.

## The registry, and what it must be able to answer later

`docs/architecture/backend-structure.md` § Persistence access, reason 3, verbatim:
"FEAT-005 needs a registry it can introspect, not mapped classes. UC-014 asks for the
current structural truth per table, answered by `PRAGMA table_info` / `index_list`
against a declaration. A Core `MetaData` with `Table` objects *is* that declaration —
`db/schema.py` stays the single introspectable source of truth and `db/drift.py` walks
it directly."

Feature `007` consumes it **per table**: `db/sync.py` takes a drift-report row plus the
registry's `Table` object and emits the batch operations that close the gap. So the
registry must expose enumerable, **named** `Table` objects — which a `MetaData`'s table
collection does natively. Nothing beyond that is needed, and nothing beyond that should
be built.

## Explicit non-goals for this step

- **No table, view, index or trigger is declared.** Every content feature adds its own.
- **No DDL is executed anywhere**, including at import. `007`'s admin-triggered `Create`
  and `Sync` are the only DDL paths this system will ever have.
- **No Alembic.** Not imported, not depended on, and no `alembic.ini`, `env.py` or
  `versions/` directory. It arrives in `007` as a batch-DDL executor only.
- **No transaction is opened by the dependency.** Services own their own
  `with conn.begin():` boundaries, which is one of the three reasons Core was chosen
  over the ORM.

## Where `vec0`'s dimension comes from

Nowhere yet. The two vector tables are declared with the designated embedding model's
dimension and belong to later features. The `vec0` table DoD-3 creates is a throwaway in
a test, not a schema object.
