# Step 004 — step-specific context

Feature-wide facts — the JSON id boundary as a cross-cutting constraint, the layout —
are in `context.md`.

## The bit layout, verbatim

From `docs/architecture/data-model.md` § Identifiers. 64-bit signed, 63 usable bits:

```
 41 bits   milliseconds since epoch 2026-01-01T00:00:00Z   (~69 years)
 10 bits   node id, from config, default 0
 12 bits   per-millisecond sequence                        (4096 ids/ms)
```

Storage is `id INTEGER PRIMARY KEY` in SQLite — the rowid alias, which holds a signed
int64 natively — and `BigInteger` in SQLAlchemy Core. Nothing in this step writes a
table; that is recorded so step `005`'s registry and every later table declaration
inherit it.

## Why the epoch is a constant

It is the whole 41-bit budget. Moving it re-bases every future id against a different
origin and invalidates the ordering of every row already stored. It is a literal in this
module and is never read from configuration.

## Ordering is a schema dependency, not a nicety

A snowflake is k-sortable, so `ORDER BY id` is chronological. The `messages` table
carries no `position` column *because of this*. So DoD-1's monotonicity is not a
cosmetic property — a generator that ever went backwards would silently reorder a
roleplayer's stream.

## Sequence exhaustion — a planner ruling

The architecture does not address what happens past 4096 ids in one millisecond. This
step chooses **block until the next millisecond**, the conventional answer. The
alternatives are both worse: wrapping the sequence mints a duplicate, which is the one
thing the lock exists to prevent; raising turns a burst of writes into an error the
caller cannot act on. Blocking costs at most the remainder of one millisecond. Recorded
in `outcome.md`.

## Backwards clock — why it refuses, and why it is not a `DomainError`

`data-model.md`: "A clock going backwards refuses to issue and raises. Silently waiting
out the drift or carrying on both mint duplicates." `backend-structure.md` adds the
classification: "it surfaces as an operational fault (a 500), not as a domain failure
the SPA is expected to render."

That classification is why the exception in this module is a plain exception and **not**
a subclass of step `003`'s base class. Making it one would give it a `code` the SPA is
expected to render and a wire shape it has no renderer for. DoD-6 asserts the
non-relationship deliberately, because "add it to the error hierarchy for consistency"
is exactly the tidying somebody attempts later.

## The clock seam

The generator takes its clock as a constructor argument, defaulting to the system
millisecond clock. That is the **only** way DoD-5 and DoD-6 are testable — a test cannot
make the machine's clock jump backwards. The skeleton freezes the callable's shape; the
test-coder needs to know only that it exists and that it returns milliseconds.

## One generator per process

`node_id` is read once at construction, one instance per process, held on application
state (step `006` does the holding). That is the code-level half of `data-model.md`'s
"exactly one generator process per node id" deployment guarantee, which today is
satisfied by the topology: one container, one uvicorn.

Recorded because it is the flip condition: if RPHelper ever runs more than one worker,
process or replica, both the layout and the string boundary need re-examination before
that change ships.

## Why the string boundary is not a style preference

A snowflake passes `Number.MAX_SAFE_INTEGER` (2^53 − 1) roughly **25 days** after the
epoch. An id deserialized into a JavaScript `number` after that silently rounds — to a
value that may be another row's id. It fails silently, late, and in production data
rather than in a test. DoD-7 exists to pin exactly that: a value above the safe integer
ceiling must survive the round trip digit for digit.

The rule reaches further than response bodies — it also binds ids inside a
`DomainError.detail` and ids on SSE frames. Neither exists yet; both are recorded in
`003.context.md` and in the architecture respectively.

## Ids are not secrets

A snowflake leaks its creation time and is roughly sequential, so ids are guessable.
That grants nothing, because every read path is scoped by `user_id` at the query level.
Noted so nobody "hardens" this later by swapping in random ids and losing the ordering
the schema depends on.
