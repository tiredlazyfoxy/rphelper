# Step 003 — step-specific context

Feature-wide facts — the redaction rule, decision D7, the layout — are in `context.md`.

## Why `errors.py` and `secrets.py` are one step

`resolve_secret` raises the `secret_ref_missing` error, which `errors.py` defines. The
orchestrator's suggested decomposition put `secrets.py` in the scaffold step; that would
have made step `001` depend on step `003`. They are merged rather than reordered because
together they are still well inside the size budget and the resolver is the base class's
only caller in this feature.

## The twelve codes — eleven are NOT in scope

`docs/architecture/backend-structure.md` § The error model tables twelve codes. This
step defines **one**: `secret_ref_missing`. The other eleven — `model_not_enabled`,
`no_embedding_model`, `llm_unreachable`, `tool_failed`, `translation_failed`,
`zone_empty`, `zone_not_empty`, `nothing_to_reopen`, `message_not_editable`,
`already_configured`, `account_disabled` — belong to the features that raise them and
must **not** be pre-declared here. A subclass with no raiser is a subclass whose
`http_status` nobody has thought about.

## The `http_status` gap, and what this step does about it

The architecture gives `http_status` as a field on the base class but supplies **no
per-code status column** in its table. Decision D7 resolves it: the status is a class
attribute each subclass sets, decided by the feature that introduces the code.

For `secret_ref_missing` this step chooses **500**. Reasoning to record: the failure is
that the deployment's environment does not carry a variable the stored configuration
points at. The caller cannot fix it by changing the request — only by changing the
environment and restarting — so it is not a 4xx. It is nonetheless a *typed* error and
travels in the same wire shape as every other, because an administrator running UC-011's
connection test has to be told specifically what went wrong rather than shown an opaque
failure.

## Handler registration is an inference, and is flagged as one

The architecture says "one base class, one wire shape, one handler" and gives the wire
JSON, but contains **no literal `@app.exception_handler` snippet and no registration
call site**. The registration entry point in this step, and the app factory calling it
in step `006`, are the planner's inference from that sentence. `outcome.md` asks the
architect to record it so it stops being an inference.

## Boundary rulings for `resolve_secret`

The verbatim docstring covers three cases and leaves three edges undecided. The test
contract needs them decided, so:

- **Present-but-empty variable** → return the empty string. The variable exists; whether
  an empty credential is *useful* is the caller's problem, not the resolver's. Treating
  it as missing would make the resolver guess at a policy nothing states.
- **A bare `"$"`** → raise. It names no variable, so it is malformed rather than
  pointing at an absent one.
- **A string that does not start with `$`** → raise, per the docstring's "anything else".
  Note that *rejecting a non-`$` value on write* is a different mechanism, belongs to
  feature `006`, and is out of scope here; this is the read-side refusal only.

## Redaction, specifically here

The handler logs `code` and HTTP status. It does **not** log `detail`, because `detail`
is where later features put model references, tool names and ids, and a blanket
`detail`-dump would eventually carry something the rule forbids. `resolve_secret`'s
failure names the **variable**, never the value — that is DoD-11, and it is the one
place in this feature where the redaction rule has a directly testable consequence.

## Detail privacy rules later features inherit

Stated here because this step defines the class they bind to: `detail` never contains
another user's data or a count derived from it; never the body text of a disabled memo;
and **any id in `detail` is a decimal string**. No id reaches a `detail` in this feature,
so none of the three is testable yet — they are recorded, not asserted.
