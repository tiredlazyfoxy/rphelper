# Step 001 — The `sessions` table, its two errors and its pydantic models

## Goal

Declare the `sessions` table in the registry (D8), add the `session_not_found` (404) and
`setup_archived` (409) domain errors (D12), and add the three request/response models for
the session routes. Keep the backend test landmines that registering `sessions` touches
passing.

backend/app/db/schema.py
backend/app/errors.py
backend/app/models/sessions.py

## Test files

backend/tests/test_db_schema.py
backend/tests/test_sessions_models.py
backend/tests/test_admin_db_router.py

## Interface intent

**`db/schema.py`** (extended)

- **`sessions`**: a module-level `Table` literal bound to the one `metadata`, with exactly
  the eight columns of D8: the snowflake `id` primary key (the registry's id form),
  `user_id` (NOT NULL, FK `users.id`), `character_id` (NOT NULL, FK `characters.id`),
  `setup_id` (**nullable**, FK `setups.id`, no server default), `last_used_at` (Text, NOT
  NULL), `archived_at` (Text, nullable), `created_at` and `updated_at` (Text, NOT NULL).
  No FK carries an `ON DELETE` clause. Plus one non-unique index on
  `(user_id, character_id)`, in that order.

**`errors.py`** (extended)

- **`SessionNotFoundError`**: a `DomainError` subclass, code `session_not_found`, HTTP
  status 404, empty `detail`. Same shape as 009's `CharacterNotFoundError`.
- **`SetupArchivedError`**: a `DomainError` subclass, code `setup_archived`, HTTP status
  409, empty `detail`.

**`models/sessions.py`** (new)

- **`SessionResponse`**: response model with `id` and `character_id` (outbound
  snowflakes → decimal strings), `setup_id` (outbound snowflake or null), `setup_name`
  (string or null), `archived_at` (string or null), `last_used_at`, `created_at`,
  `updated_at`. No `user_id`.
- **`SessionListResponse`**: response model wrapping a list of `SessionResponse` under
  the key `sessions`.
- **`StartSessionRequest`**: request model, unknown keys ignored. One field, `setup_id`:
  optional, nullable, an inbound snowflake (decimal string → int); absent and `null` both
  mean "no setup". No `character_id` field (the parent comes from the path).

## Definition of done

1. `[test]` 011 adds `sessions` to the registry, and the 011 delta in
   `tests/test_db_schema.py` uses the same later-table-proof form as 009's and 010's deltas
   (009 `001` DoD-11, 010 `001` DoD-1; `001.context.md`). `sessions` is in
   `schema.metadata.tables`, and the assertion still holds when a later feature adds a
   table.
2. `[test]` `sessions` has exactly the columns `id`, `user_id`, `character_id`,
   `setup_id`, `last_used_at`, `archived_at`, `created_at`, `updated_at`. `id` is the
   primary key. `setup_id` and `archived_at` are nullable; every other column is NOT NULL.
   The table has **no** `title`, `partner_label`, `rp_language`, `preferred_language`,
   `model_ref`, `system_prompt`, `tools`, `status` or `state` column. (D8, D4,
   `data-model.md` `sessions`, R4 deferral)
3. `[test]` `sessions.user_id` is a foreign key to `users.id`, `character_id` to
   `characters.id`, and `setup_id` to `setups.id`. `setup_id` declares no server default.
   The table declares exactly one non-unique index whose columns are `user_id`,
   `character_id` in that order. (D8, R2)
4. `[test]` `metadata.create_all` on a fresh test engine creates `sessions`. A row with
   `setup_id` NULL inserts. A row whose `character_id` names no `characters` row fails, a
   row whose `setup_id` names no `setups` row fails, and a row whose `user_id` names no
   `users` row fails (all three FKs enforced). (R2)
5. `[test]` `SessionNotFoundError` is a `DomainError` with code `session_not_found` and
   HTTP status 404. Raised from a route on an application with the exception handlers
   registered, it answers 404 with the envelope `{ "error": { "code":
   "session_not_found", … , "detail": {} } }`. (D12, R5)
6. `[test]` `SetupArchivedError` is a `DomainError` with code `setup_archived` and HTTP
   status 409; raised from a route as above it answers 409 with that code and an empty
   `detail`. (D12)
7. `[test]` `SessionResponse` built from int `id`, `character_id` and `setup_id`
   serialises all three as the decimal strings of those ints. With `setup_id` `None`,
   `setup_name` `None` and `archived_at` `None` they serialise as JSON `null`. The
   serialised object has exactly the eight keys of the wire contract (`context.md`).
   `SessionListResponse` serialises as an object whose only key is `sessions`, holding the
   rows in the order given.
8. `[test]` `StartSessionRequest`: `{}` parses with `setup_id` unset/`None`;
   `{"setup_id": null}` parses the same; `{"setup_id": "7250000000000000001"}` parses to
   the int `7250000000000000001`; `{"setup_id": "abc"}` fails validation. Unknown keys
   (`character_id`, `user_id`, `last_used_at`, `title`) are ignored, not rejected, and none
   appears on the parsed model. (D2, R2)
9. `[test]` 006's, 009's and 010's existing registry-delta assertions in
   `tests/test_db_schema.py` still pass with `sessions` registered. If they subtract a
   "declared by later features" set, `sessions` is added to that set; if they already
   tolerate later tables they are left as they are. No other assertion changes.
10. `[test]` `tests/test_admin_db_router.py`'s undeclared-name expectations (404
    `unknown_table`) still pass with `sessions` registered. After 010 `001` DoD-9 its
    `UNDECLARED_NAMES` holds no planned table name, so nothing changes; **only if** it
    names `"sessions"` is that entry replaced by a name no feature will declare. No other
    entry or assertion changes.
11. `[manual/live]` Against an existing database that pre-dates 011 (with `characters` and
    `setups` created), the admin Database page lists `sessions` as missing, and **Create**
    brings it to in-sync. (D8, FEAT-005)
