## Why a state module for one GET

The screen has four outcomes (`loading`, `ready`, `not-found`, `failed`) and an
abort-aware load, which is exactly 009's `characterScreenState.ts` shape. Putting it in a
module keeps the component free of effect logic and gives `012` / `013` an obvious place to
grow the session's stream state. Kept separate from the workspace `SessionsState`: that one
is the tree's working list, and an archived session opened by URL is not in it.

## Why not read the session from `SessionsState`

The workspace list holds working sessions only (D5); an archived session reached by URL
would be missing, and a just-loaded tree may not be ready yet. One GET by id is the
single source for this screen, archived or not.
