# Step 002 — remap engine, and user and character import

## Goal

Add the id-remap engine and the shared write path (fresh ids, reference rewrite,
FTS ensure, two-pass self-references) to `services/transfer_import.py`. Then build
the roleplayer's `user` and `character` imports on it.

## Source files

- `backend/app/services/transfer_import.py`

## Test files

- `backend/tests/test_transfer_import_owned.py`

## Interface intent

- **Remap engine** (module-private). Takes:
  - a validated export (step 001);
  - a reference policy;
  - the id generator;
  - the caller's user id;
  - the connection, used only for the model-pair lookup.

  It returns the rows to insert per table, in `sorted_tables` order, with fresh ids
  and every reference rewritten under `context.md` §"Remap rules". It raises
  `ExportInvalidError(malformed_payload)` for a reference that resolves nowhere.
  - **Minting:** per table, in ascending old-id order.
  - **FK columns:** detected from the Table's own foreign keys. `users` targets
    map to the caller.
  - **`memos.scope_id`:** handled by scope.
  - **`model_server_id` / `model_name`:** kept only if the pair exists in
    `models`, otherwise both null.

  The **reference policy** is a small value naming what this granularity allows and
  how out-of-payload references resolve:
  - the allowed memo scopes;
  - the old user id that `user_id` / `scope='user'` refs must equal, or "any";
  - per-column overrides for out-of-payload FKs.

  Step 003 supplies its own policy, so the engine has no granularity `if` chain
  that 003 must edit.
- **Payload writer** (module-private). Inside the caller's transaction it:
  - calls 024's `ensure_fts_tables(connection)` before the first insert;
  - inserts the remapped rows table by table in `sorted_tables` order;
  - inserts each self-referencing FK column (today only `messages.related_to`) as
    null, then sets it by one UPDATE per referring row.

  Step 004 reuses it with preserved ids.
- **`import_owned`** (public). Takes a connection, the id generator, the caller's
  `user_id` and the raw envelope. It:
  - validates with accepted set {`user`, `character`};
  - applies the matching policy (`context.md` §"Remap rules");
  - writes everything in one `with connection.begin():` block;
  - never writes the payload `users` row.

  It returns an owned-import result carrying the granularity and the new character
  ids in ascending order.

## Definition of done

1. **DoD-1 [test]:** Importing caller A's own `user` export as caller B creates B
   rows such that the second export compares equal to the first in every column
   except ids and `user_id`:
   - the same number of characters, setups, sessions, messages and memos;
   - the same names, sheets, descriptions, texts, bodies, flags, `sort_key`s,
     `archived_at`, `created_at`, `updated_at`, `last_used_at` and `settled_at`;
   - each memo scope pointing at the corresponding imported row.

   Here "B's export after import" is compared with "A's export before" via the
   remap. (US-079.AC-2, UC-062)
2. **DoD-2 [test]:** After a `user` import, the caller's `users` row is unchanged
   in every column, including `username`, `rp_language` and `preferred_language`,
   even when the payload `users` row carries different values. No new `users` row
   exists. (US-136.AC-1)
3. **DoD-3 [test]:** Importing a `character` export creates exactly one new
   character, owned by the caller, with its setups, its sessions (archived ones
   included, R6), their messages, and its character-, setup- and session-scoped
   memos. Each memo's `scope_id` names the new row of the right table. The result's
   `character_ids` is that one new id. (US-080.AC-2, UC-063)
4. **DoD-4 [test]:** Every imported row has an id that differed from every id in
   the database before the import, and from every id in the payload. Importing the
   same export into the same account whose originals still exist leaves those
   originals byte-for-byte unchanged. (US-136.AC-1, US-136.AC-2)
5. **DoD-5 [test]:** Importing the same `character` export twice yields two
   characters with disjoint id sets across every table, and nothing warns or
   fails. (US-136.AC-2, brief Out)
6. **DoD-6 [test]:** Messages keep their order:
   - the imported messages of a session, ordered by new id, are in the same order
     as the originals ordered by old id;
   - every buried row's `related_to` names the new id of its own head;
   - the record rows and the zone rows each appear in the views
     (`settled_entries`, `current_zone`) exactly as the originals did.
7. **DoD-7 [test]:** A character and a session carrying a `(model_server_id,
   model_name)` pair that exists in this instance's `models` keep it. When the pair
   does not exist (or names an unknown server id), both columns are null after
   import. In both cases the both-or-neither CHECK holds.
8. **DoD-8 [test]:** Each of these gives `malformed_payload` and stores nothing:
   - a character payload whose `setups` row has a `character_id` not in the
     payload;
   - a session row whose `setup_id` names no payload setup;
   - a buried message whose `related_to` names no payload message;
   - a character-granularity memo with scope `user`;
   - a memo whose `scope='setup'` `scope_id` names no payload setup;
   - a `user` payload whose `characters` row carries a `user_id` other than the
     payload user's id.

   "Stores nothing" means the row counts of every `metadata` table are unchanged.
9. **DoD-9 [test]:** Every row the import writes carries the caller's `user_id`
   whatever `user_id` the payload carried. A second user's rows are untouched, and
   no row lands under them. (R5)
10. **DoD-10 [test]:** After an import on a database where `memo_fts` /
    `message_fts` did not exist beforehand, both exist, and:
    - an FTS `MATCH` on a token from an imported memo body returns that memo's
      **new** id;
    - a token from an imported record row returns its new id;
    - a token from an imported zone row returns nothing.

    No `memo_vec` / `session_vec` row is written, whether those tables exist or
    not. (U3)
11. **DoD-11 [test]:** A `session` or `database` envelope given to `import_owned`
    raises `wrong_granularity`.
12. **DoD-12 [manual/live]:** `mypy app` and `ruff check .` pass.
