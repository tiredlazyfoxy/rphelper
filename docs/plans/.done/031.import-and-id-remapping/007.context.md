## Gotcha — a file input inside a Menu dropdown loses its change event

The Mantine `Menu` dropdown unmounts when it closes, and clicking an item closes
it. A `FileButton` placed inside a `Menu.Item` therefore takes its hidden `<input
type="file">` with it. The picker opens from an element that no longer exists, so
the `change` event never reaches React.

So in `UserMenu`:

- render one hidden `<input type="file">` **outside** the `Menu`, with a `ref` and
  an accessible label (e.g. "Choose export file to import");
- have the "Import…" item's click call the input's `click()`;
- clear the input's value after each change.

`SessionsSection`'s button is not in a menu, so a Mantine `FileButton` (with its
`resetRef`) works there. `FileButton` ships in `@mantine/core` 7.17.8. The repo has
no dropzone and no `@mantine/modals`.

## Known existing-test fallout

New required props break existing tests:

- `UserMenu` gains `charactersState` and `sessionsState`, so `UserMenu.test.tsx`
  and 030's `UserMenu.export.test.tsx` must supply them.
- `SessionsSection` gains `sessionsState`, so 030's `SessionsSection.export.test.tsx`
  must supply it. 030's `CharacterScreen.export.test.tsx` must supply whatever
  `CharacterScreen` now needs to pass through.

These files are listed in Test files for that reason only. If any other existing
test breaks under the threading (e.g. a pre-030 `SessionsSection`, `CharacterScreen`,
`WorkspaceShell` or `App` test), that is a `SPEC` hand-back per `context.md` §"Test
conventions". Nobody edits an unlisted file.
