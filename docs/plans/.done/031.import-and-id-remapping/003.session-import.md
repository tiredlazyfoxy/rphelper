# Step 003 — import a session into a chosen character

## Goal

Add `import_session`, which imports a `session` export under a character the
caller chooses and owns. It reuses step 002's remap engine and payload writer
with a session policy:
- `character_id` becomes the target;
- `setup_id` becomes null;
- only session-scoped memos are allowed.

## Source files

- `backend/app/services/transfer_import.py`

## Test files

- `backend/tests/test_transfer_import_session.py`

## Interface intent

- **`import_session`** (public). Takes a connection, the id generator, the
  caller's `user_id`, the target `character_id` and the raw envelope. It:
  1. validates with accepted set {`session`};
  2. inside one `with connection.begin():` block, looks the target character up by
     `id` **and** `user_id`, archived or not. It raises `CharacterNotFoundError`
     when there is no such row;
  3. remaps under the session policy (below);
  4. writes through step 002's payload writer.

  It returns the new session's id.
- **Session reference policy** (module-private value):
  - the allowed memo scope set is {`session`}, and the target must be the payload
    session;
  - `sessions.character_id` becomes the target character's id;
  - `sessions.setup_id` becomes null, whatever the payload held;
  - every `user_id` becomes the caller, accepting any payload value;
  - the model pair follows the shared rule.

## Definition of done

1. **DoD-1 [test]:** Importing a `session` export into the caller's character C
   creates exactly one new session, under C, owned by the caller. It carries all
   of the original's messages (settled, buried and current-zone) in the same order,
   and its session-scoped memos re-pointed at the new session id. (UC-064)
2. **DoD-2 [test]:** The imported session's `character_id` is C, not the
   exported session's character. This holds even when that original character
   still exists in the same account. The original character gains no session and no
   memo. (US-082.AC-1)
3. **DoD-3 [test]:** The imported session's `setup_id` is null, even when the
   exported session had a setup. No setup row is created, and no setup-scoped memo
   is created. (US-082.AC-2)
4. **DoD-4 [test]:** The target may be archived. The import succeeds and the
   session lands under the archived character. (R6)
5. **DoD-5 [test]:** A target character owned by another user, and a nonexistent
   character id, each raise `CharacterNotFoundError`, and nothing is stored in any
   `metadata` table. (R5)
6. **DoD-6 [test]:** A session payload carrying a memo with scope `character`,
   `setup` or `user` (one case each), or a `session` memo whose `scope_id` is not
   the payload session's id, gives `malformed_payload` and stores nothing.
7. **DoD-7 [test]:** Importing the same session export twice into C yields two
   sessions with disjoint message and memo ids. The original session, if present,
   is untouched. (US-136.AC-1, US-136.AC-2)
8. **DoD-8 [test]:** The imported session preserves `archived_at`,
   `last_used_at`, `rp_language`, `preferred_language` and `system_prompt` as
   exported. Its model pair is kept or nulled per `context.md` §"Remap rules".
9. **DoD-9 [test]:** A `user` or `character` envelope given to `import_session`
   raises `wrong_granularity`. A well-formed `session` envelope with a wrong
   `schema_version` raises `schema_mismatch`, even for a foreign target: validation
   precedes the character lookup.
10. **DoD-10 [test]:** A token from an imported record row is found in
    `message_fts` under its new id. No `session_vec` row exists for the new
    session. (U3)
11. **DoD-11 [manual/live]:** `mypy app` and `ruff check .` pass.
