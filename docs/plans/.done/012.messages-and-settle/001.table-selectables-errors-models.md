# Step 001 — The `messages` table, its three selectables, five errors and the stream models

## Goal

Declare the `messages` table in the registry with its CHECK and two indexes, the three
named read selectables `settled_entries`, `current_zone` and `message_states` (D1, D7),
the five new domain errors (D13), and the request / response models of the stream routes
(Wire contract, D9).

## Source files

backend/app/db/schema.py
backend/app/errors.py
backend/app/models/stream.py

## Test files

backend/tests/test_db_schema.py

## Interface intent

**`db/schema.py`** (extended)

- **`messages`**: a module-level `Table` literal bound to the one `metadata`, with exactly
  the columns, nullability and foreign keys of `context.md` "The `messages` table"; one
  named CHECK constraint forbidding `related_to` and `settled_at` both set; one non-unique
  index on `(session_id, settled_at)` and one on `(related_to)`. No `ON DELETE`. Declared
  after `sessions`.
- **`settled_entries`**: a module-level named `select()` of every `messages` column where
  `settled_at` is not NULL. No session filter, no ordering.
- **`current_zone`**: a module-level named `select()` of every `messages` column where
  `related_to` is NULL and `settled_at` is NULL. No session filter, no ordering.
- **`message_states`**: a module-level named `select()` over `messages` projecting only
  `id`, `user_id`, `session_id`, `related_to`, `settled_at`. No filter, no ordering.
- The module docstring's sentence about "the two SQL views" is rewritten to say the stream
  read selectables live here and are Core selects, not SQL views (D1).

**`errors.py`** (extended) — five `DomainError` subclasses, each with its class-level code
and status, a fixed non-empty default message, and an empty `detail`:

- **`ZoneEmptyError`** — `zone_empty`, 409.
- **`ZoneNotEmptyError`** — `zone_not_empty`, 409.
- **`NothingToReopenError`** — `nothing_to_reopen`, 409.
- **`MessageNotEditableError`** — `message_not_editable`, 409.
- **`MessageNotFoundError`** — `message_not_found`, 404.

**`models/stream.py`** (new)

- **`MessageResponse`**: the wire `Message` (eight keys, `context.md`): `id` and
  `session_id` as outbound snowflakes, `role`, `kind` (string or null), `text`,
  `settled_at` (string or null), `created_at`, `updated_at`.
- **`EntryListResponse`**: wraps a list of `MessageResponse` under `entries`.
- **`ZoneResponse`**: wraps a list of `MessageResponse` under `messages`.
- **`AppendMessageRequest`**: one field `text` (non-blank, D9); unknown keys ignored.
- **`FilePartnerRequest`**: `kind`, which accepts exactly the string `"partner"` and is
  required, and `text` (non-blank); unknown keys ignored.
- **`EditMessageRequest`**: one field `text` (non-blank); unknown keys ignored.
- **`SettleResponse`**: `entry_id` (outbound snowflake), `kind` (`"turn"` or
  `"decision"`), `buried_ids` (list of outbound snowflakes).
- **`ReopenResponse`**: `reopened_id` (outbound snowflake), `restored_ids` (list of
  outbound snowflakes).
- The non-blank text rule is one shared annotated type or validator in this module, used
  by all three request models.

## Definition of done

1. `[test]` 012 adds `messages` to the registry, and the 012 delta in
   `tests/test_db_schema.py` uses the same later-table-proof form as the earlier deltas
   (`001.context.md`). `messages` is in `schema.metadata.tables`; 006's, 009's, 010's and
   011's deltas still pass.
2. `[test]` `messages` has exactly the columns `id`, `user_id`, `session_id`, `role`,
   `kind`, `text`, `related_to`, `settled_at`, `tool_name`, `tool_payload`, `created_at`,
   `updated_at`; `id` is the primary key; `kind`, `related_to`, `settled_at`, `tool_name`,
   `tool_payload` are nullable and every other column is NOT NULL. There is **no**
   `position`, `discussion_id`, `language` or `status` column. (`data-model.md`)
3. `[test]` `user_id` is a foreign key to `users.id`, `session_id` to `sessions.id`, and
   `related_to` to `messages.id`; none declares an `ON DELETE` action. The table declares
   exactly two non-unique indexes, one on `(session_id, settled_at)` in that order and one
   on `(related_to)`. (`data-model.md` indexes, archive rule)
4. `[test]` On a fresh `create_all` database with a user, character and session: a row
   with `related_to` NULL and `settled_at` set inserts; a row with `related_to` set (to an
   existing message id) and `settled_at` NULL inserts; a row with **both** set is
   rejected by the database. A row whose `session_id` names no session fails, and so does
   one whose `related_to` names no message. A row with `role` `'assistant'` and `kind`
   NULL inserts (no DB CHECK on `role` / `kind`). (CHECK, FKs)
5. `[test]` With one session holding a zone row (NULL/NULL), a settled row (NULL/set) and
   a buried row (set/NULL), executing `settled_entries` returns exactly the settled row;
   executing `current_zone` returns exactly the zone row; executing `message_states`
   returns all three. `settled_entries` and `current_zone` return every `messages` column
   (the same column names as the table); `message_states` returns exactly `id`,
   `user_id`, `session_id`, `related_to`, `settled_at`. (D1, D7, R11)
6. `[test]` Declaring the selectables executes no DDL: after `create_all`, the database
   contains no SQL view (`sqlite_master` holds no row of type `view`), and none of the
   three selectable names is a key of `metadata.tables`. (D1)
7. `[test]` Each of the five errors is a `DomainError` with its code and status
   (`zone_empty` 409, `zone_not_empty` 409, `nothing_to_reopen` 409,
   `message_not_editable` 409, `message_not_found` 404). Raised with no arguments from a
   route on an application with the exception handlers registered, each answers its status
   with the envelope `{ "error": { "code": …, "message": <non-empty string>, "detail": {} } }`.
   (D13)
8. `[test]` `MessageResponse` built from int `id` and `session_id` serialises both as the
   decimal strings of those ints; `kind` and `settled_at` `None` serialise as JSON `null`;
   the serialised object has exactly the eight wire keys and no `user_id`, `related_to`,
   `tool_name` or `tool_payload`. `EntryListResponse` serialises with the single key
   `entries`, `ZoneResponse` with the single key `messages`, each preserving the given
   order.
9. `[test]` `SettleResponse` serialises `entry_id` and every element of `buried_ids` as
   decimal strings (an empty list stays `[]`); `ReopenResponse` does the same for
   `reopened_id` and `restored_ids`.
10. `[test]` `AppendMessageRequest` and `EditMessageRequest`: `{"text": "x"}` parses;
    `{"text": "  two  spaces  "}` parses with the text **unchanged** (not trimmed);
    `{}`, `{"text": ""}`, `{"text": "   \n\t"}` and `{"text": null}` fail validation; a
    text of one million characters parses (no maximum). An unknown key (`role`,
    `kind`, `session_id`) is ignored, not rejected, and does not appear on the parsed
    model. (D9, R10, US-035.AC-2)
11. `[test]` `FilePartnerRequest`: `{"kind": "partner", "text": "x"}` parses; `kind`
    `"turn"`, `"decision"`, `"Partner"`, `null`, and an absent `kind` each fail
    validation; a blank `text` fails as in DoD-10; text containing `((ooc))` parses with
    the parentheses intact. (R11 single exception, US-121.AC-2, D9)
12. `[test]` `tests/test_admin_db_router.py`'s undeclared-name expectations (404
    `unknown_table`) still pass with `messages` registered. **Only if** its
    `UNDECLARED_NAMES` names `"messages"` is that entry replaced by a name no feature will
    declare; no other entry or assertion changes.
13. `[manual/live]` Against an existing database that pre-dates 012 (with `sessions`
    present), the admin Database page lists `messages` as missing, and **Create** brings
    it to in sync. (FEAT-005)
