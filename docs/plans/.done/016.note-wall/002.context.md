## The orders, concretely

- "The current order" means the ids of `memos` in array order. The new note (`newNote`)
  is never part of it: it has no id.
- **Optimistic write**: build the new `memos` array from the held rows, in the given
  order. Ids given but not held are ignored. Held ids not given keep their place at the
  front; callers always pass the whole level, but the effect stays total.
- **Success merge**: start from the response order. For each returned id that is held,
  take the newer of returned and held (by `updated_at`). Drop returned ids not held. Put
  held ids that are absent from the response first, in their current relative order.
- **Revert**: sort the current `memos` by each id's index in the remembered pre-drop
  order. Ids not in the remembered order go first, in their current relative order.

The three rules are total functions of arrays of ids and rows. A private pure helper (or
helpers) is the natural shape and is not frozen.

## Why `reorderFailure` is level-wide

A reorder belongs to the level, not to a note: the request names the whole level and its
failure moves every note back. The text sits in the group (`003`), not under a note. It
does not use 015's per-note failure slots and does not clear them.

## What the effect must not do

- Refetch the level or the chain afterwards (015 D5; D7's 409 case included).
- Touch `sort_key` locally before the response. The optimistic write moves array
  positions only; `sort_key`s change when the server's rows are applied.
- Pass a signal, or abort (a reorder that started must land, 015 D5).
