# Step 001 — Backend: new-note-first allocation and the level reorder route

## Goal

Make `create_memo` allocate a new note's `sort_key` one below the level's minimum, so a
new note lists first (D5). Add `reorder_memos`, which rewrites one level's whole order as
0..n-1 in one owner-scoped transaction and refuses a stale set with the new
`memo_order_mismatch` (409) error (D6). Expose it as `PUT /api/memos/order` on 015's
memos router. Amend the 015 assertions the allocation change breaks.

## Interface intent

**`errors.py`** (extended)

- **`MemoOrderMismatchError`**: a `DomainError` subclass, code `memo_order_mismatch`,
  HTTP status 409, empty `detail`, with a fixed non-empty default message. Same shape as
  015's `MemoNotFoundError`.

**`models/memos.py`** (extended)

- **The reorder request model**: unknown keys ignored. Fields: `scope` (015's scope
  literal, required), `scope_id` (optional, nullable inbound snowflake, the same form
  `CreateMemoRequest` uses), `memo_ids` (required list of inbound snowflakes, possibly
  empty). A non-user `scope` without `scope_id` fails validation, as on create. The
  response reuses 015's `MemoListResponse`; no new response model.

**`services/memos.py`** (extended)

- **`create_memo`** (changed, signature unchanged): the allocation becomes one less than
  the smallest `sort_key` among the caller's notes at the same stored
  `(scope, scope_id)`, or 0 when there are none. It is still computed inside the create
  transaction, after the target check and before id minting. Nothing else in create
  changes.
- **`reorder_memos`** (new): takes the connection, `user_id` (required positional), a
  `scope`, a `scope_id` (ignored for `"user"`, whose stored scope id is the caller) and
  the ordered list of memo ids (ints). In **one** write transaction it:
  1. checks the target level exactly as create does (that level's not-found error);
  2. reads the caller's note ids at that level;
  3. raises `MemoOrderMismatchError` unless the given ids are exactly that set with no
     duplicate;
  4. sets each listed note's `sort_key` to its index (0..n-1) in the given order, writing
     **no other column** (`updated_at` included, D6);
  5. returns the level's notes as `Memo` values ordered by `sort_key`, then `id`.

  A refusal writes nothing. Every statement is owner-scoped in its own `WHERE` (R5).

**`routers/memos.py`** (extended)

- **Reorder handler**: `PUT /api/memos/order`, status 200, under the router's existing
  `require_user`. Takes the reorder request model, the current user and the connection.
  Passes `scope_id` as `None` for `"user"` and the request's value otherwise. Calls
  `reorder_memos` and answers a `MemoListResponse` in the returned order. It is declared
  in the module **before** the `PATCH` / `DELETE /api/memos/{memo_id}` handlers. It
  catches nothing and holds no SQL. `main.py` is not edited: the router is already
  registered (015 `004`).

## Definition of done

1. `[test]` Allocation (amends 015 `002` DoD-4): three creates at one level return
   `sort_key` 0, -1, -2 in that order; a create at a different level of the same caller
   returns 0. With raw-inserted rows of the caller at a level holding `sort_key` 2 and 5,
   the next create there returns 1. A raw-inserted row of **another user** at the same
   `(scope, scope_id)` with `sort_key` -40 does not affect the caller's allocation. After
   deleting the caller's **lowest** note, the next create returns the remaining minimum
   minus one. (D5, R5)
2. `[test]` `list_memos` after three creates at one level returns them **newest first**
   (`sort_key` -2, -1, 0). (D5; US-102 — the persisted order a new note takes)
3. `[test]` `reorder_memos` with the level's ids in a new order returns exactly those
   notes in that order with `sort_key` 0..n-1. A following `list_memos` returns the same
   order. Each note's `body`, `is_enabled`, `is_forced`, `scope`, `scope_id`,
   `created_at` **and `updated_at`** are unchanged. Notes of the caller's other levels
   keep their `sort_key`s. (UC-076, US-102, D6)
4. `[test]` At each of the four levels (user; the caller's character; setup; session)
   `reorder_memos` succeeds. At `"user"` a supplied `scope_id` naming some other number
   is ignored: the caller's user-level notes are reordered. A level with no notes accepts
   an empty list and returns `[]`. (UC-076, R2)
5. `[test]` `reorder_memos` raises `MemoOrderMismatchError` and changes no row's
   `sort_key` when the given ids: omit one of the level's notes; add a note of another of
   the caller's levels; add another user's note; add an id that exists for nobody; repeat
   an id (with the set otherwise complete). (US-103.AC-2 — one request is one level; R5;
   D6)
6. `[test]` `reorder_memos` with a character, setup or session id that is another user's,
   or nobody's, raises `CharacterNotFoundError`, `SetupNotFoundError` or
   `SessionNotFoundError` respectively, and changes nothing. With a raw-inserted row of
   another user at the same `(scope, scope_id)`, that row's `sort_key` is unchanged after
   the caller's reorder. (R5, D6)
7. `[test]` After a refused `reorder_memos` (each of DoD-5 / DoD-6's failures) the
   connection is not in a transaction, so a following `connection.begin()` succeeds.
8. `[test]` `MemoOrderMismatchError` is a `DomainError` with code `memo_order_mismatch`
   and HTTP status 409. Raised from a route on an application with the exception handlers
   registered, it answers 409 with
   `{ "error": { "code": "memo_order_mismatch", "message": <non-empty>, "detail": {} } }`.
   (D6)
9. `[test]` The reorder request model:
   `{"scope": "character", "scope_id": "7250000000000000001", "memo_ids": ["7250000000000000101", "7250000000000000102"]}`
   parses with `scope_id` the int and `memo_ids` the two ints in order;
   `{"scope": "user", "memo_ids": []}` parses; `{"scope": "character", "memo_ids": []}`
   fails; `{"scope": "world", "scope_id": "1", "memo_ids": []}` fails; a missing
   `memo_ids`, `"memo_ids": "7"` and `"memo_ids": ["abc"]` each fail; unknown keys
   (`user_id`, `sort_key`) are ignored. (D6)
10. `[test]` Route, success: a signed-in roleplayer with three notes at a session level
    (created through `POST /api/memos`) sends `PUT /api/memos/order` with those ids
    reversed. The answer is **200** `{"memos": [...]}` in that order, each object with
    exactly the nine wire keys, `id`s as decimal strings, and `sort_key` 0, 1, 2.
    `GET /api/memos?scope=session&scope_id=<X>` then lists that order, and
    `GET /api/sessions/<X>/memo-chain`'s session level holds that order. (UC-076, US-102)
11. `[test]` Route, failures. With no login cookie → 401 `not_authenticated`. User B
    reordering A's character, setup or session level → 404 `character_not_found` /
    `setup_not_found` / `session_not_found`. A `memo_ids` that omits a note, includes a
    note of another level or of user B, or repeats an id → **409**
    `memo_order_mismatch`. Each such body has an empty `detail`, and afterwards A's
    listing order is unchanged. A missing `memo_ids`, a non-numeric id, `scope` `"world"`,
    or a non-user scope without `scope_id` → 422, nothing changed. (US-103.AC-2, R5, D6)
12. `[test]` Amends 015 `004` DoD-14: three notes created at one level through the route
    list **newest first** with `sort_key` -2, -1, 0. After deleting the middle one, the
    next create answers `sort_key` -3 and lists first. (D5)
13. `[test]` The existing memo routes still answer with the reorder route declared:
    `PATCH /api/memos/<id>` with `{"body": "y"}` answers 200, `DELETE /api/memos/<id>`
    answers 204, and `GET /api/memos?scope=user` answers 200. (D6, route order)
14. `[test]` The source text of `app/services/memos.py` still contains no `fastapi`
    import and no import from any `app.services.` module (015 `002` DoD-15 holds), and
    `app/routers/memos.py` contains no SQL construct (`select(`, `update(`, `insert(`,
    `delete(`). (015 D11)
15. `[manual/live]` Against a running dev backend with 015 delivered, `curl` a
    `PUT /api/memos/order` with a roleplayer's cookie reversing two user-level notes. It
    answers 200 with the new order, and the order survives a re-`GET`.
