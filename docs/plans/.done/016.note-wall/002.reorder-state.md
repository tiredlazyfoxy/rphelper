# Step 002 — The reorder call and the level state's optimistic reorder

## Goal

Add `apiPut` to the shared client and `reorderMemos` to `memosApi.ts`. Give
`MemoLevelState` a reorder effect: it shows the dropped order immediately, sends the
whole level's order, applies the server's rows on success, and on failure reverts to the
pre-drop order with an inline failure (D7). While the request is in flight it refuses
further reorders in that level. Make a saved new note **prepend** to its level (D5).

## Interface intent

**`shared/api.ts`** (extended)

- **`apiPut`**: the same shape as `apiPatch`: a path, an optional JSON body and an
  optional signal. It sends a `PUT`, resolves to the parsed body (or `undefined` on 204),
  and throws the client's `ApiError` on every failure exactly as the other verbs do (D12).

**`app/memosApi.ts`** (extended)

- **`reorderMemos`**: takes a scope, a scope id (string, or `null` for the user level)
  and the ordered memo ids (strings). Sends `PUT /api/memos/order` with a JSON object of
  exactly `scope`, `scope_id` (`null` for the user level) and `memo_ids`. Resolves to the
  unwrapped `memos` array in the order received. Takes **no** signal (015 D5: mutations
  are never aborted). Failures are the client's `ApiError`s, rethrown unchanged.

**`app/memoLevelState.ts`** (extended)

- **`MemoLevelState`** gains two observable fields: whether a reorder is in flight
  (starts false), and the level's reorder failure text or `null` (starts `null`). The
  skeleton names them.
- **`isReorderInFlight`**: pure derivation. Takes the state; true while a reorder awaits
  its response.
- **`reorderFailure`**: pure derivation. Takes the state; the failure text or `null`.
- **`reorderMemoLevel`**: effect. Takes the state and the level's saved note ids in their
  new order.
  - It does nothing (no request, no write) when a reorder is already in flight, or when
    the given order equals the current one.
  - Otherwise, in one action, it remembers the current id order, rewrites `memos` into
    the given order (**optimistic**, D7), marks the reorder in flight and clears the
    reorder failure. It then calls `reorderMemos` with the level's scope and scope id.
  - **On success**, the level takes the returned order, merged by D7's rules: each
    returned row is applied only if its `updated_at` is not older than the held row's,
    and otherwise the held row is kept in that position. A held note absent from the
    response stays, placed first. A returned row not held is not inserted.
  - **On failure**, the notes return to the remembered relative order, applied to the
    level as it now is. A note added meanwhile stays first, and a note removed meanwhile
    stays removed. The reorder failure becomes **"Could not reorder the notes."**.
  - Either way the in-flight mark is cleared. It never rejects. It passes no signal.
- **`saveNewNote`** (changed, signature unchanged): on a successful create the returned
  row is **prepended** to `memos` (first entry) instead of appended. Everything else in
  its 015 contract is unchanged.

## Definition of done

1. `[test]` `apiPut("/api/x", { a: 1 })` sends method `PUT` to `/api/x` with the JSON body
   `{"a": 1}` and a JSON content type, and resolves to the parsed response body. A
   non-2xx envelope rejects with an `ApiError` carrying the backend's `code` and status.
   A transport failure rejects with code `client_transport_failed`. (D12;
   `frontend-structure.md` "Every failure is an `ApiError`")
2. `[test]` `reorderMemos("character", "7250000000000000001", ["7250000000000000102", "7250000000000000101"])`
   sends `PUT /api/memos/order` with the JSON body exactly
   `{"scope": "character", "scope_id": "7250000000000000001", "memo_ids": ["7250000000000000102", "7250000000000000101"]}`.
   `reorderMemos("user", null, [...])` sends `"scope_id": null`. Each resolves to the
   response's `memos` array in its order, every `id` the identical string the payload
   carried. (UC-076, US-102)
3. `[test]` `reorderMemos` calls `fetch` with no abort signal, and a 409 envelope with code
   `memo_order_mismatch` makes it reject with an `ApiError` of that code. (015 D5; D6)
4. `[test]` A fresh `MemoLevelState` has `isReorderInFlight` false and `reorderFailure`
   `null`.
5. `[test]` On a ready level holding notes A, B, C, `reorderMemoLevel(state, [C, A, B])`
   **immediately**, before the response, leaves `memos` in the order C, A, B with
   `isReorderInFlight` true. It sends exactly one `PUT /api/memos/order` whose `memo_ids`
   are C, A, B. (U1/D7 — optimistic; US-102)
6. `[test]` When that request answers 200 with the rows in order C, A, B carrying
   `sort_key` 0, 1, 2 (and `updated_at` not older), the level holds those rows in that
   order, `isReorderInFlight` is false and `reorderFailure` is `null`. No listing or chain
   request follows. (D7)
7. `[test]` When that request fails (a 500, a transport failure, and a 409
   `memo_order_mismatch`, each as its own case), the level returns to A, B, C,
   `reorderFailure` is "Could not reorder the notes.", `isReorderInFlight` is false, and
   the call resolves without throwing. A later successful reorder clears the failure.
   (U1/D7 — revert on failure)
8. `[test]` While a reorder is pending, a second `reorderMemoLevel` call sends no request
   and leaves the optimistic order as it is. A call whose order equals the current order
   sends no request. (U1 — further drags disabled in flight)
9. `[test]` Concurrency on revert: while a reorder of A, B, C to C, A, B is pending, a new
   note D is saved (`saveNewNote` resolves with a 201). When the reorder then fails, the
   level is D, A, B, C (D kept first, the rest in pre-drop order). In a second case a
   note B deleted meanwhile (its `saveNote` with blank text resolved 204) stays absent
   after the revert. (D7)
10. `[test]` Concurrency on success: a returned row whose `updated_at` is older than the
    held row's does not replace the held row's body or flags, yet the held row sits at the
    returned position. A held note absent from the response stays first. A returned id no
    longer held is not inserted. (D7, 015 D5 apply-a-row)
11. `[test]` Amends 015 `006` DoD-10: after a successful `saveNewNote` on a level already
    holding notes, the returned row is the **first** entry of `memos`, with `is_enabled`
    true and `is_forced` false, and `newNote` is null. The other 015 `006` DoD-10 clauses
    (exact POST body, pending behaviour, text typed during the request) hold unchanged.
    (D5, US-053.AC-1)
12. `[test]` An `autorun` reading `memos` re-runs after the optimistic write and after the
    revert, and one reading `reorderFailure` re-runs when it is set (writes are MobX
    actions).
