# Step 004 — The tool seam and the three declarations

## Goal

Create `app/services/tools/`: the three tool declarations (D5), and the dispatch seam `026` /
`027` / `028` bind to — `ToolScope`, `ToolOutcome`, the `Tool` protocol, the (empty) production
registry, the offered-tools rule, and dispatch of one provider tool call into a frame, a model
message and a persisted tool row (D6, D7). This closes the brief's open question.

## Interface intent

**`app/services/tools/definitions.py`** (new)

- **Three declarations**, as JSON-ready OpenAI tool objects
  `{"type": "function", "function": {"name", "description", "parameters"}}`, for
  `memo_search`, `session_search`, `web_search`, plus an ordered collection of them in that
  order. Each `parameters` is a JSON-schema object with exactly one property, `query`
  (string, with a description), `required: ["query"]`, and no additional properties.
  Descriptions are fixed English: `memo_search` — the roleplayer's searchable notes for this
  session; `session_search` — past sessions of the same character, by meaning; `web_search` —
  only for its three justified uses (a real-world fact; an idiom or naturalness check; a
  lookup the roleplayer asked for directly) (`llm-and-streaming.md` "`web_search`").
  Declarations only: no behaviour.

**`app/services/tools/seam.py`** (new)

- **`ToolScope`** (frozen): `user_id`, `session_id`, `character_id`, `setup_id` (or none).
- **`build_tool_scope`**: connection, user id, session id → `ToolScope`, from
  `sessions.get_session` (owner-scoped; missing or foreign → `SessionNotFoundError`; an
  archived session is fine). The only constructor the loop uses.
- **`ToolOutcome`** (frozen): `content`, `summary`.
- **`Tool`** (protocol): `name`; async `run(scope, connection, arguments)` → `ToolOutcome`,
  `arguments` being the parsed JSON object.
- **The production registry**: an empty, read-only name → `Tool` mapping.
- **`offered_tools`**: takes the session's resolved configuration (017) and a registry;
  returns the offered declarations in declaration order (D5): a declaration is offered iff
  its `tool_*` switch's resolved value is true and its name is in the registry.
- **`tool_start_frame`**: one `ToolCall` (002) → 019's tool-start frame with tool = the
  call's name, call id verbatim, args = the arguments parsed as a JSON object, or `{}` when
  they do not parse or are not an object.
- **`dispatch`** (async): inputs: the `ToolCall`, the `ToolScope`, the offered tools' names,
  the registry, the engine, the id generator. Returns a **dispatch result** holding the frame
  to emit (019's tool-result or tool-fail frame) and the tool `ChatMessage` to append (role
  tool, `tool_call_id` = the call id). Per D6:
  - not offered / not registered, or arguments not a JSON object → failure, `run` not called;
  - otherwise opens a connection from the engine, awaits `run(scope, connection, parsed
    arguments)`, closes the connection whatever happens; an `Exception` → failure; an outcome
    → success;
  - failure: frame `tool_fail(name, call_id, "tool_failed")` (code from `ToolFailedError`),
    message content = the failed literal; success: frame `tool_result(name, call_id,
    summary)`, message content = `content`;
  - before returning, writes the tool row (D7) with `append_tool_message` on a short-lived
    connection of its own; a write failure is logged (session id, tool name, exception class)
    and swallowed. A failure path logs the tool name, call id and exception class only;
  - a cancellation propagates: no failure handling, no row.

**`app/services/tools/__init__.py`** (new): package marker; may re-export the seam's public
names.

## Definition of done

1. `[test]` The declarations are exactly three, ordered `memo_search`, `session_search`,
   `web_search`; each is `{"type":"function","function":{…}}` whose `name` matches, whose
   `description` is a non-empty string, and whose `parameters` has `type` `object`,
   `properties` with exactly the key `query` (type `string`), `required` `["query"]`. No
   declaration's parameters mention `user_id`, `session_id`, `character_id`, `setup_id` or
   `scope` anywhere. (R9, D5, D6)
2. `[test]` The production registry is empty, and `offered_tools` over it with all three
   switches on returns an empty list. (D5, U3)
3. `[test]` With a registry holding fakes for `memo_search` and `web_search` and switches
   memo on / session on / web off, `offered_tools` returns exactly the `memo_search`
   declaration; with all three on and all three registered it returns all three in
   declaration order; a registered name outside the three is never returned. (D5, US-062.AC-1,
   R9)
4. `[test]` `build_tool_scope` on an owned session with a setup returns that user id, session
   id, its character id and setup id; on one without a setup, `setup_id` is `None`; on another
   user's session and on an unknown id it raises `SessionNotFoundError`; an archived session
   builds normally. (R5, FEAT-019, R6)
5. `[test]` `tool_start_frame` for arguments `'{"query":"inn"}'` carries args `{"query":"inn"}`
   and the call id verbatim (e.g. `"call_9f2"`); for `'not json'` and for `'[1,2]'` it carries
   args `{}`. (D6)
6. `[test]` Success: a fake `memo_search` returning content `C` and summary `S` → the result's
   frame is tool-result (`memo_search`, the call id, `S`); its message is role tool with that
   `tool_call_id` and content `C`; one zone row now exists with role `tool`, text `S`,
   `tool_name` `memo_search`, and `tool_payload` parsing to
   `{"call_id":…,"arguments":<raw string>,"status":"ok","content":"C"}`. The fake received
   the built `ToolScope` and the parsed arguments mapping, and the connection it received is
   closed after dispatch. (D6, D7)
7. `[test]` Failures — (a) a name registered but not offered, (b) an unknown name, (c)
   arguments `'{"query":'`, (d) a fake whose `run` raises `RuntimeError` — each give a
   tool-fail frame with code `tool_failed`, a tool message with content exactly
   `The tool failed. Continue without its result.`, and one tool row with text exactly
   `The tool failed.` and payload `{"call_id":…,"arguments":<raw string>,"status":"failed","code":"tool_failed"}`;
   `dispatch` itself raises nothing. In (a)–(c) the fake's `run` is never called. (R9, UC-051,
   UC-053, D6, D7)
8. `[test]` Arguments `'{"query":"x","user_id":"<other user id>","session_id":"<other>"}'`
   reach the fake only inside its arguments mapping; the `ToolScope` it receives still names
   the caller's user and session. (R5, D6)
9. `[test]` A fake whose `run` awaits forever, dispatched in a task that is then cancelled:
   awaiting the task raises `CancelledError`, no tool row is written, and the connection the
   fake received is closed. (`llm-and-streaming.md` consequence 4; US-133.AC-1 is a named
   divergence and is not bound)
10. `[test]` Source conventions: `seam.py` imports no `fastapi` and, from `app.services`,
    only `sessions`, `messages`, `configuration` (types only), `llm.chat`, `llm.frames` and
    `tools.definitions`; `definitions.py` imports nothing from `app`. (D15)
