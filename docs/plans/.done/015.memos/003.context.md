## The two statements

| Statement | Shape |
|---|---|
| session read | `SELECT sessions.character_id, sessions.setup_id FROM sessions WHERE id = :session_id AND user_id = :user_id` — no `archived_at` predicate (D8); no row → `SessionNotFoundError` |
| memo read | `SELECT <all memos columns> FROM memos WHERE memos.user_id = :user_id AND ( (scope = 'user' AND scope_id = :user_id) OR (scope = 'character' AND scope_id = :character_id) [OR (scope = 'setup' AND scope_id = :setup_id)] OR (scope = 'session' AND scope_id = :session_id) ) ORDER BY sort_key, id` |

The bracketed term is **built only when** `setup_id` is not NULL: the list of OR-terms is
assembled from the levels that exist, and nothing else differs between the two cases
(R2's own sketch, `domain-rules.md`). Do not write `scope_id = NULL` or a sentinel; do not
issue a second query for the no-setup case.

The setup is read from `sessions.setup_id` as stored. An archived setup is still the
session's setup (010 D3, 011 D10), so its level is present. No ownership check on the setup
row itself is needed: `memos.user_id = :user_id` already bounds every row returned.

## Grouping

SQL filters (owner and levels) and orders (`sort_key, id`). Python only **buckets** the
returned rows by `scope` into the fixed level list built from the session read — user,
character, setup if present, session — so a level with no rows is still present with an
empty list. Bucketing is not owner filtering; R5's "never filter in Python" is about the
owner predicate, which stays in SQL.
