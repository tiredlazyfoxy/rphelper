# Step 004 — The settled-entry edit effect and the copy-out effect

## Goal

Add to `app/streamState.ts` the `editEntry` effect — commit a settled entry's edit through
`PATCH`, replace that one row in `entries` on success, re-read on failure (D10) — and add
`app/copyOut.ts`, which puts a text on the clipboard as plain text with the insecure-origin
fallback and makes no request (D8, D9, UC-030).

## Source files

frontend/src/app/streamState.ts
frontend/src/app/copyOut.ts

## Test files

frontend/tests/app/entryEffects.test.ts

## Interface intent

**`app/streamState.ts`** (extended — 013 `002` / `003`)

- **`editEntry`**: free function taking the `StreamState`, the entry's id (string), the
  edited text and an optional signal; resolves to whether the editor may close; never
  rejects; writes inside `runInAction`; writes nothing and calls no `notifyFailure` once
  the signal is aborted (then resolves false). Does **not** set `busy`.
  - Blank text → no request, resolves true (revert).
  - Text identical to the held entry's current text → no request, resolves true.
  - Otherwise `editMessage` (013 `001`) with the text **verbatim**:
    - success with a **settled** row (`settled_at` not null) → replace the entry with that
      id in `entries` by the response, every other entry and the order untouched — the id
      sequence is unchanged, so `kindOverride` is untouched; resolves true;
    - success with a **non-settled** row (`settled_at` null — re-opened elsewhere) →
      re-read the entries (through `applyEntries`) and the zone; resolves true; no
      `notifyFailure`;
    - failure → `notifyFailure(error)`, re-read the entries through `applyEntries`,
      resolves false. A failed re-read calls `notifyFailure` with its own error and leaves
      `entries` as it was (013 `003`'s posture).

**`app/copyOut.ts`** (new)

- **`copyAsPlainText`**: takes a text; converts it with `toPlainText` (`002`) and writes
  the result to the system clipboard; resolves to whether the copy succeeded; never
  rejects; makes **no network request** and writes no state.
  - When `navigator.clipboard` with `writeText` exists → use it. A rejection →
    `notifyFailure` with the rejection value; resolves false.
  - When it does not exist (non-secure origin, D9) → the fallback: a temporary textarea
    holding the plain text, attached to the document off-screen and read-only, selected,
    `document.execCommand("copy")`; the textarea is removed afterwards **whatever happens**,
    and focus is returned to the element that held it before. `execCommand` returning
    false or throwing → `notifyFailure` (with the thrown value, or an `Error` whose
    message is a fixed sentence of the coder's choice); resolves false.
  - Success raises nothing (no notification of any kind).

## Definition of done

1. `[test]` `editEntry` on a held `turn` entry with changed text sends exactly `PATCH
   /api/messages/<id>` with `{"text": <text>}`; the served row (kind `turn`,
   `settled_at` set) replaces that entry only — every other entry's id and text, and the
   order, are unchanged; no GET is made; resolves true; `notifyFailure` not called.
   (US-110.AC-1, US-032.AC-1, D10)
2. `[test]` The same holds for a `partner` entry (served kind `partner`) and a `decision`
   entry edited to `"Skip to morning."` (served kind `decision`). (US-109.AC-1,
   US-110.AC-1, R12)
3. `[test]` The text is sent verbatim: `"  She ((really)) waits.  "` is the exact `text`
   in the PATCH body (no trimming, no stripping). (R12)
4. `[test]` Blank text (`""`, `"  \n"`) or text identical to the held entry's text makes
   no request and resolves true. (D10)
5. `[test]` With `kindOverride` set by `chooseKind`, a successful `editEntry` leaves
   `kindOverride` and `effectiveKind` unchanged. (D10, 013 D8)
6. `[test]` A 409 `message_not_editable` failure calls `notifyFailure` once with an
   `ApiError` of that code, re-reads `GET /api/sessions/<id>/entries` (so `entries` is the
   served list), makes no zone request, and resolves false. (D10, R10)
7. `[test]` A success whose served row has `settled_at` null re-reads both `GET …/entries`
   and `GET …/zone`, does not put the served row into `entries` itself, resolves true and
   calls no `notifyFailure`. (D10)
8. `[test]` With the signal aborted before the PATCH settles, `editEntry` writes nothing
   to `entries` and calls no `notifyFailure`; `busy` stays false throughout every
   `editEntry` call. (D10, 013 D15)
9. `[test]` `copyAsPlainText("# Scene\n\n*She smiles* and **waits**.")` with a stubbed
   `navigator.clipboard.writeText` writes exactly `"Scene\n\nShe smiles and waits."`,
   resolves true, makes **no** `fetch` call and calls no `notifyFailure`. (US-124.AC-1,
   US-033.AC-1, UC-030, UC-082)
10. `[test]` `writeText` rejecting calls `notifyFailure` once with the rejection value and
    resolves false (does not reject). (D9)
11. `[test]` With `navigator.clipboard` absent and `document.execCommand` stubbed to
    return true: at the moment `execCommand("copy")` is called a textarea attached to the
    document holds exactly the plain text; afterwards no such textarea remains in the
    document, focus is back on the element focused before the call, and the result is
    true. (D9)
12. `[test]` With `navigator.clipboard` absent and `execCommand` returning false (and
    again throwing): `notifyFailure` is called once, the textarea is removed, and the
    result is false. (D9)
