## Shape of one entry

```
listitem  (ref = merged hover + focus-within refs; key = entry id)
  header  Group: kind label · actions Group [data-revealed, opacity]
                                   Edit entry | Copy as plain text (turn) | Re-open (last)
  body    MessageBody by kind  — or —  Textarea "Edit entry text" while editing
```

013 `004` put the re-open control in the last entry's header; it now sits inside the
actions group, so it is revealed with the others. Its presence / absence rule, its
`disabled` while `busy` and its `reopenLast` call are unchanged — 013's DoD-10 / DoD-11
assert presence in the DOM and pressing, both of which hold for an opacity-0 control.

## jsdom and the hooks

- `useHover` listens to native `mouseenter` / `mouseleave` on the ref'd element;
  Testing Library's `fireEvent.mouseEnter` / `mouseLeave` dispatch them.
- `useFocusWithin` listens to `focusin` / `focusout`; `element.focus()` and
  `element.blur()` (inside `act`) dispatch them. Blurring to `document.body` leaves the
  item.
- `useMediaQuery("(hover: none)")` in jsdom reads `window.matchMedia`, which Mantine's
  provider already requires in the test environment, so the existing setup's stub answers
  it (no match → hover-capable). **If `tests/setup.ts` turns out not to provide
  `matchMedia`, stop and hand back** — `tests/setup.ts` is not in this step's scope.

## Blur ordering

Pressing another control in the same entry (e.g. "Copy as plain text") while the editor is
open first blurs the textarea, which commits — the same as 013's zone editor. Copy then
copies the **stored** text, which is the committed text only once the PATCH has resolved;
that race is accepted (the copy reflects the record as it stands).
