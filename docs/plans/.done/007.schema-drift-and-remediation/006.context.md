## The confirm's trigger condition, stated exactly

**Lossy = the row's extra-column list is non-empty.** Nothing else triggers it — not a
changed type, not a missing column, not a missing table. `context.md` D7 is the authority
and D5 says why: a rebuild carries across every column the registry still declares, so the
**only** data that disappears is the data in the columns the registry no longer declares,
and those are precisely the ones the sentence names.

Two adjacent cases that are **not** confirmed, recorded so nobody widens the trigger:

- **A retype whose data will not cast** and **a NOT NULL tightening over existing NULLs**
  are not silent losses — they **fail** the rebuild (step `003` DoD-11), the transaction
  rolls back, the table is left exactly as it was, and the administrator sees
  `schema_apply_failed` in the inline `Alert`. A confirm for them would be a confirm for
  something that cannot happen.
- **Create**, in every state. D4 makes it provably incapable of a drop, which is the whole
  reason it is offered without friction. This mirrors `005`'s D7, which recorded that
  re-enabling an account is not confirmed because it destroys nothing.

## R5, at the one place in this feature it is most tempting

A sync confirm is the exact site `domain-rules.md` warns about — the same shape as
`admin-surfaces.md`'s forbidden **"Are you sure? N sessions use this model"**. The
sentence here must describe **the action and the structure it changes**, never a blast
radius:

- **allowed**, because they are schema and are identical on every instance: the table name,
  the column names being dropped, the fact that other columns' data survives;
- **forbidden**, in the confirm and everywhere else on the page: **"1,204 rows"**, **"N
  rows will be lost"**, **"N rows will be rebuilt"**, **"rows affected"**, and every
  variant. The backend offers no count to render, which is the structural half of the same
  rule (step `003` DoD-18, step `004` DoD-3); DoD-8 here is the rendering half.

## Why an in-sync row renders no trigger at all

Three statuses, two actions, and D4 makes both actions no-ops on an in-sync table — so an
in-sync row's menu would have either zero items or two items that do nothing. A menu with
nothing in it is a defect, and a menu of no-ops is worse: it invites an administrator to
press Sync on a healthy table holding their roleplayer's material. The cell is empty. The
same reasoning is why unavailable actions are **absent rather than disabled** elsewhere in
the product (`ui-conventions.md`'s `IconArrowBackUp` note, US-093.AC-2's absent admin menu
item).

## Gotchas

- **The confirm's open flag and its target row are component-local `useState`.** Putting
  them on the MobX store makes the store's shape depend on the page's visual arrangement,
  which `ui-conventions.md` rules out and `context.md` D13 restates.
- **Re-load the whole report, not the one row.** The apply route answers with the
  re-derived row, and using that answer to patch the store in place is exactly the
  optimistic mutation `ui-conventions.md` forbids. The answer is a server-side witness for
  the router test, not a shortcut for the page.
- **`void` the handler invocation with a non-rethrowing catch**, so a rejected promise is a
  rendered error rather than an unhandled rejection.
- **No success toast**, and `notifyFailure` is not imported — the inline `Alert` is the one
  place a failure renders. `frontend/tests/conventions.test.ts` enforces the import scan
  and is not edited by any step.
- **`globals: false`** — `describe` / `it` / `expect` imported explicitly from `"vitest"`,
  each `it` title ending **`— DoD-N`**, `fetch` stubbed per test with no mocking library,
  Mantine renders wrapped in `shared/AppProviders`.
- **This step's tests live in their own file**, `frontend/tests/admin/databaseActions.test.tsx`,
  disjoint from step `005`'s — the two steps share source files, which is the same
  arrangement `006/006`–`006/009` used.
