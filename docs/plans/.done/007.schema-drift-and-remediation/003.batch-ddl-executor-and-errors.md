# Step 003 — The DDL executor on Alembic batch operations, its two error codes, and the dependency

## Goal

Build `db/sync.py` — the only module in the backend that emits DDL outside bootstrap —
implementing Create and Sync by postcondition, with Sync's drifted case running the
create-copy-drop-rename rebuild through Alembic's batch operations; add the two
`DomainError` subclasses a failed or misaddressed apply needs; and promote `alembic` to a
runtime dependency without letting it become a migration framework.

## Interface intent

**`backend/pyproject.toml`** — move `alembic` into the runtime `dependencies` with a
compatible constraint (`context.md` D6). Nothing else in the file changes. **No
`alembic.ini`, no `migrations/`, no `env.py`, no `versions/` directory, no revision chain,
no version table and no startup hook is created** — not in this step, not anywhere.

**`backend/app/errors.py`** — two new `DomainError` subclasses, appended beside
`SecretRefError` and `AlreadyConfiguredError`. Each carries `code` and `http_status` class
attributes **and nothing else**; the one handler `register_exception_handlers` already
registers renders both. **No new handler is registered and no router translates either by
hand.**

- an **unknown-table** error — `unknown_table`, **404**, `detail` carrying the table name;
- an **apply-failed** error — `schema_apply_failed`, **500**, `detail` carrying the table
  name and the operation (`create` or `sync`). **The driver's message is not carried and
  not logged** (`context.md` D9): a SQLite error text can embed a column *value*.

**`backend/app/db/sync.py`** — remediation, and the only writer. It takes a connection, a
registry and a table **name**; it resolves the `Table` from the registry itself and raises
the unknown-table error when the registry does not declare it, so the router holds no rule
and **the raw name string is never interpolated into SQL** — only the registry's own
`Table` object reaches the DDL. It may import `db/drift.py` (it needs the report to know
what to change); the reverse import is a defect.

- **A create operation** — postcondition: the table exists with the declared shape
  (`context.md` D4). It emits the declared `Table`'s own `CREATE TABLE` plus its declared
  indexes when the table is absent, and **does nothing at all** when the table already
  exists, whatever its drift state. It **never drops anything, in any state** — the
  property that earns Create its no-confirm (D7). One transaction.
- **A sync operation** — postcondition: the table matches the declared shape. Missing →
  create it. In sync → do nothing. Drifted → **rebuild** it with Alembic's
  `batch_alter_table` in **recreate mode** (`context.md` D5): build the new table from the
  registry's declaration, copy across **every column the registry still declares and the
  live table still has**, drop the old, rename the new, then recreate the declared indexes
  and drop the extra ones. The whole rebuild is **one transaction**; a failure rolls it
  back and raises the apply-failed error, leaving the table byte-for-byte as it was and
  **no `_alembic_tmp_*` table behind**.
- **Both operations answer with the per-table report re-derived *after* the apply**, by
  calling `db/drift.py` again on the same connection once the transaction has committed.
  That is what gives step `004`'s routes a server-side witness for **US-018.AC-2**.
- **The foreign-key dance** (`context.md` D8) wraps a rebuild: `PRAGMA foreign_keys = OFF`
  **outside** the transaction (SQLite silently ignores the pragma inside one),
  the rebuild inside it, `PRAGMA foreign_key_check` **before** the commit with any returned
  row treated as a failure, and `PRAGMA foreign_keys = ON` restored afterwards on **both**
  the success and the failure path.
- **No row is counted anywhere** — not to report progress, not to log, not in a return
  value (R5).

## Definition of done

1. `[test]` Create on a **missing** table creates it with every declared column, its
   declared nullability, and its declared indexes; the table is afterwards reported **in
   sync**. (US-018.AC-1, UC-015)
2. `[test]` Create on a table that **already exists** — in sync or drifted — changes
   nothing at all: no column is added, no column is dropped, no row is touched, and the
   returned report is the table's current truth. (`context.md` D4 — **no product id**)
3. `[test]` **Create never drops a column, in any state**, including on a table carrying
   columns the registry no longer declares. (`context.md` D4, D7 — **no product id**)
4. `[test]` Sync on a **missing** table creates it, and the table is afterwards reported
   in sync. (US-018.AC-1, UC-015)
5. `[test]` Sync on an **in-sync** table is a no-op that touches neither the schema nor a
   row. (`context.md` D4 — **no product id**)
6. `[test]` Sync on a table missing a declared column adds it and the table is afterwards
   reported **in sync**; every pre-existing row survives with its other column values
   intact. (US-018.AC-1, US-018.AC-2, UC-015)
7. `[test]` Sync on a table whose column **changed type or nullability** rebuilds it, the
   table is afterwards reported in sync, and the data in every surviving column is
   preserved. (US-018.AC-1; `context.md` D5)
8. `[test]` Sync on a table carrying a column the registry no longer declares **drops that
   column** and preserves the data of every column that survives the rebuild — which is
   exactly the contract the confirm in step `006` states. (US-018.AC-1; `context.md` D5,
   D7)
9. `[test]` Sync on a table with a missing or extra **index** brings the index set into
   line and the table is afterwards reported in sync. (US-018.AC-1; `context.md` D1)
10. `[test]` Both operations answer with the per-table report **re-derived after the
    apply**, so the answer already reflects the corrected state. (US-018.AC-2, UC-015)
11. `[test]` A rebuild that cannot complete — a value that will not cast to the new type,
    or a nullability tightening over existing NULLs — raises `schema_apply_failed` and
    leaves the table **exactly as it was**: same columns, same indexes, same rows, same
    drift status. (`context.md` D5, D9 — **no product id**)
12. `[test]` After a failed rebuild **no `_alembic_tmp_*` table survives** in
    `sqlite_master`. (`context.md` D5 — **no product id**)
13. `[test]` After a successful Sync **and** after a failed one, the connection reports
    `PRAGMA foreign_keys` back **ON**, and `PRAGMA foreign_key_check` reports no violation
    on a successful rebuild of a table another table references. (`context.md` D8 — **no
    product id**)
14. `[test]` A rebuild that would leave a foreign-key violation is refused: the
    `foreign_key_check` failure rolls the transaction back and raises
    `schema_apply_failed`. (`context.md` D8 — **no product id**)
15. `[test]` Either operation against a table name the **registry does not declare** raises
    `unknown_table` and emits no DDL — including for a name that exists in the live
    database but not in the registry, and for a name carrying SQL punctuation, which must
    be refused rather than executed. (`context.md` D9 — **no product id**)
16. `[test]` `unknown_table` and `schema_apply_failed` are `DomainError` subclasses
    carrying only `code` and `http_status`, render through the **already registered**
    handler as `{"error": {"code", "message", "detail"}}` with **404** and **500**
    respectively, and `register_exception_handlers` gains no second handler.
    (`backend-structure.md`'s error model; `context.md` D9 — **no product id**)
17. `[test]` `schema_apply_failed`'s `detail` carries the **table name and the operation**
    and **no driver message**, and no log line emitted by this feature carries one either.
    (`context.md` D9; `deployment.md`'s redaction rule — **no product id**)
18. `[test]` Neither operation counts rows: `db/sync.py` issues no `COUNT(*)`, returns no
    count, and its errors carry none. (R5, UC-066)
19. `[test]` `db/sync.py` imports no `fastapi` name, imports `app.db.schema` nowhere — the
    registry arrives as an argument — and `db/drift.py` still does not import it.
    (`backend-structure.md`, routers versus services and the drift/sync split — **no
    product id**)
20. `[manual/live]` `backend/pyproject.toml` lists `alembic` under runtime `dependencies`,
    and the tree contains **no** `alembic.ini`, **no** `migrations/`, **no** `env.py`,
    **no** `versions/` directory and **no** version table; `main.py`'s lifespan still runs
    no DDL. Verifier confirms by reading the tree.
    (`backend-structure.md`'s four explicit negatives; `context.md` D6)
21. `[manual/live]` Against a hand-drifted real database file, a Sync through the executor
    rebuilds the table and the data in the surviving columns is visibly intact.
22. `[manual/live]` `mypy app`, `ruff check .` and `pytest` all pass from `backend/`, and
    `uv`'s lock file is updated for the new dependency.
