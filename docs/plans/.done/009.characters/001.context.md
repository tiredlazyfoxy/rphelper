# Step 001 — step-specific context

Feature-wide facts are in `context.md`: **D5** (the columns, FK and index choices),
**D8** (the not-found and name rules), the **Wire contract** (the `Character` shape), and
**Test conventions** (backend). Only what is narrow to this step is below.

## Registry patterns to follow (harvested from built `db/schema.py`)

- Every table is a module-level `Table(...)` literal in `db/schema.py`, bound to the one
  `metadata`. No other module defines a table. Two existing tests guard this and must
  keep passing unchanged: `test_every_registry_table_is_a_literal_in_the_schema_module`
  and `test_no_other_app_module_defines_its_own_table`.
- The id column form used by every table:
  `Column("id", BigInteger().with_variant(Integer(), "sqlite"), primary_key=True, autoincrement=False)`.
  `autoincrement=False` because ids are minted before the INSERT (`data-model.md`
  Identifiers).
- Foreign keys are written `ForeignKey("users.id")`. Nullable text is `Text, nullable=True`.
  Timestamps are `Text`.
- Declare the `user_id` index in the same way the registry already declares
  `auth_sessions.user_id`'s index. The drift report compares indexes by (column list,
  uniqueness), not by name (`data-model.md` "As built by FEAT-005"), so the name is free
  but the column list must be exactly `user_id`, non-unique.

## The delta pattern, and why bare equality is the trap

`tests/test_db_schema.py` records each feature's tables as `PRE_<n>_TABLES` /
`NEW_<n>_TABLES`. Written as `set(tables) - PRE == NEW`, a delta is only true until the
next feature adds a table. That is exactly what breaks 006's assertions above. The 009
delta (DoD-1) and the rescoped 006 delta (DoD-11) are therefore written so a later table
cannot falsify them. Either:

- assert membership and absence explicitly (`NEW <= tables`, plus no unexpected table among
  those this feature could have added); or
- subtract a "declared by later features" set that later plans extend.

The test-coder picks one shape and uses it for both, so `010`+ add their delta the same way.

## Error-class pattern

`DomainError` declares `code` and `http_status` as class attributes. Each concrete subclass
sets them, and the one handler (already registered by `register_exception_handlers` in
`main.py`) renders `{ "error": { "code", "message", "detail" } }` with the instance's
status. `UserNotFoundError` is the nearest precedent (404, no detail). Copy its shape. The
per-code status record in `backend-structure.md` gets the new row at finalization
(`outcome.md`), not here.

## Model patterns

- Request models carry `model_config = ConfigDict(extra="ignore")`. The admin-users
  request models are the precedent.
- Outbound ids use `SnowflakeOut` from `app.models.ids`. Never a bare `int` field.
- Blank-name rejection is pydantic's own validation (FastAPI answers 422 natively). The
  admin-users models use `Field(min_length=1)` for their required strings. Here the
  value is **stripped first** and then length-checked. Pydantic's
  `StringConstraints(strip_whitespace=True, min_length=1)` (or an equivalent annotated
  type) expresses both in one annotation and applies to both request models.
- `models/` imports neither `services/` nor `routers/`. Converting a service value into a
  `CharacterResponse` happens in the router (`003`).

## Gotcha — `/api/health` on existing databases

Adding `characters` to the registry makes an **existing** database report
`schema: "missing"` (and `status: "degraded"`) from `/api/health` until an administrator
presses Create. That is the designed behaviour (`backend-structure.md` "Schema
evolution"), not a regression. Tests are unaffected because they build schema with
`create_all`.
