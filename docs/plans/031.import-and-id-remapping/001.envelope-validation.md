# Step 001 — import errors, envelope validation and deserializer

## Goal

Add the two typed import errors, and create `services/transfer_import.py` with
pure, write-free envelope validation and row deserialization. These check an
envelope against the route's accepted granularities and turn its payload into typed
rows, or raise `export_invalid` with the right `detail.reason`.

## Source files

- `backend/app/errors.py`
- `backend/app/services/transfer_import.py`
- `backend/app/services/transfer.py`

## Test files

- `backend/tests/test_transfer_import_validation.py`

## Interface intent

- **`ExportInvalidError`** (in `app/errors.py`). A `DomainError` subclass with code
  `export_invalid` and status 400. It is constructed from one reason out of the
  fixed five (`context.md` §"The failure contract"). Its `detail` is exactly
  `{"reason": <reason>}`, and its message is the reason's fixed sentence
  (`001.context.md`). The reason vocabulary is a string-valued type or constant set
  that later steps import, so no step re-types a reason string.
- **`DatabaseNotEmptyError`** (in `app/errors.py`). A `DomainError` subclass with
  code `database_not_empty`, status 409, empty `detail` and a fixed default message
  (`001.context.md`). Raised by step 004.
- **The id-column predicate in `services/transfer.py`.** 030's serializer already
  decides whether a column is an id column. If 030 built that test as a private
  helper, this step makes it importable under a public name, and 030's own call
  sites keep using it. Its behaviour does not change. That is the only change to
  `transfer.py`.
- **Per-granularity table sets** (in `transfer_import.py`). A module-level mapping
  from each of the four granularities to the exact payload table-name set, as given
  in `context.md` §"Granularity table sets". The database set is derived from
  `schema.metadata.sorted_tables` minus 030's database exclusion set, not
  hand-listed.
- **Root tables.** A module-level mapping from `user`, `character` and `session` to
  the table that must hold exactly one row.
- **Row deserializer.** Takes a `schema` Table, a raw row object, and an optional
  set of columns the row is allowed to omit. It returns a mapping of column name to
  Python value under `context.md` §"Deserialization", or raises `ExportInvalidError`
  with `malformed_payload`. It requires the row's key set to equal the table's
  columns, minus the allowed omissions.
- **`validate_envelope`.** Takes the raw body (any JSON value) and the set of
  granularities the caller accepts. It runs the header checks in the order
  `context.md` fixes, then:
  - the payload key set;
  - per-table list/row shapes;
  - per-row deserialization, where the `users` row at `user` granularity may omit
    030's `users` column exclusion;
  - the root count.

  It returns a validated-export value carrying the granularity and the deserialized
  rows per table, in `sorted_tables` order. It reads no database and writes nothing.
  It does **not** check references; steps 002–004 own those checks.

## Definition of done

1. **DoD-1 [test]:** Valid envelopes produced by 030's `export_user`,
   `export_character`, `export_session` and `export_database` over seeded rows each
   validate when their granularity is accepted. Every deserialized row equals the
   stored row column-for-column: ids as ints, booleans as bools, enum values as
   their stored value, timestamps as the stored text, nulls as None. (US-077.AC-2,
   US-079.AC-2, US-080.AC-2)
2. **DoD-2 [test]:** These bodies each raise `ExportInvalidError` with `detail`
   exactly `{"reason": "not_an_export"}`: a JSON array; an object missing any one of
   the six header keys; an object with an extra header key; `format` other than
   `"rphelper-export"`; and `granularity` `"everything"`.
3. **DoD-3 [test]:** `version` one higher than 030's envelope version, and
   `version` given as a string, each give `unsupported_version`. `schema_version`
   one higher **and** one lower than 030's schema version each give
   `schema_mismatch`, even when everything else is valid.
4. **DoD-4 [test]:** A valid `session` envelope validated with accepted set
   {`user`, `character`} gives `wrong_granularity`. A valid `database` envelope
   validated with the same set also gives `wrong_granularity`.
5. **DoD-5 [test]:** Each of these gives `malformed_payload`:
   - a user payload missing `memos`;
   - a character payload with an extra `llm_servers`, `models`, `auth_sessions` or
     `translations` key (one case each);
   - a session payload whose `messages` is an object rather than a list;
   - a row that is a string.
6. **DoD-6 [test]:** Each of these gives `malformed_payload`:
   - a row missing one column;
   - a row with one extra column;
   - an id `"12a"`;
   - an id given as a JSON number;
   - an id beyond the signed 64-bit range;
   - a boolean column holding `1`;
   - `memos.scope` `"galaxy"`;
   - null in a NOT NULL text column;
   - an integer non-id column holding `true`.
7. **DoD-7 [test]:** At `user` granularity, a `users` row that omits exactly 030's
   excluded `users` columns validates. A `users` row that **includes**
   `password_hash` gives `malformed_payload`. At `database` granularity, a `users`
   row missing `password_hash` gives `malformed_payload`.
8. **DoD-8 [test]:** A character payload with two `characters` rows or with none,
   a session payload with two `sessions` rows, and a user payload with two `users`
   rows each give `malformed_payload`.
9. **DoD-9 [test]:** The error's wire `detail` never carries anything but `reason`.
   For a malformed row seeded with a sentinel string value, the sentinel appears
   neither in `detail` nor in the message. The message for each reason equals the
   sentence pinned in `001.context.md`.
10. **DoD-10 [test]:** `DatabaseNotEmptyError` has code `database_not_empty`,
    status 409, empty `detail` and the pinned default message.
11. **DoD-11 [test]:** The `database` table set equals `sorted_tables` names minus
    `auth_sessions` and `translations`. The `user`, `character` and `session` sets
    equal the key sets 030's exporters produce for those granularities.
12. **DoD-12 [test]:** 030's export tests still pass, because the predicate's
    behaviour is unchanged. One regression case: a database export's
    `memos.scope_id` and `characters.model_server_id` are still decimal strings.
13. **DoD-13 [manual/live]:** `mypy app` and `ruff check .` pass.
