# Step 007 — The create-account modal, its draft, and the by-status error mapping

## Goal

Let the administrator create an account from the Users page: a header button, a modal
with a hand-rolled MobX draft, client validation, and a submit that maps a username
conflict onto the username field by **status** rather than by parsing prose.

## Source files

```

frontend/src/admin/CreateUserModal.tsx
frontend/src/admin/UsersPage.tsx
```

## Interface intent

**`frontend/src/admin/createUserDraft.ts`** — the draft and its functions, in one module
(`ui-conventions.md`'s draft convention as `002`'s D2 and `context.md` D16 amend it:
**fields only, no methods and no computed getters**).

- **A data class** holding observable fields only: username, password, password
  confirmation, the chosen role (defaulting to the lower rung), a `serverErrors` map
  keyed by **field name plus a general key**, and a submit status. Constructor is
  `makeAutoObservable(this, {}, { autoBind: true })` and nothing else.
- **Pure free functions over the draft**, not getters: the client-side errors, the merged
  view of client and server errors, and whether the draft may be submitted. Client
  validation is exactly: username required, password required, confirmation must match.
  **No length floor, no character classes and no strength meter** — `docs/product/` states
  no password policy and `003`'s D16 already refused to invent one (`context.md` D6).
  Values are validated on a trimmed view only to decide whether a field is *filled*; what
  is **sent is exactly what was typed** (`004`'s D13).
- **An effectful free function `submitCreateUser(draft, onSaved, signal?)`-shaped** — the
  submit is never a method. It posts the create request through `shared/api.ts`, and on
  success invokes the page's `onSaved` callback; the draft does not know about the list.
  It `runInAction`s every write and **early-returns on an aborted signal before
  writing**.
- **Server errors are mapped by status** (`admin-surfaces.md`, `context.md` D10): a
  **409** becomes a "username taken" message on the **username** field; **everything
  else** — any other status, a transport failure, a malformed body — lands on the
  **general key**. Nothing is mapped by reading a message string. The password-field half
  of `admin-surfaces.md`'s mapping is deliberately absent because no password policy
  exists to produce it (`context.md` D10).

**`frontend/src/admin/CreateUserModal.tsx`** — a Mantine `Modal` (never a drawer, never a
route) rendering the four fields `admin-surfaces.md` names: username, password, password
confirmation and a role `Select` over the ladder's two values. Field errors render on
their fields; the general key renders **above the form**. The submit control is disabled
while the draft may not be submitted and while a submit is in flight. `@mantine/form` is
**not** used. Passwords use a `PasswordInput`. The modal raises **no notification** and
shows **no success message** — it closes and the list refreshes.

**`frontend/src/admin/UsersPage.tsx`** — three additions and nothing else: a **Create
user** button in the page header, a component-local `useState` open flag for the modal,
and the modal **conditionally mounted** so that a fresh draft is constructed per open
through `useState(() => new CreateUserDraft())` inside the modal body — **not** a
long-lived draft reset on close (`ui-conventions.md`). `onSaved` closes the modal and
re-loads the list through step `006`'s load function.

## Definition of done

1. `[test]` The client-error function reports a missing username, a missing password and
   a confirmation that does not match, and reports nothing for a filled, matching draft;
   it is callable by constructing a draft and calling a function, with no render and no
   network. (`002`'s D2 — **no product id**)
2. `[test]` The draft applies **no password policy** beyond non-empty: a one-character
   password is valid client-side. (`context.md` D6, `003`'s D16 — **no product id**)
3. `[test]` The submit-permission function is false while a field is invalid and false
   while a submit is in flight, and true otherwise.
4. `[test]` The draft is a data class with observable fields only — **no methods and no
   computed getters** — and every derivation is a free function taking it.
   (`002`'s D2, `context.md` D16 — **no product id**)
5. `[test]` A successful submit posts **the values exactly as typed** — no trimming, no
   case folding — and invokes the saved callback exactly once. (`004`'s D13; US-008.AC-1)
6. `[test]` A **409** response puts a "username taken" message on the **username field**
   and nothing on the general key; the modal stays open and the draft's values survive.
   (`admin-surfaces.md`'s create-modal mapping — **no product id**)
7. `[test]` Any non-409 failure — another status, a transport failure, a malformed body —
   lands on the **general key** and renders above the form, and **nothing** is mapped by
   reading a message string. (`context.md` D10 — **no product id**)
8. `[test]` The modal renders the four fields `admin-surfaces.md` names, with the role
   `Select` offering exactly the two ladder values and defaulting to the lower rung.
   (**no product id**)
9. `[test]` The Create button opens the modal, and the modal body is **conditionally
   mounted**: closing and reopening yields an **empty** draft, with no value from the
   previous open surviving. (`ui-conventions.md`'s draft-lifetime rule — **no product
   id**)
10. `[test]` A successful create **closes the modal and re-loads the list**, after which
    the new account appears in the table and is shown as **enabled** — and no success
    notification is raised. (US-008.AC-1, US-008.AC-2, `ui-conventions.md`)
11. `[test]` The modal's open flag is component-local state and is **not** a field of the
    page store or of the draft. (`ui-conventions.md` — **no product id**)
12. `[test]` The created account's id is handled as a **string** everywhere it is touched,
    and nothing parses it. (`frontend-structure.md`, "Ids are strings" — **no product
    id**)
13. `[manual/live]` `@mantine/form` is imported nowhere in this step, and the password
    fields are `PasswordInput`s. Verifier confirms by reading the two modules.
14. `[manual/live]` Against a running backend, creating an account makes it appear in the
    list, enabled, and that account can then log in. (US-008.AC-1, US-008.AC-2)
15. `[manual/live]` Both colour schemes are correct for the modal, its fields and its
    error states.
16. `[manual/live]` `npm run typecheck`, `npm test` and `npm run build` all pass from
    `frontend/`.
