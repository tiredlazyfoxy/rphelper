# Step 007 — step-specific context

Feature-wide facts are in `context.md` (D6 on the absent password policy, D10 on the
by-status mapping and the half of it that does not exist, D16 on the MobX/draft rules,
plus the no-success-toast and never-optimistic rules). Only what is narrow to this step
is below.

## Borrowed interfaces, by module path and role

- **`frontend/src/admin/usersPageState.ts`** (step `006`) — the row type, the role union
  and the load free function `onSaved` calls. The role union's two values are the strings
  the backend's ladder stores (`"roleplayer"`, `"admin"`), never the Python enum's member
  names.
- **`frontend/src/shared/api.ts`** (`002/004`) — the POST helper. A **409 does not
  navigate** (only a 401 does), so the conflict reaches the submit as a thrown
  `ApiError` with `status: 409`.
- **`frontend/src/shared/apiError.ts`** (`002/004`) — `ApiError` carries `code`,
  `message`, `detail` and **`status`**. `002`'s D7 records that `status` exists
  *precisely* for the by-status half of this field mapping; `code` remains the branch key
  everywhere else.

## The route and body this step posts

`POST /api/admin/users` (`context.md` D5) with a username, a plaintext password and a
role. **The confirmation field is client-side only** and is never sent — the backend has
no such field (step `003`'s create-request model). The backend answers **201** with the
created account, **409** `username_taken` for a collision, and FastAPI's **422** for an
empty field (which the client's own validation already prevents).

## Why 409 is safe to key on here

`username_taken` is the only 409 the create route can produce (step `002`'s error set:
`username_taken` 409, `user_not_found` 404, `self_role_change_refused` 409 — and the last
two are unreachable on a create). Step `008`'s change-role modal keys 409 differently for
its own route, which is fine: the mapping is **per modal**, as `ui-conventions.md`'s
convention places it in each `submitX` function.

## Gotchas

- **The draft is constructed inside a conditionally mounted modal body.** A modal that is
  always mounted with `opened={false}` keeps its draft alive and shows the previous
  operator's typing to the next one — `ui-conventions.md` rejects the reset-on-close
  alternative explicitly.
- **Do not add a "user created" notification.** A notification whose message is a success
  is a defect; the modal closing and the row appearing is the signal.
- **Do not validate the password beyond non-empty.** A helpful six-character floor here
  would be an invented requirement, and it would also be a floor the bootstrap form
  (`003/005`) does not have — two different rules for the same column.
- **Send what was typed.** Trimming the username on the way out would create accounts
  that can never log in, because `004`'s login path matches exactly and normalizes
  nothing.
