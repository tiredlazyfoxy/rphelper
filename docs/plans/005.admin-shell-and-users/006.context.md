# Step 006 — step-specific context

Feature-wide facts are in `context.md` (D5 for the routes this page calls, D7 for the
confirm convention and which actions are confirmed, D16 for the MobX rules, plus R5, the
never-optimistic rule and the no-notification rule). Only what is narrow to this step is
below.

## Borrowed interfaces, by module path and role

- **`frontend/src/shared/api.ts`** (`002/004`) — the request function and the GET/POST
  helpers; see `004.context.md` for its full behaviour. This page uses the GET helper for
  the list and the POST helper for the two mutations. A **401 still navigates to
  `/login`**, which is correct here: an administrator whose session died mid-page belongs
  on the login screen.
- **`frontend/src/shared/apiError.ts`** (`002/004`) — branch on **`.code`**, never on
  `.message`. This page does not branch at all: it renders the error's message in the
  inline `Alert`, which is what an unclassified page-level failure is for.
- **`frontend/src/shared/IconButton.tsx`** (`002/003`) — its props are listed in
  `005.context.md`. The row's overflow trigger is its first consumer in this feature:
  `icon` is `IconDots`, `label` names the row's account, `sizeVariant` stays `"main"`.
- **`frontend/src/admin/AdminApp.tsx`** (step `005`) — the flat four-route table; only the
  `/` element changes here.

## The list payload this page binds to

Step `003`'s account model: **id (a decimal string)**, username, role, the enabled flag
and `last_login_at` (nullable), wrapped in a one-field list model. Nothing else is in the
body and nothing else may be rendered. The exact field names are step `003`'s Interface
intent and the skeleton agent resolves them; this page must not invent a field the
backend does not send.

## Routes this page calls

`GET /api/admin/users`, `POST /api/admin/users/{id}/disable`,
`POST /api/admin/users/{id}/enable` (`context.md` D5). No other route, and no query
parameter on any of them.

## Rendering `last_login_at`

The value is a UTC ISO-8601 **string**. It is rendered as a readable local date-time by
constructing a `Date` from it — which is a date, not an id, so it is not covered by the
ids-are-strings rule — and as an **em dash** when it is absent. No relative-time
formatting and no date library: `002`'s D14 installs none, and none may be added here.

## The confirm's wording, and the line it must not cross

Title and confirm label name the action; the consequence sentence says the person is
signed out immediately and cannot sign in again until the account is re-enabled. It must
carry **no count of anything** — R5's forbidden shape is a blast radius derived from
other users' data, and `admin-surfaces.md` names the LLM Servers page as the likely site
precisely because a confirm dialog is where it gets written in good faith. DoD-12 pins
the rule on the first confirm the product ships, so the precedent is right from the
start.

## Gotchas

- **The status field is what gates the `Loader`, not "rows are empty".** An explicit
  status distinguishes "not asked yet" from "asked, nothing came back"
  (`ui-conventions.md`), and an account list can legitimately be empty for a moment after
  a load.
- **Re-load after every mutation, always** — even the ones whose outcome seems obvious.
  The disable's *real* effect (revoked sessions) is invisible in the row; the re-load is
  what guarantees the page shows what the server actually did.
- **The modal's open flag is component-local `useState`.** Putting it in the store would
  make the store's shape depend on the page's visual arrangement — `ui-conventions.md`
  spells out the reasoning.
- **One icon-only control per row.** A tempting second one (a quick "disable" icon beside
  the menu) is a defect under `ui-conventions.md`'s boundary note, and DoD-8 asserts it.
- **No `Set Password` or `Change Role` item yet** — steps `007` and `008` add them to the
  same menu. Leaving a disabled placeholder item here would be a stub, not room.
