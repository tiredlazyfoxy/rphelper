# Step 001 — The shared zone insert and the start-session models

## Goal

Extract 012's inline zone-message insert into a transaction-neutral helper that
`append_message` now calls, and widen 011's start-session models: an optional
`opening_message` on the request, and a `StartedSession` response that carries the
session's eight keys plus the opening message or null (D3).

## Source files

backend/app/services/messages.py
backend/app/models/sessions.py

## Test files

backend/tests/test_zone_message_insert.py
backend/tests/test_sessions_models.py

## Interface intent

**`services/messages.py`** (changed; 012-owned)

- **Zone insert helper** (new, public): takes the connection, the id generator, the
  caller's user id, a session id, the text and the timestamp text to stamp. It mints one id
  and inserts one `messages` row as a **current-zone user row**: role `"user"`; kind,
  `settled_at` and `related_to` NULL; text verbatim; `created_at` and `updated_at` the given
  timestamp; the owner column the caller's id. It returns the message value type
  (`StreamMessage`). It opens **no** transaction, checks nothing about the session, and does
  not bump the session. The caller owns all three.
- **`append_message`**: signature, transaction, session check, ordering and bump are
  unchanged. Its own insert is replaced by a call to the helper inside its existing
  `with connection.begin():`.

**`models/sessions.py`** (changed; 011-owned)

- **`StartSessionRequest`** gains an optional **`opening_message`**: 012's `NonBlankText`,
  or absent / null (both mean "none"). `setup_id` and `extra="ignore"` are unchanged.
- **`StartedSessionResponse`** (new): exactly `SessionResponse`'s eight keys, with the same
  types and the same id serialisation, plus **`opening_message`**: a 012 `MessageResponse`,
  or null. `SessionResponse` itself is unchanged and stays the answer of every other
  session route.

## Definition of done

1. `[test]` The helper, called inside a caller's open transaction, inserts exactly one row
   for the given session. Read back, its role is `"user"`, kind, `settled_at` and
   `related_to` are NULL, text equals the given text byte for byte (leading / trailing
   whitespace and newlines kept), and both timestamps equal the given timestamp. The
   returned value's id equals the generator's next id. (R11 — a zone row; D3)
2. `[test]` The helper opens no transaction: calling it while the caller's transaction is
   open succeeds, and a caller rollback afterwards leaves no row. It does not change the
   session's `last_used_at` or `updated_at`. (D3)
3. `[test]` `append_message` still behaves as 012 built it: it appends a zone row for the
   caller's session, bumps `last_used_at`, refuses another user's session with
   `session_not_found` and inserts nothing then. (012 behaviour preserved through the
   helper)
4. `[test]` The source of `append_message` (read with `inspect.getsource`) contains no
   direct `messages` insert, and the helper's source contains exactly one. So the zone
   insert exists once. (D3 — one insert)
5. `[test]` `StartSessionRequest`: `{}`, `{"opening_message": null}` and an omitted body
   field all give no opening message. `{"opening_message": "  Hello\n"}` keeps the text
   verbatim. `{"opening_message": "   "}` and `{"opening_message": ""}` fail validation.
   `{"setup_id": "7250000000000000201", "opening_message": "Hi"}` keeps both. An unknown key
   is ignored. (Wire contract)
6. `[test]` `StartedSessionResponse` built from a session value and no message serialises
   to exactly the eight session keys plus `opening_message: null`, with ids as decimal
   strings. Built with a message value it serialises `opening_message` as 012's eight-key
   message object with string ids. `SessionResponse` still serialises exactly its eight
   keys. (Wire contract, ids are strings)
