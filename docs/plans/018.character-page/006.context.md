## 017's character routes, as declared (B — 017 `context.md` "Wire contract")

| Route | Body | Answers |
|---|---|---|
| `GET /api/characters/{character_id}/configuration` | — | 200 `CharacterConfiguration` |
| `PATCH /api/characters/{character_id}/configuration` | any subset of `{ model, system_prompt, tool_memo_search, tool_session_search, tool_web_search }` | 200 `CharacterConfiguration` |

```
CharacterConfiguration { model: ModelRef | null, system_prompt: string | null,
                         tool_memo_search: boolean | null, tool_session_search: boolean | null,
                         tool_web_search: boolean | null }
ModelRef               { server_id: "<decimal>", model_name: string }
EnabledModel           { server_id: "<decimal>", server_name: string, model_name: string }
```

- An explicit `null` clears that key back to "not set". `model: null` is allowed on the
  character route (017 D10).
- A `model` that is not enabled now → 409 `model_not_enabled` with `detail.level`
  `"character"`, and **nothing in the request is written**.
- A blank `system_prompt` is stored as null. Otherwise it is stored verbatim (017 D6).
- Unknown keys are ignored, so a language key changes nothing. Even so, the patch type
  forbids one.
- Missing or another user's character → 404 `character_not_found`. An archived character
  is configurable (017 D11).
- `GET /api/models` answers `{ models: [EnabledModel…] }` in first-enabled order (017 D7).
  It is `[]` when none is enabled.

## Why the lines are derived client-side

`CharacterConfiguration` carries no `Setting<T>`. The character level's only "inherited"
source is the default (017 D1, D5): the first enabled model at session creation, no prompt,
tool on. So "set here or default" is fully decidable from null versus non-null, and no
extra request is needed. Do not read `SessionConfiguration` or `Setting` for the character
block.
