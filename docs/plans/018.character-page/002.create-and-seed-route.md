# Step 002 — Create a session and seed its zone in one transaction

## Goal

Give `services/sessions.py` a create-and-seed operation that inserts the session and its
opening message in the **same** transaction as 011's start (after 017's model capture),
and make `POST /api/characters/{character_id}/sessions` call it when the body carries an
`opening_message`, answering `StartedSession` in every case (D1, D2, D3, US-117).

## Source files

backend/app/services/sessions.py
backend/app/routers/sessions.py

## Test files

backend/tests/test_sessions_service.py
backend/tests/test_sessions_router.py

## Interface intent

**`services/sessions.py`** (changed; 011-owned, edited by 017 `002`)

- **Started-session value** (new, frozen dataclass): the created `RpSession` and the
  opening message value (012's `StreamMessage`), or none.
- **Create-and-seed operation** (new, public): takes the connection, the generator, the
  caller's user id, the character id, the opening text and an optional setup id. In
  **one** `with connection.begin():` it does exactly what `start_session` does (parent
  check, optional setup check, id minting, `now`, 017's model capture, session insert) and
  then calls `001`'s zone insert helper with the new session id and the **same** `now`. It
  returns the started-session value. It runs no `(( ))` parsing, settles nothing, calls no
  model, and does not bump the session a second time.
- **`start_session`**: signature and return value unchanged (011 call shape, 017 capture
  intact). It and the new operation share one private transaction body, so the checks and
  the capture are written once.
- Imports from `services/messages.py` are limited to the zone insert helper and the
  message value type (D3's import exception).

**`routers/sessions.py`** (changed; 011-owned)

- `start_own_session` answers **`StartedSessionResponse`** (201). With no
  `opening_message` it calls `start_session` as before and answers `opening_message: null`.
  With one, it calls the create-and-seed operation with the body's text and `setup_id`. No
  SQL, no try/except. The module docstring's "018 later adds…" line now states what the
  route does.

## Definition of done

1. `[test]` Create-and-seed on the caller's character with "Hello there" returns a session
   with `setup_id` None and an opening message whose `session_id` is the new session's id,
   role `"user"`, kind None, `settled_at` None and text "Hello there". Reading the database
   afterwards finds exactly one new session and exactly one message, for that session.
   (US-117.AC-1, US-117.AC-2, R2, R11)
2. `[test]` The opening message's `created_at` equals the session's `created_at`, and the
   session's `last_used_at`, `created_at` and `updated_at` are all equal. (D3, 011 D3)
3. `[test]` **Atomicity.** When the message insert fails inside the transaction (a
   generator that fails on its second id), the operation raises and the database holds
   **no** new session row and no new message row. (US-117.AC-1 — one outcome; D3)
4. `[test]` Create-and-seed captures the model exactly as `start_session` does under the
   same registry state: a character with a configured model captures it, and a character
   without one captures the first enabled model. (R4, US-106.AC-1, US-139.AC-2 — 017 D1
   shared)
5. `[test]` Create-and-seed on another user's character, or on a nonexistent id, raises
   `CharacterNotFoundError`, and nothing is inserted. On the caller's **archived**
   character it succeeds. (R5, R6, 011 D2)
6. `[test]` Router: `POST /api/characters/<own id>/sessions` with
   `{"opening_message": "Hello there"}` answers 201 with the eight session keys plus
   `opening_message` (eight message keys, string ids, `session_id` equal to the returned
   `id`, role `"user"`, kind null, `settled_at` null, text "Hello there"). A following
   `GET /api/sessions/<id>/zone` lists exactly that message, and
   `GET /api/sessions/<id>/entries` is empty. (US-117.AC-1, US-117.AC-2, R11)
7. `[test]` Router: `{"opening_message": "   "}` answers 422, and the character's session
   listing is unchanged. As player B on player A's character with a valid
   `opening_message`, the route answers 404 `character_not_found`, and A's session listing
   is unchanged. (Wire contract, R5)
8. `[test]` Router: a body omitted, `{}`, or `{"setup_id": <A's working setup>}` still
   creates the session as 011 built it and answers `opening_message: null`, and the new
   session's zone is empty. Amends 011's exact-keys wire-shape assertion for **this route
   only** (eight keys + `opening_message`); every other session route keeps exactly eight.
   (011 D2, D3)
9. `[test]` Router: `{"setup_id": <A's archived setup>, "opening_message": "Hi"}` answers
   409 `setup_archived` and creates no session and no message. (011 D12; a refusal creates
   nothing)
10. `[test]` `services/sessions.py` imports from `app.services.messages` only the zone
    insert helper and the message value type, and imports no `fastapi` (read from disk).
    (D3)
