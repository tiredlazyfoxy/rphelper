# Step 006 — step-specific context

`context.md`'s "Library facts every step relies on (0.2.0)" still holds, apart
from what is listed below for 0.2.1. Its cross-cutting rules all still hold:
only the gateway imports `llm`, no provider text leaves a failure, one library
client per operation, and `from None`.

## Library 0.2.1 — what changes for RPHelper

- **Pin and lock.** The pin is `llm-client @ git+https://github.com/Iezious/PythonLLMClient.git@v0.2.1`.
  Refresh the lock with `uv lock`, which needs network access to github.com,
  then `uv sync`. `[tool.hatch.metadata] allow-direct-references` is already
  set (step 001). Constructors, exports, the Responses classes and `aiohttp`
  are unchanged.
- **`chat_with_tools(messages, *, tools_definitions, tools, system, max_loops, options, stream, on_delta, response_format, tool_errors, on_tool_event)`**:
  - `tool_errors` is `"result"` (the default, tolerant) or `"raise"` (strict).
  - `on_tool_event` may be a plain function or a coroutine function. It is
    called inline on the loop's task, and the loop waits until the observer
    returns.
- **The `ToolEvent` fields** form a total TypedDict, exported from `llm`:
  - `type`: `"start"`, `"result"` or `"error"`;
  - `name`: the model's name, `""` when empty;
  - `call_id`: the provider's id, or `None`;
  - `arguments`: the raw text the model sent, JSON-encoded if it was a mapping,
    `""` if missing;
  - `output`: on `result` only;
  - `error_kind`: on `error` only.

  The kinds (`ToolErrorKind`) are `not_offered`, `bad_arguments`,
  `unknown_argument`, `tool_raised` and `unserialisable_result`.
- **Per call, in call order**, the observer receives one `start` event before
  the tool runs, then exactly one `result` or `error`. The first three kinds
  fire with the callable never invoked. In tolerant mode an observer that
  raises makes the library emit `LLMToolObserverWarning` and tell the model the
  tool failed. DEC-035-17's observer cannot raise, so this path is never taken.
- **What tolerant mode tells the model.** For the three kinds, the library
  sends the model these fixed texts and continues the loop:
  - `Tool '<n>' is not available.`
  - `Invalid arguments for tool '<n>'.`
  - `Tool '<n>' has no argument '<a>'.`

  RPHelper never reads, forwards or logs them.
- **`LLMError` gains keyword-only `status`** (int or `None`; set on a non-2xx)
  **and `kind`** (one of `status`, `timeout`, `connection`, `interrupted`,
  `invalid_reply`, `server_failed`, `incomplete` or `tool`, or `None`). The
  message text form is unchanged. `RuntimeError` and `ValueError` raised by the
  library carry neither attribute.
- **Typing.** 0.2.1 is strictly typed:
  - `LLMClient` is generic in its options type;
  - entering a client returns `Self`;
  - `chat_with_tools` takes `messages` as `Sequence[Mapping[str, Any]]`.

  Some step 001/003 casts or ignores in `gateway.py` may now be redundant, or
  the class map's annotation may need a type argument. Adjust them inside
  `gateway.py` only (DEC-035-5). Using the library's `ToolEvent` /
  `ToolErrorKind` types is allowed inside `gateway.py` only. `ComposeRejected`'s
  kind is the gateway's own three-value type (DEC-035-17).
- **Not used:** the constructor's `read_timeout`, the constructor's `trace`, and
  `ToolEvent.call_id` (`DEC-arch-llm-client-library-17`).

## Touch sites (harvest, 2026-11-09)

### `backend/app/services/llm/gateway.py`

- `_is_auth_failure` (~105-111) parses `status 401/403` from `LLMError.message`
  and becomes a read of `.status` (DEC-035-20).
- `embed`'s `no_usable_vector` check, `message.startswith("Invalid response")`
  (~388), stays as it is.
- `compose` (~480-580) runs one task, `chat_with_tools(stream=True, max_loops=sys.maxsize)`,
  feeding one unbounded queue with an end marker. The observer closes over that
  queue, and over the same counter `invoke` (~511-519) uses to mint `call_<n>`.
- Tool callables carry the explicit `__signature__`, which is kept
  (DEC-035-19).
- `ComposeText` and `ComposeTools[E](declarations, runner)` are unchanged.

### `backend/app/services/llm_registry.py`

`ChatClientLike.compose` is a plain `def`, generic in `E`, returning
`AsyncGenerator[ComposeText | E, None]` (step 004 skeleton record in
`status.md`). Only that yield type gains `ComposeRejected`, imported from the
gateway.

### `backend/app/services/compose.py`

The private `run_tool(call, emit)` does the following:

1. emits `tool_start_frame(call)`;
2. awaits `dispatch(...)`;
3. emits `result.frame` and returns its content;
4. on any `Exception`, emits `ToolFailFrame(code=ToolFailedError.code)` and
   returns `TOOL_FAILED_CONTENT`.

The new drain branch reuses `tool_start_frame` and that same `ToolFailFrame`
construction. Do not write a second literal or a second frame shape.
`tool_start_frame` already handled raw provider argument strings, including
unreadable ones, before 035. So the model's raw text is a valid
`ToolCall.arguments` for it. If it is not, stop and report rather than editing
`frames.py`.

### `backend/app/services/tools/seam.py`

`dispatch` writes the tool row on the seam's own short-lived connection.
**Harvest gap:** the report names `dispatch` as the writer, but not the helper
it writes through. The skeleton locates that write in `seam.py` (or in the
`services/messages.py` function it calls) and freezes the call that
`compose.py` makes. Two cases:

- **The write is already importable** (a public function in `seam.py` or
  `messages.py`): `seam.py` is not edited.
- **The write is private to `seam.py`**: the only permitted edit is to make it
  callable from `compose.py` (rename to public, or add a thin public wrapper).
  The row it writes, its connection handling and `dispatch`'s behaviour do not
  change.

In either case the rejected row must be exactly the row a failed dispatch
writes (DoD-10). The only differences are that its `arguments` is the model's
raw text, and its `tool_name` is the model's name verbatim. If writing that row
needs anything beyond the two cases above, stop and report. Do not widen the
Source files.

## Logging

The seam already logs a failed dispatch. The rejection log is written in
`compose.py` at the same level and with the same logger convention, and it
carries only the tool name and the rejection kind (DEC-035-18). Because the
arguments are roleplay-derived text, they are never logged.

## Test notes (for the test-coder, from the spec)

- **The fake library's tolerant mode** (`FakeToolLibraryClient` in
  `test_llm_gateway_compose.py`) accepts `tool_errors` and `on_tool_event`, and
  plays a scripted run in order:
  - text pieces go to `on_delta`;
  - each scripted call produces a `start` event first;
  - a valid call is checked against `inspect.signature`, invoked, and followed
    by a `result` event;
  - a rejected call (an unoffered name, `""`, unreadable or non-object
    arguments, or an undeclared argument name) is followed by an `error` event
    of the matching kind, with the fixed text above returned to the model. The
    callable is never invoked.

  Every event is awaited if the observer returns an awaitable. Events may carry
  a provider `call_id` and an `output` sentinel, which is how DoD-5 and DoD-7
  become observable. In the default (strict) mode, the fake keeps its 0.2.0
  raising behaviour for the retired-tests audit.
- **Retire** `test_compose_unoffered_tool_name_is_unreachable__DoD10`,
  `test_compose_unknown_argument_name_is_unreachable__DoD10` and
