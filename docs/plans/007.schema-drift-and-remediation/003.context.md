## Borrowed interfaces, by module path and role

- **`backend/app/db/drift.py`** (steps `001`, `002`) — the report value types, the two
  shape readers, the comparison and the report builder. `db/sync.py` imports it; **the
  reverse import is a defect** and step `002` DoD-18 pins it.
- **`backend/app/errors.py`** (`001`) — `DomainError` with its `code` / `http_status` class
  attributes and `to_wire()`, and `register_exception_handlers`. The two new subclasses
  follow `SecretRefError`'s and `AlreadyConfiguredError`'s shape exactly.
- **`backend/app/db/engine.py`** (`001`) — the `connect` event listener that sets
  `PRAGMA foreign_keys = ON` and `PRAGMA journal_mode = WAL` on **every** connection, and
  `get_connection`, which opens **no** transaction. Both matter here: the transaction is
  this module's to open, and the pragma is this module's to restore.
- **`backend/tests/conftest.py`** (`001`) — `db_settings` / `db_engine`, real `.sqlite`
  **files**. **No mock may stand in for SQLite here**: what is under test is what the
  create-copy-drop-rename dance actually does to real rows.

## `register_exception_handlers` is not to be "fixed"

`errors.py` registers its handler with the decorator form
`app.exception_handler(DomainError)(handler)` **deliberately** — mypy fails on
`add_exception_handler` under the pinned FastAPI. Leave it. This step appends two
subclasses and touches nothing else in the module; **no second handler is registered**,
because the base-class handler already covers every subclass.

`backend/tests/test_errors.py` already exists and is feature `001`'s. This step's test work
extends it for the two new codes; the existing assertions about the envelope and about the
handler logging only `code` / `http_status` must keep passing.

## The Alembic surface actually used

`op.batch_alter_table(..., recreate="always")` (or its equivalent), driven from an
`alembic.migration.MigrationContext` configured against **the request's own
`Connection`**, with an `alembic.operations.Operations` built on it. Nothing else from the
library is imported — no `alembic.config`, no `ScriptDirectory`, no `EnvironmentContext`,
no `command.*`. `context.md` D6 lists the four negatives and `backend-structure.md` says
why they are written as explicit negatives: the library normally implies all four, and
*"'we use Alembic' without [the reason] is how a `versions/` directory arrives later"*.

Batch mode wants to know the table's **current** reflected shape and its **target** shape.
The target is the registry's `Table`; whether the current one is reflected by Alembic
itself or handed in from `db/drift.py` is the skeleton's call — the **contract** is DoD-6
through DoD-9 and the copy rule in D5.

## The pragma-inside-a-transaction trap

**`PRAGMA foreign_keys` is a no-op while a transaction is open.** SQLite ignores the
statement rather than erroring, so code that writes

```
with conn.begin():
    conn.exec_driver_sql("PRAGMA foreign_keys = OFF")
    ...rebuild...
```

looks correct, passes a reading, and enforces foreign keys throughout the rebuild anyway.
The order in `context.md` D8 is therefore load-bearing: pragma off → `begin()` → rebuild →
`foreign_key_check` → commit → pragma on. DoD-13 exists because the restore on the
**failure** path is the half that gets forgotten, and the connection is pooled — a Sync
that left the pragma off silently disables foreign keys for every later request served on
that connection.

## What "the table is left exactly as it was" means for DoD-11

Not "close enough". After a failed rebuild the verifier's bar is: the same column set, the
same declared types, the same indexes, the same rows with the same values, the same drift
status the report gave before the attempt, and **no `_alembic_tmp_*` entry in
`sqlite_master`**. That is one transaction plus the temp table living inside it — a
best-effort partial apply is explicitly rejected by `context.md` D5, because a
half-rebuilt table is a worse state than a drifted one.

## Why the table name is resolved here and not in the router

`context.md` D9. The router holds no rule, so it hands down the whole registry and the raw
name. This module looks the name up in `metadata.tables` and raises `unknown_table` when it
is absent. Two things follow, and DoD-15 tests both:

- **the raw string never reaches SQL** — every DDL statement is emitted from the registry's
  own `Table` object, so a name carrying quotes, a semicolon or a comment marker is
  refused by the lookup rather than executed;
- a name that exists in the live database but not in the registry is **also** refused — the
  registry is the source of truth and this feature offers no operation on a table it cannot
  describe.

## Gotchas

- **Create and Sync differ in exactly one case**: a drifted table. Everything else is the
  same code path. Resist writing Create as "call Sync and hope" — DoD-3 requires Create to
  be provably incapable of a drop, and that is a property of its own branch, not of a
  comment.
- **Recreating indexes is part of the rebuild, not a step after it.** A dropped-and-renamed
  table does not carry its old indexes forward in a way that matches the declaration, and a
  Sync that leaves the index set wrong reports drifted immediately afterwards — which
  DoD-9 catches.
- **`journal_mode = WAL` is already set per connection** and is not touched here.
- **No progress reporting, no row count, no "N rows copied" log line** (R5). The operation
  returns a report and nothing counted.
- **The re-derived report in the return value does not make the frontend re-load
  optional.** `ui-conventions.md`'s never-optimistic rule still binds step `006`.
