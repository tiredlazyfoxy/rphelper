# Step 003 — step-specific context

Feature-wide facts are in `context.md`: **D2** (check order), **D3** (level `session`),
**D8** (two functions, level-restricted inputs), **D12** (imports), the **Wire contract**
level rules, and the backend **Test conventions**. Only what is narrow to this step is
below.

## The one read

`get_session_configuration` reads, in one select:

- `sessions` (scoped `sessions.id = :session_id AND sessions.user_id = :caller`): the
  model pair, `system_prompt`, three `tool_*`, two languages, `character_id`;
- `characters` joined on `characters.id = sessions.character_id AND characters.user_id =
  :caller`: `system_prompt`, three `tool_*`. **Do not select the character's model
  columns.** The resolver input cannot hold them, and selecting them invites reading them;
- `users` joined on `users.id = :caller`: `rp_language`, `preferred_language`.

An INNER join on all three is correct: a session always has its character (FK, NOT NULL,
same owner) and the caller's user row exists. No row → `SessionNotFoundError`. Use the
module's own private read context. It leaves no transaction open (as every service read;
`002.context.md` notes the posture).

`resolve_model_for_use` reads only the session's model pair (owner-scoped), then calls
`first_enabled_chat_model` to answer "is anything enabled?" (none → D2 step 1). Then step
2, then `validate_chat_model(..., ModelRefLevel.SESSION)`.

## Generic setting value

Two concrete frozen dataclasses (text and boolean) or one generic dataclass, the
skeleton's choice. Either way the field names are exactly `session`, `inherited`,
`inherited_level`, `value`, `level`, so `001`'s response models build from attributes.
`ConfigLevel` members must equal the strings `"session"`, `"character"`, `"user"`,
`"default"`, so the response serialises them as plain strings.

## Test shape

- `test_configuration_resolver.py` tests the pure functions with hand-built inputs
  (DoD-1..5) and the two connection-taking functions against a `create_all` database
  with raw-inserted users, characters, sessions, `llm_servers` and `models` (DoD-6..9).
- DoD-5's signature check may use `inspect.signature` and `dataclasses.fields`. The
  skeleton freezes the parameter names; the test reads them from `## Skeleton`.
- DoD-9's "byte-identical" is a raw select of the whole session row before and after.
- DoD-10 reads the module source (as 015 `003`'s import test).
