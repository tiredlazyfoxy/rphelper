## Seam details this step binds to (021, B — pending)

- `dispatch` takes the provider `ToolCall` (call id, name, raw arguments string), the
  `ToolScope`, the offered tool names, the registry, the engine and the id generator. It
  returns a dispatch result holding the frame and the tool `ChatMessage`. It opens a fresh
  connection for `run` and closes it in a `finally`. It writes the tool row on a separate
  short-lived connection. Exact names come from 021's `## Skeleton`.
- `ToolScope` is built in tests directly from seeded ids or through 021's `build_tool_scope`.
  Either is acceptable. `build_tool_scope` proves the owner read.
- `ToolFailedError`'s constructor shape (detail carrying the tool name) is frozen in 021
  `001`'s `## Skeleton`.
- The production registry's exact name and type (a read-only mapping) are frozen in 021
  `004`'s `## Skeleton`. The registry dependency in `routers/stream.py` returns it, so the
  registration reaches production with no router edit.

## The import cycle, and the form that avoids it

`seam.py` must import the adapter module to build its registry constant. The adapter needs
`ToolOutcome` (and `ToolScope` for annotations) from `seam.py`. If both are top-level
imports, importing the adapter module first fails:

- the adapter module imports the seam;
- the seam then imports the adapter module, which is only partly initialised.

Known-good form:

- `seam.py` imports the adapter at the top, as normal.
- The adapter module imports seam names only under `TYPE_CHECKING`, with postponed
  annotations.
- The adapter imports `ToolOutcome` inside the function that constructs it.

DoD-14 pins the result, not the form. If the project's ruff configuration rejects
function-local imports, raise it with the skeleton rather than adding a `noqa`.
