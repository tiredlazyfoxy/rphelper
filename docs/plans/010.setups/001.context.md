# Step 001 — step-specific context

Feature-wide facts are in `context.md`: **D7** (columns, FKs, index), **D8** (not-found
and name rules), **D5** (no `character_id` in a body), the **Wire contract** (the `Setup`
shape), **Test landmines**, and backend **Test conventions**. 009's
`001.context.md` holds the registry, error-class and model patterns this step follows
("Registry patterns to follow", "Error-class pattern", "Model patterns"). They are cited,
not restated. Only what is narrow to this step is below.

## Applying 009's patterns here

- The id column form, the `ForeignKey("…")` spelling and nullable-text form are 009
  `001.context.md`'s. `character_id` uses the same column type as `user_id`
  (`BigInteger` with the SQLite `Integer` variant, matching the referenced PK).
- The composite index: declare it the way the registry declares single-column indexes,
  with two columns, `user_id` first. The drift report compares indexes by (column list,
  uniqueness), not by name, so the column list must be exactly `("user_id",
  "character_id")`, non-unique. The name is free.
- `setups` goes **after** `characters` in `schema.py`, because its FK names it. Both
  registry-literal guard tests (`test_every_registry_table_is_a_literal_in_the_schema_module`,
  `test_no_other_app_module_defines_its_own_table`) must keep passing unchanged.
- `SetupResponse` uses `SnowflakeOut` for **both** `id` and `character_id`. A bare `int`
  `character_id` would leak a JS-unsafe number onto the wire (`data-model.md`
  Identifiers).
- One annotated stripped/non-empty name type serves both request models, exactly as 009's
  models express it.

## The undeclared-name swap (DoD-9)

009 `001` DoD-12 replaced `"characters"` with `"setups"` and warned that 010 must swap
again. To end the chain, pick a name **no feature will ever declare**, rather than the
next planned table (`"memos"` would break again in `015`). Any clearly non-domain name is
fine (for example `"no_such_table"`), as long as it is a valid table identifier the route
accepts as a path segment and is not already in the list. If the list already holds such
a name, drop the `"setups"` entry instead of adding a duplicate. The coverage of "an
undeclared name answers 404 `unknown_table`" must remain.

## The delta (DoD-1, DoD-8)

009's test-coder chose one of two later-table-proof shapes for 006's and 009's deltas
(009 `001.context.md`, "The delta pattern"). The 010 delta uses **the same shape**:

- if the file asserts membership plus absence, assert `"setups"` membership and that the
  registry has no table beyond those declared through 010 that 010 could have added;
- if the file subtracts a "declared by later features" set, add `"setups"` to that set
  for 006's and 009's deltas (DoD-8), and write 010's own delta against a later-features
  set that starts empty.

The test-coder reads the file to see which shape it has. It is a test file in this step's
scope.

## Gotcha — `/api/health` on existing databases

Same as 009 `001.context.md`: registering `setups` makes an existing database report
`schema: "missing"` until an administrator presses Create. That is designed behaviour.
Tests build schema with `create_all` and are unaffected.
