# Step 003 — The sessions router

## Goal

Add `routers/sessions.py`, the six routes of the wire contract on one router with
router-level `require_user` (D9). Each route converts the service's `RpSession` into the
response models; no `PATCH` and no `DELETE` route exists. Register the router in
`main.py` after the setups router.

## Source files

backend/app/routers/sessions.py
backend/app/main.py

## Test files

backend/tests/test_sessions_router.py

## Interface intent

**`routers/sessions.py`** (new)

- **`router`**: an `APIRouter` with `require_user` as a router-level dependency,
  declaring full paths for both families (`/api/sessions…` and
  `/api/characters/{character_id}/sessions`).
- **List-all handler**: `GET /api/sessions`. Takes the boolean query parameter
  `include_archived` (default false), the current user and the connection. Calls
  `list_sessions`; answers a `SessionListResponse`.
- **List-for-character handler**: `GET /api/characters/{character_id}/sessions`. Takes the
  path id (inbound snowflake alias), `include_archived`, the current user and the
  connection. Calls `list_character_sessions`; answers a `SessionListResponse`.
- **Start handler**: `POST /api/characters/{character_id}/sessions`, status 201. Takes the
  path id, an **optional** `StartSessionRequest` body (an omitted body means no setup), the
  current user, the connection and the id generator. Calls `start_session` with the
  body's `setup_id` (or `None`); answers a `SessionResponse`.
- **Get handler**: `GET /api/sessions/{session_id}`. Calls `get_session`; answers a
  `SessionResponse`.
- **Archive handler**: `POST /api/sessions/{session_id}/archive`. **Restore handler**:
  `POST /api/sessions/{session_id}/restore`. Each calls its service operation and answers
  a `SessionResponse` with status 200.
- A private conversion from `RpSession` to `SessionResponse`.
- `SessionNotFoundError`, `CharacterNotFoundError`, `SetupNotFoundError` and
  `SetupArchivedError` propagate to the already-registered domain handler. The router
  catches nothing.
- **No `PATCH` and no `DELETE` handler.**

**`main.py`** (extended)

- Includes the sessions router immediately after the setups router.

## Definition of done

1. `[test]` With no login cookie, each of the six routes answers 401 with code
   `not_authenticated`.
2. `[test]` A signed-in roleplayer who created character C through `POST /api/characters`
   posts `{}` to `/api/characters/<C>/sessions`. It answers 201 with `id` and
   `character_id` JSON **strings** of decimal digits (`character_id` equal to C's id
   string), `setup_id` null, `setup_name` null, `archived_at` null, and `last_used_at`
   equal to `created_at`. `GET /api/sessions/<id>` answers it, and both
   `GET /api/sessions` and `GET /api/characters/<C>/sessions` contain a row with that id.
   A POST with **no body** and one with `{"setup_id": null}` each also answer 201 with
   `setup_id` null. (US-026.AC-1, US-024.AC-1, US-024.AC-3, R2)
3. `[test]` With setup S created under C through `POST /api/characters/<C>/setups`,
   posting `{"setup_id": "<S>"}` answers 201 with `setup_id` equal to S's id string and
   `setup_name` equal to S's name. A second session started with the same setup also
   answers 201, and C's listing shows both with that `setup_id`. (US-025.AC-1, UC-022, D10)
4. `[test]` Posting a `setup_id` that is a setup under another of the caller's characters,
   another user's setup, or an id that exists for nobody answers 404 with code
   `setup_not_found` and an empty `detail`, and C's listing is unchanged afterwards. (D12,
   R5)
5. `[test]` After `POST /api/setups/<S>/archive`, posting `{"setup_id": "<S>"}` answers 409
   with code `setup_archived` and an empty `detail`, and C's listing is unchanged. (D2, D12)
6. `[test]` As user B, `GET` and `POST` on `/api/characters/<A's character>/sessions`
   each answer 404 with code `character_not_found` and an empty `detail`; the body equals
   the body for a character id that exists for nobody, and A's listing holds no session
   created by B. (R5, D12)
7. `[test]` As user B, `GET /api/sessions/<A's session>`, `POST …/archive` and
   `POST …/restore` each answer 404 with code `session_not_found` and an empty `detail`;
   the body equals the body for a session id that exists for nobody, and A's session is
   unchanged when read back as A. (US-029.AC-1, R5, D12)
8. `[test]` With A owning two characters with sessions and B owning one with sessions, A's
   `GET /api/sessions` (with and without `include_archived=true`) contains only A's
   sessions, and A's per-character listing only that character's. (US-029.AC-1, R5)
9. `[test]` `POST /api/sessions/<id>/archive` answers 200 with `archived_at` a string. Both
   default listings then omit the session, both `include_archived=true` listings include
   it, and `GET /api/sessions/<id>` still answers 200 with it. Archiving again answers the
   same `archived_at`. `last_used_at` is unchanged. (US-027.AC-1, R6, D13)
10. `[test]` `POST /api/sessions/<id>/restore` on that archived session answers 200 with
    `archived_at` null; both default listings contain it again; and
    `GET /api/sessions/<id>` answers the same `id`, `character_id`, `setup_id`,
    `setup_name`, `created_at` and `last_used_at` as before the archive. (US-027.AC-2,
    US-027.AC-3 — the row half)
11. `[test]` Three sessions started under C in sequence come back newest first from both
    `GET /api/characters/<C>/sessions` and `GET /api/sessions`; with sessions under two
    characters started alternately, `GET /api/sessions` returns them in reverse start
    order regardless of character. (US-028.AC-1, D14, D3)
12. `[test]` Two `GET /api/sessions/<id>` calls leave `last_used_at` and `updated_at`
    unchanged. (D3)
13. `[test]` `DELETE /api/sessions/<id>`, `DELETE /api/sessions`,
    `DELETE /api/characters/<C>/sessions` and `PATCH /api/sessions/<id>` answer 405, and
    the session is still returned by `GET /api/sessions/<id>` afterwards. (R6, D9)
14. `[test]` After `POST /api/characters/<C>/archive`, listing C's sessions and starting a
    session under C both succeed (200 / 201), and `GET /api/sessions/<id>` of a session
    under C still answers 200. (D2)
15. `[test]` After the setup S of an existing session is archived through
    `POST /api/setups/<S>/archive`, `GET /api/sessions/<id>` and the listings still show
    that session's `setup_id` and `setup_name`. (D10, 010 D3)
16. `[test]` A non-numeric path id (`/api/sessions/abc`, `/api/characters/abc/sessions`)
    answers 422, and so does a start whose `setup_id` is `"abc"`.
17. `[test]` 009's and 010's routes still behave as before with this router registered:
    `GET /api/characters/<C>` and `GET /api/characters/<C>/setups` answer 200, and
    `POST /api/characters/<C>/archive` answers 200. (Registration order, D9)
18. `[manual/live]` Against a running dev backend whose database pre-dates 011: after the
    administrator presses Create for `sessions`, `curl`-ing `GET /api/sessions` with a
    roleplayer's cookie answers `{ "sessions": [] }`, and a `POST` to a character's
    sessions answers 201.
