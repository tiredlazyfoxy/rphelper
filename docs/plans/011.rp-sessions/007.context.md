## Why the workspace state is a parameter, not a field

The section state is a data class with observable fields only. Holding a reference to the
workspace `SessionsState` as a field would make one store reach into another invisibly;
passing it to the three effects that mutate it keeps "which stores does this touch"
readable at the call site (`frontend-structure.md`'s props-not-context reasoning applied
to functions). The section component holds both and passes both (`008`).

## Why navigation is a callback

`startSessionFromSection` does not import the router. It reports the new id through
`onStarted`, and the component navigates (`008`), the same split as 009's `submitCreate`
with `onCreated`. That keeps the effect testable with no router.

## The setup choices are a separate load

`loadSetupChoices` is independent of `loadSectionSessions` so that a failure of one never
blocks the other: a failed setup list must not stop the roleplayer starting with "No
setup" (US-024.AC-3, D18).

A successful reload that no longer contains the selected setup (archived in 010's section
meanwhile) resets the selection to "No setup" (DoD-4), so the Select never displays a value
that is not among its options and a start never sends an id the roleplayer can no longer
see. A failed reload keeps the selection: the server will still answer a stale one with
409 `setup_archived`, which lands in `startError` like any other failure.
