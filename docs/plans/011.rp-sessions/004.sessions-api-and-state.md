# Step 004 — The sessions API client and the workspace sessions state

## Goal

Add `app/sessionsApi.ts`, the `Session` type and the six calls the frontend makes over the
shared client. Add `app/sessionsState.ts`, the one workspace sessions data class (working
rows, load status) with its load effect, the pure apply-a-row upsert (D15), and the two
pure derivations the tree needs: a character's sessions in last-use order (US-089) and
the characters ordered by newest session use (D6).

## Interface intent

**`app/sessionsApi.ts`** (new)

- **`Session`**: type mirroring the wire object field for field (`id`, `character_id`
  strings; `setup_id` string or null; `setup_name` string or null; `archived_at` string or
  null; `last_used_at`, `created_at`, `updated_at` strings). No renaming layer.
- **`isSessionArchived`**: pure. Takes a `Session`; returns whether `archived_at` is
  non-null.
- **`fetchSessions`**: takes `includeArchived` (boolean) and an optional signal. GETs
  `/api/sessions` (with `?include_archived=true` only when true); resolves to the unwrapped
  array.
- **`fetchCharacterSessions`**: takes a character id, `includeArchived` and an optional
  signal. GETs the character's sessions listing the same way; resolves to the array.
- **`fetchSession`**: takes a session id and an optional signal. GETs one session.
- **`startSession`**: takes a character id, a setup id (string) or `null`, and an optional
  signal. POSTs to the character's sessions collection with the JSON body
  `{ setup_id: <the id or null> }`; resolves to the created session.
- **`archiveSession`** / **`restoreSession`**: take a session id and an optional signal.
  POST to the action route; resolve to the session.
- All failures are the shared client's `ApiError`s, rethrown unchanged. Ids are never
  coerced.

**`app/sessionsState.ts`** (new)

- **`SessionsState`**: data class, observable fields only: `sessions` (array of
  `Session`, starts empty), `status` (`"idle"`, `"loading"`, `"ready"` or `"failed"`,
  starts `"idle"`). No archived flag: the workspace list is always the working list (D5).
- **`loadSessions`**: effect. Takes the state and an optional signal. Sets `"loading"`,
  requests the working list of all the caller's sessions, and on success writes the rows
  **in the order received** with `"ready"`. On failure writes `"failed"` and leaves
  `sessions` as they were. Writes nothing once aborted; never rejects.
- **`applySession`**: takes the state and one server-returned `Session` and upserts it by
  D15: archived → removed if present, never inserted; working → removed if present, then
  inserted at its `last_used_at`-descending position (`004.context.md`).
- **`sessionsOfCharacter`**: pure. Takes a list of sessions and a character id; returns
  that character's sessions in the given order.
- **`orderCharactersByUse`**: pure. Takes a list of characters (only each character's
  `id` string is read) and a list of sessions; returns a new list of the same characters
  ordered by D6: characters with at least one session first, by the greatest
  `last_used_at` among their sessions, most recent first; then characters with no session,
  in their given order. Ties keep the given order. Does not mutate its inputs.

## Definition of done

1. `[test]` `fetchSessions(false)` requests exactly `GET /api/sessions`;
   `fetchSessions(true)` requests exactly `GET /api/sessions?include_archived=true`.
   `fetchCharacterSessions("7250000000000000001", false)` requests exactly
   `GET /api/characters/7250000000000000001/sessions`, and with `true` adds
   `?include_archived=true`. Each resolves to the payload's `sessions` array with every
   `id`, `character_id` and `setup_id` the identical string (or null) the payload carried.
2. `[test]` `fetchSession(id)` GETs `/api/sessions/<id>`. `startSession(characterId, null)`
   POSTs `/api/characters/<characterId>/sessions` with the JSON body exactly
   `{"setup_id": null}`; `startSession(characterId, "7250000000000000009")` with exactly
   `{"setup_id": "7250000000000000009"}`. `archiveSession` / `restoreSession` POST
   `/api/sessions/<id>/archive` / `/restore`. Each resolves to the response's session.
   (US-026.AC-1, US-024.AC-1, US-025.AC-1, R2)
3. `[test]` A 404 envelope with code `session_not_found` makes `fetchSession` reject with
   an `ApiError` whose `code` is `session_not_found`; a 409 envelope with code
   `setup_archived` makes `startSession` reject with that code. `isSessionArchived` is true
   for a session whose `archived_at` is a string and false when it is null.
4. `[test]` A fresh `SessionsState` has no rows and `status` `"idle"`. `loadSessions` sets
   `"loading"` while pending, requests exactly `GET /api/sessions`, then sets `"ready"`
   with exactly the server's rows in the server's order. On a failed request it sets
   `"failed"`, keeps the previous rows and resolves without throwing; with its signal
   aborted before the response settles it writes nothing. (US-028.AC-1)
5. `[test]` `applySession` with an absent working row inserts it by `last_used_at`
   descending: newer than all → first; between two existing rows → between them; older
   than all → last. With a present working row whose `last_used_at` is unchanged, it stays
   at the same index with the new values. (US-026.AC-1, US-089.AC-1)
6. `[test]` `applySession` with an archived row removes that id when present and leaves
   the rows unchanged when absent. Applying the restored (working) version of a removed
   row puts it back at its `last_used_at` position. (US-027.AC-1, US-027.AC-2)
7. `[test]` `sessionsOfCharacter` returns only the given character's sessions, in the
   given order, and an empty list for a character with none. (US-089.AC-1)
8. `[test]` `orderCharactersByUse`: given characters `[A, B, C]` (in that given order)
   where C has a session with the most recent `last_used_at`, A one older, and B none, it
   returns `[C, A, B]`. With no sessions at all it returns the given order. Two
   characters with no sessions keep their relative given order. The inputs are not
   mutated. (D6)
9. `[test]` An `autorun` reading `sessions` re-runs after `applySession`, and one reading
   `status` re-runs after `loadSessions` settles (the writes are MobX actions on observable
   fields).
