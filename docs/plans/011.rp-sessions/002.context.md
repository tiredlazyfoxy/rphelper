## Scope predicates — what each statement carries

| Operation | Statements |
|---|---|
| parent check (start, per-character list) | `SELECT characters.id FROM characters WHERE id = :character_id AND user_id = :user_id`. No `archived_at` predicate |
| setup check (start, when `setup_id` given) | `SELECT setups.id, setups.name, setups.archived_at FROM setups WHERE id = :setup_id AND user_id = :user_id AND character_id = :character_id`. No row → `SetupNotFoundError`; `archived_at` set → `SetupArchivedError` |
| start | parent check, setup check, then `INSERT … VALUES (… user_id = :user_id, character_id, setup_id …)`, all inside one `begin()` |
| list (both) | `sessions LEFT OUTER JOIN setups ON setups.id = sessions.setup_id AND setups.user_id = :user_id`; `WHERE sessions.user_id = :user_id` (and `sessions.character_id = :character_id` for the per-character list, after its parent check in the same transaction) and, unless `include_archived`, `sessions.archived_at IS NULL`; `ORDER BY sessions.last_used_at DESC, sessions.id DESC` |
| get / locate-for-write | the same join, `sessions.id = :id AND sessions.user_id = :user_id` |
| archive / restore | the UPDATE's own `WHERE` is `id = :id AND user_id = :user_id` too; it sets `archived_at` and `updated_at` only |

The join filters on **`setups.archived_at` not at all** (D10: an archived setup still
labels its sessions). A row that exists for another user and one that exists for nobody
take the same path and raise the same error (R5).

## Returning the value after a write

Archive and restore return the row as it stands after the write, **with** `setup_name`.
The simplest correct shape is: locate (joined select) inside the `begin()`, decide no-op
or write, and after a write re-read with the same joined select inside the same block. The
create builds its value from the inserted fields plus the setup name the setup check
already read; it does not need a re-read.

## Why not one join for the parent check

As 010 `002.context.md` explains: a join returns no rows both for "no sessions" and "not
your character", and the route must tell them apart (`[]` versus 404).

## Imports

`sessions`, `characters`, `setups` Tables from `app.db.schema`; `SessionNotFoundError`,
`SetupArchivedError`, `CharacterNotFoundError`, `SetupNotFoundError` from `app.errors`;
`SnowflakeGenerator` from `app.ids` (for the annotation). Nothing from any
`app.services.` module (DoD-16). The value object's name `RpSession` and the operation
names are fixed by D11 so nothing here reads like `services/auth.py`.

## Test seeding

Users first, then characters (raw insert into `characters`: `id`, `user_id`, `name`,
`sheet`, `archived_at`, `created_at`, `updated_at`), then setups (raw insert into
`setups`: `id`, `user_id`, `character_id`, `name`, `description`, `archived_at`,
`created_at`, `updated_at`). Sessions through `start_session`, except DoD-7's
out-of-order rows, which are raw inserts with chosen fixed-width `last_used_at` /
`created_at` values. DoD-13 archives the setup with a raw update. DoD-3 / DoD-4 / DoD-5 /
DoD-15 count rows in the `sessions` and `setups` tables directly.
