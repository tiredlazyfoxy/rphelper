# Step 001 — step-specific context

Feature-wide facts are in `context.md`: "The `messages` table" (columns), the **Wire
contract** (the `Message` shape, the failure table), **D1**, **D7**, **D9**, **D13**, and
**Test conventions**. 011's `001.context.md` ("Applying the patterns here", "The delta",
"Gotcha — `/api/health` on existing databases") and the 009 / 010 contexts it cites hold
the registry, error-class and model patterns this step follows. Only what is narrow to this
step is below.

## Applying the patterns here

- `user_id`, `session_id` and `related_to` use the same column type as the referenced
  snowflake PK (`BigInteger` with the SQLite `Integer` variant). `related_to` is a
  self-reference (`ForeignKey("messages.id")`) inside the `messages` literal itself.
- The CHECK is a **named** table-level `CheckConstraint` (for example
  `ck_messages_buried_or_settled`) with the expression `related_to IS NULL OR settled_at IS
  NULL`. `role` and `kind` carry **no** CHECK and no `Enum` type: they are plain `Text`
  (the pydantic boundary constrains what 012 writes).
- Index names follow the registry's `ix_…` form; the drift report keys on (column list,
  uniqueness), so the names themselves are free.
- `messages` goes **after** `sessions` in `schema.py`. The two registry-literal guard tests
  (`test_every_registry_table_is_a_literal_in_the_schema_module`,
  `test_no_other_app_module_defines_its_own_table`) must keep passing unchanged: the
  selectables are not `Table` objects, so they should not trip either guard. If one of
  them does (for example by walking every module-level SQLAlchemy object), that is a
  hand-back, not a test edit.
- The selectables are declared after the `messages` literal. They are plain `select(...)`
  values with a `.where(...)`; callers in `002` / `003` narrow them with further
  `.where(...)` / `.order_by(...)` / `.limit(...)` on the selectable's own columns.

## `MessageResponse.role` / `kind` typing

The skeleton may type `role` and `kind` as plain (optional) strings or as literals of the
known values. A literal would make serialisation fail on a value the database holds but the
model does not know; 012 writes only known values, so either is acceptable. DoD-8 pins only
that `kind` `None` serialises as `null`.

## The delta (DoD-1)

Same two-shape rule as 011 `001.context.md` "The delta": if the file asserts membership
plus absence, assert `"messages"` membership and that nothing beyond the tables declared
through 012 could be 012's; if it subtracts a "declared by later features" set, add
`"messages"` to that set for 006's, 009's, 010's and 011's deltas and write 012's own delta
against a later-features set that starts empty. The test-coder reads the file to see
which.

## Test seeding (DoD-4, DoD-5)

Raw inserts in FK order: `users`, `characters` (009's columns), `sessions` (011 D8's eight
columns, `setup_id` NULL), then `messages` rows with chosen ids. The buried row's
`related_to` points at the settled row's id. `PRAGMA foreign_keys` is on through the
engine factory, so the FK failures in DoD-4 are real.

## Gotcha — `/api/health` on existing databases

As 011: registering `messages` makes an existing database report `schema: "missing"` until
an administrator presses Create. Designed behaviour; tests build schema with `create_all`.
