# Step 004 — The stream router

## Goal

Add `routers/stream.py`, the seven JSON routes of the wire contract on one router with
router-level `require_user` (D12), each calling exactly one service operation from `002` or
`003` and converting its value into the `001` models; register it in `main.py` after 011's
sessions router. No discard, stop, compose or delete route exists.

backend/app/routers/stream.py
backend/app/main.py

## Test files

backend/tests/test_stream_router.py

## Interface intent

**`routers/stream.py`** (new)

- **`router`**: an `APIRouter` with `require_user` as a router-level dependency, declaring
  full paths.
- **List-entries handler** — `GET /api/sessions/{session_id}/entries`: calls
  `list_entries`; answers an `EntryListResponse`.
- **File-partner handler** — `POST /api/sessions/{session_id}/entries`, status 201: takes
  a `FilePartnerRequest`, the connection, the id generator and the current user; calls
  `file_partner_entry` with the body's text; answers a `MessageResponse`.
- **List-zone handler** — `GET /api/sessions/{session_id}/zone`: calls `list_zone`;
  answers a `ZoneResponse`.
- **Append handler** — `POST /api/sessions/{session_id}/zone/messages`, status 201: takes
  an `AppendMessageRequest`; calls `append_message`; answers a `MessageResponse`.
- **Settle handler** — `POST /api/sessions/{session_id}/settle`, status 200, no body:
  calls `settle`; answers a `SettleResponse`.
- **Re-open handler** — `POST /api/sessions/{session_id}/reopen`, status 200, no body:
  calls `reopen`; answers a `ReopenResponse`.
- **Edit handler** — `PATCH /api/messages/{message_id}`, status 200: takes an
  `EditMessageRequest`; calls `edit_message_text`; answers a `MessageResponse`.
- Path ids are inbound snowflakes. Private conversions from `StreamMessage`,
  `SettleResult` and `ReopenResult` to the response models. Domain errors propagate to the
  registered handler; the router catches nothing and contains no SQL.

**`main.py`** (extended) — includes the stream router immediately after the sessions
router.

## Definition of done

1. `[test]` With no login cookie, each of the seven routes answers 401 with code
   `not_authenticated`.
2. `[test]` On a session created through 011's routes, `POST …/zone/messages` with
   `{"text": "Hello there."}` answers 201 with a `Message` whose `id` and `session_id` are
   decimal-digit strings (`session_id` equal to the session's id), `role` `"user"`,
   `kind` null, `settled_at` null, `text` `"Hello there."`, and exactly the eight wire
   keys. `GET …/zone` then returns `{ "messages": [that message] }` and `GET …/entries`
   returns `{ "entries": [] }`. A body that also carries `"role": "assistant"` still
   stores `role` `"user"`. (UC-083 step 2, D12)
3. `[test]` `POST …/settle` on that zone answers 200 with `entry_id` equal to the
   message's id, `kind` `"turn"`, `buried_ids` `[]`; afterwards `GET …/zone` is empty and
   `GET …/entries` holds the message with `kind` `"turn"`, `settled_at` a string and the
   text unchanged. No partner entry was required first. (US-031.AC-1, US-034.AC-1,
   US-135.AC-1, US-127.AC-1, US-127.AC-2)
4. `[test]` Append `"She walks. ((be dramatic)) Then sits."` and settle: the entry's text
   is `"She walks. Then sits."`. Append `"((Let's skip ahead))"` and settle: the entry has
   `kind` `"decision"` and its text unchanged, and is listed in `GET …/entries` with that
   kind. (US-130.AC-1, US-129.AC-1, US-122 backend precondition, D5)
5. `[test]` Append two messages, raw-insert an assistant-role zone row after them through
   the test engine, settle: `entry_id` is the assistant row's id, `buried_ids` the two
   appended ids ascending; `GET …/entries` shows the assistant row with `role`
   `"assistant"`, and neither appended message appears in `GET …/entries` or
   `GET …/zone`. (US-126.AC-1, R11)
6. `[test]` `POST …/entries` with `{"kind": "partner", "text": "Partner says ((hi)) there"}`
   answers 201 with `kind` `"partner"`, `role` `"user"`, `settled_at` a string, and the
   text byte-for-byte as sent; it appears in `GET …/entries`, not in `GET …/zone`. Two more
   partner posts in a row all appear in `GET …/entries` in posting order. (US-121.AC-1,
   US-121.AC-2, UC-031)
7. `[test]` `POST …/entries` with `kind` `"turn"`, `"decision"`, missing, or null answers
   422, and `GET …/entries` is unchanged. (R11 single exception at the boundary)
8. `[test]` `POST …/zone/messages`, `POST …/entries` and `PATCH /api/messages/{id}` with
   text `""`, `"   "`, missing, or null each answer 422 and store nothing / change
   nothing. A text of 500 000 characters is accepted (201) by the append and the partner
   route. (D9, R10, US-035.AC-2)
9. `[test]` `POST …/settle` on an empty zone answers 409 with code `zone_empty`, a
   non-empty `message` and `detail` `{}`. (R11)
10. `[test]` Append three messages and settle; with the zone empty, `POST …/reopen`
    answers 200 with `reopened_id` the head's id and `restored_ids` the two other ids
    ascending; `GET …/zone` then lists all three in their original order with `kind` and
    `settled_at` null, and `GET …/entries` no longer holds the head. `PATCH` on the
    reopened head then answers 200. (US-041.AC-1, US-128.AC-1, D10)
11. `[test]` Settle a group, append one message, `POST …/reopen`: 409 `zone_not_empty`

12. `[test]` `POST …/reopen` answers 409 `nothing_to_reopen` with `detail` `{}` on a new
