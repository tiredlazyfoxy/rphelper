## Borrowed interfaces

## The load fetches both lists together

Both GETs are issued without waiting for each other; the state is written once, after
both succeed, so the screen never shows a record with a stale zone or vice versa. If either
fails, nothing but `status` is written.

## The override rule, precisely

"The record changed" = the new entries list's sequence of `id` strings is not equal to the
held list's (length or any position differs). Comparing kinds or texts is unnecessary:
an entry's kind never changes in place in 013, and a text edit (014) is not a change of
turn order. On the very first load the held list is empty; an override cannot be set
before the first load completes, so clearing it there is harmless either way.

## This module grows in `003`

`003` adds the mutation effects to the same file (one subject, one module —
`frontend-structure.md` "Where a store's file lives"). `busy` is declared here so the
derivations can read it; only `003` writes it.

## Test seeding

Derivation tests construct a `StreamState` and assign `entries`, `zone`, `draft`,
`kindOverride` and `busy` directly inside `runInAction` (or through `setDraft` /
`chooseKind`), with file-local `Message` builders. No render, no network, except DoD-2 and
DoD-3, which stub `fetch` by exact path.
