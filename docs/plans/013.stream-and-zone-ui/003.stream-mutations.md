# Step 003 — The stream's mutation effects

## Goal

Add to `app/streamState.ts` the five effects that change the session: send the composer
(append on *my turn*, file a partner block on *partner*), file a pasted partner block,
settle (appending unsent composer text first), re-open, and commit an in-place zone edit —
each never optimistic, each followed by the re-read it calls for, each failure routed
through `notifyFailure`.

## Source files

frontend/src/app/streamState.ts

## Test files

frontend/tests/app/streamMutations.test.ts

## Interface intent

All five are free functions taking the `StreamState` (from `002`) and an optional signal,
writing inside `runInAction`, writing nothing once the signal is aborted, and never
rejecting. "Re-read entries" writes through `002`'s `applyEntries` (so the override rule
holds); "re-read zone" replaces `zone` with the served list. A failed re-read calls
`notifyFailure` with its error and leaves the held list as it was. "Clear the draft" means:
set `draft` to empty **only if it still equals the text that was sent** — text typed while
the request was in flight is kept (R10).

- **`sendComposer`**: does nothing when the draft is blank. Otherwise sets `busy`, and by
  the effective position:
  - *my turn* — appends the draft verbatim to the zone; on success clears the draft; then
    re-reads the zone. (D6)
  - *partner* — files the draft verbatim as a partner entry; on success clears the draft;
    then re-reads the entries. (D7)
  On failure: `notifyFailure(error)`, the draft is kept, and the same re-read runs. Clears
  `busy` at the end.
- **`filePastedPartner`**: takes the pasted text too. Does nothing when it is blank.
  Otherwise sets `busy`, files it verbatim as a partner entry, then re-reads the entries;
  on failure `notifyFailure(error)` and the re-read still runs. Never touches the draft.
  Clears `busy`. (D7, US-121.AC-1)
- **`settleComposer`**: sets `busy`. If the draft is not blank, first appends it to the
  zone; if that fails: `notifyFailure(error)`, re-read the zone, keep the draft, clear
  `busy`, and stop — no settle request. On append success clear the draft. Then requests
  settle; on failure `notifyFailure(error)`. Then, whatever the settle outcome, re-reads
  **both** lists. Clears `busy`. Does not consult the position or any row's role — the UI
  gates it (D2, US-135).
- **`reopenLast`**: sets `busy`, requests re-open; on failure `notifyFailure(error)`; then
  re-reads both lists; clears `busy`. (D4)
- **`editZoneMessage`**: takes the message id and the edited text too; resolves to whether
  the editor may close. Blank text → no request, resolves true (revert). Text equal to that
  zone row's current text → no request, resolves true. Otherwise PATCHes the message; on
  success replaces **that one row** in `zone` (matched by id string) with the response,
  leaving every other row and their order untouched, and resolves true; on failure
  `notifyFailure(error)`, re-reads the zone, and resolves false. Does not set `busy`.
  (D10, US-115.AC-1)

## Definition of done

1. `[test]` `sendComposer` on *my turn* with draft `"Hello ((calm))"` POSTs exactly
   `/api/sessions/s1/zone/messages` with `{"text":"Hello ((calm))"}`, **then** GETs
   `/api/sessions/s1/zone`; afterwards `draft` is `""`, `zone` is exactly the re-read list,
   no entries request was made, and `notifyFailure` was not called. (D6, US-031.AC-1)
2. `[test]` `sendComposer` on *partner* (override set) with draft `"Partner says ((hi))"`
   POSTs `/api/sessions/s1/entries` with exactly
   `{"kind":"partner","text":"Partner says ((hi))"}`, then GETs the entries; afterwards
   `draft` is `""` and `entries` is the re-read list. (D7, US-030.AC-1, US-121.AC-2)
3. `[test]` `sendComposer` failing with a 500 envelope calls `notifyFailure` once with an
   `ApiError` of that code, keeps the draft unchanged, still re-reads the zone, and ends
   with `busy` false. A blank draft makes no request at all. (R10, D15)
4. `[test]` `busy` is true while `sendComposer`'s POST is pending and false after it
   settles. (D15)
5. `[test]` `filePastedPartner(state, "Pasted block")` POSTs the entries collection with
   exactly `{"kind":"partner","text":"Pasted block"}`, then GETs the entries; the draft is
   unchanged throughout. With zone rows present the request is still made (no zone guard).
   A whitespace-only paste makes no request. (US-121.AC-1, US-030.AC-1, 012 D14)
6. `[test]` After a successful partner filing whose re-read adds an entry, a previously
   set override is cleared, so `effectiveKind` is `"turn"`. (US-120.AC-2, D8)
7. `[test]` `settleComposer` with a blank draft and one zone row POSTs only
   `/api/sessions/s1/settle`, then GETs both the entries and the zone; `entries` and
   `zone` are the re-read lists. (US-135.AC-1, US-127.AC-1, US-127.AC-2, 012 D11)
8. `[test]` `settleComposer` with draft `"My turn text"` POSTs `…/zone/messages` with
   `{"text":"My turn text"}` **then** `…/settle` **then** re-reads both; the draft is `""`
   afterwards. (D2, US-031.AC-1)
9. `[test]` `settleComposer` whose append fails: `notifyFailure` called, **no** settle
   request, the zone re-read, the draft unchanged, `busy` false. (D2, R10)
10. `[test]` `settleComposer` whose append succeeds and whose settle fails with 409
    `zone_empty`: `notifyFailure` called with that code, the draft is `""`, and both lists
    are re-read (the zone now holds the appended row as served). (D2, R10)
11. `[test]` `reopenLast` POSTs `/api/sessions/s1/reopen` then re-reads both lists. A 409
    `nothing_to_reopen` calls `notifyFailure` with that code and still re-reads both.
    (US-128.AC-1, D4)
12. `[test]` `editZoneMessage` with changed non-blank text PATCHes
    `/api/messages/<id>` with exactly `{"text": …}`, replaces only that row with the
    response (other rows and order unchanged), makes no GET, and resolves true. It works
    the same for a row whose role is `assistant`. (US-115.AC-1, D10)
13. `[test]` `editZoneMessage` with blank text, or with text identical to the row's
    current text, makes no request and resolves true. A 409 `message_not_editable`
    failure calls `notifyFailure`, re-reads the zone, and resolves false. (D10)
14. `[test]` Each of the five effects, with its signal aborted before its first response
    settles, writes nothing to `entries`, `zone` or `draft` and calls no `notifyFailure`.
15. `[test]` No effect in this step calls `notifyFailure` on a success path. (D15)
