### DEC-001-2 — `resolve_secret`'s read-side boundary rulings
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 001.backend-foundation · **Step:** 003
- **Date:** 2026-09-28 · **Decided by:** planner
- **Plan-local:** 001 step 003 context "Boundary rulings for `resolve_secret`"
- **Question:** The resolver's docstring covers `"$NAME"`, `None` and "anything else". What happens at the three edges it leaves open?
- **Decision:**
  - A variable that is set but empty resolves to `""`.
  - A bare `"$"` raises `SecretRefError`, because it names no variable.
  - A string that does not start with `$` raises `SecretRefError`. This is the read-side refusal only. Rejecting such a value on write is a separate mechanism (see 006).
  - The environment is read at call time. There is no cache and no import-time read.
- **Reason:** The variable exists, so whether an empty credential is useful is the caller's question. Treating it as missing would make the resolver guess a policy that nothing states. A bare `$` is malformed, not a pointer to an absent variable.
- **Lands in:** `backend/app/secrets.py`
- **Cites:** `backend-structure.md` § The `"$ENV_VAR"` secret-pointer pattern

### DEC-001-3 — What a secret-pointer failure carries, and what the handler logs
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 001.backend-foundation · **Step:** 003
- **Date:** 2026-09-28 · **Decided by:** planner (detail key: skeleton; malformed case: coder)
- **Plan-local:** 001 step 003 context "Redaction, specifically here"; 001 status Notes (step 003)
- **Question:** What does `SecretRefError` put in `detail`, and what does the one domain-error handler write to the log?
- **Decision:**
  - An absent variable raises with `detail == {"variable": NAME}`.
  - A malformed reference (a bare `"$"`, or a non-`$` string) raises with an empty `detail`. Its message never echoes the reference.
  - The handler logs the error `code` and the HTTP status and nothing else. It never logs `detail`.
- **Reason:** A non-pointer reference may itself be a pasted raw credential, so echoing it would leak it. `detail` is where later features put model references, tool names and ids, so logging all of `detail` would sooner or later log something the redaction rule forbids.
- **Lands in:** `backend/app/secrets.py`, `backend/app/errors.py`
- **Cites:** `deployment.md` § The redaction rule; `backend-structure.md` § The error model

### DEC-001-4 — The handler is registered with the decorator form
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 001.backend-foundation · **Step:** 003
- **Date:** 2026-09-28 · **Decided by:** skeleton (confirmed by the coder)
- **Plan-local:** 001 D7 (the registration inference); 001 step 003 skeleton typing note
- **Question:** How does `register_exception_handlers` install the one handler for `DomainError` so that it passes `mypy app`?
- **Decision:** It uses `app.exception_handler(DomainError)(domain_error_handler)`. The app factory calls it once.
- **Reason:** It typechecks cleanly and needs no `type: ignore`.
- **Rejected:** `app.add_exception_handler(DomainError, domain_error_handler)`. It fails mypy with `arg-type`, because Starlette's parameter is invariant on `Exception`.
- **Lands in:** `backend/app/errors.py`, `backend/app/main.py`
- **Cites:** `backend-structure.md` § The error model

### DEC-001-5 — Any failure out of the extension loader becomes `ExtensionLoadError`
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 001.backend-foundation · **Step:** 005
- **Date:** 2026-09-28 · **Decided by:** coder
- **Plan-local:** 001 D8; 001 status Notes (step 005)
- **Question:** The plan requires a failed `sqlite-vec` load to be loud. Which failures does the `connect` listener convert?
- **Decision:** The listener wraps every exception raised by `load_sqlite_vec`, not only `ExtensionLoadError`, into `ExtensionLoadError`. `load_sqlite_vec` is a named module-level function, so a test can make the load fail by patching `app.db.engine.load_sqlite_vec`. `ExtensionLoadError` is a plain `Exception` and not a `DomainError`.
- **Reason:** The invariant "a connection without the extension is never handed out" then holds however the load fails, including when it is patched.
- **Lands in:** `backend/app/db/engine.py`
- **Cites:** `backend-structure.md` § Database access

### DEC-001-6 — The generator is built once, refuses an out-of-range node id, and reads an injected clock
- **Status:** accepted; superseded in part by DEC-001-9 (the backwards-reading rule)
- **Stage:** 001.instance · **Feature:** 001.backend-foundation · **Step:** 004
- **Date:** 2026-09-28 · **Decided by:** planner
- **Plan-local:** 001 step 004 context "Sequence exhaustion — a planner ruling", "The clock seam", "One generator per process"
- **Question:** How is the snowflake generator constructed and held, and how is it tested?
- **Decision:**
  - The node id is read once, at construction. A value outside the 10 bits raises `ValueError` there.
  - `build_id_generator(settings)` builds the one instance. `create_app()` keeps it on `app.state.id_generator`. There is no module-level singleton.
  - The generator takes its clock (milliseconds) as a constructor argument, defaulting to the system clock.
  - Shifts are derived from `NODE_ID_BITS` and `SEQUENCE_BITS`, never hard-coded.
  - On sequence exhaustion the generator waits by re-reading the injected clock. A backwards reading raises `BackwardsClockError`, on entry and during that wait. `BackwardsClockError` is a plain `Exception` and not a `DomainError`.
- **Reason:** The injected clock is the only way to test drift and exhaustion. One instance per process is the code-level half of the "one generator per node id" guarantee. Flip condition: more than one worker, process or replica means the layout and the string boundary must be re-examined before that ships.
- **Lands in:** `backend/app/ids.py`, `backend/app/main.py`
- **Cites:** `backend-structure.md` § The id generator; `data-model.md` § Identifiers

### DEC-001-7 — The health response field is `schema_` with the wire alias `schema`
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 001.backend-foundation · **Step:** 006
- **Date:** 2026-09-28 · **Decided by:** skeleton
- **Plan-local:** 001 step 006 skeleton record ("The `schema` gotcha and its resolution")
- **Question:** pydantic refuses a field named `schema`, because it shadows a `BaseModel` attribute. How does the wire still carry `schema`?
- **Decision:** `HealthResponse` declares `schema_: SchemaState = Field(alias="schema")` with `populate_by_name=True` and `serialize_by_alias=True`. Code under `app/` constructs it with `schema_=`, which is what the pydantic mypy plugin accepts. The internal `HealthProbeResult` dataclass keeps the plain name `schema`. The probe reads `sqlite_master` with `type IN ('table', 'view')`.
- **Reason:** `serialize_by_alias` puts `schema` on the wire for every dump, not only through FastAPI's response default.
- **Lands in:** `backend/app/models/health.py`, `backend/app/routers/health.py`, `backend/app/services/health.py`
- **Cites:** `backend-structure.md` § `/api/health`

### DEC-001-8 — The app factory takes no parameters, and its collaborators are patchable names
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 001.backend-foundation · **Step:** 006
- **Date:** 2026-09-28 · **Decided by:** skeleton
- **Plan-local:** 001 step 006 skeleton record (`create_app`, the five imports)
- **Question:** How do tests observe `create_app()`'s calls and override its settings?
- **Decision:**
  - `create_app()` takes no parameters and resolves settings with `get_settings()`.
  - `main.py` imports `get_settings`, `configure_logging`, `build_id_generator`, `register_exception_handlers` and the health router as names into its own namespace, and calls them by those names.
  - Tests patch `app.main.<name>`, and they override settings through the `lru_cache` or `dependency_overrides`, never by passing a `Settings` in.
  - `get_connection` takes its settings in the `Annotated[..., Depends(get_settings)]` form with no default, so a direct caller must pass a `Settings` instance.
- **Reason:** Module-qualified calls would make the logging, generator and handler steps unobservable in tests.
- **Rejected:** Calling the collaborators by module-qualified names, which breaks the seams.
- **Lands in:** `backend/app/main.py`, `backend/app/db/engine.py`

### DEC-001-9 — A backwards clock reading up to 1000 ms is treated as the last issued millisecond
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 001.backend-foundation · **Step:** —
- **Date:** 2026-11-10 · **Decided by:** orchestrator (delegated by the user)
- **Question:** WSL and NTP-slewed hosts step the wall clock back by tens of milliseconds (about 70 ms was observed under the parallel test suite, failing random tests). Must every backwards reading still refuse?
- **Decision:**
  - A new public constant `BACKWARDS_TOLERANCE_MS = 1000`.
  - A clock reading up to that far behind the last issued millisecond is treated as the last issued millisecond: the sequence increments within it. On sequence exhaustion the generator waits, re-reading the clock, until the reading passes the last issued millisecond.
  - Ids stay strictly increasing and unique, because they are issued from the last millisecond and never from the earlier reading.
  - A reading further behind than the tolerance still raises `BackwardsClockError`, on entry and during the exhaustion wait. It is still a plain `Exception` and not a `DomainError`, so it answers 500.
- **Reason:** Refusing a small step fails requests the caller cannot act on, and a slewed host produces such steps in ordinary operation. Issuing from the last millisecond keeps uniqueness without trusting the earlier reading.
- **Rejected:** A monotonic clock — ids would drift from wall time across restarts. An unbounded tolerance — a large step would stall issuing until wall time caught up.
- **Supersedes:** DEC-001-6 in part — its "a backwards reading raises `BackwardsClockError`, on entry and during that wait" now holds only beyond the tolerance.
- **Lands in:** `backend/app/ids.py` (`BACKWARDS_TOLERANCE_MS`, the generator)
- **Cites:** `data-model.md` § Identifiers; `backend-structure.md` § The id generator. Flip condition: a host that routinely steps its clock back by more than 1 s.
