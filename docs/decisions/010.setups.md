# Decisions — 010.setups
**Stage:** 002.record · **Feature:** 010.setups

Decisions behind setups: the `setups` table, the setups routes, and the interim Setups section on the character page. The contracts are in `data-model.md` § `setups`, `backend-structure.md`, `domain-rules.md` R2 / R6, `forms-and-lists.md` and `ui-conventions.md`. Recorded at finalization (2026-11-09). Several entries apply 009's rules to setups and cite them rather than restate them.

### DEC-010-1 — Setups are a section of the character page; no setup route
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 010.setups · **Step:** 006
- **Date:** 2026-10-02 · **Decided by:** user
- **Plan-local:** 010 D1
- **Question:** Where does the roleplayer see and manage a character's setups?
- **Decision:** A "Setups" section on `/characters/:id`, shown in existing mode once the character is ready, between the persona block and Sessions. It also renders for an archived character. There is no setup route. The 018 page rebuild later reshaped this section.
- **Reason:** A setup belongs to its character's page (US-096).
- **Lands in:** `frontend/src/app/SetupsSection.tsx`; `frontend/src/app/CharacterScreen.tsx`
- **Cites:** `frontend-structure.md` § Routing inside the `app` entry ("Setups have no route"); `workspace-shell.md` § The character page

### DEC-010-2 — Create and edit in a Modal with a fresh draft
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 010.setups · **Step:** 005, 006
- **Date:** 2026-10-02 · **Decided by:** user
- **Plan-local:** 010 D2; 010 005.context (modal error and close)
- **Question:** How are setups created and edited?
- **Decision:**
  - The "New setup" button is labelled, with `IconPlus`. A row's "Edit" item opens the same Mantine `Modal` (titled "New setup" or "Edit setup"), holding Name plus the shared editor labelled "Description".
  - The modal is mounted conditionally, so its draft is new on each open. Which modal is open is component-local `useState`.
  - Edit sends both fields in one `PATCH`. Save is enabled only when the draft differs from the row.
  - A failure renders as one error string in the modal's `Alert`, and the modal stays open.
  - The modal never closes itself. The section closes it from `onSaved`.
- **Reason:** It is a multi-field form, and the draft-page exception names only `/characters/new`.
- **Lands in:** `frontend/src/app/setupDraft.ts`; `frontend/src/app/SetupModal.tsx`; `frontend/src/app/SetupsSection.tsx`
- **Cites:** `forms-and-lists.md` (Create and edit are a Modal; draft lifetime)

### DEC-010-3 — Archiving a setup is always silent and always succeeds
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 010.setups · **Step:** 002
- **Date:** 2026-10-02 · **Decided by:** user
- **Plan-local:** 010 D3
- **Question:** Does archiving a setup that sessions reference warn, refuse, or count them?
- **Decision:** Archive never warns, never refuses and counts nothing. It reads and writes `setups` only.
  - An archived setup is not offered when starting a session.
  - Existing sessions keep their `setup_id` and their label.
- **Reason:** Archive does not cascade (R6). A refusal would make a reversible filter depend on other rows, and a warning would need a reverse count.
- **Rejected:** A reference-count warning. A refusal while referenced.
- **Lands in:** `backend/app/services/setups.py`
- **Cites:** `domain-rules.md` R6 (setups); `data-model.md` § … and the archive rule

### DEC-010-4 — "Show archived setups" switch, not persisted
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 010.setups · **Step:** 004, 006
- **Date:** 2026-10-02 · **Decided by:** user
- **Plan-local:** 010 D4
- **Question:** How are archived setups surfaced?
- **Decision:**
  - The section header carries a switch labelled "Show archived setups". It starts off and is never persisted.
  - When on, archived rows render dimmed with an "Archived" badge, and their menu offers Restore in place of Archive.
  - Neither Archive nor Restore asks for confirmation.
- **Reason:** The label differs from the tree's "Show archived" because both are on screen at once, and two controls with one accessible name are ambiguous. It follows DEC-009-3's reasoning for not persisting.
- **Lands in:** `frontend/src/app/setupsSectionState.ts`; `frontend/src/app/SetupsSection.tsx`
- **Cites:** `frontend-structure.md` § Routing inside the `app` entry (archive toggle)

### DEC-010-5 — Route surface: nested collection, flat single resource
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 010.setups · **Step:** 003
- **Date:** 2026-10-02 · **Decided by:** orchestrator
- **Plan-local:** 010 D5
- **Question:** Where do the setups routes hang, and what may a request change?
- **Decision:**
  - List and create are nested at `/api/characters/{character_id}/setups`. Get, `PATCH`, archive and restore are flat at `/api/setups/{setup_id}`.
  - There is one router with router-level `require_user`, registered after characters.
  - An archived parent character may list and create setups.
  - `character_id` is immutable. It is in neither request model, so a body carrying it is ignored.
  - PATCH treats null as absent, and an empty PATCH is a no-op, as DEC-009-6.
- **Reason:** A setup is created under one character, but its id is globally unique.
- **Lands in:** `backend/app/routers/setups.py`; `backend/app/models/setups.py`; `backend/app/main.py`
- **Cites:** `backend-structure.md` (setups route surface)

### DEC-010-6 — The setups service checks the parent with its own scoped select
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 010.setups · **Step:** 002
- **Date:** 2026-10-02 · **Decided by:** orchestrator
- **Plan-local:** 010 D6; 010 002.context (parent check, read rollback)
- **Question:** How does the setups service verify the parent character?
- **Decision:**
  - The service runs its own owner-scoped `SELECT` on `characters`, in the same transaction as the list or the insert. It never calls `services/characters.py`.
  - The check is a separate select, not a join, so an empty list (`[]`) and a missing parent (404) stay distinguishable.
  - The list read rolls back on both exits and leaves no transaction open.
- **Reason:** A service operation owns its transaction. Calling another service would nest a `begin()` or split one decision across two transactions.
- **Rejected:** Calling the characters service. A join that cannot tell "no setups" from "no parent".
- **Lands in:** `backend/app/services/setups.py`
- **Cites:** `backend-structure.md` § Routers versus services (services do not call each other)

### DEC-010-7 — The `setups` table
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 010.setups · **Step:** 001
- **Date:** 2026-10-02 · **Decided by:** orchestrator
- **Plan-local:** 010 D7
- **Question:** Which columns and indexes does `setups` carry?
- **Decision:**
  - Eight columns, exactly as `data-model.md` lists them.
  - Neither FK has `ON DELETE`. `description` has no server default; the service writes `""`.
  - One non-unique composite index on `(user_id, character_id)`.
  - No DDL runs at startup. An existing instance picks the table up through Create.
- **Reason:** The list query filters on both columns, and the `user_id` prefix serves every by-owner scan. One index does the work of two.
- **Lands in:** `backend/app/db/schema.py`
- **Cites:** `data-model.md` § `setups`

### DEC-010-8 — Not-found and validation, as 009
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 010.setups · **Step:** 001, 002
- **Date:** 2026-10-02 · **Decided by:** orchestrator
- **Plan-local:** 010 D8
- **Question:** Which codes do setups use for not-found and validation?
- **Decision:**
  - `setup_not_found` (404, empty `detail`) answers both a missing setup and another user's.
  - A missing or foreign parent reuses `character_not_found`.
  - `name` is stripped and required non-empty, with a 422 on failure. `description` is never stripped.
  - Unknown keys are ignored.
- **Reason:** Each code names what the path addresses. A second code for the same condition adds nothing.
- **Lands in:** `backend/app/errors.py`; `backend/app/models/setups.py`
- **Cites:** DEC-009-7; `backend-structure.md` § The error model

### DEC-010-9 — Archive semantics and order, as 009
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 010.setups · **Step:** 002
- **Date:** 2026-10-02 · **Decided by:** orchestrator
- **Plan-local:** 010 D9; 010 D10
- **Question:** How do archive, restore, edits and listing order work for setups?
- **Decision:**
  - Archive is idempotent and keeps the original `archived_at`. A no-op writes nothing.
  - An archived setup stays editable, and its row menu keeps "Edit".
  - Lists are ordered `created_at DESC, id DESC`.
- **Reason:** Setups take characters' semantics so the two cannot diverge.
- **Lands in:** `backend/app/services/setups.py`
- **Cites:** DEC-009-8; DEC-009-9

### DEC-010-10 — Section-owned state keyed by character id; a separate `applySetup`
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 010.setups · **Step:** 004
- **Date:** 2026-10-02 · **Decided by:** orchestrator
- **Plan-local:** 010 D11; 010 004.context (section state)
- **Question:** Where does setups state live, and how is a returned row applied?
- **Decision:**
  - `SetupsSection` owns one `SetupsSectionState`, and is rendered keyed by character id.
  - A returned row is upserted by DEC-009-10's rule, with no refetch.
  - The upsert is `applySetup`, a separate function. `applyCharacter` is not generalised.
  - One `pendingId` marks the row whose action is in flight.
  - The load path is guarded by `state.characterId !== null`. A `?? ""` fallback was rejected because it would request `/api/characters//setups`.
- **Reason:** Setups appear nowhere else yet, so they need no workspace-level state.
- **Lands in:** `frontend/src/app/setupsSectionState.ts`
- **Cites:** `forms-and-lists.md` § narrowed re-load (apply-a-row rule)

### DEC-010-11 — Fixed failure sentences, no `notifyFailure`
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 010.setups · **Step:** 004, 005, 006
- **Date:** 2026-10-02 · **Decided by:** planner
- **Plan-local:** 010 D12
- **Question:** How do setups failures render?
- **Decision:**
  - A load failure renders "Could not load setups" with "Retry".
  - Row action failures render "Could not archive the setup." or "Could not restore the setup." in an inline `Alert`.

### DEC-010-12 — The list is a plain table with one overflow menu per row
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 010.setups · **Step:** 006
- **Date:** 2026-10-02 · **Decided by:** planner
- **Plan-local:** 010 D13; 010 006.context (menu trigger, reload effect)
- **Question:** How does a setup row render, and what does an empty list say?
- **Decision:**
  - The list is a plain Mantine `Table`. Each row has one `IconDots` `IconButton` labelled "Actions for <name>", wrapped in a `span` inside `Menu.Target`. Its items are Edit and Archive, or Edit and Restore.
  - The description is not shown in the row.
  - An empty list reads "No setups yet." with no invitation to create one.
  - The reload effect keyed on the switch is the only load on a toggle; the handler does not also load.
- **Reason:** A table row holds exactly one icon-only control. A setup is optional (R2), so an invitation would push for one.
- **Lands in:** `frontend/src/app/SetupsSection.tsx`
- **Cites:** `forms-and-lists.md` (tables, row menus); `domain-rules.md` R2
