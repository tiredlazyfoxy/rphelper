# Decisions — 029.my-search
**Stage:** 004.retrieval · **Feature:** 029.my-search

Decisions for the roleplayer's own search: `GET /api/search`, the per-kind matching,
hydration, the results page and landing on a hit. The feature was delivered on
2026-10-05. The contracts are in `search-and-retrieval.md` § My-search,
`workspace-shell.md` and `frontend-structure.md`; the port is `DEC-025-1`..`-14`.
Three entries were later superseded in part — session matching and the session/entry
display keys by 034 (`DEC-arch-session-names-5`, `DEC-034-8`), and name matching by
`fast/006` (`DEC-F006-3`, `-4`, `-5`); each entry states the half that survives.

### DEC-029-1 — An embedding failure fails the whole search
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 029.my-search · **Step:** 002, 003, 005
- **Date:** 2026-10-05 · **Decided by:** user
- **Plan-local:** 029 U1
- **Question:** When the memo or session port call raises, does my-search return what it could?
- **Decision:** No. The request fails with the error envelope unchanged (`no_embedding_model` 409 including `dimension_mismatch`, `secret_ref_missing`, `llm_unreachable` 502). No partial groups, no lexical-only degrade; the route catches nothing. The page shows the failure inline with Retry, never as a notification. With no usable model, my-search answers nothing — even a character-name match.
- **Reason:** R4 — no silent substitution; a partial answer would look complete.
- **Lands in:** `backend/app/services/search/my_search.py`, `backend/app/routers/search.py`, `frontend/src/app/SearchScreen.tsx`
- **Cites:** `search-and-retrieval.md` § My-search (fail-whole)

### DEC-029-2 — Matching per kind; no flag predicate on memos
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 029.my-search · **Step:** 001, 002
- **Date:** 2026-10-05 · **Decided by:** user
- **Plan-local:** 029 U2
- **Question:** How is each of the five kinds matched?
- **Decision:** Characters (`name`, `sheet`) and setups (`name`, `description`) by escaped case-insensitive substring match outside the port — no FTS table and no schema change for them. Sessions through the port's session variant (vector only), entries through the entry variant (lexical over `settled_entries`), memos through the memo variant with **no** extra predicate: nothing reads `is_forced`, and `is_enabled` is read only to report it.
- **Reason:** Characters and setups are small and unindexed. R3 constrains the assistant, not the owner (US-137).
- **Lands in:** `backend/app/services/search/my_search.py`
- **Cites:** `search-and-retrieval.md` § My-search; `domain-rules.md` R3

### DEC-029-4 — Landing targets, the query in the URL, the two triggers
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 029.my-search · **Step:** 004, 005, 006
- **Date:** 2026-10-05 · **Decided by:** user (targets, trigger); planner (helpers)
- **Plan-local:** 029 U4; 004.context "Targets"; step 004 skeleton (target helpers)
- **Question:** Where does each hit land, and how is the search reached?
- **Decision:**
  - Character → `/characters/<id>`; setup → its character's page (setups have no route); session → `/sessions/<id>`; entry → `/sessions/<session_id>?entry=<id>`; memo → its level's page (user → `/settings`; character and setup → the character page; session → `/sessions/<scope_id>?notes=open`). No per-note focus.
  - Five pure `*Target` helpers, one per kind, because the wire carries no kind tag on a hit. A memo target with no id to route to gets the empty string, which the router's catch-all answers.
  - The query lives in the URL as `/search?q=<text>`. The tree header's Search button became a text input (Enter navigates). The collapsed rail keeps its Search button, which navigates to `/search`.
- **Reason:** A link should land on the thing it names; the URL makes a search shareable and back-navigable.
- **Lands in:** `frontend/src/app/searchState.ts`, `frontend/src/app/CharacterTree.tsx`
- **Cites:** `workspace-shell.md` (my-search at the top of the tree, duplicated on the rail)

### DEC-029-5 — One route, five fixed groups; blank `q` costs nothing
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 029.my-search · **Step:** 003
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 029 D1
- **Question:** What is the route's shape for a blank or missing query?
- **Decision:** `GET /api/search?q=<text>` behind `require_user` answers 200 with five keys in order `characters`, `setups`, `sessions`, `entries`, `memos`, each a list. `q` defaults to `""` with no `Query()` wrapper. A blank or whitespace-only `q` returns five empty lists with no SQL and no embed. The route is a sync `def`, so the port's `asyncio.run` bridge runs on a worker thread.
- **Reason:** A fixed shape the page can render without branching; a blank query is not an error.
- **Lands in:** `backend/app/routers/search.py`, `backend/app/services/search/my_search.py`
- **Cites:** `search-and-retrieval.md` § My-search

### DEC-029-6 — 20 per group; name order for unscored kinds
- **Status:** accepted; superseded in part by DEC-arch-session-names-5 (session group order)
- **Stage:** 004.retrieval · **Feature:** 029.my-search · **Step:** 001, 002
- **Date:** 2026-10-05 · **Decided by:** planner

- **Question:** How many hits per group, in what order?
- **Decision:** `MY_SEARCH_PER_KIND_LIMIT = 20`, passed to the port as `limit` and to the LIKE queries. Entries and memos keep the port's order. Characters and setups are ordered by `name`, then `id`.

### DEC-029-7 — Substring semantics for the name corpora
- **Status:** accepted; superseded in part by DEC-F006-4 (case folding) and DEC-F006-3 (how the fold is applied)
- **Stage:** 004.retrieval · **Feature:** 029.my-search · **Step:** 001
- **Date:** 2026-10-05 · **Decided by:** planner; orchestrator (spelling, harvest decision 3)
- **Plan-local:** 029 D3; 029 harvest decision 3
- **Question:** How is the needle matched against characters and setups?
- **Decision:** The needle is the query stripped of leading and trailing whitespace, matched as **one** substring (not split into words). `%`, `_` and the escape character are escaped through SQLAlchemy's `contains(..., autoescape=True)`, whose declared escape character is `/` (a backslash in the needle is literal). A row matches when either column contains the needle and appears once.
- **Rejected:** `icontains` — adds `lower()` on both sides for no gain on SQLite, whose `LIKE` was already ASCII-case-insensitive.
- **Reason:** User input can never act as a wildcard.
- **Superseded in part by:** `DEC-F006-4` — case-insensitivity is no longer ASCII-only: both sides are case-folded (no accent folding). `DEC-F006-3` — the fold is applied to both sides through one helper while keeping `autoescape`. Code check: `my_search.py`'s comments still describe the plain-`LIKE` / ASCII behaviour (open, flagged by `DEC-F006-5`). The one-substring, either-column and escaping rules survive.
- **Lands in:** `backend/app/services/search/my_search.py`

### DEC-029-8 — Hydration: one owner-scoped read per kind
- **Status:** accepted; superseded in part by DEC-034-8 (session and entry display keys)
- **Stage:** 004.retrieval · **Feature:** 029.my-search · **Step:** 002
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 029 D4
- **Question:** The port returns ids, scores, snippets and memo levels. How are display fields read?
- **Decision:** One read per kind, each carrying `user_id = :user_id` on every base table it names: sessions (`sessions` ⨝ `characters` ⟕ `setups`: character name, setup name or null, `created_at`, archived); entries (`settled_entries` ⨝ `sessions` ⨝ `characters`: character name, the session's `created_at`); memos (`memos` ⟕ `setups`: `is_enabled`, and the character id a character- or setup-level memo routes to). A port hit missing from its hydration read is dropped, not raised. Entry reads go through `settled_entries`, never raw `messages`. The helpers take `Sequence[SearchHit]`.
- **Reason:** R5 in SQL; R11 for entries.
- **Superseded in part by:** `DEC-034-8` — a session hit also carries `name` and an entry hit `session_name`, hydrated by the same reads. The read-per-kind, drop-not-raise and R11 rules survive.
- **Lands in:** `backend/app/services/search/my_search.py`
- **Cites:** `search-and-retrieval.md` § My-search (the result shape); `domain-rules.md` R5, R11

### DEC-029-9 — Memo hydration reports `scope_id` as `null` for the user level
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 029.my-search · **Step:** 002
- **Date:** 2026-10-05 · **Decided by:** orchestrator
- **Plan-local:** 029 harvest decision 5; 029 Notes & Issues (steps 001/002)
- **Question:** The wire contract says a user-level memo's `scope_id` is `null`, but the port passes the stored value (the owner's own id, `DEC-025-3`). Who reduces it?
- **Decision:** My-search's memo hydration sets `scope_id` to `None` for `scope == "user"`, the way `services/memos.py`'s `to_memo` does, and leaves every other level's stored id. `character_id` is `scope_id` for a character memo, the setup's `character_id` for a setup memo, and `null` for user and session memos.
- **Reason:** Missing it is silent data corruption, not a crash: the client would receive the owner's id as a level id. The port's `ports.py` docstring claiming `None` is stale (`DEC-025-3`).
- **Lands in:** `backend/app/services/search/my_search.py`
- **Cites:** `DEC-025-3`

### DEC-029-10 — Execution order: model-opening calls first, then everything else
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 029.my-search · **Step:** 002
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 029 D5
- **Question:** In what order does `run_my_search` do its work?
- **Decision:** Session port call, memo port call, entry port call, the two name queries, then hydration, then the result. An exception at any step propagates to the single `DomainError` handler; no half-built result is returned.
- **Reason:** Order does not change correctness (`DEC-029-1`); it makes a missing model cost no other work.
- **Lands in:** `backend/app/services/search/my_search.py`
- **Note:** Known cost: the query is embedded twice per search (once per model-opening scope), because the port takes text, not a vector.

### DEC-029-11 — Read posture: a local `_reading` that rolls back only its own transaction
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 029.my-search · **Step:** 001, 002
- **Date:** 2026-10-05 · **Decided by:** planner (confirmed: orchestrator, step 001 DoD-9 adjudication)
- **Plan-local:** 029 D6; 029 "Adjudicated: step 001 DoD-9's mid-read clause"
- **Question:** How do my-search's reads end the transaction they autobegin?
- **Decision:** `my_search.py` copies `services/memos.py`'s `_reading` verbatim (never imported): note whether a transaction was open before, and in a `finally` roll back only if this call opened it — on return and on raise. A caller's transaction is left alone. This wins over step 001 DoD-9's looser wording. Each read helper opens its own window, so one search is several read windows (accepted).
- **Rejected:** The 026/027 "roll back whenever a transaction is open" posture — right for their contract to the tool seam, wrong for a service that would then roll back its caller's transaction. In production the two never differ: the route's connection opens no transaction.
- **Reason:** A service that rolled back its caller's transaction would be a defect.
- **Lands in:** `backend/app/services/search/my_search.py`

### DEC-029-12 — Presentation: archived and disabled markings, plain-text snippets
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 029.my-search · **Step:** 005
- **Date:** 2026-10-05 · **Decided by:** planner; coder (row repair after verify CODE fault)
- **Plan-local:** 029 D7; 029 "The one CODE fault" (step 005 repair)
- **Question:** How are archived and disabled hits shown, and how are snippets rendered?
- **Decision:**
  - Archived character, setup and session rows: a gray light `Badge` "Archived" and dimmed text — the tree's idiom.
  - A disabled memo: the snippet with `c="dimmed"` and `td="line-through"` plus a gray `Badge` "Disabled". Enabled or forced memos get no badge.
  - Snippets render as plain text, never markdown.
  - Each row's link (`Anchor`) holds both the primary and the secondary line; the badge is a sibling outside the link inside the row item. The link's accessible name therefore folds in the secondary line.
  - Mantine props only; no stylesheet, no class name.
- **Reason:** A cut markdown fragment can open a structure it never closes. A session has no name, so with the secondary line outside the link a session row was identifiable only by its timestamp; `CharacterTree.tsx`'s session `NavLink` is the precedent.
- **Lands in:** `frontend/src/app/SearchScreen.tsx`
- **Cites:** `search-and-retrieval.md` § My-search (disabled notes shown); `frontend-structure.md` (snippet rendering)

### DEC-029-13 — The landing URL contract
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 029.my-search · **Step:** 004, 006
- **Date:** 2026-10-05 · **Decided by:** planner; orchestrator (open-only, harvest decision 11)
- **Plan-local:** 029 D8; 029 harvest decision 11
- **Question:** What query parameters drive landing, and what happens to them?
- **Decision:** `q` on `/search` (URL-encoded query); `entry=<message id>` on `/sessions/:id` (scroll to and highlight once the record loads); `notes=open` on `/sessions/:id` (open the note wall). An unknown `entry` id does nothing. Parameters are not removed after use. The `notes` effect only ever **opens** the wall — absence, another value or a later in-entry navigation never closes it or touches its pin.
- **Reason:** The session screen already decides when the wall closes on navigation between session URLs; an effect keyed on the search parameters that also closed on absence would break that delivered behaviour.
- **Lands in:** `frontend/src/app/searchState.ts`, `frontend/src/app/SessionScreen.tsx`

### DEC-029-15 — The entry highlight: a Mantine `bg`, 2000 ms, one centred scroll

- **Plan-local:** 029 context literals (highlight duration, anchor attributes); 029 harvest decisions 10, 12
- **Question:** How is the landed-on entry marked and brought into view?
- **Decision:** Each entry carries `data-entry-id="<message id>"` (never `data-entry`). The focus entry scrolls into view centred **once** — a `scrolledForId` ref records the id already scrolled for, so no re-render scrolls again — and holds `data-highlighted="true"` plus `bg={HIGHLIGHT_BG}` (`"yellow.1"`) for `HIGHLIGHT_DURATION_MS = 2000`, the timer cleared on cleanup. Tests bind to `data-highlighted`, never the shade; the shade may be re-tuned as long as it stays a Mantine `bg` value.
