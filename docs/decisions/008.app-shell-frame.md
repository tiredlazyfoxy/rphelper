### DEC-008-2 — The boot gate: five outcomes, with 401 keyed on `not_authenticated`
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 008.app-shell-frame · **Step:** 005
- **Date:** 2026-10-01 · **Decided by:** user
- **Plan-local:** 008 D2; 008 D13
- **Question:** What does the `app` entry render before and after `GET /api/me`?
- **Decision:**
  - In flight: nothing.
  - 401 with code `not_authenticated`: nothing of its own, because the shared client has already navigated.
  - Not-ready: a full-page screen, re-probed every 2000 ms, plus "Retry now".
  - Anything else, including a well-formed 403 or 5xx: a failure panel plus "Retry".
  - Success, for either role: the shell, with the user as a prop.
  - The branch keys on the code, never on `.status`. The gate is a component (`AppBoot`) that `main.tsx` mounts.
  - Neither screen raises a notification.
- **Reason:** This mirrors the admin boot without the role deny. The component form makes each outcome testable by mounting it. The code was verified against `NotAuthenticatedError`.
- **Lands in:** `frontend/src/app/appBootState.ts`; `frontend/src/app/AppBoot.tsx`; `frontend/src/app/AppBootScreens.tsx`; `frontend/src/app/main.tsx`
- **Cites:** `frontend-structure.md` § The `app` entry (boot sequence)

### DEC-008-3 — Re-probe timing: armed from each probe's completion
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 008.app-shell-frame · **Step:** 005
- **Date:** 2026-10-01 · **Decided by:** coder (confirmed: verifier PASS)
- **Plan-local:** 008 005.context (re-probe loop)
- **Question:** How is the 2000 ms not-ready re-probe scheduled without overlap or a stall?
- **Decision:**
  - The timer is armed when each probe completes, not from an effect keyed on `status`. A not-ready → not-ready outcome never changes `status`.
  - An in-flight flag keeps two probes from overlapping.
  - The timer is cleared at the start of every probe and on unmount.
  - Unmount also aborts the controller.
  - `probeCurrentUser` never sets `"probing"`. `restartBoot` does, before a manual Retry.
- **Reason:** An effect keyed on an unchanged status would fire once and stall.
- **Lands in:** `frontend/src/app/AppBoot.tsx`; `frontend/src/app/appBootState.ts`

### DEC-008-4 — Below 820px: always the rail; expand opens the same column as an overlay
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 008.app-shell-frame · **Step:** 002, 004
- **Date:** 2026-10-01 · **Decided by:** user (behaviour); planner (query form)
- **Plan-local:** 008 D3; 008 D12; 008 002.context (overlay width)
- **Question:** How does the left column behave on a narrow viewport, and how do CSS and JS agree on "narrow"?
- **Decision:**
  - Narrow is the range query `(width < 820px)`. It is one exported constant, and `shell.css` repeats the same string verbatim. `useMediaQuery` receives it with `getInitialValueInEffect: false`, so the first render already knows the width and a narrow screen never flashes the wide layout.
  - At narrow width, `--navw` is 48px in the media query. Expand lifts the same nav column out of the track by the `nav-overlay-open` class, with `position: fixed`, top/bottom/left 0, a literal `width: 252px` and `z-index: 100`.
  - The overlay's open state is not persisted. `navCollapsed` is neither read nor written at narrow width.
  - The CSS media query is the layout authority. JS only decides what expand and collapse mean.
- **Reason:** The range syntax keeps the doc's literal `820px`, so "below" means strictly below. One string written twice cannot drift.
- **Rejected:** `max-width: 819.98px` — it hides the threshold. A Mantine breakpoint token — `workspace-shell.md` records why `md` is wrong. A third overlay component — the overlay is the same markup.
- **Lands in:** `frontend/src/shell.css`; `frontend/src/app/shellState.ts`; `frontend/src/app/WorkspaceShell.tsx`
- **Cites:** `workspace-shell.md` § The three columns, § Geometry

### DEC-008-5 — Dismissing the overlay
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 008.app-shell-frame · **Step:** 004
- **Date:** 2026-10-01 · **Decided by:** planner
- **Plan-local:** 008 D11
- **Question:** What closes the narrow overlay?
- **Decision:** Three things close it: its own "Collapse tree" control, any in-entry route change (an effect keyed on `location.key`), and crossing the threshold in either direction. There is no click-outside dismissal and no backdrop.
- **Reason:** Each further interaction is one more thing to test, and no requirement asks for it.
- **Flip condition:** the roleplayer asks for click-outside dismissal.
- **Lands in:** `frontend/src/app/WorkspaceShell.tsx`; `frontend/src/app/shellState.ts`
- **Cites:** `workspace-shell.md` § The three columns

### DEC-008-8 — The user menu and the logout failure posture
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 008.app-shell-frame · **Step:** 003
- **Date:** 2026-10-01 · **Decided by:** user (menu); planner (logout failure)
- **Plan-local:** 008 D6; 008 D7
- **Question:** What does the user menu hold, and what does a failed logout do?
- **Decision:**
  - Trigger: an avatar, plus the username when expanded. Its accessible name is "User menu". The menu opens upward.
  - Items: Settings (router navigation), then Admin area, then Log out.
    - Admin area is a real `<a href="/admin">`, rendered only for `admin`.
    - Log out posts `/api/auth/logout`, then navigates the document to `/login`.
  - On failure: `notifyFailure`, no navigation.
  - An aborted logout neither navigates nor notifies.
- **Reason:** A failure probably leaves the cookie live, so navigating would fake a logout. A closed menu has no place to render the failure.
- **Lands in:** `frontend/src/app/UserMenu.tsx`; `frontend/src/app/logout.ts`
- **Cites:** `workspace-shell.md` § The user menu; `ui-conventions.md` § Async feedback

### DEC-008-9 — The persisted layout record
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 008.app-shell-frame · **Step:** 001
- **Date:** 2026-10-01 · **Decided by:** user
- **Plan-local:** 008 D8
- **Question:** How is the collapse state persisted while the module stays DOM-free?
- **Decision:**
  - Storage: key `rphelper.workspace-layout`, record `{ navCollapsed, wallPinned }`, both defaulting to `false`.
  - Read: total. Every failure, including a throwing `getItem`, falls back per field. Unknown keys are ignored.
  - Write: best-effort. It merges the patch over a fresh total read, so it drops unknown keys.
  - The storage is passed in as a parameter (`getItem` / `setItem`, or `null`).
- **Reason:** Taking storage as a parameter makes every fallback a plain unit test. Dropping stale keys on write is intended.
- **Lands in:** `frontend/src/app/workspaceLayout.ts`
- **Cites:** `workspace-shell.md` § Layout persistence

### DEC-008-10 — Shell state is written on the toggle; wide toggles write unconditionally
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 008.app-shell-frame · **Step:** 002
- **Date:** 2026-10-01 · **Decided by:** user (D9); coder (unconditional wide write, confirmed: verifier PASS)
- **Plan-local:** 008 D9
- **Question:** When does the shell write the record?
- **Decision:** Shell state is an observable-fields-only class with free functions. At wide width, `expandTree` and `collapseTree` set `navCollapsed` and always write that one field. At narrow width, they only open or close the overlay and write nothing.
- **Reason:** The step's interface intent specified the unconditional wide write. D9's "only on a change" rule holds through the narrow branches, which never touch `navCollapsed`.
- **Lands in:** `frontend/src/app/shellState.ts`
