### DEC-003-1 — Argon2id with library defaults, no rehash-on-verify
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 003.first-run-bootstrap · **Step:** 001
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 003 D1
- **Question:** How are passwords hashed and stored?
- **Decision:** Argon2id via `argon2-cffi`, with the library's defaults, behind `services/passwords.py`. The stored value is the self-describing encoded string. Verifying never rehashes.
- **Reason:** The encoded string carries its own parameters, so a later change of defaults stays verifiable. The architecture holds the mechanism. Flip condition: once the defaults are raised, add rehash-on-verify.
- **Lands in:** `backend/app/services/passwords.py`
- **Cites:** `backend-structure.md` (passwords); `deployment.md`

### DEC-003-2 — `already_configured` is 409 with no detail
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 003.first-run-bootstrap · **Step:** 002
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 003 D2; 003 step 002 context (default message)
- **Question:** What status refuses a create on an instance that is already configured?
- **Decision:** 409 with an empty `detail`. The subclass supplies a non-empty default message itself. The base class and the handler do not.
- **Reason:** The request conflicts with the instance's state.
- **Rejected:** 403, because no identity is being judged. 404, because it would make the refusal impossible to diagnose.
- **Lands in:** `backend/app/errors.py`
- **Cites:** `backend-structure.md` § The error model

### DEC-003-3 — "Configured" is defined once, in the bootstrap service

### DEC-003-4 — Pre-bootstrap health reads degraded, and only `configured` is branched on
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 003.first-run-bootstrap · **Step:** 002
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 003 D5
- **Question:** What does `/api/health` report before the first admin exists, and what may clients branch on?
- **Decision:** Before bootstrap it reports status degraded, `configured: false` and schema missing. The frontend branches on `configured` only. The container healthcheck tests the status code, never the body.
- **Reason:** An instance with no schema is not fully up, so degraded is the honest report. The healthcheck tests the status code so that a container waiting for its first admin is not restarted as unhealthy.
- **Lands in:** `backend/app/services/health.py`, `frontend/src/bootstrap/`
- **Cites:** `backend-structure.md` § `/api/health`; `deployment.md`

### DEC-003-5 — The guard and the generator dependency live in the bootstrap router
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 003.first-run-bootstrap · **Step:** 003
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 003 D6; 003 step 003 context (generator dependency, 201 without Location, re-check inside the transaction)
- **Question:** Where does the "unconfigured only" guard sit, how does the id generator reach the service, and what does create answer?
- **Decision:**
  - `require_unconfigured` is a router-level dependency in `routers/bootstrap.py`.
  - `get_id_generator`, which reads `request.app.state.id_generator`, is declared in `routers/bootstrap.py`. The translation and stream routers import it from there. The generator is passed into the service as a plain argument.
  - The service re-checks the predicate inside the creation transaction.
  - Create answers 201 with the response model and no `Location` header.
- **Reason:** The refusal belongs to the operation, so the in-transaction re-check closes the race between two first-run tabs. There is no `GET /api/users/{id}` for a `Location` header to point at.
- **Lands in:** `backend/app/routers/bootstrap.py`, `backend/app/services/bootstrap.py`

### DEC-003-7 — Schema creation runs inside the creation transaction
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 003.first-run-bootstrap · **Step:** 002
- **Date:** 2026-09-29 · **Decided by:** user (step 002 widened to cover it)
- **Plan-local:** 003 D8
- **Question:** How do `create_all` and the first admin's insert become one atomic unit on SQLite?
- **Decision:** The engine uses transactional DDL engine-wide: `isolation_level=None` plus a `begin` listener that emits `BEGIN`. `create_all` runs inside the creation transaction. The PRAGMAs stay outside any transaction. The architecture holds the mechanism.
- **Reason:** The stdlib driver's default transaction handling commits DDL implicitly, which would leave a schema with no admin after a failed insert.
- **Rejected:** PEP 249 `autocommit=False`.
- **Lands in:** `backend/app/db/engine.py`
- **Cites:** `backend-structure.md` § Database access. Flip condition: leaving the stdlib driver, or a driver release that makes this the default.

### DEC-003-9 — The not-ready predicate

- **Plan-local:** 003 D10

### DEC-003-10 — A fixed 2-second re-probe with no cap, and a manual retry
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 003.first-run-bootstrap · **Step:** 004
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 003 D11; 003 step 004 context (manual retry)
- **Question:** How does the bootstrap entry wait for a backend that is not ready?
- **Decision:**
  - It re-probes every 2000 ms with no attempt cap, and the loop is cancelled on unmount.
  - A manual Retry stops the current loop and starts a new one.
  - The current panel stays visible while the probe is in flight.
- **Reason:** The start-up window is short, so backoff buys nothing, and a fixed interval can be asserted with fake timers.
- **Rejected:** Jittered exponential backoff.
- **Lands in:** `frontend/src/bootstrap/bootstrapState.ts`, `frontend/src/bootstrap/main.tsx`

### DEC-003-14 — The bootstrap form's credential rules
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 003.first-run-bootstrap · **Step:** 003, 005
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 003 D16; 003 step 005 context (visibility toggle, password in error text)
- **Question:** What does the form check, what does the server check, and how do failures render?
- **Decision:**
  - The form has a password confirmation field. It is a UI check only and is never sent.
  - There is no length floor, no character-class rule and no strength meter.
  - Server side, both credentials are `min_length=1`. An empty value gets FastAPI's 422 with no domain code. Undeclared keys are ignored.
  - In the frontend, a 422 arrives as `client_malformed_error` at status 422 and renders in the general inline alert, not the not-ready screen.
  - If the general error text would contain the typed password, it is replaced with generic text.
  - The "refused" outcome is recognised by its code, not by the 409 status.
- **Reason:** The product states no password policy, so none is invented. The confirmation covers the typo risk, and there is no reset path to recover from a typo.
- **Rejected:** A show/hide password toggle, because the confirmation already covers the typo risk.
- **Lands in:** the bootstrap request model under `backend/app/models/`, `frontend/src/bootstrap/createAdminDraft.ts`
