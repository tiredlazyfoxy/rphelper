# Decisions — 035.llm-client-gateway
**Stage:** — · **Feature:** 035.llm-client-gateway

Planning-time decisions for the feature that builds the LLM gateway over
`llm-client` 0.2.0. The architecture-level mechanisms are
`DEC-arch-llm-client-library-1` .. `-12` and are cited, not restated, here.

### DEC-035-1 — The factory takes `kind` first; the gateway class is the production factory
- **Status:** accepted
- **Stage:** — · **Feature:** 035.llm-client-gateway · **Step:** 002, 004
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** How does `llm_servers.kind` reach the gateway through the injectable client factory, and what replaces the `LlmClient` default?
- **Decision:** Both factory aliases in `services/llm_registry.py` (`LlmClientFactory` for probe/embed, `ChatClientFactory` for complete/compose) take four positional arguments: `(kind, base_url, api_key, timeout_seconds)`. The names `LlmClientFactory`, `LlmClientLike`, `ChatClientFactory` and `ChatClientLike` stay. The gateway class `LlmGateway` (in `services/llm/gateway.py`) has exactly that constructor and *is* the production factory. Every `client_factory=LlmClient` default, and every dependency provider that returned `LlmClient` (`get_llm_client_factory`, `get_chat_client_factory`, `get_translation_chat_client_factory`), now uses `LlmGateway`. The registry's probe and designation selects add `kind`. The chat and embedding call sites pass the `kind` of the server already in scope.
- **Reason:** It keeps the injection seam the architecture keeps (021 D14), one construction call shape at all four sites, and the existing protocol names, so a test that only passes a fake through is untouched.
- **Rejected:** A keyword `kind=` with a default — a forgotten `kind` would silently pick one backend. Keeping the name `LlmClient` as an alias of the gateway — it leaves the removed module's name alive in twenty signatures.
- **Lands in:** `backend/app/services/llm_registry.py`, `backend/app/services/embedding.py`, `backend/app/dependencies.py`, `backend/app/routers/stream.py`, `backend/app/routers/translation.py`, every service, search and tool module carrying a factory default
- **Cites:** `llm-and-streaming.md` § The gateway (injectable client factory), § One protocol; `kind` selects the library class; `data-model.md` `llm_servers.kind`

### DEC-035-2 — Probe value types move to the gateway; the delta types are deleted
- **Status:** accepted
- **Stage:** — · **Feature:** 035.llm-client-gateway · **Step:** 001, 005
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** Where do `ProbeOutcome`, `ProbeResult`, `EMBED_NO_VECTOR_REASON`, `ChatDelta` and `ToolCallDelta` live once `client.py` is removed?
- **Decision:** `ProbeOutcome`, `ProbeResult` and `EMBED_NO_VECTOR_REASON` move unchanged (names, values, fields, defaults) into `services/llm/gateway.py` in step 001. Until step 005 deletes `client.py`, it imports them from the gateway, so there is one definition throughout. `ChatDelta` and `ToolCallDelta` are not re-homed: they describe `chat_stream`'s output, which no longer exists, and they go with `client.py`.
- **Reason:** The architecture names the probe-outcome value set as the gateway's. One definition keeps enum identity stable while both modules exist.
- **Lands in:** `backend/app/services/llm/gateway.py`, `backend/app/services/llm/client.py` (until removed)
- **Cites:** `backend-structure.md` § Layout (`gateway.py` holds the probe-outcome value set)

### DEC-035-3 — The gateway's test seam is a keyword-only map of library client classes
- **Status:** accepted
- **Stage:** — · **Feature:** 035.llm-client-gateway · **Step:** 001
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** How do gateway adapter tests (`DEC-arch-llm-client-library-11`) put fake library clients under the gateway without a network?
- **Decision:** After its four positional arguments, `LlmGateway`'s constructor takes a keyword-only `library_clients` mapping from `kind` to a library client class. It defaults to `{"openai": OpenAIAPIClient, "llamaswap": LlamaSwapAPIClient}`. The gateway builds every library client through this mapping, with the keyword arguments `model`, `base_url`, `timeout` and `bearer_token`. A fake class must accept those keywords, be an async context manager, and offer the method the operation uses. The factory seam (DEC-035-1) never passes the keyword.
- **Reason:** Tests can inject fakes without monkeypatching module globals, which would leak across the parallel test run. The production call shape is untouched.
- **Rejected:** A module-level mapping that tests patch — global state under `pytest -n auto`. A mocked `aiohttp` transport — it tests the library, not RPHelper (`DEC-arch-llm-client-library-11`).
- **Lands in:** `backend/app/services/llm/gateway.py`; `backend/tests/test_llm_gateway_*.py`
- **Cites:** `DEC-arch-llm-client-library-11`

### DEC-035-4 — `to_wire_message` is kept and builds the library's `messages`
- **Status:** accepted
- **Stage:** — · **Feature:** 035.llm-client-gateway · **Step:** 003
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** `chat.py`'s `to_wire_message` produced the chat-completions dict for `client.py`. Do we keep it or replace it?
- **Decision:** Keep it unchanged. `complete` and `compose` convert each `ChatMessage` with `to_wire_message`, in order, and pass the list as the library's `messages`. The leading system message stays a message item. The library's `system=` keyword is not used, because the library turns a system message item into the same input item. `test_chat_wire.py` stays.
- **Reason:** It already emits exactly the history shape that `chat_with_tools` converts to Responses call and call-output items: an assistant message with `tool_calls`, and a `role: tool` message with `tool_call_id`. Context replay therefore keeps one mapping site.
- **Rejected:** A second mapper inside the gateway — two statements of the wire shape.
- **Lands in:** `backend/app/services/llm/gateway.py` (caller); `backend/app/services/llm/chat.py` unchanged
- **Cites:** `llm-and-streaming.md` § How one exchange runs (context replay works through the library)

### DEC-035-5 — Library typing gaps are absorbed inside `gateway.py` only
- **Status:** accepted
- **Stage:** — · **Feature:** 035.llm-client-gateway · **Step:** 001
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** `llm-client` 0.2.0 has unannotated `__aenter__`/`__aexit__`, types `messages` as `List[Dict[str, str]]`, and has an options type mismatch. How does `mypy app` stay clean?
- **Decision:** Only in `gateway.py`: `typing.cast` at the boundary, and narrow `# type: ignore[<code>]` comments that name the exact error code, each on the line that needs it. There is no `[[tool.mypy.overrides]]` for the gateway or for `llm.*` in `pyproject.toml`. No library type appears in any signature outside `gateway.py`.
- **Reason:** It keeps the gate strict everywhere else, and puts every exception to it where the one library import lives.
- **Rejected:** A per-module mypy override — it silences the whole module, not the lines.
- **Lands in:** `backend/app/services/llm/gateway.py`
- **Cites:** `llm-and-streaming.md` § The gateway — the one module that knows the library. Flip condition: a library release annotates these.

### DEC-035-6 — The chat-client protocol: `complete`, `compose`, and the tool bundle
- **Status:** accepted
- **Stage:** — · **Feature:** 035.llm-client-gateway · **Step:** 003, 004
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** What exactly do `complete` and `compose` take and yield? How is the per-tool wrapper (`DEC-arch-llm-client-library-5`, `-6`, `-7`) split between the gateway and the compose source?
- **Decision:**
  - **The protocols.** `ChatClientLike` is `complete(model, messages) -> str` and `compose(model, messages, tools) -> async iterator of events`. `LlmClientLike` stays `probe()` and `embed(model, texts)`.
  - **The `tools` argument** is one gateway value, `ComposeTools`. It holds the offered declarations, in offered order, and a **runner**: an async callable that takes a `ToolCall` and an `emit` callback and returns the tool's output text.
  - **The events** are `ComposeText` (one text piece, verbatim) or whatever the runner emitted, passed through unchanged. The stream is generic in the runner's event type.
  - **The gateway half of the wrapper** builds one library callable per declaration and does these things for each call:
    - gives the callable an explicit keyword-only signature built from the declaration's `properties`, each parameter defaulting to an absent-marker (`DEC-arch-llm-client-library-6`);
    - mints `call_<n>` from a per-`compose` counter that starts at 1 and counts in invocation order (`DEC-arch-llm-client-library-5`);
    - builds `ToolCall(call_id, name, json.dumps(present_kwargs, ensure_ascii=False))`;
    - awaits the runner and returns its text.
  - **The compose half of the wrapper** is the runner, in `compose.py`. It emits `tool_start`, awaits the seam's `dispatch`, emits the frame `dispatch` returns, and returns the message content. On any `Exception` it emits a `tool_fail` frame with `tool_failed` and returns the seam's fixed failed text (`DEC-arch-llm-client-library-7`). `CancelledError` and `GeneratorExit` propagate.
- **Reason:** The gateway stays the only module that knows how the library calls a tool. It imports nothing from `frames.py` or the tool seam, because those imports would cycle back to the gateway through `messages` → `llm_registry`. The compose source keeps every RPHelper rule about a tool call.
- **Rejected:** The gateway yielding SSE frames itself — that imports `frames.py` and its persistence dependencies into the gateway. The wrapper wholly in `compose.py` — `compose.py` would then have to know the library's signature check.
- **Lands in:** `backend/app/services/llm/gateway.py`, `backend/app/services/llm_registry.py`, `backend/app/services/compose.py`
- **Cites:** `llm-and-streaming.md` § The gateway (the four operations), § How one exchange runs; `DEC-arch-llm-client-library-5`, `-6`, `-7`

### DEC-035-7 — One unbounded queue, an end marker, and cancel-and-await on close
- **Status:** accepted
- **Stage:** — · **Feature:** 035.llm-client-gateway · **Step:** 003, 004
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** How does `compose` deliver events in order, end, surface errors, and stop the library task?
- **Decision:**
  1. `compose` is an async generator. On its first iteration it creates one unbounded `asyncio.Queue` and starts one task. The task builds the library client (`async with`) and awaits `chat_with_tools(stream=True, max_loops=sys.maxsize)`.
  2. `on_delta` and the runner's `emit` put onto the queue without awaiting (`put_nowait`).
  3. When the task finishes, a done-callback enqueues a private end marker. The marker carries the task's exception, or none.
  4. The generator yields queued events until it reaches the end marker. If the marker carries an exception, the generator raises the gateway's `llm_unreachable` per DEC-035-8. The task's return value is discarded (`DEC-arch-llm-client-library-8`).
  5. A `finally` cancels the task if it is still running and awaits it, suppressing whatever it ends with. The library's request is therefore closed before the generator returns.
  6. `compose.py` iterates the gateway stream inside `contextlib.aclosing`, so closing the compose source closes the gateway stream.
- **Reason:** One queue is what keeps the frame order equal to the order things happened (`llm-and-streaming.md`). Awaiting the cancelled task is what makes "the stop closes the provider request" true before the harness persists and returns.
- **Rejected:** A bounded queue — backpressure inside the library's `on_delta` would stall the provider read for no benefit within one exchange. Not awaiting the cancelled task — the request may still be open when the handler returns.
- **Lands in:** `backend/app/services/llm/gateway.py`, `backend/app/services/compose.py`
- **Cites:** `llm-and-streaming.md` § How one exchange runs, § Stopping model work in flight; `DEC-arch-llm-client-library-4`, `-8`

### DEC-035-8 — How each operation maps library failures
- **Status:** accepted
- **Stage:** — · **Feature:** 035.llm-client-gateway · **Step:** 001, 002, 003
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** `DEC-arch-llm-client-library-3` and `-9` fix the probe taxonomy and the embed reasons. What do the operations do at the edges those leave open?
- **Decision:**
  - **probe** catches every `Exception`, so it raises nothing:
    - an `LLMError` whose message contains `status 401` or `status 403` → `auth_failed`;
    - any other `LLMError` or exception → `unreachable`;
    - an empty listing → `model_list_empty`;
    - a listing → `reachable`, with the names as a tuple in server order.
    The gateway never sets `ProbeResult.note`.
  - **embed** raises `llm_unreachable` with one of these `detail.reason` values:
    - `auth_failed` on `status 401` or `status 403`;
    - `no_usable_vector` (`EMBED_NO_VECTOR_REASON`) on an `LLMError` whose message starts with `Invalid response`;
    - `unreachable` otherwise.
  - **complete** and **compose** raise `llm_unreachable` with one of these `detail.reason` values, which is the same reason the replaced client's streamed chat carried:
    - `auth_failed` on an `LLMError` whose message contains `status 401` or `status 403`, and in the `DEC-arch-llm-client-library-9` no-credential case;
    - `unreachable` on every other `LLMError`, `RuntimeError` or `ValueError` out of the library. This includes the temporary-limitation cases: an unoffered tool name, unparseable tool arguments, and unknown argument names.
  - **An unrecognised `kind`** (the column has no `CHECK`) is caught before any library client is built. Probe reports `unreachable`. The other three operations raise `llm_unreachable` with `reason: unreachable`.
  - **Every `llm_unreachable` the gateway raises** carries a fixed RPHelper message and is raised with no chained cause or context (`from None`). The gateway logs nothing from the library error.
- **Reason:** The feature preserves behaviour, and the replaced client already raised `llm_unreachable` from its chat stream with `detail.reason` of `auth_failed` (401/403) or `unreachable` (everything else). This also keeps "the provider's body never reaches a log line, an exception message or a `detail`" true even for a formatted traceback, by the same reasoning as 028 D5 for `web_search`. And it keeps `detail` to "RPHelper's own reason values, where one applies" (`backend-structure.md` error table).
- **Rejected:** An empty `detail` for complete and compose — it would change the existing `llm_unreachable` detail that the chat path carries today.
- **Lands in:** `backend/app/services/llm/gateway.py`
- **Cites:** `llm-and-streaming.md` § Errors, and what never leaves a failure; `backend-structure.md` § The error model; `DEC-arch-llm-client-library-3`, `-9`, `-10`

### DEC-035-10 — `compose` uses the tool loop even when no tool is offered
- **Status:** accepted
- **Stage:** — · **Feature:** 035.llm-client-gateway · **Step:** 003
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** With no tool offered, does `compose` call the library's plain streamed `chat`, or `chat_with_tools` with no tools?
- **Decision:** Always `chat_with_tools`, with an empty definitions list and an empty callables map.
- **Reason:** The zone may hold replayed tool pairs from an earlier exchange even when tools are now switched off, and `chat` takes role/content messages only, so it cannot carry them. In this case the library sends an empty `tools` list.
- **Rejected:** Branching to `chat(stream=True)` — it breaks replay of earlier tool rows.
- **Lands in:** `backend/app/services/llm/gateway.py`
- **Cites:** `llm-and-streaming.md` § The gateway ("With no tools offered, it offers none"), § Tool rows are replayed. Flip condition: a live server refuses an empty `tools` list (step 005's live test checks this). Then tools are omitted only when the history holds no tool pair.

### DEC-035-11 — Base-URL normalisation rule
- **Status:** accepted
- **Stage:** — · **Feature:** 035.llm-client-gateway · **Step:** 001
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** The architecture keeps "normalise to end in `/v1`, tolerating a trailing slash and an existing `/v1`". What is the exact rule?
- **Decision:** Strip trailing `/` characters. If the result does not end with `/v1`, append `/v1`. Nothing else is rewritten: scheme, host, port and any other path are kept.
- **Reason:** It tolerates the two named inputs and no more. A wider rewrite would hide a mistyped path that the administrator should see as `unreachable`.
- **Lands in:** `backend/app/services/llm/gateway.py`
- **Cites:** `llm-and-streaming.md` § Base-URL composition stays RPHelper's
