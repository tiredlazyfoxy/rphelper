# Decisions — 034.session-names
**Stage:** — · **Feature:** 034.session-names

Planning-time decisions for session names. The binding architecture-level choices are `DEC-arch-session-names-1..7`, which these entries do not re-decide.

### DEC-034-1 — The rename body's `name`: a required key, string or null, normalised on both sides
- **Status:** accepted
- **Stage:** — · **Feature:** 034.session-names · **Step:** 002
- **Date:** 2026-11-06 · **Decided by:** orchestrator
- **Question:** What shape does `name` take in the rename body, and where are trimming and blank-to-NULL applied?
- **Decision:** `name` is a **required** key whose value is a string or `null`. A missing key is a 422, and a non-string, non-null value is a 422. The request model trims with an `AfterValidator` of the same shape as `_normalise_language`, and blank becomes `None`. The service's `rename_session` applies the same normalisation itself, so a direct service caller cannot store a blank name. A missing key is not treated as "leave unchanged", because the route has nothing else to change.
- **Reason:** A required key makes `{}` a visible client error instead of a silent no-op. Normalising in the service as well realizes DEC-arch-session-names-1's "trim on write" where the write happens.
- **Rejected:** The `model_fields_set` / `UNSET` approach used by configuration — it distinguishes "not sent" from "null", which is meaningless when `name` is the only key. Treating `null` as "not supplied", as setups do — that would make clearing a name impossible (US-150.AC-3).
- **Lands in:** `backend/app/models/sessions.py`; `backend/app/services/sessions.py`
- **Cites:** `backend-structure.md` § `/api/sessions` (the `PATCH` table); DEC-arch-session-names-1, -2; US-150.AC-3

### DEC-034-2 — `extra="forbid"` on the rename request model: the one named exception
- **Status:** accepted
- **Stage:** — · **Feature:** 034.session-names · **Step:** 002
- **Date:** 2026-11-06 · **Decided by:** orchestrator
- **Question:** How is "any other key is a 422" realized when every request model in the codebase uses `extra="ignore"`?
- **Decision:** The rename request model sets pydantic `ConfigDict(extra="forbid")`. It is the first and only request model to do so, and a comment at the config cites this entry.
- **Reason:** This is the mechanism for DEC-arch-session-names-2's strict body. Pydantic's own refusal produces FastAPI's standard 422 with no custom handler.
- **Rejected:** A hand-written check over the raw body — it duplicates what pydantic does and needs a raw-body dependency.
- **Lands in:** `backend/app/models/sessions.py`; `backend/app/models/AGENTS.md` `## Conventions`
- **Cites:** `backend-structure.md` § `/api/sessions` (deliberate deviation from 009 D8)

### DEC-034-3 — No length cap on a session name

### DEC-034-7 — The version-1 upgrade: the deserializer learns the file's version; only `sessions.name` may be absent
- **Status:** accepted
- **Stage:** — · **Feature:** 034.session-names · **Step:** 001
- **Date:** 2026-11-06 · **Decided by:** planner
- **Question:** How does the importer realize DEC-arch-session-names-7 inside the existing validation and row-deserialization path?
- **Decision:**
  - Envelope validation accepts `schema_version` ∈ {1, 2}. It keeps the strict int-not-bool check and refuses everything else as `schema_mismatch`. The validated export carries the file's version.
  - For version 1 only, `sessions` rows are deserialized with `name` allowed missing, through the existing `allow_missing` mechanism, and the absent value is set to NULL.
  - A version-1 `sessions` row that **does** carry `name` is `malformed_payload`, because version 1 had no such column.
  - Version 2 is unchanged.
  - Every import entry point, including bootstrap, inherits the change through the shared validation.
- **Reason:** One named relaxation at the one place column sets are checked, beside the existing `users`-row allowance. Refusing a v1 row carrying `name` keeps the version meaningful.
- **Rejected:** Rewriting the payload to version 2 before validation — it hides the upgrade inside a mutation of the input. Accepting `name` on v1 rows — a v1 file cannot legitimately contain it.
- **Lands in:** `backend/app/services/transfer_import.py`; `backend/app/services/transfer.py` (`SCHEMA_VERSION` = 2)
- **Cites:** `transfer.md` § Accepted schema versions; DEC-arch-session-names-7

### DEC-034-8 — My-search wire keys and hydration: session hit `name`, entry hit `session_name`; name hits by name then id
- **Status:** accepted
- **Stage:** — · **Feature:** 034.session-names · **Step:** 003, 004
- **Date:** 2026-11-06 · **Decided by:** orchestrator
- **Question:** Which keys carry the name to the client, and how is the name arm ordered and merged?
- **Decision:**
  - A session hit gains `name`. An entry hit gains `session_name`, next to `session_created_at`. Both are a string or `null`, and both are hydrated by my-search's own owner-scoped read.
  - The name arm orders its hits by `name`, then `id`, as the character and setup matches do.
  - A pure merge places name hits first, then the vector hits not already matched, capped at the per-kind limit.
  - A blank query issues no name query.
- **Reason:** The client labels every surface with one rule and needs the stored name wherever a session is named, including entry hits. The `session_` prefix follows the entry hit's existing `session_created_at`.
- **Lands in:** `backend/app/services/search/my_search.py`; `backend/app/models/search.py`; `backend/app/routers/search.py`; `frontend/src/app/searchApi.ts`
- **Cites:** `search-and-retrieval.md` § The result shape (hydration table); DEC-arch-session-names-5; US-152.AC-2

### DEC-034-9 — The client label module: `sessionLabel`, a local-date fallback, `formatLocalDateTime`
- **Status:** accepted
- **Stage:** — · **Feature:** 034.session-names · **Step:** 004, 006
- **Date:** 2026-11-06 · **Decided by:** planner
- **Question:** What does the one label derivation look like, and how is the tree's second line composed?
- **Decision:**
  - `sessionLabel.ts` exports `sessionLabel`, which takes anything with `name` and `created_at` plus an optional time zone. It returns the name, or the local `YYYY-MM-DD` of `created_at` when the name is null.
  - The existing `formatSessionStart` is renamed `formatLocalDateTime`, with the same `YYYY-MM-DD HH:MM` contract, because after this feature it formats the last use, not the start.
  - The tree's line 2 is `formatLocalDateTime(last_used_at)`, then ` · ` and the setup name, or the time alone when there is no setup.
  - Nothing else formats `created_at` to name a session.
- **Reason:** One derivation means four surfaces cannot drift (`workspace-shell.md`'s label rule). The rename stops the old name from misdescribing its new use.
- **Lands in:** `frontend/src/app/sessionLabel.ts`; `frontend/src/app/CharacterTree.tsx`; `frontend/src/app/AGENTS.md` `## Conventions`
- **Cites:** `workspace-shell.md` § Geometry (the label rule, line 2); DEC-arch-session-names-1, -3

### DEC-034-10 — Rename affordances: an `IconEdit` button on every tree session row and beside the header title
- **Status:** accepted
- **Stage:** — · **Feature:** 034.session-names · **Step:** 006
- **Date:** 2026-11-06 · **Decided by:** orchestrator
- **Question:** Where exactly does the "Rename session" control sit, given that the tree row has no actions menu?
- **Decision:**
  - **Tree.** Each tree session row carries an `IconEdit` `IconButton` labelled "Rename session", as a sibling of the row's link, never nested in it. While that row is being edited, the editor replaces the link. Whether the button is visually revealed on hover or focus through `ui-conventions.md`'s opacity idiom is the coder's call; it stays in the DOM and the tab order either way.
  - **Header.** The session header carries the same control beside its `Title`, which the editor replaces while editing. The header offers it on archived sessions too, because the backend allows renaming an archived session.
  - **Sessions tab.** The character page's Sessions tab offers no rename.
- **Reason:** A per-row overflow menu holding one item is a menu with nothing to choose between. The tree row is a nav list, not a table, so `forms-and-lists.md`'s table-row menu rule does not reach it.
- **Rejected:** A row `IconDots` menu with a single "Rename" item — an extra click for nothing.
- **Lands in:** `frontend/src/app/CharacterTree.tsx`; `frontend/src/app/SessionScreen.tsx`
- **Cites:** DEC-arch-session-names-2, -4; `ui-conventions.md` § icon table; `workspace-shell.md` § rename

### DEC-034-11 — Rename editor semantics: unchanged sends nothing, one in flight, inline failure, apply the returned row
- **Status:** accepted
- **Stage:** — · **Feature:** 034.session-names · **Step:** 005, 006
- **Date:** 2026-11-06 · **Decided by:** orchestrator
- **Question:** What exactly do commit, cancel, failure and success do in the in-place editor?
- **Decision:**
  - Each host (the tree, the header) owns one `SessionRenameState`: editing id, draft, original name, pending, error.
  - **Commit** (Enter or blur): trims the draft, and blank becomes `null`. A value equal to the original sends nothing and closes. Otherwise exactly one request goes out; a second commit and Escape are ignored while it is pending.
  - **Escape** closes and sends nothing.
  - **Success:** the returned session is applied to the workspace `SessionsState` and handed to the host's callback, which the header uses to replace its screen state's session. Then the editor closes.
  - **Failure:** the fixed sentence "Could not rename the session." renders **inline** under the editor. The editor stays open with the draft, and no list changes. Nothing is applied before the answer.
- **Reason:** The editor is on screen and is where the roleplayer is looking. `ui-conventions.md`'s async-feedback rule sends a failure with an in-page place to that place, not to a notification. Applying the returned row is the narrowed re-load the archive/restore actions already use. Because a rename never moves `last_used_at`, it changes no order (DEC-034-12).
- **Rejected:** `notifyFailure` plus closing the editor — it loses the typed text. Re-fetching the session lists after success — a second request for data the response already carries.
- **Supersedes:** DEC-arch-session-names-4 **in part** (that entry allows planner refinement): its "a failure goes through `notifyFailure`" becomes an inline failure, and its "the session lists are re-read" becomes applying the returned session. The architect flips or annotates it at finalization; see `outcome.md` `## Architecture`.
- **Lands in:** `frontend/src/app/sessionRenameState.ts`; `frontend/src/app/SessionNameEditor.tsx`; `frontend/src/app/SessionScreen.tsx`; `frontend/src/app/CharacterTree.tsx`
- **Cites:** `forms-and-lists.md` § named exceptions, § never optimistic, § narrowed re-load; US-150.AC-2, US-150.AC-3

### DEC-034-12 — `applySession` orders `last_used_at` ties by id descending
- **Status:** accepted
- **Stage:** — · **Feature:** 034.session-names · **Step:** 005
- **Date:** 2026-11-06 · **Decided by:** orchestrator
- **Question:** How does applying a renamed session keep its tree position when today's insert places it after equal-`last_used_at` rows?
- **Decision:** `applySession` inserts by `last_used_at` descending, then id descending, compared numerically on the decimal-string ids. This is the server's own list order (`last_used_at DESC, id DESC`), so re-applying a row whose `last_used_at` is unchanged lands it at its old index.
- **Reason:** It matches the server order exactly, so every apply is position-stable without special-casing rename.
- **Rejected:** Replacing in place when `last_used_at` is unchanged — a special case that still leaves ties misordered for every other apply.
- **Lands in:** `frontend/src/app/sessionsState.ts`
- **Cites:** US-150.AC-4; US-089.AC-1; `backend-structure.md` § `/api/sessions` (list order)

### DEC-034-13 — The character page's Sessions list follows the workspace store by the apply-a-row rule
- **Status:** accepted
- **Stage:** — · **Feature:** 034.session-names · **Step:** 006
- **Date:** 2026-11-06 · **Decided by:** planner
- **Question:** A rename from the tree can happen while the character page is mounted beside it. How does the page's section-owned Sessions list learn the new name?
- **Decision:** While `SessionsSection` is mounted, a MobX reaction runs a pure sync. Each section row whose id matches a workspace session with a **strictly newer** `updated_at` is replaced in place by that session. Rows are never added, removed or reordered.
- **Reason:** The tree cannot reach the section's store, but both see the workspace store. The comparison is `forms-and-lists.md`'s apply-a-row rule, so an older copy cannot overwrite a newer one.
- **Rejected:** Threading the section store to the tree — it couples the shell to one page. Re-reading the section on every workspace change — a request per stream write.
- **Lands in:** `frontend/src/app/sessionsSectionState.ts`; `frontend/src/app/SessionsSection.tsx`
- **Cites:** `forms-and-lists.md` § narrowed re-load (apply-a-row rule); `frontend-structure.md` (workspace vs section stores)

### DEC-034-15 — Rename host rules: `onRenamed` never throws, and each host lifetime gets a fresh `SessionRenameState`
- **Status:** accepted
- **Stage:** — · **Feature:** 034.session-names · **Step:** 005, 006
- **Plan-local:** 034 `status.md` Notes & Issues, step 005 (orchestrator, from verifier concerns)
- **Date:** 2026-11-06 · **Decided by:** orchestrator
- **Question:** `commitRename` applies the returned session to the workspace store before it calls the host's `onRenamed`, and an aborted commit returns without clearing `pending`. What must a host do about each?
- **Decision:**
  - A host's `onRenamed` must not throw. A throw after `applySession` would leave the workspace list updated while the editor shows the failure sentence.
  - A host must not reuse its `SessionRenameState` after aborting a commit, because the aborted commit leaves `pending` true. Each host creates one `SessionRenameState` per mounted lifetime and aborts in-flight commits on unmount. The tree and the session header each hold their own state and an unmount-aborted controller.
- **Reason:** Both rules keep DEC-034-11's guarantees ("nothing applied on failure", "one in flight") true at the host boundary.
- **Lands in:** `frontend/src/app/CharacterTree.tsx`; `frontend/src/app/SessionScreen.tsx`; `frontend/src/app/sessionRenameState.ts` (the contract the hosts honour)
- **Cites:** refines DEC-034-11; `forms-and-lists.md` § never optimistic
