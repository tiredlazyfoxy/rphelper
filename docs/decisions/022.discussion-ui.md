### DEC-022-1 — The discussion is read per entry
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 022.discussion-ui · **Step:** 001
- **Plan-local:** 022 D1, U1
- **Date:** 2026-10-04 · **Decided by:** user
- **Question:** How does the client read the discussion buried behind a settled entry?
- **Decision:** `GET /api/messages/{id}/discussion`, addressed by the entry's message id. A zone id or a buried id answers 404 `message_not_found`. The response is a list of entries with no count field.
- **Reason:** The entry is what the roleplayer looks at; a count is the list's length.
- **Lands in:** `backend/app/routers/stream.py`, `backend/app/services/messages.py`
- **Cites:** `session-stream.md` § The discussion read

### DEC-022-3 — Tool fields on the wire are derived from the stored payload
- **Status:** accepted; supersedes DEC-021-7's "not on the wire" half
- **Stage:** 003.assistant · **Feature:** 022.discussion-ui · **Step:** 001
- **Plan-local:** 022 D3, U2; 022 step 001 context payload table
- **Date:** 2026-10-04 · **Decided by:** user (shape); planner (derivation)
- **Question:** What does the client see of a tool row?
- **Decision:** Three fields: the tool name, a status and the arguments. Status is `"ok"` only when the payload is a JSON object whose `status` is exactly `"ok"`, otherwise `"failed"`. Arguments are the payload's arguments when they parse to a JSON object, otherwise `{}`. Non-tool rows carry `null` for all three. Never on the wire: the raw payload, the call id, the content, the code.

  | # | role | tool_name | payload | → status | → args |
  |---|---|---|---|---|---|
  | 1 | user | null | null | null | null |
  | 2 | assistant | null | null | null | null |
  | 3 | tool | memo_search | ok, arguments `{"query":"lighthouse"}` | ok | that object |
  | 4 | tool | session_search | status failed, arguments `{"query":"x"}` | failed | `{"query":"x"}` |
  | 5 | tool | web_search | ok, arguments `"not json"` | ok | `{}` |
  | 6 | tool | web_search | ok, arguments `"[1,2]"` | ok | `{}` |
  | 7 | tool | memo_search | ok, no arguments | ok | `{}` |
  | 8 | tool | memo_search | status `"weird"` | failed | `{}` |
  | 9 | tool | memo_search | `not json at all` | failed | `{}` |
  | 10 | tool | memo_search | payload null | failed | `{}` |
  | 11 | tool | null | ok, arguments `{"a":1}` | ok | `{"a":1}` (name null) |
  | 12 | tool | memo_search | `"a string"` | failed | `{}` |
- **Reason:** The view needs what was asked and whether it worked; tool output can be long and is the model's, not the roleplayer's. Any unreadable payload degrades to "failed" rather than an error.
- **Lands in:** `backend/app/models/stream.py`, `backend/app/services/messages.py`
- **Cites:** `session-stream.md` § The tool seam and dispatch, § The discussion read

### DEC-022-4 — The think parser and its worked examples
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 022.discussion-ui · **Step:** 002
- **Plan-local:** 022 D4
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** How does the client split an assistant text into thinking and answer segments?
- **Decision:** One linear scan with the tags of DEC-021-4 (case-sensitive). Think text is never trimmed. Answer pieces are trimmed and empty ones dropped only when at least one block was found; with no block the whole text is one answer segment, byte for byte, even when empty. A stray `</think>` is answer text. Empty think segments are kept. Worked examples (binding):

  | # | Input | Segments |
  |---|---|---|
  | 1 | `Hello` | answer `Hello` |
  | 2 | `  Hello  ` | answer `  Hello  ` |
  | 3 | `<think>plan</think>\n\nHello` | think `plan` (closed); answer `Hello` |
  | 4 | `<think>a</think>One<think>b</think> two` | think `a` (closed); answer `One`; think `b` (closed); answer `two` |
  | 5 | `Start<think>never closed` | answer `Start`; think `never closed` (not closed) |
  | 6 | `<think>only</think>` | think `only` (closed) |
  | 7 | `a </think> b` | answer `a </think> b` |
  | 8 | `<think>x\ny</think>\n((ooc))` | think `x\ny` (closed); answer `((ooc))` |
  | 9 | `<think>` | think `` (empty, not closed) |
  | 10 | `` (empty) | answer `` (empty) |
- **Reason:** Mirrors the server's strip rule so what the view calls the answer is what settle keeps; an unclosed block is still visible while streaming.
- **Lands in:** `frontend/src/app/thinking.ts`
- **Cites:** DEC-021-4

### DEC-022-7 — The live tool list
- **Status:** accepted; supersedes DEC-019-18
- **Stage:** 003.assistant · **Feature:** 022.discussion-ui · **Step:** 003
- **Plan-local:** 022 D7
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** What does the compose effect do with tool frames?
- **Decision:** It keeps a live tool list on the stream state: `tool_start` adds an entry in state running; `tool_result` sets ok with its summary; `tool_fail` sets failed with the summary "The tool failed."; a frame for an unknown call id is ignored. The list is emptied at run start and cleared together with the streaming text; nothing is written to the zone.
- **Reason:** The persisted tool rows arrive with the terminal re-read; the live list only bridges the stream.
- **Supersedes:** DEC-019-18
- **Lands in:** `frontend/src/app/streamState.ts`
- **Cites:** `frontend-structure.md` § The SSE consumer

### DEC-022-8 — Regenerate
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 022.discussion-ui · **Step:** 003
- **Plan-local:** 022 D8, U3
- **Date:** 2026-10-04 · **Decided by:** user
- **Question:** When is Regenerate offered and what does it do?
- **Decision:** It is shown when not streaming, not busy, and the zone holds a non-tool row; otherwise it is absent, not disabled. It runs the textless compose (DEC-021-2) through the same run machinery as Send and never touches the draft. It is not gated by the send-blocked reason — a recorded widening, since the server answers a missing model with an `error` frame.
- **Reason:** A retry must stay reachable after any failure, and it carries no text that could be lost.
- **Lands in:** `frontend/src/app/streamState.ts`, `frontend/src/app/SessionStream.tsx`
- **Cites:** `frontend-structure.md` § The SSE consumer

### DEC-022-11 — The Discussion group behind a record entry
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 022.discussion-ui · **Step:** 004
- **Plan-local:** 022 D11, U1; 022 context "UI strings"
- **Date:** 2026-10-04 · **Decided by:** user
- **Question:** How is the discussion shown under a settled entry?
- **Decision:** A collapsed group under non-partner entries only. It fetches lazily on first open and once only; loaded rows are kept across collapse. A failure is shown inline, without a notification, and is forgotten on collapse so reopening retries. Strings (tests bind to them):

  | Where | String |
  |---|---|
  | Thinking toggle | "Show thinking" / "Hide thinking"; label "Thinking" |
  | Tool toggle | "Show tool call" / "Hide tool call" |
  | Tool status | "Running" / "Done" / "Failed"; name fallback "Unknown tool" |
  | Tool body | "Arguments", then the arguments pretty-printed, or "No arguments."; then the summary when non-null |
  | Live reply | region "Live reply"; author "Assistant" |
  | Regenerate | "Regenerate" |
  | Discussion toggle | "Show discussion" / "Hide discussion" |
  | Discussion header | "Discussion", "Discussion (N)" once loaded; marker "Read-only" |
  | Discussion list | list "Discussion messages" |
  | Discussion empty | "No discussion behind this entry." |
  | Discussion failure | "The discussion could not be loaded." |
- **Reason:** A partner entry has no discussion; a lazy, cached read keeps the record fast.
- **Lands in:** `frontend/src/app/` (record entry and discussion group components)
- **Cites:** `workspace-shell.md` § The record
