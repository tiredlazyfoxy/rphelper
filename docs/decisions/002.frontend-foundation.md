### DEC-002-1 — Stores and drafts are pure data; effects are free functions
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 002.frontend-foundation · **Step:** —
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 002 D2
- **Question:** What shape does a MobX store or draft take?
- **Decision:** A store or draft is a pure data contract with no methods and no getters. Effects are free functions that take an abort signal, write through `runInAction`, and return early once aborted. The architecture holds the full rule.
- **Reason:** Code comments in every draft and page store cite "002 D2", so the id must resolve.
- **Lands in:** `frontend/src/**/*Draft.ts`, `frontend/src/**/*State.ts`
- **Cites:** `frontend-structure.md` (state conventions)

### DEC-002-2 — The client decodes once; each draft maps its own fields

- **Reason:** Code comments in the drafts cite "002 D6", so the id must resolve.

### DEC-002-5 — A minimal Mantine theme, dark by default
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 002.frontend-foundation · **Step:** 002, 005
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 002 D3
- **Question:** How much of the Mantine theme does the shared theme set?
- **Decision:**
  - It sets `primaryColor: "blue"` explicitly, the system font stack, and `defaultRadius: "sm"`.
  - It sets no `defaultProps`, no custom palette and no type scale.
  - The default colour scheme is dark. The scheme is stored under the key `rphelper.color-scheme`, which is separate from the workspace-layout key.
- **Reason:** The plan's D3 records the reason. Semantic colours come from Mantine's built-in palette, and geometry lives in `shell.css`, never in the theme. `primaryColor` is set explicitly so that a later change is a visible edit to a named token, not a discovery. The scheme gets its own key because it applies to all four entries, while the workspace-layout record belongs to the app entry alone.
- **Rejected:** Component `defaultProps`, an invented palette and a type scale; folding the scheme into the workspace-layout record.
- **Lands in:** `frontend/src/shared/theme.ts`, `frontend/src/shared/AppProviders.tsx`
- **Cites:** `ui-conventions.md`

### DEC-002-6 — Vitest shares the Vite config, and build does not run tsc
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 002.frontend-foundation · **Step:** 002
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 002 D10
- **Question:** How are the test runner, the build and the typecheck wired?
- **Decision:**
  - Vitest runs with `globals: false`, so tests import `describe`, `it` and `expect`.
  - `defineConfig` comes from `vitest/config`, so there is one config file and no second Vitest config.
  - `npm test` is `vitest run`.
  - `npm run build` does not chain `tsc`. Build and typecheck are independent gates.
- **Reason:** The plan's D10 records the reason for sharing the config: Vitest reusing `vite.config.ts` means no second pipeline, resolver or alias set to keep in step. It also records why `globals` is off: one fewer ambient type surface, and an import names its source. For the build not chaining `tsc`: _TBD: reason not recorded in the plan folder_.
- **Rejected:** A separate `vitest.config.ts`; a `build` that runs `tsc && vite build`.
- **Lands in:** `frontend/vite.config.ts`, `frontend/package.json`

### DEC-002-7 — API client request and response edges
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 002.frontend-foundation · **Step:** 004
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 002 step 004 context (path guard, body rule, empty response, codes as strings, 401 navigation)
- **Question:** How does the shared client behave at its edges?
- **Decision:**
  - A path that does not start with `/api/` throws before `fetch` is called.
  - A body is sent if and only if `body !== undefined`, so `null` is a body. The JSON content type is set only when there is a body.
  - A 204, or any empty 2xx, returns `undefined`.
  - Error codes are plain strings, not an enum.
  - A 401 calls `documentNavigation.assign("/login")` and still throws. A 403 does not navigate.
- **Reason:** An enum would need editing in every feature and would turn an unknown code into a type error. Navigating does not end the caller's code, so the client still throws, and the `documentNavigation` seam makes the navigation testable.
- **Rejected:** A code enum; returning instead of throwing after the 401 redirect.
- **Lands in:** `frontend/src/shared/api.ts`
- **Cites:** `frontend-structure.md` (API client)

### DEC-002-8 — The colour-scheme toggle names the action
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 002.frontend-foundation · **Step:** 005
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 002 step 005 context (ColorSchemeToggle)
- **Question:** How does the shared toggle read the current scheme, and how is it labelled?
- **Decision:** It reads `useComputedColorScheme` with `"dark"` as the fallback, because the raw value can be `"auto"`. The label names the action: "Switch to light theme" or "Switch to dark theme". It shows a sun while dark and a moon while light, at the main icon size.
- **Reason:** The raw value cannot decide which way to flip when it is `"auto"`. A label that names the action tells a screen-reader user what the button does, not what state the page is in.
- **Lands in:** `frontend/src/shared/ColorSchemeToggle.tsx`
- **Cites:** `ui-conventions.md` (icon buttons)
