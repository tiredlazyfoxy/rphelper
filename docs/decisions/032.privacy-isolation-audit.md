# Decisions — 032.privacy-isolation-audit
**Stage:** 005.portability · **Feature:** 032.privacy-isolation-audit

Decisions behind FEAT-019's systematic privacy audit. The audit closed three logging and engine leaks found at plan time and one owner-predicate gap found by the sweep, and otherwise proves owner isolation through a shared two-user world in `backend/tests/privacy_audit_support.py`. The rules it proves are in `domain-rules.md` R5 and R9, `deployment.md` "The redaction rule" and `backend-structure.md`. These entries record how the audit is built and why its witnesses take the shape they do.

Plan-local numbering: the plan's `## Ultra phase` numbers its orchestrator decisions 1–35 in one sequence. Orientation decisions 1–3 come first; harvest, skeleton and gate decisions follow from 4. Code comments cite them as "decision N". The test-coder resolutions (1–7) and the verify adjudications (1–5) are separate lists. Written at finalization (2026-11-09).

### DEC-032-1 — Leak-fix policy: a small leak is fixed in the step that finds it; a redesign is handed back
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 032.privacy-isolation-audit · **Step:** —
- **Plan-local:** 032 context "Leak-fix policy (user-confirmed)"
- **Date:** 2026-10-05 · **Decided by:** user
- **Question:** When the audit finds a leak, does it fix it or report it?
- **Decision:** A small leak is fixed inside the step that finds it, within that step's source budget and fix-allowance. A small leak is an owner predicate missing from one query, a field dropped from a response, or a log call that formats content. Anything needing a surface redesign, or outside the fix-allowance, is recorded and handed back as a `/bug-fixer` run against the owning feature, and the step is `blocked` on it.
- **Reason:** It closes cheap gaps where they are found, without letting an audit redesign another feature's contract.
- **Lands in:** process only (the steps' fix-allowances)
- **Cites:** `domain-rules.md` R5

### DEC-032-2 — The sweep's one finding: the session-vector refresh resolves empty-text ids owner-scoped before deleting
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 032.privacy-isolation-audit · **Step:** 004
- **Plan-local:** 032 decision 19; 032 verify adjudication 3
- **Date:** 2026-10-05 · **Decided by:** orchestrator (under DEC-032-1)
- **Question:** `refresh_session_vectors(conn, A, [B's session])` deleted B's `session_vec` row, because a foreign session composes to empty text and the empty-text branch deleted every such id. No route reaches it, so it was not an attack path. Fix or record?
- **Decision:** Fix it in step 004's fix-allowance. One owner-scoped read (`sessions.id IN (empty ids) AND sessions.user_id = :user_id`, with no `archived_at` term) resolves which empty-text ids are the caller's, and only those are deleted. The vector write and delete primitives stay user-agnostic, because the gap was in the caller.
- **Reason:** This is exactly a small leak under DEC-032-1. A pinned test stops a refactor from reopening it. The owner's own empty-text deletes and writes still happen, because a fix that scoped too tightly would have been worse than the bug.
- **Lands in:** `backend/app/services/session_index.py` (`refresh_session_vectors`)
- **Cites:** `domain-rules.md` R5, R6; `search-and-retrieval.md` (the vector and full-text tables have no user column, so every caller resolves ids owner-scoped); see also DEC-F005-2 (the degraded path's same rule)

### DEC-032-3 — uvicorn access-log redaction: a filter on the logger, rewriting only the target's query
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 032.privacy-isolation-audit · **Step:** 001
- **Plan-local:** 032 decision 9 (idempotence); 032 context plan-time leak 1; 032 verify adjudications 1, 2
- **Date:** 2026-10-06 · **Decided by:** orchestrator (arity guard: coder, confirmed at verify)
- **Question:** How is user text kept out of uvicorn's access log, given that my-search puts it in the query string?
- **Decision:**
  - `AccessQueryRedactionFilter` goes on the `uvicorn.access` **logger**, not a handler, so it runs before `InterceptHandler` pre-formats with `getMessage()` and every sink sees the rewritten target.
  - It rewrites only `record.args[2]`, cutting it at the first `?`, and only when `args` is a tuple of length at least 3 whose third item is a string containing `?`.
  - It always returns true, so a record is never dropped.
  - Installation is idempotent: every existing instance is removed by type and then one is added. `create_app()` runs at import and the test world is built many times per process.
- **Reason:** A handler filter would miss a handler uvicorn attaches itself. Testing `len(args) >= 3` rather than uvicorn's exact 5 is the safer failure mode for a redactor: pinning 5 would silently stop redacting if uvicorn changed its argument count. Without idempotence the filter would pile up for the life of the process.
- **Rejected:** Pinning `len(args) == 5` — brittle against a uvicorn change.
- **Lands in:** `backend/app/logging.py` (`AccessQueryRedactionFilter`, `configure_logging`)
- **Cites:** `deployment.md` "The redaction rule"; nginx's own access log is `fast/001.dev-and-container-harness`'s (DEC-F001-6)

### DEC-032-4 — Every log sink runs without diagnose or backtrace; the engine hides bound parameters
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 032.privacy-isolation-audit · **Step:** 001, 007
- **Plan-local:** 032 context plan-time leaks 2, 3; 032 red-gate "recorded expectation" correction; 032 verify adjudication 4
- **Date:** 2026-10-06 · **Decided by:** planner
- **Question:** How are traceback frame locals and SQL bound values kept out of logs?
- **Decision:**
  - Both loguru sinks, console and file, are added with `diagnose=False` and `backtrace=False`.
  - The engine is created with `hide_parameters=True`, the only option added; it is read back as `engine.hide_parameters`. Because engines are cached per resolved path, the flag is fixed when that path's engine is first created.
  - Known witness gaps: the only test guarding the console sink's `diagnose=False` is step 001's DoD-4. Under `TestClient` an unhandled exception is re-raised to the test, not logged, so step 007's console clauses cannot see it. `backtrace=False` has no witness.
- **Reason:** `diagnose=True` renders frame locals that hold message text and memo bodies. Hidden parameters keep bound values out of any SQLAlchemy record and out of a rendered statement error, even if someone lowers the logger level.
- **Lands in:** `backend/app/logging.py`; `backend/app/db/engine.py`
- **Cites:** `deployment.md` "The redaction rule" and its `diagnose` paragraph

### DEC-032-5 — The route-classification guard: a recursive walk, exact two-way equality, and no empty pass
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 032.privacy-isolation-audit · **Step:** 002
- **Plan-local:** 032 decisions 4, 5; 032 context "The enumeration"
- **Date:** 2026-10-05 · **Decided by:** orchestrator
- **Question:** How does the guard enumerate the app's routes, given that under FastAPI 0.141.1 `app.routes` holds no `APIRoute` at all?
- **Decision:**
  - The guard uses the in-suite recursive walk over the included routers, `_api_routes(routes, found, seen)`, and raises if the walk finds nothing.
  - It compares the registered operations with the enumeration literal `ENUMERATED_ROUTES` by exact two-way set equality. HEAD is excluded, and path parameters are normalised to `{}`.
  - Probes fill paths with an unknown id, `UNKNOWN_ID` `"7250000000000000002"`, and use `characters` for `{table_name}`.
  - A new API route needs its row in `ENUMERATED_ROUTES` before it ships.
- **Reason:** `[r for r in app.routes if isinstance(r, APIRoute)]` is empty under that FastAPI, which would make the guard pass against nothing — the worst failure for an inventory guard. The recursive walk is delivered precedent.
- **Rejected:** `isinstance(APIRoute)` over `app.routes` — empty. `fastapi.routing.iter_route_contexts` — a private helper an upgrade may move. `app.openapi()["paths"]` — correct, but not the suite's precedent.
- **Lands in:** `backend/tests/privacy_audit_support.py` (`ENUMERATED_ROUTES`, `ENUMERATED_OPERATIONS`, `route_operations`); `backend/tests/test_privacy_audit_routes.py`
- **Cites:** `domain-rules.md` R5; `backend-structure.md` (route guards)

### DEC-032-7 — The fake model seam: one atomic install of the four override keys, and nothing else sets them
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 032.privacy-isolation-audit · **Step:** 002
- **Plan-local:** 032 decisions 7, 8, 33
- **Date:** 2026-10-05 · **Decided by:** orchestrator
- **Question:** How does the audit world guarantee no test reaches the user's real model server?
- **Decision:**
  - `install_fake_model_seam` overrides all four keys or none: `get_llm_client_factory`, `get_chat_client_factory`, `get_translation_chat_client_factory` and `get_tool_registry`.
  - It raises if any of the four is already overridden, and removes exactly those four on exit.
  - `audit_world` calls it exactly once. No other test sets any of the keys.
  - The registry override builds the memo and session tools over injected fakes, and `web_search` over an `httpx.MockTransport` recorder. The chat, probe and web fakes live in the support module, which consolidated three file-local copies; `tests/llm_fakes.py` was not modified.
- **Reason:** Missing any one seam lets a real client run, which in a privacy audit means a real request to the configured server. The production registry would also omit `web_search`, because the test config blanks its keys.
- **Lands in:** `backend/tests/privacy_audit_support.py` (`FAKE_SEAM_OVERRIDE_KEYS`, `install_fake_model_seam`)
- **Cites:** holds after `035.llm-client-gateway`: the four keys are still the seams, and the factories now return `LlmGateway` (DEC-035-1). Open: the support module's docstrings still say "real LlmClient".

### DEC-032-8 — Seeding order and payload shape follow the built validation; user content goes through the API only
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 032.privacy-isolation-audit · **Step:** 002
- **Plan-local:** 032 decision 13; 032 test-coder resolution 1; 032 context "Inconsistent-owner rows"
- **Date:** 2026-10-05 · **Decided by:** orchestrator (memo ordering: test-coder, confirmed at red gate)
- **Question:** In what order does the world builder seed, so that a refusal never looks like a finding?
- **Decision:**
  1. Enable models before creating any session, because a session captures its model.
  2. Enable the embedding model, then designate it, before any memo create or character-sheet or setup-description PATCH.
  3. Seed memos before the compose exchange, so the scripted `memo_search` finds the tool-result sentinel planted in a searchable session-scope memo.
  4. Install `web_search` but never call it.
  5. Archive the archived session last.

  User content is never raw-inserted; every row comes through the API.
- **Reason:** Each step above is forced by a validation rule that answers 409 otherwise. Routing the tool-result sentinel through `web_search` would have tied the world to a Google response shape no record states. No API path can write an inconsistent-owner row, so seeding one by insert would test a non-path.
- **Lands in:** `backend/tests/privacy_audit_support.py` (`audit_world`)

### DEC-032-9 — Sentinel carriers follow the real schema; sentinels are single lowercase alphanumeric tokens
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 032.privacy-isolation-audit · **Step:** 002
- **Plan-local:** 032 decisions 14, 15 (reach half), 30, 31, 32
- **Date:** 2026-10-05 · **Decided by:** orchestrator
- **Question:** Several planned carriers (session title, partner label, a memo title, a reach column) do not exist. Where does each sentinel live?
- **Decision:**
  - Session-level carriers are `sessions.system_prompt` and the text embedded into `session_vec`. User settings are `users.rp_language` and `users.preferred_language`. Configuration is a column on characters and on sessions.
  - The memo carrier is `body` alone, seeded across all 12 combinations of scope and reach. Reach is derived from `is_enabled` and `is_forced`, not stored.
  - Vector carriers are registered with `stored=False`. My-search target words are not carriers.
  - Every sentinel is a single lowercase alphanumeric token, distinct, never a substring of another, and never in a username, server name or model name.
- **Reason:** One-token sentinels tokenise as one full-text term and are matchable by `LIKE`. Usernames and registry names are administrative data, so a sentinel there would read as a false leak.
- **Lands in:** `backend/tests/privacy_audit_support.py` (`SentinelRegistry`)
- **Cites:** extended by DEC-034-4 (`sessions.name` carrier)

### DEC-032-13 — Admin sweep boundaries: the export excluded, the import only against the seeded world, matchers that cannot false-positive
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 032.privacy-isolation-audit · **Step:** 006
- **Plan-local:** 032 decisions 20, 21, 24, 25, 26, 27; 032 test-coder resolution 6; 032 red-gate fault 3
- **Date:** 2026-10-05 · **Decided by:** orchestrator
- **Question:** How does the admin sweep avoid both false findings and a destructive call that empties the world?
- **Decision:**
  - **The admin GET sweep** excludes `GET /api/admin/database/export` by name, because that export carries every user's content by design and its opacity rule is 030's. Its role gate stays armed.
  - **The mutation loop** calls `POST /api/admin/database/import` only against the fully seeded world and asserts the 409. It also pins no success status, only "carries no sentinel" and "the handler ran".
  - **The frontend count-name matcher** matches whole identifiers and strips comments first.
  - **The prefix scan** covers the admin entry's own files. An allowed bare prefix needs a segment boundary, so `/api/me` does not admit `/api/memos`.
  - **The live check** covers the five confirms that exist. There is no model-disable confirm.
  - **The export file size** shown on the Database page is a recorded non-finding: US-078 authorises it, and the admin already holds the file.
- **Reason:** On an empty database the import wipes and replaces, which would turn every later absence assertion vacuously green. A substring matcher produced about fifty false positives (`inUse` inside `AdminUser`, `count` inside `account`). The prefix hole was a real weakness that the matcher self-tests caught.
- **Lands in:** `backend/tests/test_privacy_audit_admin.py`; `frontend/tests/adminPrivacyAudit.test.ts`
- **Cites:** `domain-rules.md` R5; `admin-surfaces.md`

### DEC-032-14 — The log sweep is dynamic: no static scan of logger call sites
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 032.privacy-isolation-audit · **Step:** 007
- **Plan-local:** 032 `007.context` "No AST scan of `logger.*` call sites (user decision)"; 032 decision 12; 032 decision 9 (restore half); 032 test-coder resolution 7; 032 red-gate fault 4
- **Date:** 2026-10-05 · **Decided by:** user (mechanics: orchestrator)
- **Question:** How does the audit prove no log record at any level carries forbidden text?
- **Decision:**
  - The proof is dynamic, with no AST scan of logger call sites. The whole world is driven with real logging and a level-0 capture.
  - Swept per record: the message, `repr(extra)` and the exception text, plus the real console sink's text and the log file. The capture sink's own `formatted` field is not swept.
  - Failures are driven through the fake seam, both through the handled `LlmUnreachableError` and through an unhandled class.
  - The console witness is bound by a `bound_console()` context opened as the outermost `with` in each test body, because pytest re-installs `sys.stderr` at the call phase.
  - Tests restore each touched logger's level, handlers, `propagate` and `.filters`.
  - A bodied row may answer 404 or 422.
- **Reason:** A dynamic sweep covers the formatting sites a static scan cannot see. The `formatted` field is rendered with the capture sink's own settings, so it says nothing about the application's sinks. Without the outermost binding the console witness observed nothing.
- **Lands in:** `backend/tests/test_privacy_audit_logs.py`; `backend/tests/privacy_audit_support.py` (log capture)
- **Cites:** `deployment.md` "The redaction rule"

### DEC-032-15 — Session and character list routes accept `include_archived`; the workspace store deliberately never sends it
