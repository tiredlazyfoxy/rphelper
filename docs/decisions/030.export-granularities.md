# Decisions — 030.export-granularities
**Stage:** 005.portability · **Feature:** 030.export-granularities

Decisions for exporting material as a downloadable JSON envelope at four
granularities (database, user, character, session). The feature was delivered on
2026-10-05. The envelope contract and the import policy it serves are in
`data-model.md` § Export / import contract and `transfer.md`; opacity is
`admin-surfaces.md`'s. Import (031) consumes what these entries produce.

### DEC-030-1 — What each granularity contains
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 030.export-granularities · **Step:** 001, 002
- **Date:** 2026-10-03 · **Decided by:** user
- **Plan-local:** 030 context "Granularity boundaries (decided; user-confirmed 2026-10-03)"
- **Question:** Which tables and rows does each granularity carry?
- **Decision:**
  - **database** — every table in `schema.metadata.sorted_tables` except `auth_sessions` and `translations`; every row and column, including `users.password_hash` and `llm_servers.api_key_ref` as the stored `$ENV_VAR` pointer. Admin only.
  - **user** — the caller's `users` row (minus the columns in `DEC-030-5`), their characters, setups, sessions, messages and **all** their memos.
  - **character** — the character, its setups, its sessions (archived included) with their messages, and memos at that character, its setups or its sessions.
  - **session** — the session, **all** its messages (settled, buried, current-zone), and memos at that session only.
  - Never exported: `translations` (a derived cache, like vectors), `auth_sessions` (live login tokens) and the FTS/vec tables (outside `metadata`, so absent by construction; still asserted). Archived rows are included everywhere (R6). A resolved secret never appears. Dangling references (owner ids below database granularity, `character_id` / `setup_id` at session granularity, model references) are expected; import decides remap or null.
- **Reason:** A character export carrying its sessions and messages is what makes the character portable; translations are recomputable.
- **Lands in:** `backend/app/services/transfer.py`
- **Cites:** `data-model.md` § Export / import contract; `domain-rules.md` R5, R6

### DEC-030-2 — The envelope's shape: no root header, two version numbers, a `TypedDict`
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 030.export-granularities · **Step:** 001
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 030 context "The envelope"; step 001 skeleton (`ExportEnvelope`)
- **Question:** What does the envelope hold besides the payload?
- **Decision:** Keys `format` (`"rphelper-export"`), `version` (`ENVELOPE_VERSION`), `granularity`, `created_at` (UTC ISO-8601, the services' `_now_text()` shape), `schema_version` (`SCHEMA_VERSION`, see `DEC-030-3`) and `payload` (table name → rows). There is no root-reference field: below database granularity the root table's list holds exactly one row, which is the root. `version` moves when the envelope's own shape or serialization rules change, `schema_version` when `db/schema.py` changes a table's shape; they move independently. `ExportEnvelope` is a `TypedDict`, the backend's first.
- **Reason:** The envelope must stay a plain JSON mapping, dumped directly and read by import; a `TypedDict` freezes its keys without making it a model.
- **Lands in:** `backend/app/services/transfer.py`
- **Cites:** `data-model.md` § Export / import contract; `transfer.md`

### DEC-030-3 — `SCHEMA_VERSION` starts at 1 and is bumped by hand
- **Status:** accepted; superseded in part by DEC-arch-session-names-7 (current value)
- **Stage:** 005.portability · **Feature:** 030.export-granularities · **Step:** 001
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 030 context "The two version constants are kept separate on purpose"; step 001 skeleton (`SCHEMA_VERSION`)
- **Question:** Where does `schema_version` come from?
- **Decision:** A separate int constant in `services/transfer.py`, starting at 1. No schema-version constant exists anywhere else, so it is bumped by hand whenever `db/schema.py` changes a table's shape.
- **Reason:** There is no migration framework and no version table to derive it from.
- **Superseded in part by:** `DEC-arch-session-names-7` (with `DEC-034-7`) — the value is now 2 (`transfer.md`), and import accepts version 1 through one named upgrade. The separate-constant, bump-by-hand rule survives.
- **Lands in:** `backend/app/services/transfer.py`

### DEC-030-4 — Row serialization is column-agnostic
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 030.export-granularities · **Step:** 001, 002
- **Date:** 2026-10-05 · **Decided by:** planner; orchestrator (table order, harvest decision 4; enum column, harvest decision 5)
- **Plan-local:** 030 context "Row serialization rules", "Build-order assumption"; 001.context (id rule, enums); 030 harvest decisions 4, 5; step 001 Notes & Issues
- **Question:** How are rows read and turned into JSON without naming columns?
- **Decision:**
  - Every read is a Core `select(<Table>)` through one seam, `read_table(connection, table, where, *, drop_columns)`, ordered by primary key. Table sets are explicit; column lists are not, so later columns flow through. `search_tables.py` is not imported.
  - An integer column is an id — emitted as a decimal string, null staying null — when it is in the primary key, carries a foreign key, or is named `id` or ends in `_id` (`_ID_SUFFIX`; the bare name is derived from it). This catches the FK-less `memos.scope_id` and `model_server_id`.
  - Booleans are JSON booleans; an enum (e.g. `users.role`, a `StrEnum`) is its string value; timestamps are the stored text; other numbers stay numbers. A terminal `str()` arm stringifies any type the registry does not declare today.
  - Payload keys follow `schema.metadata.sorted_tables` restricted to the included tables — a topological sort in which `memos` precedes `setups` / `sessions` / `messages`. That order beats any sequence written in the step prose.
- **Reason:** The exporter must survive schema growth; ids stay JS-safe (the `SnowflakeOut` rule); parents-first lets import insert in order.
- **Lands in:** `backend/app/services/transfer.py`
- **Cites:** `backend-structure.md` § The JSON id boundary
- **Note:** The `str()` catch-all would stringify rather than surface a new column shape; worth revisiting when `schema_version` next moves.

### DEC-030-5 — The user export's exclusions are their own constants
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 030.export-granularities · **Step:** 002
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 002.context "Why `role` and `is_enabled` leave the user export"; step 002 skeleton
- **Question:** Which parts of the account leave the user export, and why separate constants?
- **Decision:** `USER_EXCLUDED_COLUMNS = {password_hash, role, is_enabled}`; every other `users` column flows through, and `id` stays. `USER_EXCLUDED_TABLES` is a separate constant from `DATABASE_EXCLUDED_TABLES` though its value is identical today.
- **Reason:** `role` and `is_enabled` are administrator-controlled state; a `role` in a roleplayer-held file is a privilege grant waiting for an import path. `id` is every other row's `user_id` and user-level memos' `scope_id`, so import needs it to remap. The two granularities justify their exclusions differently and may diverge.
- **Lands in:** `backend/app/services/transfer.py`

### DEC-030-6 — The owned selections
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 030.export-granularities · **Step:** 002
- **Date:** 2026-10-05 · **Decided by:** planner (sibling-id mechanism: coder)
- **Plan-local:** 002.context (root lookup, memo predicates, raw messages); step 002 Notes & Issues
- **Question:** How are a character's or session's rows selected, owner-scoped?
- **Decision:**
  - The root row is the exporter's own full-row select on both `id` and `user_id`; none → `CharacterNotFoundError` / `SessionNotFoundError` (404, foreign and missing alike, no 403).
  - Memo predicates (all also on `user_id`): user — no scope filter; character — (`character`, the character) or (`setup`, one of its setup ids) or (`session`, one of its session ids); session — (`session`, the session).
  - Sibling ids come from the setup and session rows already read, not from an `in_` subquery, so `read_table` stays the only `select`. An empty id list contributes no term; with no sessions the message read is skipped and the key is present as an empty list.
  - Messages are read from the raw `messages` table by `session_id`, not through `settled_entries` / `current_zone`.
  - The whole export is one read snapshot (`_reading`).
- **Reason:** The full row is needed anyway and stays inside the snapshot; the existing getters may filter archived rows, which R6 forbids here. The views drop buried rows, and `related_to` would dangle; this is a read, so R11's two-writers rule is untouched.
- **Lands in:** `backend/app/services/transfer.py`
- **Cites:** `domain-rules.md` R5, R6, R11

### DEC-030-7 — Routes: placement, a raw `Response`, one header
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 030.export-granularities · **Step:** 003
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 003.context; step 003 skeleton and Notes & Issues
- **Question:** Where do the four export routes live, and what do they answer?
- **Decision:**
  - `GET /api/admin/database/export` lives on `admin_db.py`, inheriting its router-level admin guard. The three roleplayer routes live in a new `routers/transfer.py` with a router-level `require_user`, registered last.
  - Every route is annotated `-> Response` and returns a raw `Response`: status 200, body `encode_envelope(envelope)` (UTF-8 JSON), media type `application/json`, and exactly one header, `Content-Disposition: attachment; filename="<export_filename(envelope)>"`. The filename is `rphelper-<granularity>-<compact UTC timestamp>.json`, from the envelope's `granularity` and `created_at` only.
  - `transfer.py` shares a private `_attachment` helper; `admin_db.py` builds the same response inline. Neither router imports the other or translates an error; `admin_db.py` holds no `raise` at all (007 D13).
- **Reason:** A route on the admin router cannot forget the guard; routers group by feature. The `-> Response` annotation is load-bearing: FastAPI skips response-model generation, and a column-agnostic envelope has no static model. The id boundary is held upstream by the serializer. The filename never embeds user content (opacity).
- **Rejected:** A pydantic response model — impossible for a column-agnostic envelope.
- **Lands in:** `backend/app/routers/transfer.py`, `backend/app/routers/admin_db.py`, `backend/app/main.py`
- **Cites:** `backend-structure.md` § Authorization as router dependencies, § Layout; `admin-surfaces.md` (opacity)

### DEC-030-8 — `apiDownload` in the shared client
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 030.export-granularities · **Step:** 004
- **Date:** 2026-10-05 · **Decided by:** planner; orchestrator (decode reuse, harvest decision 7)
- **Plan-local:** 004.context; 030 harvest decision 7; step 004 skeleton and Notes & Issues
- **Question:** How does the browser receive a file download through the API client?
- **Decision:**
  - `apiDownload(path, signal?)` sits in `shared/api.ts` beside the JSON calls and reuses the public `decodeErrorResponse` / `mapFetchRejection`, so errors, the 401 navigation and the synthetic client codes behave exactly as elsewhere. No decode refactor.
  - It resolves to `DownloadResult { filename, size }` — `size` is the `Blob`'s byte count. No field carries body content.
  - The filename comes from the `Content-Disposition` quoted parameter; the fallback is `rphelper-export.json`.
  - The save is object URL → anchor appended to `document.body` → click → anchor removed and URL revoked in a `finally`.
  - After the body read it re-checks `signal.aborted` and rethrows the signal's own reason, so an abandoned call saves no file even when the transport resolved.
- **Reason:** One decode in the client. A detached anchor's click does not bubble to a document listener.
- **Lands in:** `frontend/src/shared/api.ts`
- **Cites:** `frontend-structure.md` § The API client (one decode)

### DEC-030-9 — The admin Database page's Export action
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 030.export-granularities · **Step:** 005
- **Date:** 2026-10-05 · **Decided by:** user (placement); planner
- **Plan-local:** 005.context; step 005 skeleton; 030 "Carried forward" (mid-flight abort)
- **Question:** Where does the admin export sit, and what does the page report?
- **Decision:**
  - A page-level action group beside the Database title holds the one `Export` button (`IconDownload`, icon size 18 — the page-action metric, not the menu metric of 16). No placeholder for Import or Rebuild.
  - The only report is an inline size line, `Export downloaded — <size>`, with 1024-based units (B, KB, MB).
  - Failures go to an independent inline `Alert` (`exportErrorMessage`, separate from the drift report's message), never to a notification.
  - State is three observable fields (`exportStatus`, `exportSizeBytes`, `exportErrorMessage`) and a free `exportDatabase(state, signal)`.
- **Reason:** The size line is the one permitted report; the page already has an in-page error place.
- **Lands in:** `frontend/src/admin/DatabasePage.tsx`, `frontend/src/admin/databasePageState.ts`
- **Cites:** `admin-surfaces.md` (page-level actions, opacity); `ui-conventions.md` § Async feedback
- **Note:** Accepted: an abort mid-export returns without restoring `exportStatus` to idle, consistent with "write nothing once aborted"; the signal is the page's own unmount controller, so it is not observable.

### DEC-030-10 — The app's three export controls and the shared `runExport`
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 030.export-granularities · **Step:** 006
- **Date:** 2026-10-05 · **Decided by:** planner; coder (abort predicate, after verify CODE fault)
- **Plan-local:** 006.context; step 006 skeleton; 030 "Verify round 1 — step 006, Fault CODE"; 030 "Carried forward"
- **Question:** How do the three app-entry controls download, and how is failure reported?
- **Decision:**
  - `exportDownloads.ts` is a module of free functions: three path builders (`/api/export`, and the character and session routes, which interpolate the id through `encodeURIComponent`) and `runExport(path)`, which awaits `apiDownload`, discards the result, stays silent on an abort and calls `notifyFailure` once for anything else. It never rethrows.
  - The abort test matches any non-null object whose `name` is `AbortError`, independent of its constructor.
  - Controls: `Export my data` in the user menu (every role, above Log out); `Export` beside Archive/Restore on the character page (never on the draft page), with a component-local in-flight flag; `Export` in each session row's menu.
- **Reason:** One effect keeps the failure routing in one place. The real abort is a `DOMException`, which is not an `Error` instance in jsdom or browsers, so the house `instanceof Error` form let it reach `notifyFailure`.
- **Rejected:** The house `error instanceof Error && error.name === "AbortError"` predicate.
- **Lands in:** `frontend/src/app/exportDownloads.ts`, `frontend/src/app/UserMenu.tsx`, `frontend/src/app/CharacterScreen.tsx`, `frontend/src/app/SessionsSection.tsx`
- **Cites:** `ui-conventions.md` § Async feedback (no success toast)
- **Note:** Open: the narrow predicate still lives in other copies under `frontend/src/admin/` (code check counts nine or more), mostly shielded by a `signal.aborted` pre-check. Outstanding `[manual/live]`: step 003 DoD-11, step 005 DoD-11, step 006 DoD-9 (browser downloads).
