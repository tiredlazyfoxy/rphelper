### DEC-004-1 — One uniform refusal, with a decoy verify
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 004.authentication-session · **Step:** 001
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 004 D1
- **Question:** How does login refuse a wrong username, a wrong password and a disabled account without telling them apart?
- **Decision:**
  - All three get the same `invalid_credentials` refusal. `account_disabled` is never raised.
  - An unknown username still runs a verify, against a real encoded hash computed once at import time, never per request.
  - A failed login never logs the username.
  - Timing equality is checked by reading the code's structure manually, not by a wall-clock test.
- **Reason:** Distinct refusals or a skipped verify would let a caller enumerate accounts. Hashing a decoy per request would make the refusal slower than a real verify, which is its own signal. A wall-clock test would be flaky.
- **Lands in:** `backend/app/services/auth.py`
- **Cites:** `backend-structure.md` (authentication)

### DEC-004-2 — `invalid_credentials` is 400
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 004.authentication-session · **Step:** 001
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 004 D2
- **Question:** What status does a failed login answer?
- **Decision:** 400.
- **Reason:** The plan's D2 records the reason. The shared client navigates to `/login` on any 401 (DEC-002-7). A 401 for bad credentials would reload the login page and lose the message the user must see. A 400 means the submitted pair is not valid and no identity has been established.
- **Rejected:** These alternatives are recorded in D2:
  - 401 plus a per-call opt-out, which widens the shared client's contract for one call site.
  - 403, because nothing has been authenticated.
  - 422, which is FastAPI's validation shape and already serves as the empty-field backstop.
- **Lands in:** `backend/app/errors.py`
- **Cites:** `backend-structure.md` § The error model

### DEC-004-3 — 401 versus 403, and authentication first
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 004.authentication-session · **Step:** 002
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 004 D3
- **Question:** Which codes do the guards raise, and in which order?
- **Decision:** `not_authenticated` is 401 and `insufficient_role` is 403. Both are typed errors. Authentication runs before authorization, so a request with no session gets 401, never 403.
- **Reason:** Clients must be able to tell "sign in" apart from "not allowed".
- **Lands in:** `backend/app/dependencies.py`, `backend/app/errors.py`
- **Cites:** `backend-structure.md` (authorization as router dependencies)

### DEC-004-4 — Absolute session expiry, never extended
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 004.authentication-session · **Step:** 001
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 004 D4
- **Question:** Does a session slide forward as it is used?
- **Decision:** No. Expiry is absolute, set at creation from `session_ttl_hours` (default 720) and never moved. There is no refresh route.
- **Reason:** A sliding expiry writes on every request, which contends for SQLite's single writer.
- **Rejected:** Sliding expiry; a refresh route.
- **Lands in:** `backend/app/services/auth.py`, `backend/app/config.py`

### DEC-004-5 — Session tokens: random, stored as a SHA-256 digest
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 004.authentication-session · **Step:** 001
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 004 D5
- **Question:** How is a session token minted and stored?
- **Decision:** It is minted with `secrets.token_urlsafe(32)`. Only its SHA-256 digest is stored.
- **Reason:** A high-entropy random token needs no slow hash, and a fast digest keeps the per-request lookup cheap.
- **Rejected:** Argon2 for the token.
- **Lands in:** `backend/app/services/auth.py`

### DEC-004-6 — Cookie attributes
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 004.authentication-session · **Step:** 002
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 004 D6; 004 step 002 context (cookie read and clear)
- **Question:** What does the session cookie carry, and how is it read?
- **Decision:**
  - The name comes from settings.
  - It is `HttpOnly`, `SameSite=Lax` and `Path=/`, with `Max-Age = session_ttl_hours * 3600`.
  - `Secure` is off.
  - It is read as `request.cookies[<configured name>]`. The clearer uses the same name and path.
- **Reason:** `Cookie(...)` fixes its alias at import time, so a name overridden in settings or `dependency_overrides` would be ignored. Flip condition: turn `Secure` on once the deployment serves TLS.
- **Rejected:** FastAPI's `Cookie(...)` parameter.
- **Lands in:** `backend/app/dependencies.py`
- **Cites:** `backend-structure.md` (authentication); `deployment.md`

### DEC-004-7 — The role is read live on every request
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 004.authentication-session · **Step:** 002
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 004 D7
- **Question:** Is the role copied into the session, or read through to the user?
- **Decision:** It is read live, through the session to `users`.
- **Reason:** The plan's D7 records the reason. `data-model.md` fixes it: every authenticated request resolves through `auth_sessions`, and that table has no `role` column. As a consequence, a role change or a disable takes effect on the caller's next request, with no session rewrite and no cache to invalidate.
- **Lands in:** `backend/app/dependencies.py`

### DEC-004-8 — Where the role ladder and the guards live
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 004.authentication-session · **Step:** 002
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 004 D8
- **Question:** Which modules hold the role ladder and the auth dependencies?
- **Decision:**
  - `roles.py` holds `ROLE_LADDER` and a pure comparison. This supersedes the "no ladder" part of DEC-003-6.
  - `app/dependencies.py` is a top-level leaf. It holds `CurrentUser`, `require_user`, `require_role` and the cookie writers.
- **Reason:** The plan's D8 records the reason. `db/schema.py` imports `roles.py`, so a FastAPI dependency there would pull `fastapi` into `db/`. The dependencies have many router consumers, so they sit at top level, not inside one router. The cookie writers sit beside the readers because they share the cookie's name and flags.
- **Rejected:** These names are recorded in D8:
  - `app/security.py`, which implies crypto.
  - `app/auth_deps.py`, an abbreviation.
  - `routers/deps.py`, which would put a non-router in the router package.
- **Lands in:** `backend/app/roles.py`, `backend/app/dependencies.py`

### DEC-004-9 — Logout is idempotent and needs no session
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 004.authentication-session · **Step:** 003
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 004 D9; 004 step 003 context (revoke scope)
- **Question:** What does logout require, and what does it touch?
- **Decision:** It answers 204 and does not require a user. It revokes only the calling session, and only if that session is neither revoked nor expired. It always clears the cookie.
- **Reason:** A user with a stale cookie must still be able to log out cleanly.
- **Lands in:** `backend/app/routers/auth.py`, `backend/app/services/auth.py`

### DEC-004-10 — Route paths, and login answers with the identity
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 004.authentication-session · **Step:** 003
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 004 D10; 004 step 003 context (Response parameter, no per-user session cap)
- **Question:** Where do the routes live, and what does login return?
- **Decision:**
  - The routes are `POST /api/auth/login` and `POST /api/auth/logout`. `/api/me` stays at the root.
  - Login answers 200 with the identity model. The route takes a `Response` parameter to set the cookie and still returns the model.
  - There is no cap on sessions per user.
- **Reason:** Returning the identity saves the client a second request.
- **Rejected:** Answering login with 204.
- **Lands in:** `backend/app/routers/auth.py`
- **Cites:** `backend-structure.md` (route surface)

### DEC-004-11 — Bootstrap create signs the new admin in
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 004.authentication-session · **Step:** 003
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 004 D11; 004 step 001 context (`open_session` transaction join)
- **Question:** After the first admin is created, does the user have to log in?
- **Decision:** No. Create opens a session inside its own transaction and sets the cookie on the 201, and the client hands off to `/`. `open_session` joins the caller's transaction if there is one, and opens its own otherwise. This supersedes DEC-003-8.
- **Reason:** One transaction means the admin row and the session commit together or not at all.
- **Lands in:** `backend/app/services/bootstrap.py`, `backend/app/services/auth.py`, `frontend/src/bootstrap/`

### DEC-004-13 — Credentials are not normalised
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 004.authentication-session · **Step:** 004
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 004 D13
- **Question:** Are the username or password trimmed or case-folded?
- **Decision:** No. Trimming is used only to decide whether a field counts as filled.
- **Reason:** Normalising at login only would reject accounts created before the rule existed. Flip condition: if normalisation is ever wanted, apply it at creation and at login together.
