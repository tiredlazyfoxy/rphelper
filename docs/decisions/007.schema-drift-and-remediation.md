### DEC-007-1 — What the report compares, and how both sides are normalised
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 007.schema-drift-and-remediation · **Step:** 001, 002
- **Date:** 2026-09-30 · **Decided by:** user
- **Plan-local:** 007 D1
- **Question:** Which differences make a table "drifted", and how are declared and live shapes made comparable?
- **Decision:**
  - Compared: the column set (missing / extra by name), each surviving column's SQLite type and NOT NULL flag (a "changed" column), and the index set keyed on (column list, uniqueness), not on index name.
  - Not compared: server defaults, `CHECK` text and foreign-key clauses.
  - Type text on both sides is upper-cased, runs of whitespace are collapsed, and spaces around `(`, `)` and `,` are dropped.
  - The declared type is compiled through the SQLite dialect before comparison, so `BigInteger().with_variant(Integer(), "sqlite")` reads as `INTEGER` and a non-native `Enum` as its `VARCHAR(n)`.
  - Only `PRAGMA index_list` rows with origin `c` count as live indexes. The `u` and `pk` rows SQLite creates implicitly are ignored.
- **Reason:** SQLite stores defaults, CHECKs and FK clauses as raw SQL text that does not round-trip against a SQLAlchemy declaration. A false "drifted" row invites a destructive rebuild that fixes nothing. Without the two normalisations and the origin filter, a correct, fresh database reports drift forever. For example, `users.username` is `unique=True` with no explicit index.
- **Rejected:** Comparing defaults, CHECK text and FK clauses — false drift from whitespace, quoting and parenthesisation.
- **Lands in:** `backend/app/db/drift.py`
- **Cites:** `admin-surfaces.md` § Database page (the compared set); `data-model.md` § Schema drift and rebuild

### DEC-007-2 — Three statuses; `seed-missing` declined
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 007.schema-drift-and-remediation · **Step:** 001
- **Date:** 2026-09-30 · **Decided by:** planner
- **Plan-local:** 007 D2
- **Question:** Does the report adopt BookWriter's fourth status, `seed-missing`, and a Seed action?
- **Decision:** No. The status set is closed at three values: in sync, missing, drifted. Each per-table record carries the table name, the status, the missing / extra / changed columns (expected and actual type and nullability) and the missing / extra indexes. It carries no row count, byte size or timestamp. The `_TBD:` on Seed in `admin-surfaces.md` stays a `_TBD:`.
- **Reason:** `docs/product/` holds no seed data, so a Seed action would have nothing to insert. A count is content (R5).
- **Rejected:** A `seed-missing` status or a placeholder Seed action — it invents a requirement.
- **Lands in:** `backend/app/db/drift.py`; `backend/app/models/admin_db.py`
- **Cites:** `admin-surfaces.md` § Database page; `domain-rules.md` R5

### DEC-007-3 — The walk covers `metadata.tables` only
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 007.schema-drift-and-remediation · **Step:** 002
- **Date:** 2026-09-30 · **Decided by:** planner
- **Plan-local:** 007 D3
- **Question:** Does the report also walk views and `vec0` / FTS5 virtual tables?
- **Decision:** No. It iterates `metadata.tables` in declaration order, with no `kind` discriminator. A feature that introduces a non-table schema object owns extending the report.
- **Reason:** None of those objects existed when the report was built. A discriminator with one reachable value, or a virtual-table comparison designed against zero examples, is worse than a recorded gap.
- **Rejected:** A `kind` field on the report row now.
- **Lands in:** `backend/app/db/drift.py`
- **Cites:** `admin-surfaces.md` § Database page (the recorded gaps)

### DEC-007-4 — Create and Sync are defined by postcondition, so no "wrong state" error exists
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 007.schema-drift-and-remediation · **Step:** 003
- **Date:** 2026-09-30 · **Decided by:** planner
- **Plan-local:** 007 D4
- **Question:** What do Create and Sync do in the states they were not designed for?
- **Decision:** Both actions are idempotent and total. Create on an existing table, in any state, does nothing and answers the current row. Sync creates a missing table, rebuilds a drifted one and does nothing to an in-sync one. Neither route has a state precondition, and no `table_already_exists` or `table_not_missing` code exists.
- **Reason:** Create can then never drop anything, which is what earns it no confirm (DEC-007-7). A stale-report press is a harmless no-op that answers with the truth.
- **Rejected:** State-precondition error codes — a refusal for something that has a correct answer.
- **Lands in:** `backend/app/db/sync.py`
- **Cites:** `admin-surfaces.md` § Database page (Create and Sync)

### DEC-007-5 — The rebuild: Alembic batch recreate, inside one all-or-nothing transaction
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 007.schema-drift-and-remediation · **Step:** 003
- **Date:** 2026-09-30 · **Decided by:** user (shape); coder (mechanism, confirmed by verifier PASS)
- **Plan-local:** 007 D5
- **Question:** How is a drifted table brought into the declared shape without losing surviving data?
- **Decision:** The shape is the user's: "Create a temporal table, move data, re-create table, move data back". It is realized as follows.
  - The autobegun read transaction is ended first, then the FK pragma is switched as DEC-007-8 states.
  - One `begin()` then holds every step below:
    1. Each missing column is added with `ADD COLUMN` as an untyped BLOB carrying its declared server default.
    2. `batch_alter_table(recreate="always", copy_from=<registry Table>)` rebuilds the table.
    3. Declared indexes Alembic skips are created explicitly.
    4. A post-copy `typeof` probe refuses values that will not cast. It runs only on columns retyped to INTEGER, REAL, NUMERIC, DECIMAL or BOOLEAN.
    5. `PRAGMA foreign_key_check` runs.
  - Any failure rolls back and raises `SchemaApplyFailedError` `from None`. The table is left as it was, and no `_alembic_tmp_*` table survives.
  - The row is re-derived after commit.
- **Reason:** Batch recreate is the tested implementation of SQLite's rebuild recipe. A half-rebuilt table is a worse state than a drifted one, and a silent lossy cast is what the page exists to prevent. SQLite's type affinity accepts uncastable text in a numeric column without error, which is why the `typeof` probe exists.
- **Rejected:** A best-effort partial apply.
- **Lands in:** `backend/app/db/sync.py`
- **Cites:** `admin-surfaces.md` § Database page (the rebuild and what it preserves); `backend-structure.md` § Schema evolution

### DEC-007-6 — `alembic` is a runtime dependency, used for batch operations only
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 007.schema-drift-and-remediation · **Step:** 003
- **Date:** 2026-09-30 · **Decided by:** planner
- **Plan-local:** 007 D6
- **Question:** How does Alembic enter the project without becoming a migration framework?
- **Decision:** `alembic>=1.14,<2.0` goes in `backend/pyproject.toml`'s runtime `dependencies`. Only `MigrationContext` and `Operations` are used, around the request's own `Connection`, with `batch_alter_table` in recreate mode. The four negatives hold: no `versions/`, no revision chain, no version table, no upgrade at startup. No `alembic.ini` or `env.py` exists.
- **Reason:** The library normally implies all four negatives, so they are written out explicitly.
- **Lands in:** `backend/pyproject.toml`; `backend/app/db/sync.py`
- **Cites:** `backend-structure.md` § Schema evolution (point 4)

### DEC-007-7 — The lossy-Sync confirm, and what the row menu offers
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 007.schema-drift-and-remediation · **Step:** 006
- **Date:** 2026-09-30 · **Decided by:** user (warn and confirm); planner (UI detail)
- **Plan-local:** 007 D7; 007 006.context (row menu)
- **Question:** Does a Sync that drops columns refuse, warn or apply, and is Create ever confirmed?
- **Decision:**
  - A Sync is lossy exactly when the row's `extra_columns` is non-empty.
  - A lossy Sync opens the shared `ConfirmModal`:
    - title `Sync <table>?`
    - a consequence sentence naming the table and every dropped column, and stating that other columns' data is preserved, with nothing counted
    - confirm label `Sync`, `color="red"`
  - A Sync with nothing to drop applies directly. Create is never confirmed.
  - A missing row offers Create and a drifted row offers Sync, each in one `IconDots` menu. An in-sync row renders no trigger.
- **Reason:** The page is the only path by which the schema changes, so refusing would leave a table drifted forever with no remedy. The confirm is conditioned on data loss, not on the action's name.
- **Rejected:** Refusing a lossy Sync. Confirming Create — it cannot destroy anything (DEC-007-4).
- **Lands in:** `frontend/src/admin/databasePageState.ts`; `frontend/src/admin/DatabasePage.tsx`
- **Cites:** `ui-conventions.md` § the confirm convention; US-018

### DEC-007-8 — Foreign keys during a rebuild: off outside the transaction, on again in `finally`
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 007.schema-drift-and-remediation · **Step:** 003
- **Date:** 2026-09-30 · **Decided by:** planner
- **Plan-local:** 007 D8
- **Question:** How does a batch recreate coexist with `PRAGMA foreign_keys = ON` on every connection?
- **Decision:**
  1. `PRAGMA foreign_keys = OFF` is issued on the raw DBAPI cursor, outside any transaction.
  2. The rebuild runs in one transaction, and `PRAGMA foreign_key_check` runs before commit. Any row it returns fails the rebuild.
  3. `PRAGMA foreign_keys = ON` is restored in `finally`, on both the success and the failure path.
- **Reason:** SQLite silently ignores this pragma inside a transaction. The connection is pooled, so leaving the pragma off would disable FKs for every later request on that connection.
- **Lands in:** `backend/app/db/sync.py`
- **Cites:** `backend-structure.md` § Schema evolution, § Database access

### DEC-007-9 — Two error codes, the route surface, and where the table name is made safe
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 007.schema-drift-and-remediation · **Step:** 003, 004
- **Date:** 2026-09-30 · **Decided by:** planner
- **Plan-local:** 007 D9
- **Question:** Which codes do the apply routes fail with, and where is `{table_name}` validated?
- **Decision:**
  - `unknown_table` (404, `detail` = table name) and `schema_apply_failed` (500, `detail` = table name and operation) are the only two codes.
  - The driver's message never reaches `message`, `detail` or a log line.
  - The table-name lookup happens inside `db/sync.py`, against the registry. Only the registry's `Table` object reaches the DDL, and the raw string is never interpolated into SQL.
  - The router makes one call per handler and holds no lookup.
- **Reason:** A SQLite error text can embed a column value. Lookup in the executor keeps rules out of the router.
- **Lands in:** `backend/app/errors.py`; `backend/app/db/sync.py`; `backend/app/routers/admin_db.py`
- **Cites:** `backend-structure.md` § The error model, § Schema evolution (the executor resolves the table)

### DEC-007-10 — `/api/health`'s schema roll-up: missing > drift > ok, uncached
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 007.schema-drift-and-remediation · **Step:** 002
- **Date:** 2026-09-30 · **Decided by:** planner
- **Plan-local:** 007 D10
- **Question:** How is the `drift` value produced, and at what cost?
- **Decision:** `probe_health` runs the drift report. `missing` outranks `drift`, which outranks `ok`. The `status` precedence and the result shape are unchanged, and the registry is still a parameter. The probe is not cached.
- **Reason:** A missing table fails every query, while a drifted one mostly works. A health check that cannot fail tells an operator nothing.
- **Rejected:** Caching the probe.
- **Flip condition:** if the walk shows against the healthcheck interval, the roll-up narrows back to presence and the drift branch moves behind the admin route.
- **Lands in:** `backend/app/services/health.py`
- **Cites:** `backend-structure.md` § `/api/health`

### DEC-007-13 — The report table: two summary cells from one pure helper
- **Status:** accepted

- **Date:** 2026-09-30 · **Decided by:** planner
- **Plan-local:** 007 005.context (summary cells)
- **Question:** How do five difference lists render in a table row?
- **Decision:** As two cells, Columns and Indexes, built by one pure helper.
  - Wording: "Missing: …; Extra: …; Changed: name (expected TYPE NOT NULL, actual TYPE NULL)". Index column lists take a "unique" prefix where relevant.

### DEC-007-14 — After any apply the page re-loads the whole report
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 007.schema-drift-and-remediation · **Step:** 006
- **Date:** 2026-09-30 · **Decided by:** planner
- **Plan-local:** 007 006.context (re-load after apply)
- **Question:** After a Create or Sync, does the page patch the row from the response or re-read?
- **Decision:** It re-reads the whole report and never patches in the returned row. A failure goes to the inline `Alert` above the table.
- **Reason:** It follows the never-optimistic rule, and it gives US-018.AC-2 a client-side witness besides the route's re-derived row.
- **Rejected:** Patching the row from the apply response — it can leave other rows stale after a rebuild.
- **Lands in:** `frontend/src/admin/databasePageState.ts`
- **Cites:** `ui-conventions.md` § mutations are never optimistic; US-018.AC-2
