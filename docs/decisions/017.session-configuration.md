# Decisions — 017.session-configuration

**Stage:** 003.assistant · **Feature:** 017.session-configuration

This feature covers the per-character and per-session configuration of the model, system prompt, languages and tools; their capture when a session starts; the use-time and set-time checks; and the session configuration bar. The contracts and the resolution rules are described in `data-model.md`, `domain-rules.md` and `llm-and-streaming.md`. User decisions 1–5 are recorded as D1, D5 and D8.

### DEC-017-1 — Model captured when a session is created
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 017.session-configuration · **Step:** —
- **Plan-local:** 017 D1; user decision 1
- **Date:** 2026-10-03 · **Decided by:** user (refined by planner)
- **Question:** Which model does a new session get?
- **Decision:**
  - The character's model, captured as-is and not validated.
  - Otherwise, the first enabled model.
  - Otherwise, NULL.
  - Existing sessions are not backfilled.
- **Reason:** The session keeps the model that was in effect when it started. The refinement against US-139.AC-2 is discharged by US-143.
- **Lands in:** `backend/app/services/sessions.py`.
- **Cites:** `domain-rules.md` configuration.

### DEC-017-2 — Use-time check order
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 017.session-configuration · **Step:** —
- **Plan-local:** 017 D2
- **Date:** 2026-10-03 · **Decided by:** planner
- **Question:** In what order are model problems reported when the model is used?
- **Decision:** `no_model_enabled` → `model_not_chosen` → `model_not_enabled` (level session). The checks run in `resolve_model_for_use`. The new errors have an empty detail and default messages: "No model is enabled on this instance." / "No model is chosen for this session."
- **Reason:** The most general problem is reported first.
- **Lands in:** `backend/app/services/configuration.py`, `backend/app/errors.py`.

### DEC-017-4 — Model stored as two columns
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 017.session-configuration · **Step:** —
- **Plan-local:** 017 D4
- **Date:** 2026-10-03 · **Decided by:** orchestrator
- **Question:** How is a model reference stored?
- **Decision:**
  - **Columns.** `model_server_id` (no FK) plus `model_name`.
  - **Constraints.** The CHECKs `ck_characters_model_both_or_neither` and `ck_sessions_model_both_or_neither` require both columns or neither.
  - **Names.** The literal names `model_ref` and `tools` stay forbidden by the schema tests.
- **Reason:** Both parts can be queried, and they are kept consistent by constraint.
- **Rejected:** a single encoded string.
- **Lands in:** `backend/app/db/schema.py`.
- **Cites:** `data-model.md`.

### DEC-017-6 — Text normalisation in the request models
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 017.session-configuration · **Step:** —
- **Plan-local:** 017 D6
- **Date:** 2026-10-03 · **Decided by:** planner
- **Question:** How are the prompt and language strings normalised?
- **Decision:** The prompt is kept verbatim, and a blank prompt becomes null. Languages are trimmed, and a blank language becomes null. Normalisation happens in the request models.
- **Reason:** A prompt's whitespace may matter; a language name's does not.

### DEC-017-7 — The enabled set and its order
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 017.session-configuration · **Step:** —
- **Plan-local:** 017 D7
- **Date:** 2026-10-03 · **Decided by:** planner
- **Question:** Which models are "enabled", and which is first?
- **Decision:** A model is enabled when `is_enabled` is set and its server exists. An embedding-designated model is included. Order is `llm_servers.id`, then `models.id`.
- **Reason:** The server grouping keeps the "first enabled" choice stable and readable.
- **Rejected:** ordering by `models.id` alone.
- **Lands in:** `backend/app/services/llm_registry.py`.

### DEC-017-10 — Set-time check
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 017.session-configuration · **Step:** 004
- **Plan-local:** 017 D10; 004.context update order, UNSET reuse
- **Date:** 2026-10-03 · **Decided by:** planner
- **Question:** How is a model checked when it is set?
- **Decision:**
  - **Transaction.** The check runs in the same transaction as the write, in this order: existence check → set-time check → one UPDATE. Nothing is written on refusal.
  - **Session model.** It is never cleared; null answers 422.
  - **Character model.** It accepts null.
  - `llm_registry`'s `UNSET` is reused.
- **Reason:** A session always has a model to use once created. A character may defer to "first enabled".
- **Lands in:** `backend/app/services/configuration.py`.

### DEC-017-21 — Setting<T> and the model select encoding
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 017.session-configuration · **Step:** —
- **Plan-local:** 017 Setting<T>; select encoding
- **Date:** 2026-10-03 · **Decided by:** planner
- **Question:** How are resolved settings typed, and how is a model chosen in a select?
- **Decision:** `Setting<T>` is a uniform generic whose value is `T | null`, booleans included; a null tool means unknown. Model select values are `"<server_id>:<model_name>"`, split at the first `:`. The list index is never used.
- **Reason:** One shape for every setting. A model name may contain `:`, but a server id cannot.
- **Lands in:** `frontend/src/app/configurationApi.ts` and the model selects under `frontend/src/app/`.

### DEC-017-22 — Session config state loads and failures
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 017.session-configuration · **Step:** 008
- **Plan-local:** 008.context two statuses, branch on code, 409 re-read
- **Date:** 2026-10-03 · **Decided by:** planner
- **Question:** How does the session configuration state load and react to errors?
- **Decision:**
  - **Loads.** Two statuses, config and models, share one Retry.
  - **Errors.** The state branches on the error `.code` only.
  - **Choosing a model.** `chooseModel` takes no signal. A 409 re-reads the models.
- **Reason:** The two reads fail independently. A 409 means the model list is stale.
- **Lands in:** `frontend/src/app/sessionConfigState.ts`.
