# Decisions — 028.web-search-tool
**Stage:** 004.retrieval · **Feature:** 028.web-search-tool

Decisions for the assistant's `web_search` tool: the provider, the credentials, how
an unconfigured instance hides the tool, the failure shape, and the logging fix the
verify run forced. The feature was delivered on 2026-10-05. The contracts are in
`llm-and-streaming.md` § `web_search`, `backend-structure.md` § Configuration and
`deployment.md` § The redaction rule; the adapter pattern is `DEC-026-3`..`-7`.

### DEC-028-1 — Provider: the Google Custom Search JSON API, key in a header
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 028.web-search-tool · **Step:** 001
- **Date:** 2026-10-05 · **Decided by:** user (provider); planner (request shape)
- **Plan-local:** 028 U1, D1; 001.context "The Google request"
- **Question:** Which search provider, and what exactly is sent?
- **Decision:** One `GET https://www.googleapis.com/customsearch/v1` per call with exactly the parameters `cx` (engine id), `q` (the query, verbatim) and `num` (the limit), passed through httpx's `params`, and the key in the `X-goog-api-key` header. No other parameter. Only the plain-text `title` / `snippet` are used, never `htmlTitle` / `htmlSnippet`.
- **Reason:** In the query string the key would be part of the URL, which reaches exception text, proxy logs and access logs; in a header it never appears in a URL.
- **Rejected:** The `key` query parameter — puts the secret in the URL.
- **Lands in:** `backend/app/services/web_search/google.py`
- **Cites:** `llm-and-streaming.md` § `web_search`. Flip condition: the live check (step 001 DoD-13; passed 2026-11-10 — the API accepted the header key and returned results) shows the API refusing the header; the switch goes through the user because the alternative puts the key in the URL. Known risk: Google has closed this API to new customers and existing ones must move off it by 2027-01-01; the provider sits behind its own seam (`DEC-028-4`) for that reason.

### DEC-028-2 — Credentials from the environment, directly, without the `RPHELPER_` prefix
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 028.web-search-tool · **Step:** 001
- **Date:** 2026-10-05 · **Decided by:** user
- **Plan-local:** 028 U2, D2
- **Question:** Where do the search credentials come from, and do they follow the `$ENV_VAR` pointer convention?
- **Decision:** `Settings` gains `search_cse_key: SecretStr | None` (alias exactly `SEARCH_CSE_KEY`) and `search_cse_id: str | None` (alias exactly `SEARCH_CSE_ID`), both defaulting to `None`. `RPHELPER_SEARCH_CSE_KEY` is not read. No pointer layer, no database row, no admin UI. The key is the repo's first `SecretStr`, so a logged or printed `Settings` masks it. An empty environment value stays empty (`SecretStr("")` / `""`), not `None`.
- **Reason:** The pointer convention exists because database rows are exported; a `Settings` field never is. The names are the ones the user's environment already uses. Rotation is an environment change plus a restart, the same answer the pointer gives.
- **Rejected:** An `$ENV_VAR` pointer — indirection with no export to protect against. The `RPHELPER_` prefix — not the names the environment holds.
- **Lands in:** `backend/app/config.py`
- **Cites:** `backend-structure.md` § Configuration, § The `$ENV_VAR` secret-pointer pattern; `deployment.md` § Configuration conventions

### DEC-028-3 — Unconfigured means not offered; the registry is built per request
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 028.web-search-tool · **Step:** 002
- **Date:** 2026-10-05 · **Decided by:** user (gating); planner (mechanism); orchestrator (import path, harvest decision 3)
- **Plan-local:** 028 U3, D3; 028 harvest decision 3; step 002 skeleton
- **Question:** How is `web_search` absent on an instance without credentials, without changing 021's offering rule?
- **Decision:**
  - `configured_web_search_tool(api_key, engine_id)` in `tools/web_search.py` is the one place that decides "configured": both values non-blank after trimming → `WebSearchTool(GoogleCustomSearchProvider(key, id))` with the provider's own defaults; otherwise `None`.
  - `build_tool_registry(api_key, engine_id)` in `seam.py` returns a new `MappingProxyType` over the production registry constant's entries, plus `web_search` when the factory returns an adapter. The constant is never written to and still holds exactly `memo_search` and `session_search`.
  - `get_tool_registry` in `routers/stream.py` depends on `get_settings` and calls the builder with the key's plain value (or `None`) and the engine id on every request — no trimming, no "configured" test, no cache there. It imports the builder from `app.services.tools.seam`, not the package (the package `__init__` was out of scope).
  - `WebSearchTool` is a frozen dataclass whose one field, `provider`, is required positional-or-keyword; `name` is a `ClassVar`.
- **Reason:** A tool the model cannot see cannot be attempted. Reading settings per request lets a `get_settings` override take effect; services stay settings-free. A default-constructed adapter could not search, so the provider is required.
- **Lands in:** `backend/app/services/tools/web_search.py`, `backend/app/services/tools/seam.py`, `backend/app/routers/stream.py`
- **Cites:** `llm-and-streaming.md` § The tool-calling loop (absent rather than refused); `backend-structure.md` § Routers versus services

### DEC-028-4 — The provider seam
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 028.web-search-tool · **Step:** 001
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 028 D4
- **Question:** What does the rest of the product depend on, so the provider can be replaced?
- **Decision:** `app/services/web_search/provider.py` holds the frozen `WebResult(title, url, snippet)` and the `WebSearchProvider` protocol with one async `search(query, limit) -> list[WebResult]`. `google.py` holds the one implementation, building a fresh `httpx.AsyncClient` per call with an optional injected transport. The package imports no `fastapi`, `app.config`, `app.secrets`, `app.db` or `app.services.tools`, and `__init__` re-exports nothing.
- **Reason:** Replacing Google is one new provider class and a factory change; the tool, its format and its tests stay.
- **Lands in:** `backend/app/services/web_search/`

### DEC-028-5 — Every failure is `ToolFailedError`, raised `from None`
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 028.web-search-tool · **Step:** 001, 002
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 028 D5; 001.context "Exception mapping"
- **Question:** What does a provider failure raise, and what may it carry?
- **Decision:** A timeout, a transport error, a non-2xx status (3xx included; redirects are not followed), an undecodable body, a non-object body and a non-list `items` all raise `ToolFailedError(detail={"tool": "web_search"})` with the default message, `from None`. Nothing — query, key, engine id, URL, status, body — is interpolated. Bad tool arguments raise the same error. No new error code.
- **Reason:** An httpx exception's text can contain the request URL, which contains the query; a chained cause is exactly what a traceback formatter prints. The provider exists only to serve this tool, so 021's typed tool failure is the honest code. `DEC-035-8` follows the same reasoning for the gateway.
- **Rejected:** A new `DomainError` — it would need its own status record for an error that is never an HTTP response.
- **Lands in:** `backend/app/services/web_search/google.py`, `backend/app/services/tools/web_search.py`
- **Cites:** `backend-structure.md` § The error model; `deployment.md` § The redaction rule

### DEC-028-6 — Only the query leaves; only `query` is read; the scope is unused
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 028.web-search-tool · **Step:** 002
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 028 D6, D8
- **Question:** What crosses the outbound boundary, and which tool inputs are used?
- **Decision:** Only the query, the engine id, the result count and the key (in the header) leave the instance. No user, session, character or setup id, message, memo or persona is sent. `run` reads exactly the `query` argument; every other key is ignored. `ToolScope` is accepted (the protocol requires it) and unused.
- **Reason:** Web search is not a scoped read of the user's data.
- **Lands in:** `backend/app/services/tools/web_search.py`
- **Cites:** `domain-rules.md` R5

### DEC-028-7 — Nothing logs the query, the results or the key; nothing is cached
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 028.web-search-tool · **Step:** 001, 002
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 028 D7
- **Question:** What may the provider and the adapter log or keep?
- **Decision:** The provider and the adapter emit no log records. The only failure log is the seam's existing one (tool name, call id, exception class). Results are not logged, not persisted beyond 021's tool row, and not cached: two identical calls make two requests.
- **Reason:** The query is composed from the discussion and counts as message text under the redaction rule. The brief rules caching out.
- **Lands in:** `backend/app/services/web_search/google.py`, `backend/app/services/tools/web_search.py`
- **Cites:** `deployment.md` § The redaction rule. The library-side half of this rule is `DEC-028-11`.

- **Decision:** `DEFAULT_TIMEOUT_SECONDS = 10.0` in `google.py`, overridable through the provider's constructor and applied as `httpx.Timeout(t)`. `RESULT_COUNT = 5` in `tools/web_search.py`, no paging, no count argument.

### DEC-028-9 — Parsing the response, formatting the content, the query rule
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 028.web-search-tool · **Step:** 001, 002
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 001.context "The Google response"; 002.context "What the model receives", "Query rule"
- **Question:** How are Google's items read, how are they shown to the model, and what is a valid query?
- **Decision:**
  - **Parse.** A 2xx JSON object is a success. `items` absent → zero results; present but not a list → failure. An element that is not an object, or has no string `link`, is skipped; a missing or non-string `title` / `snippet` becomes `""`. At most `limit` results. No whitespace normalisation in the provider.
  - **Format.** `format_results` returns `(content, summary)`. One block per result, in provider order: title, `\n`, url, `\n`, snippet — the snippet line omitted when blank. Title and snippet have whitespace runs collapsed and ends trimmed; the url is trimmed only. A blank title becomes `(untitled)`. Blocks joined by `\n\n`. Zero results: `No web results.`. Summary: exactly `<N> results`, never content.
  - **Query.** `query` must be a string that is non-blank after trimming, else `ToolFailedError` before any request. It is sent untrimmed.
- **Reason:** A blank query is a bad argument and an outbound call is not free (unlike 026/027, there is no port that returns `[]`).
- **Lands in:** `backend/app/services/web_search/google.py`, `backend/app/services/tools/web_search.py`

### DEC-028-10 — Test isolation sets both variables to `""`
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 028.web-search-tool · **Step:** 001
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 028 D12
- **Question:** How does every test see an unconfigured instance, whatever a developer's `.env` holds?
- **Decision:** The shared autouse fixture `isolated_settings_environment` sets `SEARCH_CSE_KEY` and `SEARCH_CSE_ID` to the empty string for every test and restores them afterwards, beside its existing `RPHELPER_*` deletion. Tests that need values set them afterwards (init arguments, a `get_settings` override, or their own `setenv`).
- **Reason:** pydantic-settings gives environment variables priority over the `.env` file, so an empty variable masks the file; deleting the variable would not.
- **Rejected:** `delenv` — a developer's `.env` would still supply real credentials.
- **Lands in:** `backend/tests/conftest.py`

### DEC-028-11 — Third-party request logs are silenced by level in `app/logging.py`
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 028.web-search-tool · **Step:** 001
- **Date:** 2026-10-05 · **Decided by:** user (route: fix the bridge); coder (mechanism; confirmed by verifier)
- **Plan-local:** 028 decision 6 (user decision on the SPEC fault, 2026-10-05)
- **Question:** httpx logs every completed request through `httpx._client`, which propagates to the root bridge and reaches loguru's sinks. The record is the full request URL, which carries `q=<query>` — a redaction breach at every level. How is it stopped?
- **Decision:**
  - `app/logging.py` holds `_SILENCED_LOGGERS` and `_SILENCED_LEVEL = logging.CRITICAL + 1`; `configure_logging` sets each named logger's level to that value. No other module touches a third-party logger. As of 035 the tuple is `("httpx", "aiohttp")` — `aiohttp` was added for the `llm-client` library (`DEC-arch-llm-client-library-10`).
  - **A level, not a filter.** A filter attached to `httpx` is not applied to records that merely propagate from a child, so it would miss `httpx._client`. A level on the parent is inherited by a child at `NOTSET`, so it covers the whole tree.
  - **Above `CRITICAL`, not at it.** The redaction rule has no level exception; a `CRITICAL` threshold would still pass a `CRITICAL` record.
  - Narrow by construction: propagation, the root bridge, both sinks and every other logger are unchanged.
- **Reason:** The only route that breaks no existing commitment — the request shape (`DEC-028-1`), `DEC-028-7` and the redaction rule all stay as written. `app/logging.py` already owns the bridge and reserves logger configuration to itself.
- **Rejected:** Amending `deployment.md`'s prohibition — weakens the rule. Changing the request shape (`DEC-028-1`) — the query must travel in the URL for this API. A provider mutating httpx's level or `propagate` at import — a global logging change hidden in a service module.
- **Accepted cost:** a genuine httpx (or aiohttp) warning or error record is also dropped; none exists today, and errors reach the app as exceptions.
- **Lands in:** `backend/app/logging.py`; pinned by a test in `backend/tests/test_web_search_google.py`
- **Cites:** `deployment.md` § The redaction rule; `backend-structure.md` (`app/logging.py` owns third-party logger suppression)
- **Note (risks carried forward):** the mechanism lapses if a library release sets an explicit level on a child logger; nothing restores the logger's level between tests, so once any test configures logging it stays silenced for the process; the pinning test's natural home is the privacy audit (032), not `test_web_search_google.py`.
