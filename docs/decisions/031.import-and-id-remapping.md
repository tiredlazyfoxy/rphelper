# Decisions — 031.import-and-id-remapping
**Stage:** 005.portability · **Feature:** 031.import-and-id-remapping

Decisions behind the import halves of FEAT-018: the three roleplayer imports, which mint new ids, and the whole-database replace, which preserves them. The contracts are in `data-model.md` § "Export / import contract" (Import policy), `transfer.md`, `backend-structure.md` (the import routes, the error model, the JSON id boundary) and `admin-surfaces.md` (the Database page's Import). These entries record the choices, and the alternatives weighed, beneath those contracts. Written at finalization (2026-11-09) from the plan's context, step contexts and `status.md`.

### DEC-031-1 — A session export is imported into a character the roleplayer chooses, with no setup
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 031.import-and-id-remapping · **Step:** 003
- **Plan-local:** 031 U1
- **Date:** 2026-10-03 · **Decided by:** user
- **Question:** A session export carries no character. Where does an imported session go, and what happens to its setup reference?
- **Decision:** The session is imported into the character the roleplayer picks, which is the character page it is imported from. `sessions.character_id` is that character and `sessions.setup_id` is null, whatever the payload held. An archived target character is accepted. A foreign or missing target is `character_not_found` (404), with no 403.
- **Reason:** The export's own character and setup do not exist on the importing side, and inventing either would create rows the roleplayer did not ask for. The imported session therefore takes the chosen character's persona.
- **Lands in:** `backend/app/services/transfer_import.py` (`import_session`, the session policy, the owner-scoped target lookup with no `archived_at` term)
- **Cites:** `data-model.md` § Import policy (session import target); `domain-rules.md` R5, R6; US-082

### DEC-031-2 — The whole-database import is a replace that preserves ids, allowed only on an empty or single-admin instance
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 031.import-and-id-remapping · **Step:** 004
- **Plan-local:** 031 U2
- **Date:** 2026-10-03 · **Decided by:** user
- **Question:** Should the `database` granularity merge as new like the roleplayer granularities, or replace?
- **Decision:** It is a REPLACE that keeps the export's own ids. It is allowed only when the instance has no users, or exactly one user whose role is admin. Any other state is `database_not_empty` (409) and nothing changes. The service takes no request user, so the bootstrap restore (`fast/003.bootstrap-from-export`) can call it.
- **Reason:** "Mint unconditionally" was written for the roleplayer's granularities. A restore onto an empty instance has nothing to collide with, and keeping the ids makes the restored instance identical to its source.
- **Rejected:** Merge-as-new for the whole database — it rewrites every id for no gain on an instance that holds nothing to collide with.
- **Flip condition:** a requirement to merge a whole-database export into a populated instance.
- **Lands in:** `backend/app/services/transfer_import.py` (`import_database`, the eligibility guard)
- **Cites:** `data-model.md` § Import policy (the deliberate deviation); `domain-rules.md` R6 (a whole-instance restore, not a per-entity delete); UC-061, US-077.AC-2

### DEC-031-3 — No import embeds anything; full text is kept current inside the import
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 031.import-and-id-remapping · **Step:** 002, 004, 006
- **Plan-local:** 031 U3 (the brief's open question)
- **Date:** 2026-10-03 · **Decided by:** user
- **Question:** Does an import embed the memos and sessions it writes?
- **Decision:** No. No granularity needs an embedding model, and none calls one. Imported memos and sessions have no vector until the administrator's rebuild (`fast/002.vector-index-rebuild`). The full-text half is kept current: the full-text tables are ensured inside the import transaction before the first insert, so the triggers index the inserted rows. A roleplayer import never touches the vector tables. Every successful roleplayer import raises the coverage warning unconditionally.
- **Reason:** An import must not fail on an instance with no designated model, so a memo without a vector becomes a normal post-import state.
- **Lands in:** `backend/app/services/transfer_import.py` (`_write_payload`); `frontend/src/app/importUploads.ts`
- **Cites:** `data-model.md` § Import policy (vectors); `search-and-retrieval.md` (the rebuild)

### DEC-031-4 — Import lives in a sibling service module, and the file travels as a JSON body
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 031.import-and-id-remapping · **Step:** 001, 005, 006
- **Plan-local:** 031 context "Module placement (decided)", "Transport (decided)"; 031 harvest decisions 10, 11, 12
- **Date:** 2026-10-05 · **Decided by:** planner (harvest corrections: orchestrator)
- **Question:** Where does the import code live relative to 030's read-only export module, and how does the browser send the file?
- **Decision:**
  - All import code (validation, deserialization, the remap engine, the three roleplayer imports and the database replace) is in `services/transfer_import.py`. It imports from `services/transfer.py` (the format literal, both version constants, the granularity type, the exclusion sets and the id-column predicate). Nothing in `transfer.py` imports the import module.
  - 030's private id-column predicate is made public as `is_id_column`, with the same two arguments, so serializer and deserializer share one rule. The runtime granularity set is derived from 030's `Literal` type with `get_args`, because no runtime constant existed.
  - The browser reads the chosen file as text, parses it, and posts the parsed object as the JSON body through the existing `apiPost`. The routes take a raw JSON object. There is no multipart and no new Python or npm dependency. A body that is not a JSON object is FastAPI's own 422 before any service runs.
- **Reason:** The export module stays auditable as read-only, and each file keeps to one subject. A JSON body reuses the existing client and needs no form parsing, so the practical bound on an upload is the nginx body limit.
- **Rejected:** Adding import to `transfer.py`, which `backend-structure.md`'s layout pre-named for "export/import" — it would mix writes, id minting and the wipe into the read-only path. A multipart upload — it needs a new dependency for no gain.
- **Lands in:** `backend/app/services/transfer_import.py`; `backend/app/services/transfer.py` (`is_id_column`); `frontend/src/shared/importFile.ts`
- **Cites:** `backend-structure.md` § Layout, § The JSON id boundary (raw-body exception); `deployment.md` (`client_max_body_size`)

### DEC-031-5 — Envelope validation: five reasons in a fixed order, and every bad value refused before any write
- **Status:** accepted; superseded in part by DEC-arch-session-names-7 and DEC-034-7 (`schema_version` is no longer equal-only: version 1 imports through one named upgrade)
- **Stage:** 005.portability · **Feature:** 031.import-and-id-remapping · **Step:** 001, 004
- **Plan-local:** 031 context "The failure contract", "Deserialization"; 031 harvest decisions 13, 15
- **Date:** 2026-10-05 · **Decided by:** planner (decision 15: orchestrator)
- **Question:** In what order are the `export_invalid` reasons checked, and where are malformed cell values caught?
- **Decision:**
  - The first failing check decides the reason: `not_an_export` (the body is not an object, a header key is missing or extra, the format is wrong, or the granularity is unknown), then `unsupported_version`, then `schema_mismatch`, then `wrong_granularity` (the route does not accept the envelope's granularity), then `malformed_payload` (everything about the payload).
  - As planned, `schema_version` had to equal the current version. That half is superseded; see the status line.
  - The deserializer is the inverse of 030's row serialization. It rejects a bad enum string, an id outside the signed 64-bit range and a JSON integer in a Boolean column before any write.
  - Only the database replace relies on the database to refuse a row. It catches `IntegrityError` alone, for the FK, UNIQUE and CHECK cases, and maps it to `malformed_payload` without forwarding the driver's text.
- **Reason:** A bad enum surfaces as `StatementError`, an overflow as `OverflowError` at bind time, and a JSON `1` in a nullable Boolean is accepted by both SQLAlchemy and SQLite. The write phase cannot catch these, so all three must be refused during validation. That keeps "any failure stores nothing" true.
- **Rejected:** Catching every driver error at write time — three of the cases never raise `IntegrityError`, and one is silently accepted.
- **Lands in:** `backend/app/services/transfer_import.py` (`validate_envelope`, `deserialize_row`); `backend/app/errors.py` (`ExportInvalidError`, the five reason constants)
- **Cites:** `backend-structure.md` § The error model (`export_invalid`, `database_not_empty`); `transfer.md` § Accepted schema versions; `domain-rules.md` R5

### DEC-031-6 — The remap engine: ascending minting, one reference policy, a two-pass self-reference
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 031.import-and-id-remapping · **Step:** 002, 003
- **Plan-local:** 031 context "Remap rules"; 031 skeleton ruling 23
- **Date:** 2026-10-05 · **Decided by:** planner (ruling 23: orchestrator)
- **Question:** How does one engine serve the user, character and session granularities without a granularity branch inside it?
- **Decision:**
  - Ids are minted per table in ascending order of the old id, so the stream's `ORDER BY id` survives.
  - Every FK whose target is in the payload, `messages.related_to` and `memos.scope_id` are rewritten. Every `user_id` becomes the caller. A model pair is kept only if it exists in this instance's `models`; otherwise both columns are nulled, which honours the both-or-neither CHECK. The payload `users` row is never written.
  - Whatever differs by granularity is carried by a private three-field policy: the allowed memo scopes, a required old user id (or none), and per-column overrides (present with an id writes that id, present with null writes NULL).
  - The session policy fits those three fields unchanged (ruling 23). Its overrides are `character_id` set to the target and `setup_id` set to null, and it has no required user id. The one `if granularity` sits outside the engine.
  - Self-references are inserted null and then set by one UPDATE per referring row, inside the same transaction. Foreign keys are never deferred and `PRAGMA foreign_keys` is never toggled.
- **Reason:** One engine with a data-only policy keeps the three imports byte-identical in their shared rules. The two-pass write is needed because a buried row's head has a higher id and every FK is immediate.
- **Rejected:** Widening the policy with a fourth field for the session rules — the three fields already express them. Deferring foreign keys — nothing in the schema is deferrable, and the Sync rebuild stays the one path that suspends FKs.
- **Lands in:** `backend/app/services/transfer_import.py` (`_ReferencePolicy`, `_remap_payload`, `_write_payload`, `_owned_policy`, `_session_policy`)
- **Cites:** `data-model.md` § Import policy; `backend-structure.md` § Database access

### DEC-031-7 — Two payload rows sharing a primary key are `malformed_payload`
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 031.import-and-id-remapping · **Step:** 002
- **Plan-local:** 031 coder judgement call 1; 031 verify adjudication 3
- **Date:** 2026-10-05 · **Decided by:** coder (confirmed: orchestrator at verify)
- **Question:** The failure contract does not list a duplicate primary key inside one table of the payload. What does the engine do with one?
- **Decision:** The minting step refuses it as `malformed_payload` before any write.

### DEC-031-8 — The database replace: the writer is called directly, and the vector tables are dropped, not cleared
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 031.import-and-id-remapping · **Step:** 004
- **Plan-local:** 031 skeleton ruling 22; 031 context "Database import" item 3 ("orchestrator decision"); `transfer.md` "orchestrator decision, plan 031"
- **Date:** 2026-10-05 · **Decided by:** orchestrator
- **Question:** How does the replace keep the export's ids through the shared writer, and what happens to the vector tables?
- **Decision:**
  - No identity policy exists. The validated rows go to the shared writer unchanged, and the minting engine is not on this path (ruling 22).
  - One transaction runs, in this order:
    1. the eligibility guard, which reads the stored role and toggles nothing;
    2. envelope validation;
    3. the memo scope-target check, which is pure because `memos.scope_id` has no FK, and where `scope='user'` resolves to a payload `users` row;
    4. the full-text tables ensured, before the wipe, so the delete triggers clear old entries;
    5. one DELETE per table in reverse `sorted_tables` order, with FKs left on;
    6. the drop of `memo_vec` and `session_vec` when they exist, named once from 024's constants so no payload string can reach the DDL;
    7. the insert.
- **Reason:** A vec0 table's declared dimension belongs to the previous designation. Dropping both lets ensure-on-write re-create them at the then-designated model's dimension, so a restore never leaves the instance in `dimension_mismatch`. Nothing is lost, because restored rows have no vectors until the rebuild either way. DDL is transactional, so a failed import keeps both tables and their rows.
- **Rejected:** A "database identity policy" value through the remap engine — the engine mints unconditionally and is the wrong seam. Clearing the vector tables' rows — keeps a dimension that may no longer match.
- **Lands in:** `backend/app/services/transfer_import.py` (`import_database`, `_require_replaceable_database`, `_require_memo_scope_targets`, `_wipe_registry_rows`, `_drop_vector_tables`)
- **Cites:** `data-model.md` § Import policy and § Vector tables (dropping is a state transition, not drift); `transfer.md`; `backend-structure.md` § Database access

### DEC-031-10 — Client import effects: one coverage warning through a new warning id, and a fixed reload scope
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 031.import-and-id-remapping · **Step:** 006
- **Plan-local:** 031 harvest decisions 4, 5, 17, 18; 031 context "Reload scope after a roleplayer import (orchestrator decision)"
- **Date:** 2026-10-05 · **Decided by:** orchestrator
- **Question:** How is the post-import coverage sentence raised when `notifyWarning` takes a closed id union, and what does a successful import reload?
- **Decision:**
  - The sentence is a new `WarningId` member, `"import-search-coverage"`, with its entry in `notifyWarning.ts`. This keeps the `@mantine/notifications` importer set at its two shared modules.
  - `shared/importFile.ts` raises no notification. It throws, and each entry routes the error its own way: `notifyFailure` in `app`, the inline `Alert` in `admin`.
  - A user or character import reloads the characters list and the workspace `SessionsState`. A session import refreshes the Sessions section and reloads `SessionsState`. A failed import reloads nothing.
  - The `app` effects check both halves of the abort contract: the signal, and the constructor-independent name check.
- **Reason:** `SessionsState` drives the tree's session level, so every import changes what it shows. Importing the notification inside the shared helper would make the admin page start notifying, which breaks its inline-only rule.
- **Rejected:** A new `shared/` indirection to route the warning past the `ComposerCore` importer guard — it keeps a guard whose premise 031 legitimately retires, and makes the code worse.
- **Lands in:** `frontend/src/shared/notifyWarning.ts`; `frontend/src/shared/importFile.ts`; `frontend/src/app/importUploads.ts`
- **Cites:** `ui-conventions.md` § Async feedback (a warning attached to a success); `frontend-structure.md` § The API client

### DEC-031-11 — App entry points: reuse the existing sessions prop, a hidden input outside the menu, reset before dispatch
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 031.import-and-id-remapping · **Step:** 007
- **Plan-local:** 031 harvest decisions 6, 9; 031 coder judgement call 3; 031 verify adjudication 4
- **Date:** 2026-10-05 · **Decided by:** orchestrator (reset-first: coder, confirmed at verify)
- **Question:** How do the user menu's "Import…" and the Sessions section's "Import session" get the stores and the file they need?
- **Decision:**
  - `SessionsSection` reuses its existing `sessions` prop, and `CharacterScreen` and `App` are untouched.
  - Only `UserMenu` gains two required props, the characters state and the sessions state. `WorkspaceShell` passes them at both of its `UserMenu` call sites, the compact and the wide.
  - The user menu's file input is hidden and sits outside the `Menu`, because a file input inside a `Menu.Item` loses its change event when the dropdown unmounts. Its accessible label is "Choose a file to import", which avoids the word "export" and the other words the export suites forbid in control names.
  - Both controls clear or reset the input before dispatching, so picking the same file again fires a fresh change event whatever the import's timing.
- **Reason:** A new prop would have broken unlisted delivered tests for nothing. Resetting first is strictly more robust than resetting after the import settles.
- **Lands in:** `frontend/src/app/UserMenu.tsx`; `frontend/src/app/WorkspaceShell.tsx`; `frontend/src/app/SessionsSection.tsx`
- **Cites:** `workspace-shell.md` § User menu; `ui-conventions.md` (the Menu file-input gotcha); US-136.AC-2

### DEC-031-12 — Admin Database page import: three fields, a derived confirm, no state written on success
- **Status:** accepted
- **Stage:** 005.portability · **Feature:** 031.import-and-id-remapping · **Step:** 008
- **Plan-local:** 031 harvest decision 8; 031 coder judgement call 4; 031 verify adjudication 2; "two abort predicates" note
- **Date:** 2026-10-05 · **Decided by:** orchestrator (abort predicate: coder, confirmed at verify)
- **Question:** What state does the page's import hold, and is its abort check sufficient?
- **Decision:**
  - `DatabasePageState` gains `importFile`, `importStatus` and `importErrorMessage`.
  - The replace confirm's openness is derived from a chosen file, so no open or confirm flag is stored.
  - On success `importDatabase` writes no state and navigates to `/login`, so the confirm stays loading while the page leaves. On failure it stores the message, clears the file and returns to idle.
  - Its `importFile === null` early return is unreachable through the UI and exists for free-function hygiene.
  - It reuses 030's narrow `instanceof Error` abort predicate, paired with a `signal.aborted` check.
- **Reason:** The pairing is safe by construction: `shared/api.ts` lets a raw rejection escape only when `signal.aborted` is already true, so the first operand always decides. The narrow form was a real fault in 030's `exportDownloads.ts` only because that module has no signal.
- **Lands in:** `frontend/src/admin/databasePageState.ts`; `frontend/src/admin/DatabasePage.tsx`
- **Cites:** `admin-surfaces.md` § page-level actions (Import); open: the two abort predicates in the tree (`app/importUploads.ts` widened, `admin/databasePageState.ts` narrow) are an acknowledged asymmetry awaiting one unification pass
- **Note:** Outstanding `[manual/live]`, needing a live run: step 005 DoD-12 (a multi-megabyte user export imports through the dev proxy and nginx), step 007 DoD-11 (in a browser, a character and a session export each imported back through the user menu and another character's Sessions section), step 008 DoD-11 (in a browser, a database export imported onto an admin-only instance lands on `/login` and a restored user can sign in).
