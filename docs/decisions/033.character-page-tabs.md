# Decisions — 033.character-page-tabs
**Stage:** — · **Feature:** 033.character-page-tabs

Decisions behind the tabbed character page (`/characters/:id`). The work was frontend only; the create route already accepted `setup_id` together with `opening_message`. The page's contract is in `workspace-shell.md` § "The character page", `forms-and-lists.md` § "The named exceptions", `ui-conventions.md` (`IconButton`, the icon table) and `frontend-structure.md` (routing, the editor wrapper). D1–D10 are the plan's user-confirmed decisions, and their numbering is kept as the `<n>` here. Written at finalization (2026-11-09).

### DEC-033-1 — Five tabs, Sessions first and default; the active tab is component state
- **Status:** accepted
- **Stage:** — · **Feature:** 033.character-page-tabs · **Step:** 001
- **Plan-local:** 033 D1
- **Date:** 2026-10-08 · **Decided by:** user
- **Question:** How is the single-scroll character page split, and where does the active tab live?
- **Decision:** The tabs, in order, are Sessions (selected on open), Main info, Configuration, Notes and Setups. This is the app's first Mantine `Tabs`; it uses Mantine only, with no new CSS. The active tab is local component state, never in the URL and never persisted. `Tabs` is keyed by character id, so moving to another character lands on Sessions. Every link to `/characters/<id>`, including search hits for character and setup memos, lands on Sessions.
- **Reason:** User decision. Sessions is the page's main activity. Keeping the tab out of the URL leaves every existing link and route unchanged.
- **Lands in:** `frontend/src/app/CharacterScreen.tsx`
- **Cites:** `workspace-shell.md` § The character page; `frontend-structure.md` § Routing

### DEC-033-2 — `keepMounted` stays at Mantine's default: every section loads once on open
- **Status:** accepted
- **Stage:** — · **Feature:** 033.character-page-tabs · **Step:** 001
- **Plan-local:** 033 D2
- **Date:** 2026-10-08 · **Decided by:** user
- **Question:** Do inactive tab panels mount, and when do their sections load?
- **Decision:** `keepMounted` stays true. Every section mounts and loads once when the page opens, and switching tabs sends no request. The draft page `/characters/new` renders no tabs and no sections. Sibling sections keep distinct keys, so each region is rendered exactly once.
- **Reason:** It keeps today's load behaviour and the section-owned stores unchanged. Lazy panels would re-request data on every tab switch.
- **Lands in:** `frontend/src/app/CharacterScreen.tsx`
- **Cites:** `frontend-structure.md` (section-owned stores)

### DEC-033-3 — The page header carries icon-only Archive/Restore and Export; busy means disabled
- **Status:** accepted
- **Stage:** — · **Feature:** 033.character-page-tabs · **Step:** 001
- **Plan-local:** 033 D3; 033 context "Cross-cutting constraints" (`IconButton` not widened)
- **Date:** 2026-10-08 · **Decided by:** user (busy-as-disabled: planner)
- **Question:** What sits above the tabs, and how does an icon-only control show it is busy?
- **Decision:** The header holds the saved-name Title, the "Archived" badge, and icon-only `IconButton`s:
  - Archive (`IconArchive`) or Restore (`IconArchiveOff`);
  - Export (`IconDownload`).

  The label is both the tooltip and the accessible name. An in-flight icon action is expressed as `disabled` (Export while exporting). `IconButton`'s props are not widened with `loading`. The draft page shows no header actions.
- **Reason:** User decision. The shared `IconButton` keeps one small prop surface, and `disabled` already blocks a second click.
- **Rejected:** Adding a `loading` prop to `IconButton` — it widens a deliberately narrow shared component for one state that `disabled` already expresses.
- **Lands in:** `frontend/src/app/CharacterScreen.tsx`
- **Cites:** `ui-conventions.md` § `IconButton`, the icon table

### DEC-033-4 — The Main info persona editor is taller, through an optional minimum height on the shared editor
- **Status:** accepted
- **Stage:** — · **Feature:** 033.character-page-tabs · **Step:** 001
- **Plan-local:** 033 D4
- **Date:** 2026-10-08 · **Decided by:** user (mechanism: planner)
- **Question:** How is the persona editor made substantially taller without forking the shared markdown editor?
- **Decision:** `MarkdownEditor` gains an optional `contentMinHeight`, in pixels. ### DEC-033-7 — Setups tab: a header '+' opens an inline create form; edit stays in the modal
- **Status:** accepted
- **Stage:** — · **Feature:** 033.character-page-tabs · **Step:** 003
- **Plan-local:** 033 D7; 033 `003.context` "Why an inline form here"
- **Date:** 2026-10-08 · **Decided by:** user
- **Question:** Setups follow "the same as notes". Does create stay a modal?
- **Decision:**
  - **Header.** An `IconPlus` `IconButton` labelled "New setup" replaces the labelled button; it is disabled while the form is open. The "Show archived setups" switch stays in the header.
  - **Form.** '+' mounts `SetupCreateForm` above the list (and above the loader, failure line and empty line). It is conditionally mounted with a fresh `SetupDraft` per mount and holds Name and Description.
  - **Save and Cancel.** Save is `IconDeviceFloppy`, "Save setup", enabled only when `canSubmit`. Cancel is `IconX`, "Cancel new setup"; it sends no request and is disabled while submitting.
  - **Outcome.** A failure renders inside the form. On success the returned row is applied, and then the form unmounts.
  - **Edit.** `SetupModal` is mounted for edit only.
- **Reason:** User decision. This is a named exception to "create is always a modal". It keeps the draft-lifetime half of the modal convention (fresh draft per open, failure inside, list updated before the form goes) and drops the dialog.
- **Rejected:** Keeping create in `SetupModal` — the user wanted it to match the notes' inline creation.
- **Lands in:** `frontend/src/app/SetupsSection.tsx`; `frontend/src/app/SetupCreateForm.tsx`
- **Cites:** `forms-and-lists.md` § The named exceptions (inline setup create)

### DEC-033-8 — Sessions tab: composer with an optional setup choice, a divider, then the list with an icon Import
- **Status:** accepted
- **Stage:** — · **Feature:** 033.character-page-tabs · **Step:** 004, 005
- **Plan-local:** 033 D8
- **Date:** 2026-10-08 · **Decided by:** user (mechanics: planner)
- **Question:** What does the Sessions tab hold, and how does the composer offer a setup?
- **Decision:**
  - **Order.** The "New session" composer, a `Divider`, then the sessions list.
  - **The setup choice.** The composer carries a size `xs` "Setup" `Select` in `ComposerCore`'s `underArea`. "No setup" is first and is the default, followed by working setups only.
    - Choices load on mount (aborted on unmount) and again whenever the dropdown opens.
    - A selection that is no longer offered resets to "No setup".
    - A load failure shows the non-blocking line "Could not load setups to choose from.", and sending with "No setup" still works.
    - The select is disabled while sending.
  - **The request.** `startSessionWithMessage(characterId, text, setupId = null, signal)` posts `{opening_message, setup_id}` with a setup, and exactly `{opening_message}` without one.
  - **The list header.** "Sessions", the "Show archived sessions" switch, and an icon-only "Import session" (`IconUpload`). The import control is an `IconButton` given the `FileButton` render-prop's `onClick`, and it is disabled while importing. There is no kind switch.
- **Reason:** User decision. The composer and the sessions list are separate section-owned stores, so the composer loads its own setup choices.
- **Lands in:** `frontend/src/app/CharacterComposer.tsx`; `frontend/src/app/characterComposerState.ts`; `frontend/src/app/sessionsApi.ts`; `frontend/src/app/SessionsSection.tsx`
- **Cites:** `workspace-shell.md` § The composer, and starting a session by writing; `session-stream.md` (create-and-seed with `setup_id`); DEC-033-10

### DEC-033-9 — The message-less session start is removed
- **Status:** accepted
- **Stage:** — · **Feature:** 033.character-page-tabs · **Step:** 005
- **Plan-local:** 033 D9
- **Date:** 2026-10-08 · **Decided by:** user
- **Question:** With the composer starting sessions with a setup, does the Sessions section keep its inline Setup select and "Start session" button?
- **Decision:**
  - No. A session starts only by writing a first message.
  - The section loses its Setup select, its "Start session" button, `startSessionFromSection`, and the section's setup-choice and start state.
  - `startSession` stays exported in `sessionsApi.ts` with no caller, because deleting it was out of scope. (Removed 2026-11-10, with its `toSession` helper; the character page starts sessions through `startSessionWithMessage`.)
- **Reason:** Two ways to start a session on one tab is one too many once the composer carries the setup choice.
- **Lands in:** `frontend/src/app/sessionsSectionState.ts`; `frontend/src/app/SessionsSection.tsx`; `frontend/src/app/sessionsApi.ts` (the dead `startSession` and `toSession` deleted 2026-11-10)
- **Cites:** `workspace-shell.md` (the inline start control retired). The dead export confirmed 2026-11-09 is closed: deleted 2026-11-10.
