# Decisions — 024.embedding-lifecycle
**Stage:** 004.retrieval · **Feature:** 024.embedding-lifecycle

Decisions for the feature that keeps vectors and full-text rows in step with every write:
the embedding bridge, the search tables, the session text, strict versus degraded writes,
the persona and setup fan-out, and the client's coverage banner and failure sentences.
Delivered 2026-10-04; landed here at the finalization of 2026-11-09. The `Plan-local:`
line names the feature's own ids (U-ids are the user's answers). The architecture holds
the lifecycle (`search-and-retrieval.md`, `data-model.md`); entries here are the mechanisms
below it.

### DEC-024-1 — A synchronous bridge: one client and one embed call per write
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 024.embedding-lifecycle · **Step:** 002
- **Plan-local:** 024 D1, U1
- **Date:** 2026-10-04 · **Decided by:** user
- **Question:** How do synchronous service writes call the asynchronous embedding client?
- **Decision:** Through `asyncio.run` inside the write. Each write builds one client and makes one embed call; a fan-out sends all its texts in that one call. The write lock is held across the call. The client factory now returns the gateway (DEC-035-1).
- **Reason:** The write and its vector commit together, so the index cannot drift from the text.
- **Rejected:** Embedding after commit (a crash leaves text without its vector).
- **Flip condition:** If the held lock hurts, move to mark-stale plus a background rebuild.
- **Lands in:** `backend/app/services/embedding.py`

### DEC-024-2 — Search tables are ensured on write, outside the schema metadata
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 024.embedding-lifecycle · **Step:** 001
- **Plan-local:** 024 D2, U2
- **Date:** 2026-10-04 · **Decided by:** user
- **Question:** When are the `vec0` and FTS5 tables created?
- **Decision:** By ensure-on-write DDL in `db/search_tables.py`, outside the schema metadata; the FTS ensure also runs at bootstrap. The write's rollback covers the DDL. An instance created before 024 back-fills FTS on the first qualifying write.
- **Reason:** A `vec0` table's dimension is only known once a model is designated; virtual tables do not fit the drift page's metadata comparison.
- **Lands in:** `backend/app/db/search_tables.py`
- **Cites:** `data-model.md` § Search tables

### DEC-024-3 — No KNN `IN` push-down on snowflake keys
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 024.embedding-lifecycle · **Step:** 001
- **Plan-local:** 024 D3, U6
- **Date:** 2026-10-04 · **Decided by:** user
- **Question:** Can a KNN query filter by an `IN` list of ids pushed into `vec0`?
- **Decision:** No. Above roughly 2^50 the push-down gives false negatives (18–36 % of queries in a probe on sqlite-vec 0.1.9 / SQLite 3.47.1, 5000 × 768). Use a scan ordered by `vec_distance_l2`, or over-fetch then join / filter by id.
- **Reason:** Snowflake ids sit far above that bound.
- **Flip condition:** A sqlite-vec release that fixes large-key push-down.
- **Lands in:** `backend/app/db/search_tables.py`, search services
- **Cites:** `search-and-retrieval.md`

### DEC-024-4 — Vector upsert is delete-then-insert; the key column is looked up
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 024.embedding-lifecycle · **Step:** 001
- **Plan-local:** 024 D4; 024 status probe (step 001)
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** How is a vector replaced in `vec0`?
- **Decision:** DELETE then INSERT. In sqlite-vec 0.1.9, `INSERT OR REPLACE` and `INSERT OR IGNORE` on an existing id fail with a UNIQUE error, and UPDATE only works when the row is known to exist. The serialized float32 vector is bound as a plain parameter; snowflake ids round-trip. `rowid` is unusable; the key column is resolved with `SELECT name FROM pragma_table_info(:t) WHERE pk=1`, which also detects an absent table. Deleting an absent id is a no-op, and an absent table is guarded.
- **Reason:** The only form that works on the installed version for both new and existing ids.
- **Lands in:** `backend/app/db/search_tables.py`

### DEC-024-5 — FTS triggers and back-fill
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 024.embedding-lifecycle · **Step:** 001
- **Plan-local:** 024 D5
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** How are the external-content FTS tables kept in step?
- **Decision:** `memo_fts` uses an `UPDATE OF body` trigger; `message_fts` uses one conditional update trigger (an unconditional one corrupts an external-content FTS table). Back-fill is `'rebuild'` for memos and an `INSERT … SELECT` of record rows for messages.
- **Reason:** Only record rows are indexed for messages; the conditional trigger avoids deleting index entries for rows that were never indexed.
- **Lands in:** `backend/app/db/search_tables.py`

### DEC-024-6 — The session text that is embedded
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 024.embedding-lifecycle · **Step:** 003
- **Plan-local:** 024 D6
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** What text represents a session?
- **Decision:** The character sheet, then the setup description (if any), then the settled entries in id order, joined with `"\n\n"`, empty parts dropped. An empty text deletes the session's vector row, resolves no model, and counts as complete.
- **Reason:** Persona first, because models truncate from the end.
- **Lands in:** `backend/app/services/session_index.py`

### DEC-024-8 — Strict authoring writes, degraded record-keeping writes
- **Status:** accepted; the caught set is now DEC-F005-1's
- **Stage:** 004.retrieval · **Feature:** 024.embedding-lifecycle · **Step:** 002, 004, 005, 006
- **Plan-local:** 024 D8, U3
- **Date:** 2026-10-04 · **Decided by:** user
- **Question:** What happens to a write when the embedding cannot be made?
- **Decision:** Authoring writes (memos, persona, setup description) are strict: the error propagates and the whole write rolls back. Record-keeping writes (settle, re-open, settled edits, partner filing) are degraded: they catch the no-model and unreachable errors, still commit, and report incomplete coverage. A dimension mismatch is a no-model error with `detail.reason = "dimension_mismatch"`, raised at two sites. No savepoint is used. `secret_ref_missing` is not caught (defect D-03).
- **Reason:** Authoring text exists to be found, so it must not be saved unfindable; the record must never be blocked by search.
- **Lands in:** `backend/app/services/embedding.py`, `backend/app/services/session_index.py`
- **Cites:** `search-and-retrieval.md`; DEC-F005-1

### DEC-024-10 — The coverage flag on the wire
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 024.embedding-lifecycle · **Step:** 005, 007
- **Plan-local:** 024 D10; 024 status skeleton (step 005)
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** How does the client learn that a write was not indexed?
- **Decision:** `search_coverage_incomplete`, a boolean. On the server it is required with no default on the message, settle and re-open responses, so every service must decide it; the internal stream message defaults it to false (list reads answer false). On the client it is optional and absent means false.
- **Reason:** Required on the server forces each path to decide; optional on the client keeps existing fixtures valid.
- **Lands in:** `backend/app/models/stream.py`, `frontend/src/app/streamApi.ts`

### DEC-024-11 — Which responses set the client flag
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 024.embedding-lifecycle · **Step:** 007
- **Plan-local:** 024 D11
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** Which client effects write the flag?
- **Decision:** Settle and re-open always; an edit or a partner filing only when the returned row is settled. The flag starts false per mount, tracks the latest write (it does not latch), and a failed request leaves it unchanged.
- **Reason:** A zone write does no vector work, so its answer says nothing about coverage.
- **Lands in:** `frontend/src/app/streamState.ts`

### DEC-024-12 — Fan-out includes archived sessions; fail hard only when there is work
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 024.embedding-lifecycle · **Step:** 006
- **Plan-local:** 024 U4
- **Date:** 2026-10-04 · **Decided by:** user
- **Question:** Which sessions does a persona or setup edit re-embed, and when may it fail?
- **Decision:** All sessions of the character (or using the setup), archived included. The strict failure applies only when that set is non-empty. "Changed" means the new value differs from the stored one.
- **Reason:** Archived sessions are still searchable; an edit with nothing to re-embed must not need a model.
- **Lands in:** `backend/app/services/characters.py`, `backend/app/services/setups.py`

### DEC-024-15 — Fan-out diffs against the stored value and runs last
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 024.embedding-lifecycle · **Step:** 006
- **Plan-local:** 024 step 006
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** How do the character and setup services decide and order the fan-out?
- **Decision:** The stored sheet or description is read before the update and compared with the new value; the fan-out is the last statement in the transaction; an empty set resolves no model. Session ids are listed ascending for a deterministic embed order.
- **Reason:** The vector must reflect the committed text; a deterministic order makes the batch reproducible.
- **Lands in:** `backend/app/services/characters.py`, `backend/app/services/setups.py`, `backend/app/services/session_index.py`

### DEC-024-17 — Embedding failure sentences for authoring writes
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 024.embedding-lifecycle · **Step:** 008
- **Plan-local:** 024 step 008
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** What does the roleplayer read when a strict write is refused for embedding reasons?
- **Decision:** One free function maps an error to a sentence, inspecting the code only (never the status): `no_embedding_model` → "Not saved: no embedding model is configured, so this text can't be indexed for search. Ask your administrator to set one."; `llm_unreachable` → "Not saved: the embedding server could not be reached. Try again in a moment."; anything else → nothing, and the caller keeps its generic sentence. Used by the note save and create, the persona commit and the setup submit.
- **Reason:** A generic "could not save" hides that the fix is configuration, not retrying.
- **Lands in:** `frontend/src/shared/embeddingFailure.ts`

### DEC-024-18 — Service-import guards narrowed for the index service
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 024.embedding-lifecycle · **Step:** 004, 005
- **Plan-local:** 024 user call 2026-10-04 (guard narrowing)
- **Date:** 2026-10-04 · **Decided by:** user (principle); orchestrator (fourth guard)
- **Question:** The memos, settle and messages services are guarded against importing other services. How do they reach embedding?
- **Decision:** Each guard permits exactly one named module (exact match, never a prefix): memos may import `app.services.embedding`; settle and messages may import `app.services.session_index`. Modules import through one re-exporting service.
- **Reason:** Keeps every other cross-service import an offender while allowing the one dependency the lifecycle needs.
- **Lands in:** `backend/app/services/memos.py`, `settle.py`, `messages.py`
