# Decisions — 025.hybrid-search-port
**Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port

Decisions for the hybrid search port: the one `search` entry point, its three scope
variants, the two arms, fusion and hit hydration. The feature was delivered on
2026-10-04. The contracts it realizes are in `search-and-retrieval.md` (§ The narrow
port, § Reciprocal-rank fusion, § Query shape, § A memo hit is a snippet plus a level)
and are cited, not restated, here. Since `DEC-035-1` the port's `client_factory`
default is the gateway, not the removed `LlmClient`.

### DEC-025-1 — One port method over three typed scope variants
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port · **Step:** 001, 004
- **Date:** 2026-10-04 · **Decided by:** user
- **Plan-local:** 025 U1; 001.context "Typing notes for the skeleton"; step 001 skeleton (variant names)
- **Question:** How does a caller ask the port for a search, and how does it bring its own filters?
- **Decision:**
  - One `search(connection, scope, query_text, limit, *, client_factory, timeout_seconds)` returning an ordered `list[SearchHit]`.
  - One frozen scope dataclass per indexed corpus: `MemoSearchScope`, `SessionSearchScope`, `EntrySearchScope`. Each has a required, defaultless `user_id` and an optional `extra_predicate`. The variant fixes the arms (memo: vector + lexical; session: vector only; entry: lexical only); no caller chooses arms.
  - The extra predicate is a builder, `Callable[[FromClause], ColumnElement[bool]]`: given the base relation the port uses as its FROM object, it returns a boolean clause the port ANDs with `user_id = :user_id`. `FromClause` is the narrowest type covering both a `Table` and a `Subquery`.
  - Characters and setups are not variants (no index exists for them).
- **Reason:** The owner predicate cannot be forgotten because a scope cannot be built without it, and callers (026, 027) bring their filters without the port knowing them.
- **Rejected:** A bare `Select` as the builder's parameter — `settled_entries` is a `Select`, which is not a `FromClause`, so the entry variant passes `.subquery()`.
- **Lands in:** `backend/app/services/search/ports.py`, `backend/app/services/search/hybrid.py`
- **Cites:** `search-and-retrieval.md` § The narrow port

### DEC-025-2 — No embedding model propagates; absent tables are empty
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port · **Step:** 003, 004
- **Date:** 2026-10-04 · **Decided by:** user
- **Plan-local:** 025 U2
- **Question:** What does the port do when a vector arm runs without a usable model, or a search table does not exist?
- **Decision:** The model is opened only when a vector arm runs; the entry variant never opens it. `NoEmbeddingModelError`, `secret_ref_missing` and `LlmUnreachableError` propagate unchanged — no lexical-only degrade. An absent or empty vec or FTS table yields no hits from that arm and is not an error.
- **Reason:** R4 forbids substitution; a pre-024-bootstrapped instance lacks the tables until a qualifying write or a rebuild.
- **Lands in:** `backend/app/services/search/vector.py`, `backend/app/services/search/lexical.py`, `backend/app/services/search/hybrid.py`
- **Cites:** `search-and-retrieval.md` § The narrow port (failure mode); `domain-rules.md` R4

### DEC-025-3 — A memo hit's level is `memo_scope` + `memo_scope_id`, the stored value passed through
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port · **Step:** 001, 004
- **Date:** 2026-10-04 · **Decided by:** user (level shape); planner (stored-value pass-through, step 004 DoD-4)
- **Plan-local:** 025 U3; step 001 skeleton (field names); step 004 Files Changed / Notes & Issues
- **Question:** What does a memo hit carry to say which level it belongs to?
- **Decision:**
  - The level is the memo's `scope` literal and its `scope_id` only; the port does no name join. A caller that wants a level's name resolves it.
  - The fields are named `memo_scope` / `memo_scope_id`, populated only for `kind == "memo"`.
  - **As built, `memo_scope_id` is the value stored in `memos.scope_id`, unchanged — including for a `"user"`-level memo, where the stored value is the owner's own user id.** This differs from `services/memos.py`'s `Memo.scope_id` convention (`None` for the user level). A caller that needs `None` there does the reduction itself (029 does: `DEC-029-9`).
  - The frozen docstring on `SearchHit.memo_scope_id` in `ports.py` (~L101) still says "`None` for the user level". That sentence is stale; the code is the truth. Open: a one-line docstring correction.
- **Reason:** Step 004's DoD-4 and hydration read named the stored value; the port stays a pass-through of what the row holds.
- **Rejected:** Bare `scope` / `scope_id` field names — on a module that also defines `SearchScope`, `scope` would read as the search scope variant.
- **Lands in:** `backend/app/services/search/ports.py`, `backend/app/services/search/hybrid.py`
- **Cites:** `search-and-retrieval.md` § A memo hit is a snippet plus a level

### DEC-025-4 — Fusion constants: `k = 60`, depth 50, ties by ascending id
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port · **Step:** 001
- **Date:** 2026-10-04 · **Decided by:** planner
- **Plan-local:** 025 D1
- **Question:** The architecture leaves k, per-arm depth and snippet length `_TBD:`. What does the port ship with?
- **Decision:** `RRF_K = 60`, `ARM_DEPTH = 50`, `SNIPPET_CHARS = 160` as `Final[int]` constants in `ports.py`. Score is `Σ 1/(k + rank)`, rank 1-based, rank only (raw distances and BM25 scores never mixed). Fusion is within one corpus. A single-arm scope is fused over its one ranking so the score means the same everywhere. Ties break by ascending id. `rrf_fuse` takes `k` keyword-only. The final count is the caller's `limit`.
- **Reason:** Conventional values; there is no relevance data to tune against. Flip condition: relevance data exists.
- **Lands in:** `backend/app/services/search/ports.py`
- **Cites:** `search-and-retrieval.md` § Reciprocal-rank fusion

### DEC-025-5 — Early exits issue nothing
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port · **Step:** 004
- **Date:** 2026-10-04 · **Decided by:** planner
- **Plan-local:** 025 D2
- **Question:** What does `search` do with a non-positive limit or a blank query?
- **Decision:** `limit <= 0`, or a query that is empty or whitespace-only, returns `[]` as the very first statement: no model opened, no embed call, no SQL, not even the candidate select built.
- **Reason:** One home for the blank-query exit; callers never pre-sanitise.
- **Lands in:** `backend/app/services/search/hybrid.py`

### DEC-025-6 — `SearchHit`'s shape and defaults
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port · **Step:** 001
- **Date:** 2026-10-04 · **Decided by:** planner
- **Plan-local:** 025 D3
- **Question:** What fields does a hit carry, per kind?
- **Decision:** A frozen dataclass with fields in this order: `kind`, `id`, `score` (defaultless), then `snippet`, `memo_scope`, `memo_scope_id`, `session_id`, each defaulting to `None`. A session hit's snippet is `None` (`sessions` has no text column). A memo hit's snippet is never `None`. An entry hit carries its `session_id`. No title field, ever.
- **Reason:** A session hit is then `SearchHit("session", id, score)`; US-119 forbids a memo title.
- **Lands in:** `backend/app/services/search/ports.py`
- **Cites:** `search-and-retrieval.md` § The narrow port (`SearchHit`)

### DEC-025-7 — Memo snippets: FTS `snippet()` or the leading extract, same plain shape
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port · **Step:** 001, 002, 004
- **Date:** 2026-10-04 · **Decided by:** planner
- **Plan-local:** 025 D4; 002.context "Lexical query shape" (snippet parameters)
- **Question:** What text represents a memo hit, whichever arm found it?
- **Decision:**
  - Found by the lexical arm: `snippet(T, 0, '', '', '…', 16)` — column 0, empty markers (no highlight markup), U+2026, `SNIPPET_TOKENS = 16` in `lexical.py`. The token count is distinct from `SNIPPET_CHARS` (characters).
  - Found by the vector arm only: the leading extract of `body` — every whitespace run collapsed to one space, ends stripped, and if longer than `SNIPPET_CHARS` the first 160 characters plus `…` (total 161). "Longer than" is strict.
  - The lexical snippet is kept by id from the arm's result and preferred with an `is None` test, so an empty FTS snippet still beats the body extract.
- **Reason:** Both shapes are plain strings, so callers render one kind of text.
- **Lands in:** `backend/app/services/search/ports.py`, `backend/app/services/search/lexical.py`, `backend/app/services/search/hybrid.py`
- **Cites:** `search-and-retrieval.md` § A memo hit is a snippet plus a level

### DEC-025-8 — Filters first: each arm ranks inside an `IN (candidate subquery)`
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port · **Step:** 002, 003
- **Date:** 2026-10-04 · **Decided by:** planner
- **Plan-local:** 025 D5
- **Question:** How do the relational filters constrain the arms?
- **Decision:** `candidate_ids(scope)` builds (never executes) a select of base-relation ids with the owner and extra predicates. Each arm embeds it as `… IN (<candidate select>)` inside its own statement, so nothing is filtered after ranking. The vector arm uses only the exact-scan form; the vec0 KNN with a pushed-down id constraint never appears.
- **Reason:** Filtering after ranking is forbidden by the architecture; the pushed-down KNN silently drops true candidates at snowflake-sized ids (024).
- **Rejected:** The over-fetching KNN alternative 024 also permits — candidate sets are hundreds of rows, the scan is exact, and it has no recall parameter.
- **Lands in:** `backend/app/services/search/candidates.py`, `backend/app/services/search/lexical.py`, `backend/app/services/search/vector.py`
- **Cites:** `search-and-retrieval.md` § Query shape

### DEC-025-9 — The owner predicate is in every statement; the base relation is built once
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port · **Step:** 002, 004
- **Date:** 2026-10-04 · **Decided by:** planner
- **Plan-local:** 025 D6; step 002 / 004 skeleton ("base_relation must be called once")
- **Question:** Where does `user_id = :user_id` appear, and how is the entry variant's subquery kept consistent?
- **Decision:** Every statement against a base relation — the candidate select and each hit-hydration read — carries the owner predicate itself. `base_relation(scope)` returns the module-level `memos` / `sessions` Table for those variants but a **fresh** `settled_entries.subquery()` for the entry variant on every call. Every statement therefore calls it once and uses that one object for its columns, its owner predicate, the extra-predicate builder and its FROM. The memo hydration read uses `schema.memos` directly (the identical object).
- **Reason:** A clause built against one subquery and spliced into a select over another compiles to an extra FROM — a silent cross join that raises nothing.
- **Rejected:** Caching the subquery per scope — it would outlive the call and buy nothing.
- **Lands in:** `backend/app/services/search/candidates.py`, `backend/app/services/search/hybrid.py`
- **Cites:** `domain-rules.md` R5, R11

### DEC-025-10 — Read posture: a local `_reading`, the embed inside the read window
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port · **Step:** 003, 004
- **Date:** 2026-10-04 · **Decided by:** planner
- **Plan-local:** 025 D7
- **Question:** How does a read-only search end the transaction its reads autobegin?
- **Decision:** `vector.py` and `hybrid.py` each replicate `services/memos.py`'s private `_reading` context manager (copied, never imported): roll back only a transaction it opened itself. The query embed happens inside that window; the port holds no write lock.
- **Reason:** Every read, including `vector_table_dimension`, autobegins; `_reading` is private to each module by house convention.
- **Lands in:** `backend/app/services/search/vector.py`, `backend/app/services/search/hybrid.py`

### DEC-025-11 — FTS query sanitising rules
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port · **Step:** 001
- **Date:** 2026-10-04 · **Decided by:** planner
- **Plan-local:** 001.context "FTS query sanitising — exact rules" (rules 1–6)
- **Question:** How does user text become an FTS5 `MATCH` expression that can never raise a syntax error?
- **Decision:** (1) split on whitespace runs (`str.split()`); (2) remove every `"` in each token; (3) drop emptied tokens; (4) wrap each survivor in double quotes as an FTS5 phrase; (5) join with ` OR `; (6) no tokens left → `None`, and the lexical arm is skipped. A phrase that tokenises to nothing (e.g. `"---"`) is kept; case is preserved.
- **Reason:** Inside a quoted string FTS5 treats every operator as text. `None` is load-bearing: `MATCH ''` raises. OR-join is a deliberate recall choice; BM25 ranks rows matching more tokens higher.
- **Lands in:** `backend/app/services/search/ports.py`
- **Cites:** `search-and-retrieval.md` § Query shape

### DEC-025-12 — The lexical arm's statement
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port · **Step:** 002
- **Date:** 2026-10-04 · **Decided by:** planner
- **Plan-local:** 002.context "Lexical query shape", "Absent-table check"; step 002 skeleton
- **Question:** What exactly does the lexical arm issue?
- **Decision:** `SELECT rowid, snippet(T, …) FROM T WHERE T MATCH :expr AND rowid IN (<candidates>) ORDER BY bm25(T), rowid LIMIT :depth`. `MATCH` takes the table name on the left; the bare name is a `literal_column` over a lightweight `table()` construct. Table existence is the port's own `SELECT 1 FROM sqlite_master WHERE type='table' AND name=:name`. A `None` expression or an absent table short-circuits to `[]` before any statement reaches the FTS table. `table_name` is typed `str`, not a `Literal`, and arrives from 024's constants.
- **Reason:** `bm25()` is lower-is-better; the table-name `MATCH` searches the indexed column; 024 exposes no FTS existence helper; a `Literal` would re-type the virtual-table names inside a 025 module, which the feature forbids.
- **Lands in:** `backend/app/services/search/lexical.py`

### DEC-025-13 — The vector arm: exact L2 scan, check order, key-column map
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port · **Step:** 003
- **Date:** 2026-10-04 · **Decided by:** planner (key-column map and message constant: coder)
- **Plan-local:** 003.context "The one permitted query form", "Dimension handling", "Ordering rationale"; step 003 Files Changed
- **Question:** What does the vector arm issue, and in what order does it check its preconditions?
- **Decision:**
  - The statement is `SELECT C FROM V WHERE C IN (<candidates>) ORDER BY vec_distance_l2(embedding, :blob), C LIMIT :depth`, the query vector bound as `sqlite_vec.serialize_float32` bytes. L2 is used; only rank reaches fusion, so the metric's scale is irrelevant.
  - The key column is named outright (`memo_id`, `session_id`) through a module-level `_KEY_COLUMNS` keyed by 024's `MEMO_VEC_TABLE` / `SESSION_VEC_TABLE` constants. `rowid` is unusable on a vec0 table.
  - Order: open the model first, then read the table's declared dimension (`None` → `[]`, no embed), then the table-versus-designation width guard (`NoEmbeddingModelError`, detail `{"reason": "dimension_mismatch"}`, fixed message), then one embed, then the scan.
  - The message constant is `_DIMENSION_CONFLICT_MESSAGE`, so the module source contains no `MATCH` substring at all.
- **Reason:** Model first means a missing model always raises, even before the tables exist (the degrade U2 rules out). A width mismatch would otherwise reach `vec_distance_l2` as a raw SQLite error.
- **Rejected:** Deriving the key column via `pragma_table_info` — a redundant statement inside the read window, since existence is already answered.
- **Lands in:** `backend/app/services/search/vector.py`
- **Cites:** `search-and-retrieval.md` § Query shape

### DEC-025-14 — `search` lives in `hybrid.py`; memo arms run vector first; `limit` is required
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 025.hybrid-search-port · **Step:** 004
- **Date:** 2026-10-04 · **Decided by:** planner
- **Plan-local:** 004.context "Where `search` lives", "Hydration reads", "Arm order inside a memo search"; step 004 skeleton
- **Question:** Where is the entry point, and how does it assemble hits?
- **Decision:**
  - `search` is in `hybrid.py`; `ports.py` holds the types and pure helpers every arm imports. Callers import types from `ports.py` and `search` from `hybrid.py`.
  - In a memo search the vector arm runs first.
  - Hydration is one owner-scoped read per kind (memo: `id, scope, scope_id, body`; entry: `id, session_id` through `settled_entries`; session: none). A kept id missing from its hydration read is skipped, never raised.
  - `limit` is the fourth positional-or-keyword parameter, required, with no default.
- **Reason:** `search` in `ports.py` would make the contract import its implementation (a cycle). Vector first makes "no model raises even though FTS matches" the cheapest path. A default result count would hide each caller's budget.
- **Lands in:** `backend/app/services/search/hybrid.py`
- **Cites:** `backend-structure.md` § Layout (`services/search/`)
