# Decisions — 026.memo-search-tool
**Stage:** 004.retrieval · **Feature:** 026.memo-search-tool

Decisions for the assistant's `memo_search` tool: its result cap, where the chain
predicate lives, how the sync port runs under the async compose loop, and what the
model receives. The feature was delivered on 2026-10-05. The tool's contract is in
`search-and-retrieval.md` § `memo_search` and `llm-and-streaming.md` § The
tool-calling loop; the port is `DEC-025-1`..`-14`. Since `DEC-035-1` the injected
factory's production default is the gateway.

### DEC-026-1 — At most 8 hits, no paging
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 026.memo-search-tool · **Step:** 001
- **Date:** 2026-10-05 · **Decided by:** user
- **Plan-local:** 026 D1
- **Question:** How many hits does `memo_search` return, and can the assistant page?
- **Decision:** `MEMO_SEARCH_LIMIT = 8` in `services/search/memo_search.py`, passed to the port as `limit`. No paging, no offset, no count argument; the declaration stays `query` only. An assistant that wants more re-queries with different words.
- **Reason:** Closes the brief's open question. Conventional, not measured; the architecture's relevance `_TBD:` stays open.
- **Lands in:** `backend/app/services/search/memo_search.py`
- **Cites:** `search-and-retrieval.md` § `memo_search`

### DEC-026-2 — The chain predicate has one home, `chain_clause`
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 026.memo-search-tool · **Step:** 001
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 026 D2
- **Question:** Where is the session's memo chain (R2) defined, and how is the memo-search filter built from it?
- **Decision:**
  - `chain_clause(relation, user_id, character_id, setup_id | None, session_id)` in `services/memo_chain.py` returns the OR of `(scope = level AND scope_id = level id)` in the order user, character, setup, session, omitting the setup term when `setup_id` is `None`. The user level's id is the user id.
  - `resolve_chain` is re-routed through it, with its emitted select, row order and errors unchanged.
  - `searchable_chain_predicate` in `services/search/memo_search.py` returns a builder answering `and_(is_enabled, not_(is_forced), chain_clause(...))` — `is_enabled` first (R3); SQLite renders `is_enabled = 1 AND is_forced = 0`. Both flags always appear. The port ANDs `user_id`.
- **Reason:** One definition of the chain, shared by the system-prompt path and the tool.
- **Lands in:** `backend/app/services/memo_chain.py`, `backend/app/services/search/memo_search.py`
- **Cites:** `domain-rules.md` R2, R3; `search-and-retrieval.md` § `memo_search`

### DEC-026-3 — Placement, and the sync port under the async loop
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 026.memo-search-tool · **Step:** 001, 002
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 026 D3; step 001 / 002 Files Changed and skeleton
- **Question:** The port is sync and embeds through an `asyncio.run` bridge; the tool runs inside the async compose loop. Where does each part live and how does it run?
- **Decision:**
  - `services/search/memo_search.py` holds the constant, the predicate and a **sync** `search_memos`, which builds `MemoSearchScope`, calls the port, returns the hits unchanged, and in a `finally` rolls back whenever `connection.in_transaction()` — so neither exit leaves a transaction open. It knows nothing of tools.
  - `services/tools/memo_search.py` holds `MemoSearchTool`, a frozen keyword-only dataclass with `name` as a `ClassVar` and optional `client_factory` / `timeout_seconds` fields defaulting to `None`. `run` calls `search_memos` through one `asyncio.to_thread` on the connection the seam handed it, forwarding the two injected values only when not `None`, so the callee's own defaults apply otherwise. The keyword bundle is typed `dict[str, Any]` for mypy.
  - The production registry in `services/tools/seam.py` maps `memo_search` to `MemoSearchTool()` inside a read-only `MappingProxyType`.
- **Reason:** The engine sets `check_same_thread=False` and the awaiting coroutine never touches the connection meanwhile, so one thread at a time uses it. The worker thread has no running loop, so the port's `asyncio.run` works there. `search_memos` rolls back regardless because that is its contract to 021's seam.
- **Rejected:** Duplicating the port's defaults on the adapter — two statements of the same default that can drift.
- **Lands in:** `backend/app/services/search/memo_search.py`, `backend/app/services/tools/memo_search.py`, `backend/app/services/tools/seam.py`
- **Cites:** `search-and-retrieval.md` § `memo_search`; `backend-structure.md` § Routers versus services

### DEC-026-4 — The adapter-to-seam import cycle: `TYPE_CHECKING` plus a function-local import
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 026.memo-search-tool · **Step:** 002
- **Date:** 2026-10-05 · **Decided by:** planner (confirmed lint-clean by orchestrator at 027 harvest)
- **Plan-local:** 026 002.context "The import cycle"; 027 harvest decision 5
- **Question:** `seam.py` imports the adapter to register it, and the adapter needs seam types. How is the cycle broken?
- **Decision:** The adapter imports seam names only under `TYPE_CHECKING` (string annotations) and imports `ToolOutcome` inside the function that constructs it. `seam.py` imports each adapter module at the top. 027 and 028 use the same form.
- **Reason:** Ruff selects `E, F, I, B, UP, W` and no `PL*` rule, so the function-local import is lint-clean without a `noqa`.
- **Rejected:** A module-bottom import — trips `E402`.
- **Lands in:** `backend/app/services/tools/memo_search.py`, `backend/app/services/tools/session_search.py`, `backend/app/services/tools/web_search.py`

### DEC-026-5 — What the model receives
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 026.memo-search-tool · **Step:** 002
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 026 D4
- **Question:** How are hits formatted for the model and the `tool_result` summary?
- **Decision:** `format_hits` returns `(content, summary)`. Content is one line per hit in the port's order, `[<level>] <snippet>`, the level being the scope literal, each snippet's whitespace collapsed to one space and stripped, lines joined by `\n`. Zero hits is a success with content `No matching notes.`. Summary is exactly `<N> memos`, never pluralised by rule (`1 memos`), never carrying content. No titles, names or ids.
- **Reason:** FTS snippets of markdown bodies can contain newlines; one line per hit keeps the list readable.
- **Lands in:** `backend/app/services/tools/memo_search.py`
- **Cites:** `search-and-retrieval.md` § `memo_search`

### DEC-026-6 — The tool raises; the seam reports
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 026.memo-search-tool · **Step:** 002
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 026 D5
- **Question:** How does a failure reach the assistant?
- **Decision:** `run` never builds a failure outcome. Port errors propagate unchanged; arguments without a string `query` raise `ToolFailedError(detail={"tool": "memo_search"})`. The seam turns any `Exception` into the `tool_fail` frame (021 D6). No transaction is left open on either path.
- **Reason:** One failure path for every tool, owned by the seam.
- **Lands in:** `backend/app/services/tools/memo_search.py`
- **Cites:** `search-and-retrieval.md` § `memo_search` — Failure; `domain-rules.md` R9

### DEC-026-7 — Ids come only from `ToolScope`
- **Status:** accepted
- **Stage:** 004.retrieval · **Feature:** 026.memo-search-tool · **Step:** 002
- **Date:** 2026-10-05 · **Decided by:** planner
- **Plan-local:** 026 D6
- **Question:** Which inputs does `run` read?
- **Decision:** Exactly one argument key, `query`. Any other key (`user_id`, `session_id`, `character_id`, `setup_id`, `scope`) is ignored; every level id comes from the seam's `ToolScope`.
- **Reason:** A tool's scope is the seam's, never the model's (R5).
- **Lands in:** `backend/app/services/tools/memo_search.py`
- **Cites:** `domain-rules.md` R5
