### DEC-019-2 — Seven frame value types, one encoder, and the wire JSON form
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 019.streaming-transport-and-stop · **Step:** 001
- **Plan-local:** 019 D2
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** How is a frame represented in Python, and exactly how is it written to the wire?
- **Decision:** One immutable value type per event (`accepted`, `token`, `tool_start`, `tool_result`, `tool_fail`, `error`, `done`), a union of the seven, and one encoder producing `data: <json>\n\n`. A source yields frame values, never strings. Wire JSON: `event` is the first key, then the event's fields in the order of `llm-and-streaming.md`'s example; compact separators (`,` and `:`); `ensure_ascii` off; ids via `str()` in the encoder only; `call_id` verbatim; `tool_result` carries a summary and no raw-content field. The `error` frame is built from a `DomainError`'s inner `code` / `message` / `detail`, not `to_wire()`'s wrapper; a `None` message stays JSON `null`; a missing `detail` becomes `{}`.
- **Reason:** Values let the harness tell a `token` from a terminal frame without re-parsing its own output, and one encoder is the one site of the int → string id conversion.
- **Lands in:** `backend/app/services/llm/frames.py`
- **Cites:** `llm-and-streaming.md` § The SSE event protocol; `backend-structure.md` § The JSON id boundary

### DEC-019-4 — The persist rule and the order of a stream's ending
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 019.streaming-transport-and-stop · **Step:** 002
- **Plan-local:** 019 D4
- **Date:** 2026-10-04 · **Decided by:** planner (accepted at the 2026-10-06 finalization)
- **Question:** When is the partial assistant text written, and in what order relative to the frames?
- **Decision:** The harness accumulates `token` text and, whenever the stream ends without a `done` having passed through, calls `on_partial` with it unless it is empty or whitespace only. Order per ending:
  - client disconnect (poll, cancellation, generator close): persist, close the source, emit nothing;
  - the source raises a `DomainError` or any other exception, or exhausts with no terminal frame: persist, then emit the `error` frame (DEC-019-5 for the non-domain cases);
  - the source yields its own `error`: pass it through, then persist, then end;
  - the source yields `done`: pass it through, persist nothing, close the source.
  Persist happens at most once per stream (a flag), and nothing is pulled from the source after a terminal frame. The success-path row is the source's, written before it yields `done`; the compose source (021) never writes a partial row on any failure path.
- **Reason:** One rule — no `done` means keep what streamed — extends R10 to the assistant's side for a stop and for a failure alike, and the server cannot tell the silent cases apart anyway. Persisting before a raised error's frame means a client that re-reads on `error` sees the row.
- **Lands in:** `backend/app/services/llm/frames.py`
- **Cites:** `llm-and-streaming.md` § Stopping model work in flight — UC-085 (consequence 1); `domain-rules.md` R10

### DEC-019-5 — A non-domain exception and a terminal-less exhaustion end as `llm_unreachable`
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 019.streaming-transport-and-stop · **Step:** 002
- **Plan-local:** 019 D5
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** What does the harness emit when the source fails without a `DomainError` or simply runs out?
- **Decision:** An `error` frame with code `llm_unreachable` and `detail` `{}`. Messages: "The reply could not be completed." for an exception; "The reply ended before it was complete." for exhaustion. A non-domain exception is logged by class name only.
- **Reason:** Every server-ended stream ends in exactly one of `error` or `done`, so silence on the wire always means the connection went away. The message of an arbitrary exception may embed provider text, so it is never logged.
- **Lands in:** `backend/app/services/llm/frames.py`
- **Cites:** `llm-and-streaming.md` § Four ways a stream ends — and no new frame for the fourth; `deployment.md` § The redaction rule

### DEC-019-6 — Disconnect detection: one `finally`, a poll as backstop
- **Status:** accepted; superseded in part by DEC-035-7 (how closing the source cancels the upstream request)
- **Stage:** 003.assistant · **Feature:** 019.streaming-transport-and-stop · **Step:** 002
- **Plan-local:** 019 D6; 019 step 002 context "Cleanup details"
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** How does the harness learn of a client disconnect across Starlette's three delivery paths (task cancellation, generator close, only `is_disconnected()`)?
- **Decision:** It awaits `request.is_disconnected()` before writing each frame and stops when true. A `finally` keyed on "no terminal frame was emitted" runs the persist rule and closes the source. Inside it: the persist is a plain synchronous call with no `await` before it (an await during cancellation can be cancelled again); `aclose()` is called only if the source has one, awaited under `asyncio.shield` with any exception suppressed; a `CancelledError` / `GeneratorExit` is always re-raised. The error paths catch `Exception`, never `BaseException`, so a cancellation reaches the `finally` as a disconnect.
- **Reason:** Treating "no terminal frame when the `finally` runs" as the disconnect condition removes any dependence on which path the installed Starlette takes; a stop, a network drop and a closed tab take one path.
- **Supersedes:** —. **Superseded in part by:** DEC-035-7 — the original half "closing the source unwinds the `httpx.AsyncClient` context of `chat_stream`, which cancels the upstream request" no longer holds; closing the source now closes the gateway stream, which cancels and awaits the library task.
- **Lands in:** `backend/app/services/llm/frames.py`
- **Cites:** `llm-and-streaming.md` § Stopping model work in flight — UC-085 (consequence 3)

### DEC-019-7 — The partial row is written on its own short-lived connection

### DEC-019-9 — The consumer resolves to exactly one of four outcomes and never rejects
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 019.streaming-transport-and-stop · **Step:** 003
- **Plan-local:** 019 D9; 019 step 003 context "Parsing a frame"
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** What exactly does `shared/sse.ts` parse and return?
- **Decision:** One function (path starting `/api/`, JSON body, frame callback, signal) resolving to done (message id string), error (`ApiError`), stopped, or unexpected end. Rules beyond the architecture's outline:
  - `data:` lines are joined with `\n`, one leading space stripped; comment lines and other fields are ignored; a frame with no `data:` line yields nothing; `\r\n` is out of scope (the backend emits `\n` only).
  - Reading uses `TextDecoder` with `{stream: true}` per chunk and a final flush; frames split on `"\n\n"`, the trailing partial kept; a trailing fragment with no blank line at body end is discarded.
  - An `error` frame's non-string `message` becomes `""` and an absent `detail` `{}`; an unparseable frame or one with no `event` string is `client_malformed_error`; an unknown event name is skipped.
  - "Stopped" is decided on `signal.aborted` at the moment the stream ends or rejects, never on the bytes; after a terminal frame the reader is cancelled and a later abort cannot change the outcome.
  - No id is ever converted with `Number()` or `parseInt`.
  The consumer itself never constructs `llm_unreachable` for an unexpected end; the caller does (DEC-019-14).
- **Reason:** A never-rejecting single outcome keeps every caller's handling a table rather than a try/catch, and deciding "stopped" on the client's own abort state is the only reliable signal (there is nothing in the bytes).
- **Lands in:** `frontend/src/shared/sse.ts`
- **Cites:** `frontend-structure.md` § The SSE consumer; `llm-and-streaming.md` § Four ways a stream ends — and no new frame for the fourth

### DEC-019-10 — `api.ts` exports its failure decoding; `sse.ts` does not duplicate it
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 019.streaming-transport-and-stop · **Step:** 003
- **Plan-local:** 019 D10
- **Date:** 2026-10-04 · **Decided by:** briefing (confirmed: planner)
- **Question:** How does the SSE consumer decode a non-2xx response and a fetch rejection the same way `apiRequest` does?
- **Decision:** `api.ts` exports `decodeErrorResponse` (the non-2xx decode: 401 navigation first, then the envelope or the `client_malformed_error` fallback) and `mapFetchRejection` (an abort returned unchanged, anything else `ApiError(client_transport_failed, "The server could not be reached.", 0)`); `apiRequest` uses both. `apiRequest` keeps its own body read, and an aborted read is rethrown raw before any navigation. `apiRequest`'s observable behaviour is unchanged.
- **Reason:** One decode site with two callers, so a stream's failure and a JSON call's failure can never be decoded differently.
- **Lands in:** `frontend/src/shared/api.ts`, `frontend/src/shared/sse.ts`
- **Cites:** `frontend-structure.md` § The API client

### DEC-019-12 — The compose handle: one non-observable field, linked to the mount signal
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 019.streaming-transport-and-stop · **Step:** 004, 005
- **Plan-local:** 019 D12; 019 step 005 context "The linking, precisely"
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** Where do the compose's `AbortController` and its wind-down promise live, and how does unmount reach them?
- **Decision:** One `StreamState` field excluded from `makeAutoObservable` (annotation `false`) holds the compose's own controller and a promise that settles when the compose has fully wound down, re-read included; `null` when idle. `isStreaming` derives from the streaming-text field. The compose effect registers an `abort` listener on the mount signal once, which aborts the compose controller, and removes it when the compose ends. "Mount aborted" is always read from the mount signal, which is how a user stop is told apart from an unmount. Every compose re-read passes the mount signal, never the compose signal (which is already aborted after a stop).
- **Reason:** A controller and a promise are not data any view renders. Removing the listener keeps a long-lived mount signal from accumulating one per compose.
- **Lands in:** `frontend/src/app/streamState.ts`
- **Cites:** `frontend-structure.md` § State — MobX 6, § The SSE consumer

### DEC-019-13 — `busy` and streaming are separate; the derivations that read streaming
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 019.streaming-transport-and-stop · **Step:** 004, 005
- **Plan-local:** 019 D13
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** Does a compose set `busy`, and which derivations change while streaming?
- **Decision:** Compose never sets or clears `busy`; a stop leaves it as it was. `canSend` and `showsDiscard` additionally require not streaming. `canSettle` is unchanged (Settle stays enabled during a stream). The compose effect is a no-op while a compose is in flight or the draft is blank.

### DEC-019-14 — What each consumer outcome does on the client
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 019.streaming-transport-and-stop · **Step:** 005
- **Plan-local:** 019 D14
- **Date:** 2026-10-04 · **Decided by:** briefing (confirmed: planner)
- **Question:** For each outcome, what is notified, re-read and cleared?
- **Decision:**
  - done: no notice; zone re-read; streaming cleared.
  - error: `notifyFailure(apiError)`; zone re-read; nothing else cleared (R10); streaming cleared.
  - stopped by the user: no notice; zone re-read; streaming cleared.
  - stopped by unmount: no notice; no re-read; nothing written.
  - unexpected end: `notifyFailure(ApiError("llm_unreachable", "The reply ended unexpectedly.", 0, {}))`; zone re-read; streaming cleared.
  "Cleared" sets the streaming text and the handle to `null` in the same action as the re-read result, so the in-flight text is replaced, not blanked first. A failed re-read notifies its own error and clears the streaming state regardless.
- **Reason:** The server's rows are the only truth after any outcome, and a stop is not a failure.
- **Lands in:** `frontend/src/app/streamState.ts`
- **Cites:** `frontend-structure.md` § The SSE consumer; `domain-rules.md` R10

### DEC-019-15 — `accepted`: clear the sent draft, re-read, keep re-reads ordered
- **Status:** accepted; narrowed by DEC-019-19 (the no-`accepted` failure case)
- **Stage:** 003.assistant · **Feature:** 019.streaming-transport-and-stop · **Step:** 005
- **Plan-local:** 019 D15
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** What does the effect do on `accepted`, and how are its re-reads ordered?
- **Decision:** On `accepted` the draft is cleared only if it still equals the sent text, and a zone re-read starts so the committed message arrives with its real id. The terminal re-read is issued only after that accepted-triggered re-read has settled. If no `accepted` arrives, the draft is untouched (R10) — except in the case DEC-019-19 covers.
- **Reason:** Text typed meanwhile is kept, and a slow early `GET` can never land after and overwrite the final one.
- **Lands in:** `frontend/src/app/streamState.ts`
- **Cites:** `domain-rules.md` R10

### DEC-019-16 — Pressing Settle mid-stream stops the compose first, then settles
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 019.streaming-transport-and-stop · **Step:** 005
- **Plan-local:** 019 D16
- **Date:** 2026-10-04 · **Decided by:** user
- **Question:** What does Settle do while a compose is streaming?
- **Decision:** `settleComposer` gains a prefix when a compose is in flight: set `busy`; abort the compose controller as Stop does (no notice); await the handle's wind-down promise, which includes the compose's post-stop zone re-read and the clearing of streaming state; return if the mount signal is aborted; then run the existing settle flow unchanged, reading the draft only after the wait. The wind-down promise never rejects, including when its re-read fails.
- **Reason:** Sequencing the stop's re-read before the settle request means a stale zone list can never land after the settle's fresh one; a never-rejecting promise means the settle cannot hang or throw.
- **Lands in:** `frontend/src/app/streamState.ts`
- **Cites:** `workspace-shell.md` § The stop control

### DEC-019-17 — Accepted residual races after a stop
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 019.streaming-transport-and-stop · **Step:** 005
- **Plan-local:** 019 D17
- **Date:** 2026-10-04 · **Decided by:** user
- **Question:** The server persists the partial row when it detects the disconnect, which the client cannot wait for. Is anything engineered around the resulting orderings?
- **Decision:** No. Both orderings are accepted: a mid-stream settle may settle the partial row or leave it as a candidate in the fresh zone below the new entry; a plain stop's re-read may run before the persist commits, so the partial appears on the next re-read. No retry or delay is added.
- **Reason:** The row is never lost, only late or one zone later; any wait would need a server-side signal the stop design deliberately does not have.
- **Lands in:** `frontend/src/app/streamState.ts` (no code; the absence of a retry is the decision)
- **Cites:** `workspace-shell.md` § The stop control

### DEC-019-19 — A failed send whose text was already stored clears the draft; the retry is textless
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 019.streaming-transport-and-stop · **Step:** 005
- **Plan-local:** DEC-019-BF1 (019 `outcome.md` `## Decisions`, bug fix of 2026-11-05)
- **Date:** 2026-11-05 · **Decided by:** user
- **Question:** A text-bearing compose can commit the roleplayer's row and then fail without the client ever handling `accepted` (lost frame, transport or proxy drop, an unreadable response). DEC-019-15 then leaves the draft untouched, so the next Send re-posts the same text and the zone holds two identical user rows (observed 2026-11-05: two identical 322-character rows 8.7 s apart, the first with no reply).
- **Decision:** After a failed text-bearing compose with no handled `accepted`, the effect's terminal zone re-read decides: if the served zone's last non-tool row is a `user` row whose text equals the sent text, the text is stored, and the draft is cleared under DEC-019-15's own rule (only while it still equals the sent text). The retry is then the existing textless compose (Regenerate, body `{}`), which uses the stored row; no text is re-sent. When the re-read does not show the sent text stored, DEC-019-15 holds unchanged and the draft is kept (R10).
- **Reason:** The user: "for the retry — do it flag or new call, server has the full conversation, so no new text is needed, the stored one can be used." The served zone is the source of truth for whether the text is stored, so the draft is cleared only when nothing can be lost.
- **Rejected:** Server-side dedupe of an identical unanswered user text in `begin_compose` — it changes the "a text compose always appends" route contract and could swallow a deliberate repeat. Keeping DEC-019-15 as is and only adding logging — it leaves the duplicate.
- **Supersedes:** narrows DEC-019-15's "if no `accepted` arrives … the draft is untouched" for the case the re-read proves the text stored.
- **Lands in:** `frontend/src/app/streamState.ts` (the compose effect's failure path)
- **Cites:** `domain-rules.md` R10; US-044.AC-1, US-044.AC-3
