# Decisions — 011.rp-sessions
**Stage:** 002.record · **Feature:** 011.rp-sessions

Decisions behind roleplay sessions: the `sessions` table, the session routes, the tree's session level, the character page's Sessions section and the session screen. The contracts are in `data-model.md` § `sessions`, `backend-structure.md` § `/api/sessions`, `domain-rules.md` R2 / R6, `frontend-structure.md` and `workspace-shell.md`. Recorded at finalization (2026-11-09). Two of 011's decisions were later revised by the session-names work: D4, and half of D9. They are kept here as superseded entries so their plan-local ids still resolve.

### DEC-011-1 — Starting a session is inline in the Sessions section
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 011.rp-sessions · **Step:** 007, 008
- **Date:** 2026-10-02 · **Decided by:** user
- **Plan-local:** 011 D1
- **Question:** Where and how does the roleplayer start a session?
- **Decision:**
  - The Sessions section holds an inline `Select` labelled "Setup", whose first and default option is "No setup", followed by the working setups. A labelled "Start session" button (`IconPlus`) sits beside it.
  - There is no modal.
  - On success the returned row is applied, then the client pushes `/sessions/<id>`.
  - "No setup" still starts a session when the setup list is empty or failed to load.
- **Reason:** A one-choice control is not a form. A push keeps the character page as a valid Back target.
- **Rejected:** A modal. A `replace` navigation.
- **Lands in:** `frontend/src/app/SessionsSection.tsx`; `frontend/src/app/sessionsSectionState.ts`
- **Cites:** `forms-and-lists.md` (named exception to the modal rule); `domain-rules.md` R2

### DEC-011-2 — The create route: no opening message; setup checks
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 011.rp-sessions · **Step:** 002, 003
- **Date:** 2026-10-02 · **Decided by:** user
- **Plan-local:** 011 D2
- **Question:** What does `POST /api/characters/{character_id}/sessions` accept in 011?
- **Decision:**
  - Accepted bodies: omitted, `{}`, or `{ setup_id: string | null }`. The answer is 201 with the session.
  - An archived character is allowed.
  - `setup_id`, when supplied, must be the caller's setup under that same character, or the answer is 404 `setup_not_found`. An archived setup is 409 `setup_archived`.
  - Unknown keys are ignored.
  - Feature 018 later extended the same route with an optional opening message.
- **Reason:** Archive does not cascade. A request naming an archived setup is stale or hand-made, because one is never offered.
- **Lands in:** `backend/app/routers/sessions.py`; `backend/app/services/sessions.py`; `backend/app/models/sessions.py`
- **Cites:** `backend-structure.md` § `/api/sessions`

### DEC-011-3 — `last_used_at`: set at creation, bumped only by content writes
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 011.rp-sessions · **Step:** 002
- **Date:** 2026-10-02 · **Decided by:** user
- **Plan-local:** 011 D3
- **Question:** What moves `last_used_at`?
- **Decision:**
  - At creation, `last_used_at`, `created_at` and `updated_at` are the same instant.
  - Only content writes bump it.
  - Opening, reading, archive and restore never bump it.
  - There is no resume or touch route. Resuming is the by-id GET.
- **Reason:** A read that writes would turn every navigation into a write on SQLite's single writer. "Last use" means working, not glancing.
- **Rejected:** A resume or touch route.
- **Lands in:** `backend/app/services/sessions.py`
- **Cites:** `data-model.md` § `sessions` (`last_used_at`)

### DEC-011-6 — Tree characters are ordered by newest session use, client-side
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 011.rp-sessions · **Step:** 004, 006
- **Date:** 2026-10-02 · **Decided by:** user
- **Plan-local:** 011 D6
- **Question:** In what order does the tree list characters?
- **Decision:**
  - Characters sort by the maximum `last_used_at` of their working sessions, newest first.
  - Characters without sessions follow, in the characters state's own order.
  - Ties keep that order.
  - One pure function computes it, comparing the fixed-width text.
- **Reason:** US-089 orders by use. The server's character order (DEC-009-9) is left alone.
- **Lands in:** `frontend/src/app/sessionsState.ts` (ordering helper); `frontend/src/app/CharacterTree.tsx`
- **Cites:** `workspace-shell.md` § The three columns (the tree)

### DEC-011-7 — The per-character chevron and its persisted collapse set
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 011.rp-sessions · **Step:** 005, 006
- **Date:** 2026-10-02 · **Decided by:** user (chevron, default); orchestrator (storage key); planner (glyph, absence)
- **Plan-local:** 011 D7
- **Question:** How are a character's sessions collapsed, and where is the state kept?
- **Decision:**
  - Chevron: shown only when the character has sessions. Labelled "Collapse <name>" or "Expand <name>", `sizeVariant` "chevron".
  - Glyph: `IconChevronDown`, rotated -90° when collapsed. The rotation comes from two module-level icon components handed to `IconButton`; `IconButton`'s props are not widened.
  - Persistence: the collapsed set is persisted under its own key, `rphelper.tree-collapsed`, as a JSON array of id strings. It is written in the same posture as DEC-008-9.
  - Live state: the collapsed set is held as component-local state in the tree.
- **Reason:** A control for an action that cannot happen is absent, not inert. The layout record's reader drops unknown keys by design, so the collapse set needs its own key.
- **Rejected:** A field in `rphelper.workspace-layout`. A Down/Right icon pair.
- **Lands in:** `frontend/src/app/treeCollapse.ts`; `frontend/src/app/CharacterTree.tsx`
- **Cites:** `workspace-shell.md` § Layout persistence; `ui-conventions.md` § icon table

### DEC-011-8 — The `sessions` table as first declared
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 011.rp-sessions · **Step:** 001
- **Date:** 2026-10-02 · **Decided by:** orchestrator
- **Plan-local:** 011 D8
- **Question:** Which columns and indexes does 011 declare?
- **Decision:**
  - Eight columns: `id`, `user_id`, `character_id`, `setup_id` (nullable, no default, no sentinel), `last_used_at`, `archived_at`, `created_at` and `updated_at`. No FK has `ON DELETE`.

### DEC-011-10 — `setup_name` by an owner-scoped LEFT JOIN, archived or not
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 011.rp-sessions · **Step:** 002
- **Date:** 2026-10-02 · **Decided by:** orchestrator
- **Plan-local:** 011 D10
- **Question:** How does a session carry its setup's label?
- **Decision:** Every read, and every create, archive and restore response, carries the referenced setup's current `name`, by an owner-scoped LEFT JOIN. The name is shown even when the setup is archived.
- **Reason:** With a join, a renamed setup relabels its sessions without a fan-out write, and the tree needs no second request.
- **Rejected:** Copying the name into a column.
- **Lands in:** `backend/app/services/sessions.py`
- **Cites:** `data-model.md` § `sessions` (the read shape)

### DEC-011-12 — `session_not_found` 404, `setup_archived` 409, and the check order
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 011.rp-sessions · **Step:** 001, 002
- **Date:** 2026-10-02 · **Decided by:** orchestrator
- **Plan-local:** 011 D12
- **Question:** Which codes and statuses do session failures use, and in what order are they checked?
- **Decision:**
  - `session_not_found` is 404, the same for a missing session and another user's.
  - `setup_archived` is 409 with an empty `detail`.
  - Inside the create transaction, the checks run in this order: character, then setup existence, then setup archive state.
- **Reason:** The request is well formed and the setup is owned, but its state conflicts. A 404 would be false because the setup exists. A 422 would be wrong because no field is malformed.
- **Lands in:** `backend/app/errors.py`; `backend/app/services/sessions.py`
- **Cites:** `backend-structure.md` § The per-code status record

### DEC-011-13 — Archive semantics; archive never moves `last_used_at`
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 011.rp-sessions · **Step:** 002
- **Date:** 2026-10-02 · **Decided by:** orchestrator
- **Plan-local:** 011 D13
- **Question:** What do archive and restore write?
- **Decision:**
  - Archive and restore are idempotent, as DEC-009-8.
  - A state change bumps `updated_at` and never `last_used_at`.
  - Archiving a session's character or setup leaves the session untouched.
- **Reason:** This holds the rule in DEC-011-3.
- **Lands in:** `backend/app/services/sessions.py`
- **Cites:** `domain-rules.md` R6; `data-model.md` § … and the archive rule

### DEC-011-15 — Workspace `SessionsState` plus a section state; apply the row to both
- **Status:** accepted; superseded in part by DEC-034-12 (the client now orders `last_used_at` ties by id descending, reversing "never tie-break on id")
- **Stage:** 002.record · **Feature:** 011.rp-sessions · **Step:** 004, 007
- **Date:** 2026-10-02 · **Decided by:** orchestrator
- **Plan-local:** 011 D15; 011 004.context ("never tie-break on id"); 011 007.context, 009.context (effects and selection)
- **Question:** Where does session state live, and how does a mutation reach the tree and the section?
- **Decision:**
  - `App` creates one `SessionsState`, holding working sessions for the tree.
  - The section owns one `SessionsSectionState`, rendered keyed by character id.
  - `applySession`:
    - an archived row is removed
    - a working row is removed, then re-inserted at its `last_used_at`-descending position
    - (as built) ties went after equals and never compared ids — reversed by DEC-034-12
  - Applying a row:
    - the section's start, archive and restore apply the returned row to both states
    - effects take the workspace state as a parameter, never as a field
  - Navigation and screen loading:
    - navigation after a start goes through an `onStarted` callback
    - the setup selection resets on a successful choices reload and is kept on failure
    - the session screen has its own GET module
- **Reason:** The tree updates without a refetch racing the mutation.
- **Lands in:** `frontend/src/app/sessionsState.ts`; `frontend/src/app/sessionsSectionState.ts`; `frontend/src/app/sessionScreenState.ts`
- **Cites:** `frontend-structure.md` § State; `forms-and-lists.md` § narrowed re-load; DEC-034-12

### DEC-011-18 — Fixed failure sentences, including a non-blocking choices failure
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 011.rp-sessions · **Step:** 007, 008, 009
- **Date:** 2026-10-02 · **Decided by:** planner
- **Plan-local:** 011 D18
- **Question:** How do session failures render?
- **Decision:**
  - Start, archive and restore failures render "Could not start the session.", "Could not archive the session." or "Could not restore the session." in an inline `Alert`.
  - List failures render "Could not load sessions" with Retry, in the section and in the tree.
  - A failed choices load renders the dimmed line "Could not load setups to choose from.", with no retry and no effect on starting.
  - There is no `notifyFailure` call site.
- **Reason:** A silent failure would hide why the list holds only "No setup".
- **Lands in:** `frontend/src/app/sessionsSectionState.ts`; `frontend/src/app/SessionsSection.tsx`; `frontend/src/app/CharacterTree.tsx`; `frontend/src/app/SessionScreen.tsx`

### DEC-011-20 — Build-time mechanisms: optional snowflake body, join operator, 24-hour format
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 011.rp-sessions · **Step:** 001, 002, 003, 005
- **Date:** 2026-10-02 · **Decided by:** coder (confirmed: verifier PASS)
- **Plan-local:** 011 001/003/005 mid-flight notes
- **Question:** Which library mechanisms realize the optional `setup_id`, the optional body, the owner-scoped join and the label format?
- **Decision:**
  - `setup_id`: typed `OptionalSnowflakeIn = Annotated[int | None, BeforeValidator(...)]`.
  - Body: the route takes `body: StartSessionRequest | None = None`.
  - Join: the join condition is combined with `&`.
  - Time label: the formatter uses `Intl.DateTimeFormat(...).formatToParts` with `hourCycle: "h23"`.
- **Reason:** `SnowflakeIn | None` produced 500s for `{}` / `[]` inputs. `hour12: false` can render midnight as `24`.
- **Rejected:**
  - `SnowflakeIn | None`.
  - `Body(default=None)`.
  - `and_()` for the join.
  - `hour12: false`.
- **Lands in:** `backend/app/models/sessions.py`; `backend/app/routers/sessions.py`; `backend/app/services/sessions.py`; `frontend/src/app/sessionLabel.ts`
