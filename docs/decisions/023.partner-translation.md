# Decisions — 023.partner-translation
**Stage:** 003.assistant · **Feature:** 023.partner-translation

Decisions for the feature that translates a settled partner entry into the roleplayer's
preferred language on demand, with a stored cache. Delivered 2026-10-04; landed here at
the finalization of 2026-11-09. The `Plan-local:` line names the feature's own id (U-ids
are the user's answers, the rest the orchestrator's). D2 (joining `chat_stream`) is
superseded by the gateway's whole-reply call; it keeps a short entry, DEC-023-2, because
`llm-and-streaming.md` and DEC-arch-llm-client-library-1 cite it by its plan-local id.
D16 was the step map.

### DEC-023-1 — A translation is awaited whole, not streamed
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 023.partner-translation · **Step:** 002
- **Plan-local:** 023 D1, U1
- **Date:** 2026-10-04 · **Decided by:** user
- **Question:** Does the translation stream into the entry?
- **Decision:** No. One JSON request returns the whole translation.
- **Reason:** A half-translated entry is not useful to read, and a cache write needs the whole text anyway.
- **Lands in:** `backend/app/routers/translation.py`, `backend/app/services/translation.py`

### DEC-023-2 — The model call reuses the streaming chat call and joins its content
- **Status:** superseded by DEC-arch-llm-client-library-1
- **Stage:** 003.assistant · **Feature:** 023.partner-translation · **Step:** 002
- **Plan-local:** 023 D2, U2
- **Date:** 2026-10-04 · **Decided by:** user
- **Question:** How does the translation service call the model?
- **Decision:** As built in 023, through 021's `chat_stream` with no tools, concatenating each delta's content in arrival order and ignoring reasoning and tool calls. This is replaced: translation now calls the gateway's non-streamed whole-reply completion and takes the text it returns (`llm-and-streaming.md` § Translation).
- **Reason:** Reuse kept the provider surface at one streaming function. With the library the non-streamed call already exists, so there was nothing left to keep small.
- **Lands in:** `backend/app/services/translation.py`
- **Cites:** `llm-and-streaming.md` § Translation, § Decision history (2026-11-08, translation calls a non-streamed `complete()`); DEC-arch-llm-client-library-1

### DEC-023-3 — The fallback target language, and the cache key
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 023.partner-translation · **Step:** 001
- **Plan-local:** 023 D3, U3
- **Date:** 2026-10-04 · **Decided by:** user
- **Question:** What is the target when the user has no preferred language, and what is cached under?
- **Decision:** The fallback target is `"English"`, a constant. The cache is keyed by message and the effective target language (after fallback).
- **Reason:** Matches DEC-020-4's English default; keying by the effective target keeps a later preference change from serving a wrong-language hit.
- **Lands in:** `backend/app/services/translation.py`
- **Cites:** US-142

### DEC-023-4 — Cancelling a translation; the probe before the cache write
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 023.partner-translation · **Step:** 002, 004
- **Plan-local:** 023 D4, U4
- **Date:** 2026-10-04 · **Decided by:** user
- **Question:** What happens when the roleplayer toggles off a pending translation, or leaves?
- **Decision:** Toggling off aborts that entry's own request, with no notification; the composer's Stop does not reach translations. On the server a disconnect probe is injected and awaited once before the cache write; if the client is gone the write is skipped. This is best-effort.
- **Reason:** A cancelled request should not cost a stored row the user never saw, but guaranteeing it is not worth the cost.
- **Rejected:** A transaction spanning the model call (holds the write lock for the whole call). A compensating delete after a late disconnect (a second write for a cosmetic gain).
- **Lands in:** `backend/app/services/translation.py`, `frontend/src/app/` (translation state)
- **Cites:** `deployment.md` (request lifetime)

### DEC-023-5 — Failure mapping and messages
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 023.partner-translation · **Step:** 002, 004
- **Plan-local:** 023 D5
- **Date:** 2026-10-04 · **Decided by:** orchestrator
- **Question:** What error does a failed translation produce, and what does the roleplayer see?
- **Decision:** 502 `translation_failed` with detail `{"message_id": "<id>"}`. Messages: "Translation failed: the model server could not be reached." and "Translation failed: the model returned no text." The client's default sentence is "The translation failed. Showing the original." Model-designation errors and `secret_ref_missing` propagate unchanged.
- **Reason:** The entry stays readable in the original; configuration errors must still read as configuration errors.
- **Lands in:** `backend/app/errors.py`, `backend/app/services/translation.py`, `frontend/src/app/` (translation state)

### DEC-023-6 — Which entries can be translated
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 023.partner-translation · **Step:** 002
- **Plan-local:** 023 D6
- **Date:** 2026-10-04 · **Decided by:** orchestrator
- **Question:** Which messages may be translated?
- **Decision:** Settled partner entries the user owns; anything else answers 404. Whether the source and target languages are equal is not checked.
- **Reason:** Only the partner's words are in a language the roleplayer may not read; a language check would need language detection.

### DEC-023-7 — The translations table
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 023.partner-translation · **Step:** 001
- **Plan-local:** 023 D7
- **Date:** 2026-10-04 · **Decided by:** orchestrator
- **Question:** How is the cache stored?
- **Decision:** One `translations` table with `user_id`, a `message_id` foreign key without cascade, the target language, the text and `created_at`; unique `uq_translations_message_id_target_language`. No `updated_at`, no state column.
- **Reason:** A row is written once and deleted on invalidation (DEC-023-11), never updated; deletion is explicit, so no cascade.
- **Lands in:** `backend/app/db/schema.py`
- **Cites:** `data-model.md` § translations

### DEC-023-8 — Three phases; a hit needs no model
- **Status:** accepted; superseded in part by DEC-arch-llm-client-library-1 (the model call)
- **Stage:** 003.assistant · **Feature:** 023.partner-translation · **Step:** 002
- **Plan-local:** 023 D8
- **Date:** 2026-10-04 · **Decided by:** orchestrator
- **Question:** How is a translation request structured?
- **Decision:** Read (eligibility and cache lookup), then the model call outside any transaction, then a write transaction. A cache hit returns without resolving a model. The insert ignores a conflicting row, so concurrent requests settle on one. The system prompt is a fixed constant.
- **Superseded in part by:** DEC-arch-llm-client-library-1 — the model call is the gateway's whole-reply call, not a joined `chat_stream`.
- **Reason:** No transaction spans the network call.
- **Lands in:** `backend/app/services/translation.py`

### DEC-023-9 — The stale-text guard
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 023.partner-translation · **Step:** 002
- **Plan-local:** 023 D9
- **Date:** 2026-10-04 · **Decided by:** planner
- **Question:** What if the entry is edited while its translation is in flight?
- **Decision:** Inside the write transaction the entry's current text is compared with the text that was translated; if it changed, nothing is written and the translation is still returned.
- **Reason:** A cache row must never describe text the entry no longer holds.
- **Lands in:** `backend/app/services/translation.py`

### DEC-023-11 — Editing an entry deletes its translations
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 023.partner-translation · **Step:** 003
- **Plan-local:** 023 D11; user call 2026-10-04 (012 no-delete guard narrowed)
- **Date:** 2026-10-04 · **Decided by:** orchestrator; user (guard narrowing)
- **Question:** How is the cache invalidated?
- **Decision:** Inside the edit transaction, after the update, every translation of the message is deleted on any text change. The messages service's no-delete guard (from 012) is narrowed to permit deletes on `translations` only.
- **Reason:** Invalidation in the same transaction cannot be missed; narrowing by table keeps every other delete an offender.
- **Lands in:** `backend/app/services/messages.py`

### DEC-023-13 — One translation state per mount
- **Status:** accepted
- **Stage:** 003.assistant · **Feature:** 023.partner-translation · **Step:** 004
- **Plan-local:** 023 D13
- **Date:** 2026-10-04 · **Decided by:** orchestrator
- **Question:** How is per-entry translation state held on the client?
- **Decision:** One translation state per session-stream mount. The per-entry abort controllers live in a non-observable map; a result is applied only if its controller is still the current one for that entry. A shown translation going stale after a language change is accepted.
- **Reason:** The identity guard stops a cancelled request's late answer overwriting a newer one.
- **Lands in:** `frontend/src/app/` (translation state)
