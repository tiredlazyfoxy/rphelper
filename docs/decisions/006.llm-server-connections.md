### DEC-006-2 — Designation measures the dimension with one real embeddings call
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 006.llm-server-connections · **Step:** 004
- **Date:** 2026-09-30 · **Decided by:** user
- **Plan-local:** 006 D2
- **Question:** How is `models.embedding_dim` learned?
- **Decision:** Designating a model embeds one fixed short string against it and records the vector's length. A failed call, or a response with no usable vector, blocks the designation with a typed error. A changed dimension prompts no rebuild, raises no warning and is not compared with the previous value.
- **Reason:** Neither provider kind exposes the dimension in its model listing. Recording a designation that cannot produce vectors would fail later, at the first search, far from the cause.
- **Lands in:** `backend/app/services/llm_registry.py`
- **Cites:** `admin-surfaces.md` (Embedding modal); `data-model.md` (`models`)

### DEC-006-7 — The four-value probe outcome, stored as the value itself
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 006.llm-server-connections · **Step:** 002, 003
- **Date:** 2026-09-30 · **Decided by:** planner
- **Plan-local:** 006 D6; 006 step 002 context (taxonomy declared once, probe returns / embed raises); 006 step 003 context (`last_test_error` holds a typed value)
- **Question:** How is a probe result classified and stored?
- **Decision:**
  - There are four outcomes: `reachable`, `unreachable`, `auth_failed` and `model_list_empty`.
  - Only `reachable` counts as ok.
  - `last_test_error` stores the outcome value itself, or NULL when reachable, and never prose.
  - The value set is declared once and reused by every layer.
  - The probe returns an outcome and never raises. Embedding raises a typed error.
  - An unreadable 2xx listing is classified as `unreachable`.
  - The architecture holds the contract.
- **Reason:** Every probe state is an answer the page must show, whereas an embedding has no useful partial result.
- **Rejected:** Narrowing to two values.
- **Lands in:** the LLM client module, `backend/app/services/llm_registry.py`
- **Cites:** `admin-surfaces.md` (LLM Servers page); `backend-structure.md` (the connection probe)

### DEC-006-9 — Write-time pointer validation is a field type answering 422

### DEC-006-10 — The pointer field: omitted, empty or a value
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 006.llm-server-connections · **Step:** 003, 005, 007
- **Date:** 2026-09-30 · **Decided by:** planner
- **Plan-local:** 006 D9; 006 step 003 context (empty on create stored as NULL; malformed stored row raises); 006 step 007 context (`pointerTouched`, empty on edit)
- **Question:** How does an edit tell "leave the key alone" apart from "clear the key"?
- **Decision:**
  - On `PATCH`, an omitted field leaves the pointer unchanged, `""` clears it, and a value replaces it. The service signature keeps "omitted" and "empty" as distinct inputs.
  - An empty pointer on create is stored as NULL, not `""`.
  - The form sends the field only when its explicit touch marker is set. The field starts empty on edit, with no fake placeholder.
  - A stored non-`$` pointer, written before this feature or by hand, makes `resolve_secret` raise, and the error is never swallowed.
- **Reason:** A form that sends `""` for an untouched field silently deletes the credential on every save. Storing NULL keeps "has a key" honest.
- **Lands in:** `backend/app/services/llm_registry.py`, `backend/app/routers/admin_llm.py`, `frontend/src/admin/serverFormDraft.ts`
- **Cites:** `admin-surfaces.md` (Server form modal)

### DEC-006-11 — Enabling and disabling flip flags; rows are never deleted

- **Plan-local:** 006 D10; 006 step 004 context (set-enabled-models not async)

- **Decision:** It upserts flags and never deletes a row. Set-enabled-models is synchronous, because it reaches no network.

### DEC-006-12 — Failed-probe resilience holds by construction
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 006.llm-server-connections · **Step:** 008, 009
- **Date:** 2026-09-30 · **Decided by:** planner
- **Plan-local:** 006 D11; 006 step 008 context (shared picker, stable union order, "no longer offered" mark, empty save); 006 step 009 context (single select, preselection from the list payload)
- **Question:** How do the model modals keep the selection when the probe fails?
- **Decision:**
  - The selection is seeded from the page's list payload, and the probe writes only the available list.
  - Both modals share one picker module.
  - The union is sorted in a pure function by code-unit order, so checkboxes don't reshuffle.
  - A stale model gets a "No longer offered by the server" mark on its option, not a separate list.
  - An empty save is legal.
  - The embedding modal is a single-select radio group, not a checkbox list limited to one tick.
- **Reason:** With this shape, no code path lets a probe failure reach the selection.
- **Lands in:** `frontend/src/admin/modelPicker.ts`, `frontend/src/admin/EnabledModelsModal.tsx`, `frontend/src/admin/EmbeddingModal.tsx`
- **Cites:** `ui-conventions.md`; `admin-surfaces.md` (LLM Servers page)

### DEC-006-16 — The admin LLM route surface and the designation's transaction
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 006.llm-server-connections · **Step:** 004, 005
- **Date:** 2026-09-30 · **Decided by:** planner
- **Plan-local:** 006 D17; 006 step 004 context (call outside the transaction, table-wide designation, server-scoped clear, `embedding_dim` kept on clear)
- **Question:** What does the route surface look like, and how does designating write?
- **Decision:**
  - The architecture holds the nine routes under `/api/admin/llm-servers`. It uses `POST` rather than `PUT` for the enabled set, and the clear is server-scoped.
  - Designating runs in the order read → resolve → embeddings call → measure. Only then does one transaction clear the flag on every other row, table-wide, and upsert this one.
  - Clearing is scoped to one server.
  - Clearing leaves `embedding_dim` on the row.
- **Reason:** A network call inside a transaction would hold SQLite's single writer for as long as the provider takes. "At most one designation" is a rule across the whole table, so a `WHERE server_id` clause would be wrong. The dimension belongs to the model, not to the designation.
- **Rejected:** `PUT` for the enabled set, because the shared client has no `PUT`. A `GET` of the enabled names, because they ride on the list payload.
- **Lands in:** `backend/app/routers/admin_llm.py`, `backend/app/services/llm_registry.py`
- **Cites:** `backend-structure.md` (admin LLM route surface)

### DEC-006-17 — Only Delete and Clear Embedding are confirmed
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 006.llm-server-connections · **Step:** 006, 009
- **Date:** 2026-09-30 · **Decided by:** planner
- **Plan-local:** 006 D18; 006 step 007 context (base-URL check); 006 step 009 context (clear failure to the page Alert)
- **Question:** Which LLM-server actions ask for confirmation, and where do their failures show?
- **Decision:**
  - Delete and Clear Embedding are confirmed, with a consequence sentence that counts nothing. Saving a form or an enabled-model set is not confirmed.
  - A failed clear renders in the page `Alert`, because the action has no form.
  - The form's base-URL check is non-empty and an absolute `http` or `https` URL, nothing stronger.
- **Reason:** Saving is fully reversible, and the only consequence sentence that would make its confirm informative is forbidden by the domain rules. A stricter URL check would refuse the trailing-slash and `/v1` forms that the client accepts.
- **Lands in:** `frontend/src/admin/LlmServersPage.tsx`, `frontend/src/admin/embeddingDraft.ts`, `frontend/src/admin/serverFormDraft.ts`
- **Cites:** `ui-conventions.md` (confirm convention)
