# Decisions — 012.messages-and-settle
**Stage:** 002.record · **Feature:** 012.messages-and-settle

Decisions behind the backend door into a session's record: the `messages` table, its named read selectables, append, partner filing, zone edit, settle and re-open, and the `(( ))` parser. Most of the contract has landed in `data-model.md` § `messages`, `session-stream.md`, `backend-structure.md` (§ The stream routes, § Settle and re-open) and `domain-rules.md` R11 / R12. These entries anchor the plan-local ids that text cites, and keep the reasons and rejected alternatives. Recorded at finalization (2026-11-09).

### DEC-012-1 — The two "views" are Core selectables, not SQL VIEWs
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 012.messages-and-settle · **Step:** 001
- **Date:** 2026-10-02 · **Decided by:** user
- **Plan-local:** 012 D1; 012 D6
- **Question:** Are `settled_entries` and `current_zone` real SQL views or query builders?
- **Decision:** They are named module-level `select()` objects over `messages` in `db/schema.py`. They execute no DDL and carry no session filter and no ordering; callers narrow and order them. The drift registry has nothing to describe for them, which closes the brief's second open question (D6).
- **Reason:** Nothing in the codebase can manage a view. Create/Sync and drift handle tables only, a batch recreate of `messages` would break a view at the rename step, and an existing instance has no creation path for one. A selectable keeps the predicate in exactly one place.
- **Rejected:** Real SQL VIEWs.
- **Lands in:** `backend/app/db/schema.py`
- **Cites:** `data-model.md` § `messages` (the named selectables)

### DEC-012-2 — `PATCH /api/messages/{id}` edits current-zone rows only
- **Status:** superseded in part by DEC-014-1 (settled rows became editable) and DEC-F014-10 (a blank edit delegates to delete) — the buried-row refusal stands
- **Stage:** 002.record · **Feature:** 012.messages-and-settle · **Step:** 002
- **Date:** 2026-10-02 · **Decided by:** planner
- **Plan-local:** 012 D2
- **Question:** Which rows may 012's PATCH edit?
- **Decision:** As built in 012:

  - A buried row is refused with `message_not_editable`. This still stands.

  - A missing or foreign row is `message_not_found`.
- **Reason:** 013 needed zone editing, and 014's brief owned editing a settled row.
- **Lands in:** `backend/app/services/messages.py`
- **Cites:** `backend-structure.md` § The stream routes

### DEC-012-3 — Every content write bumps the session; one instant per operation
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 012.messages-and-settle · **Step:** 002, 003
- **Date:** 2026-10-02 · **Decided by:** planner
- **Plan-local:** 012 D3
- **Question:** Which operations move `sessions.last_used_at`, and with what timestamp?
- **Decision:**
  - Append, partner filing, zone edit, settle and re-open each set `sessions.last_used_at` and `sessions.updated_at`, in the same transaction as the message write.
  - Every timestamp one operation writes is a single instant.
  - Reads and refused operations write nothing.
- **Reason:** It closes DEC-011-3's forward note. `updated_at` moves on any write to the row.
- **Lands in:** `backend/app/services/messages.py`; `backend/app/services/settle.py`
- **Cites:** `data-model.md` § `sessions`

### DEC-012-6 — A third, text-free selectable for the edit target
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 012.messages-and-settle · **Step:** 001, 002
- **Date:** 2026-10-02 · **Decided by:** planner (confirmed: user)
- **Plan-local:** 012 D7
- **Question:** How does PATCH tell a buried row from a missing one without a raw `select()` on `messages`?
- **Decision:** A `message_states` selectable projects only `id`, `user_id`, `session_id`, `related_to` and `settled_at`. It carries no `text` and no `kind`.
- **Reason:** It can classify a row's state but cannot carry content, so no buried scaffolding can leak through it.
- **Rejected:** A raw `select()` in `services/messages.py`.
- **Lands in:** `backend/app/db/schema.py`; `backend/app/services/messages.py`
- **Cites:** `data-model.md` § `messages`; `domain-rules.md` R11

### DEC-012-7 — The `(( ))` classifier and strip rules
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 012.messages-and-settle · **Step:** 003
- **Date:** 2026-10-02 · **Decided by:** user (classifier); planner (strip rules)
- **Plan-local:** 012 D8; 012 003.context ("The parser, as spec")
- **Question:** When is a settled head a decision, and what does stripping do to a turn?
- **Decision:**
  - Decision: after trimming outer whitespace, the text starts with `((` and ends with `))`. A decision is stored verbatim.
  - Turn: anything else. Each shortest `((`…`))` span is stripped, with the specified whitespace tidy-up. A turn with no fragment settles byte-for-byte unchanged.
  - An empty turn cannot occur, so settle has no refusal for one.
  - The full rules, the examples and the known nested-parens oddity are in `session-stream.md` § The `(( ))` seam.
- **Reason:** The classifier is the user's. `"((a)) prose ((b))"` being a decision is an accepted consequence.
- **Lands in:** `backend/app/services/parens.py`
- **Cites:** `session-stream.md` § The `(( ))` seam; `domain-rules.md` R12; US-129, US-130

### DEC-012-8 — `text` is required, non-blank, stored verbatim, with no maximum
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 012.messages-and-settle · **Step:** 001
- **Date:** 2026-10-02 · **Decided by:** planner
- **Plan-local:** 012 D9
- **Question:** How is `text` validated in the three request bodies?
- **Decision:** `text` is a required string. An empty or whitespace-only value is a 422. It is never trimmed or normalised, and it has no maximum length. Services trust the router's validation.
- **Reason:** R12 takes text literally, and R10 says an enormous paste is never refused.
- **Lands in:** `backend/app/models/stream.py`
- **Cites:** `domain-rules.md` R10, R12

### DEC-012-9 — Re-open is the literal R11 rule
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 012.messages-and-settle · **Step:** 003
- **Date:** 2026-10-02 · **Decided by:** user
- **Plan-local:** 012 D10
- **Question:** What can be re-opened?
- **Decision:** Only the last settled row of the session, by id, and only if it has a buried group. Checks run in this order: session, zone (`zone_not_empty`), last settled row, then group (`nothing_to_reopen`).
  - A lone turn, a lone decision or a partner block is not re-openable.
  - Ids never move.
  - The head's text is not restored to its pre-strip form.
- **Reason:** The rule is the literal R11 text, and UC-037 makes earlier groups unreachable.
- **Lands in:** `backend/app/services/settle.py`
- **Cites:** `domain-rules.md` R11; `backend-structure.md` § Settle and re-open

### DEC-012-10 — Service isolation; settle and re-open return ids
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 012.messages-and-settle · **Step:** 002, 003
- **Date:** 2026-10-02 · **Decided by:** planner
- **Plan-local:** 012 D11
- **Question:** How do `services/messages.py` and `services/settle.py` relate?
- **Decision:**
  - Neither imports the other or any other service. Each has its own session check, its own bump and its own `_now_text()`.
  - Settle answers `{ entry_id, kind, buried_ids }`. Re-open answers `{ reopened_id, restored_ids }`. Neither returns message values.
- **Reason:** No value type can be shared without an import. The client reconciles by re-reading entries and the zone.
- **Lands in:** `backend/app/services/messages.py`; `backend/app/services/settle.py`; `backend/app/models/stream.py`
- **Cites:** `backend-structure.md` § Settle and re-open

### DEC-012-12 — Five new error codes: four 409s and one 404

- **Decision:**

### DEC-012-13 — A partner block may be filed over a zone draft
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 012.messages-and-settle · **Step:** 002
- **Date:** 2026-10-02 · **Decided by:** user
- **Plan-local:** 012 D14
- **Question:** Does filing a partner block require an empty zone?
- **Decision:** No. There is no backend refusal and no UI guard. The partner block gets a larger id than the draft. If the draft is settled later, it sorts above the partner block, and its group is not re-openable.
- **Reason:** The user accepted this as chronologically true and harmless. UC-027 says a paste is never refused.
- **Lands in:** `backend/app/services/messages.py`
- **Cites:** `backend-structure.md` § The stream routes

### DEC-012-14 — R11's "two operations" read as a rule about the record columns
- **Status:** accepted
- **Stage:** 002.record · **Feature:** 012.messages-and-settle · **Step:** 002, 003
- **Date:** 2026-10-02 · **Decided by:** planner
- **Plan-local:** 012 D16
- **Question:** How do "raw `messages` is touched by exactly two operations" and the append, partner and PATCH writes coexist?
- **Decision:**
  - Every reader except settle and re-open goes through a selectable.
  - Only settle and re-open write `related_to`, `kind`, or `settled_at` on an existing row.
  - `services/messages.py` inserts zone and born-settled rows, and updates `text` and `updated_at` on current-zone rows.
- **Reason:** It is the only reading consistent with the route table. The architect worded R11 this way.
- **Lands in:** `backend/app/services/messages.py`; `backend/app/services/settle.py`
- **Cites:** `domain-rules.md` R11
