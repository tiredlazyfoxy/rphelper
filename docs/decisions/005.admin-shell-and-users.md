### DEC-005-1 — Change Role is built, and the client never re-implements the refusal

### DEC-005-2 — `last_login_at` is stamped inside the login transaction
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 005.admin-shell-and-users · **Step:** 001
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 005 D2
- **Question:** Where is the last login recorded?
- **Decision:** `users.last_login_at` is nullable. It is stamped inside `open_session`'s existing transaction, and `updated_at` is not bumped.
- **Reason:** A login is not an edit of the account. Using the existing transaction adds no extra write.
- **Lands in:** `backend/app/services/auth.py`, `backend/app/db/schema.py`
- **Cites:** `data-model.md` (`users`)

### DEC-005-3 — Account management lives in `services/users.py`
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 005.admin-shell-and-users · **Step:** 002
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 005 D3; 005 step 002 context (`username_taken`, idempotent disable, not-found order, result shape, ordering)
- **Question:** Where are the account operations, and how do they behave at the edges?
- **Decision:**
  - The operations live in `services/users.py`.
  - `username_taken` is raised from the unique index's `IntegrityError`.
  - Disable is idempotent.
  - `user_not_found` is raised before any write.
  - Every operation returns the same result shape.
  - `list_users` orders by id ascending.
- **Reason:** A check-then-insert takes a read lock that can fail when it upgrades to a write under SQLite. Flip condition: if `users` gains a second unique constraint, narrow the `IntegrityError` mapping to the username index.
- **Rejected:** Check-then-insert.
- **Lands in:** `backend/app/services/users.py`

### DEC-005-4 — Bulk session revoke on disable
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 005.admin-shell-and-users · **Step:** 002
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 005 D4
- **Question:** How are a user's sessions revoked when the account is disabled?
- **Decision:** A helper in `services/auth.py` revokes them. It opens no transaction of its own and selects with `revoked_at IS NULL` only, not on `expires_at`. It deletes nothing. It returns a count, which is only logged.
- **Reason:** The helper runs inside the caller's transaction. Revoking an already expired row does no harm and keeps the predicate simple.
- **Lands in:** `backend/app/services/auth.py`

### DEC-005-6 — An admin sets a password directly; non-empty is the only rule
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 005.admin-shell-and-users · **Step:** 002
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 005 D6
- **Question:** What happens when an admin sets a user's password?
- **Decision:** The password is replaced directly, and existing sessions are not revoked. The only rule is that it is non-empty (`min_length=1`, so an empty value gets 422), on the server and in the create and set-password drafts. There is no minimum length beyond that. Code checked on 2026-11-09 confirms this.
- **Reason:** The product states no password policy. Flip condition: if a password change should end existing sessions, reuse DEC-005-4's helper.
- **Lands in:** `backend/app/models/admin_users.py`, `frontend/src/admin/createUserDraft.ts`, `frontend/src/admin/setPasswordDraft.ts`

### DEC-005-13 — The access gate: five outcomes, 2-second retry while not ready
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 005.admin-shell-and-users · **Step:** 004
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 005 D13
- **Question:** How does the admin entry gate itself before rendering?
- **Decision:**
  - The gate has five outcomes.
  - While not ready it retries every `ADMIN_ACCESS_RETRY_INTERVAL_MS = 2000`, declared in `adminAccess.ts`.
  - `main.tsx` owns the `setInterval`, and only the latest probe's result is applied.
  - The failed outcome does not retry by itself.
- **Reason:** It uses the same fixed-interval reasoning as DEC-003-10. A failed probe is not a start-up delay, so retrying it would loop on a real error.
- **Lands in:** `frontend/src/admin/adminAccess.ts`, `frontend/src/admin/main.tsx`
- **Cites:** `admin-surfaces.md`

### DEC-005-14 — The gate's classification is pure, and denial navigates through the seam
- **Status:** accepted
- **Stage:** 001.instance · **Feature:** 005.admin-shell-and-users · **Step:** 004
- **Date:** 2026-09-29 · **Decided by:** planner
- **Plan-local:** 005 D14
- **Question:** How is the gate's failure split, and how does a denial leave the page?
- **Decision:** As built (code checked on 2026-11-09):
  - `enforceAdminAccess(signal?)` returns a `Promise<AdminAccessResult>`. The failed result carries a message.
  - The pure `classifyAdminAccessError(error)` returns `"not-ready"` or `"failed"`.
  - `resolveAdminAccess` is the decision step that sits between them.
  - A denial navigates through the `documentNavigation` seam in `shared/api.ts`.
- **Reason:** A pure classifier can be tested without the network, and the seam makes the navigation testable.
- **Lands in:** `frontend/src/admin/adminAccess.ts`
